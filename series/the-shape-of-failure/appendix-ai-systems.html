Mapping the Shape of Failure to LLM Infrastructure

December 5, 2026 · Appendix · AI/LLM Frontier

“All models are wrong, but some are useful.”

— George E. P. Box, Statistician

This appendix is an engineering reference, not a catalogue that assigns a probability distribution to every component in an AI stack. A model is useful only when its assumed data-generating mechanism is plausible, its parameters can be estimated from telemetry, and the resulting decision improves an operational outcome.

AI infrastructure combines several distinct sources of variability: externally generated arrivals, variable input and output lengths, shared GPU scheduling, retrieval fan-out, stateful orchestration, tool dependencies, and imperfect evaluation. These mechanisms should be modelled separately before they are composed.

The distinction from conventional query processing also needs precision. A database or query engine can provide deterministic logical semantics: for a fixed query and fixed data snapshot, the result is defined by the query's semantics. That does not imply an identical physical execution path, latency, task schedule, memory footprint, or byte-for-byte output in every environment. Parallel aggregation order, floating-point arithmetic, adaptive plans, caches, concurrency, and engine versions can affect physical behaviour. AI generation adds another source of variability: token selection and model behaviour may depend on decoding configuration, runtime kernels, batching, and implementation details. Neither category should be described as universally deterministic or non-deterministic without specifying the boundary.

The operating rule

Start with the physical mechanism, define the random variable and its unit, test whether a candidate model fits the observations, and then choose a control. Do not infer a distribution from a component name.

Core infrastructure calculations

1. KV-cache memory: a per-token estimate is not a capacity plan

For a conventional decoder-only transformer, a useful first-order estimate of KV-cache bytes per token across all layers is:

\[ M_{\text{token}} = 2 L_{\text{layers}} H_{\text{kv}} d_h b_{\text{bytes}} \]

The factor of two accounts for keys and values. \(L_{\text{layers}}\) is the number of transformer layers, \(H_{\text{kv}}\) is the number of KV heads, \(d_h\) is the head dimension, and \(b_{\text{bytes}}\) is the stored bytes per element. This is a theoretical tensor-size estimate. It can change with multi-head versus grouped-query or multi-query attention, cache quantization, architecture-specific layouts, and implementation choices.

Do not calculate production token capacity as total GPU memory divided by this expression. Total device memory is not all available to KV cache. The runtime also needs model weights, activations and workspaces, CUDA/runtime allocations, communication buffers, graph-capture pools, metadata, allocator overhead, and operational headroom. Paged/block-based engines allocate cache in blocks; internal fragmentation, block rounding, sequence-length variation, prefix sharing, eviction, and preemption all affect usable capacity. Tensor/pipeline parallelism and engine-specific placement further change the per-device budget.

Production admission control

Use the serving engine's own memory accounting and allocation model. Derive safe admission limits from allocatable KV blocks, reserved memory, model/runtime footprint, expected sequence-length distributions, batching policy, and measured preemption behaviour. Reconcile estimates with engine metrics and load tests under realistic prompt/output mixes.

2. HBM and KV-cache thresholds are operational policies, not constants

An 85% occupancy threshold can be a useful starting point for an experiment or an illustrative load-shedding policy. It is not a universal safe limit for HBM or KV-cache occupancy. The usable margin depends on the engine's allocator, memory fragmentation, batch composition, transient activation/workspace demand, graph capture, preemption policy, cache-block granularity, and whether memory can be reclaimed promptly.

Monitor more than a single percentage: allocated and free HBM, engine-reported KV-cache block utilization, allocation failures, preemption and recomputation counts, queue depth, batch composition, TTFT, inter-token latency, and out-of-memory events. Set thresholds from observed failure boundaries and a defined recovery margin. Revisit them after model, engine, hardware, or workload changes.

3. Correcting an imperfect semantic judge

Suppose an evaluator labels outputs as positive (for example, “incorrect”). Let \(p_{\text{obs}}\) be the observed positive fraction, \(\alpha_{\text{fp}}\) the judge's false-positive rate, and \(\beta_{\text{fn}}\) its false-negative rate, measured against a trusted reference set. The Rogan–Gladen adjustment is:

\[ \hat p_{\text{true}} = \frac{p_{\text{obs}}-\alpha_{\text{fp}}} {1-\alpha_{\text{fp}}-\beta_{\text{fn}}} \]

The adjustment assumes that sensitivity \(1-\beta_{\text{fn}}\) and specificity \(1-\alpha_{\text{fp}}\) are applicable to the population being evaluated, and that their sum exceeds one. The result estimates the underlying positive prevalence. Sampling noise can produce an estimate outside \([0,1]\); that is a warning about sampling variation or calibration, not a value to silently accept as a probability.

Do not apply an ordinary Wilson interval directly to \(\hat p_{\text{true}}\). Wilson's binomial interval applies to a binomial proportion such as the observed positive rate. It does not, by itself, account for uncertainty in the judge's sensitivity and specificity.

Two defensible uncertainty treatments

Option A — fixed judge characteristics. If sensitivity and specificity are treated as known constants from a sufficiently large, representative, independently labelled calibration set, first calculate a Wilson interval \([L_{\text{obs}},U_{\text{obs}}]\) for the observed positive rate, then transform both endpoints:

\[ L_{\text{true}} = \frac{L_{\text{obs}}-\alpha_{\text{fp}}} {1-\alpha_{\text{fp}}-\beta_{\text{fn}}}, \qquad U_{\text{true}} = \frac{U_{\text{obs}}-\alpha_{\text{fp}}} {1-\alpha_{\text{fp}}-\beta_{\text{fn}}} \]

Because the denominator is positive when the judge is better than chance, this monotone transformation preserves endpoint order. Intersecting the result with \([0,1]\) may be useful for display, but retain the untruncated interval in diagnostics because out-of-range endpoints reveal weak information or incompatible assumptions. This interval captures uncertainty in the observed evaluation sample only; it treats the judge error rates as fixed.

Option B — propagate calibration uncertainty. When sensitivity and specificity are estimated from finite calibration samples, model them as uncertain too. One practical Bayesian approach assigns beta priors to sensitivity and specificity, updates them using independently adjudicated calibration examples, and samples jointly with a prevalence parameter. For each posterior draw, generate the implied observed-positive probability and evaluate the likelihood of the observed evaluation count; the resulting posterior for prevalence propagates uncertainty from all three quantities. A frequentist alternative is a stratified bootstrap that resamples the calibration and evaluation datasets separately and recomputes the adjustment for each replicate.

Either approach requires a representative reference standard, clear positive-class definitions, and attention to class-conditional judge performance. If judge error rates vary by tenant, task type, language, or difficulty, stratify or use a hierarchical model rather than assuming one global sensitivity and specificity. The calibration set should not be reused as though it were independent evaluation data.

Interactive subsystem guide

Select a subsystem to see a compact interpretation of its mechanism, candidate model, evidence to collect, and controls. These are hypotheses to validate, not universal distribution assignments.

Inference serving

Arrival process + conditional service-time model

Physical mechanism: Requests arrive at the gateway; each request consumes prefill and decode resources. Arrival behaviour and service time are separate random processes.

Assumptions and limits: Poisson arrivals require approximate stationarity and independent increments. Service time must be conditioned on input/output length, batch composition, cache state, hardware, and scheduler policy.

Telemetry:

  • Arrival timestamps and burst variance
  • Input/output tokens, queue wait, TTFT and TPOT
  • Batch size, KV blocks, preemptions and HBM pressure

The operational trap

Planning from mean requests per second ignores burstiness and the joint distribution of prompt and completion lengths.

Architectural control

Use per-tenant token and concurrency budgets, deadlines, engine-aware admission control, chunked prefill where supported, and measured load shedding.

Three practical modelling examples

1. Arrival bursts and inference queueing

Suppose a gateway receives interactive prompts and scheduled summarization jobs. A single average arrival rate may conceal two traffic regimes. Plot inter-arrival times and count variance across several window sizes, segmented by tenant and workload class. If the rate changes between identifiable states, an MMPP may be a useful candidate; if the arrival trace is dominated by synchronized batch starts, replaying the empirical trace may be more defensible.

Feed the observed arrival trace and measured conditional service times into a queue simulation. Preserve the joint relationship between prompt length, completion length, and service time rather than independently sampling each marginal. Compare queue wait and TTFT percentiles under alternative concurrency limits, token budgets, and admission policies. Validate the simulation against a held-out production interval before using it to justify capacity.

2. A tool timeout is not proof that the operation failed

An agent calls a payment, provisioning, or ticketing API. The client times out, but the downstream service may have committed the side effect before the response was lost. Treating the timeout as a definite failure and blindly retrying can create duplicate operations. Model the outcome as at least three states: confirmed success, confirmed failure, and unknown outcome. The unknown state needs reconciliation, not an automatic repeat.

Use a stable idempotency key tied to the logical operation, persist the operation identifier, and expose a status/reconciliation path. Measure timeout rates and confirmed side effects separately. A geometric retry model is inappropriate if retries hit the same outage or if the first attempt may already have succeeded.

3. Semantic quality measurement with an imperfect judge

For an evaluation sample, first report the raw judge-positive rate and a Wilson interval for that observed rate. Separately report the judge's sensitivity and specificity with their calibration sample sizes and uncertainty. If these characteristics are treated as fixed, transform the observed interval through the Rogan–Gladen equation. If they are estimated, propagate their uncertainty with a joint model or stratified bootstrap. Report both raw and adjusted results so readers can see how much the correction depends on the judge.

Repeat calibration by task class, language, and difficulty when those factors plausibly alter judge error. A narrow interval around a biased judge's raw score is not evidence of accurate measurement.

A verification workflow for production systems

The post-mortem protocol
  1. Define the outcome. Separate availability, latency, resource exhaustion, structural validity, semantic correctness, and task completion. A single “success” metric hides distinct failure mechanisms.
  2. Locate the boundary. Trace gateway, queue, prefill, decode, retrieval, orchestration, tool, validation, and final task outcome with correlated request and operation IDs.
  3. Specify the random variable. State its unit, population, conditioning variables, observation window, and censoring rules.
  4. Propose a mechanism-based model. Start with empirical distributions. Test stationarity, independence, tail fit, mixture effects, and common-cause dependencies before choosing a parametric family.
  5. Validate out of sample. Compare predicted and observed percentiles, tail exceedances, queue lengths, and failure rates. Refit when workload, model, engine, or hardware changes.
  6. Choose a control that bounds the failure. Examples include admission limits, deadlines, idempotency, constrained decoding, independent evaluation, or human approval. State the invariant the control is intended to preserve.
  7. Monitor model risk. Track drift, calibration error, unmodelled cohorts, and the gap between predicted and observed operational outcomes.

A final architectural perspective

When the Model Meets Reality

Assumptions, failure boundaries, and engineering judgment. Probability models help us reason about distributed systems, but production systems do not know which distribution we fitted to their telemetry. They continue to change, interact, degrade, and fail regardless of how elegant our equations are.

Throughout this series, we have used probability distributions, queueing theory, reliability models, statistical tests, simulation, and extreme-value methods to reason about the behaviour of distributed systems. These methods are powerful precisely because they simplify reality enough to make it understandable.

That simplification is also their limitation. A model is not the system. A statistically acceptable fit does not establish a physical mechanism, a simulated result does not prove production behaviour, and a mathematically optimal control is not necessarily an economically or operationally optimal architecture.

The governing principle

A model is useful not because it captures every detail of reality, but because its assumptions are explicit, its predictions are testable, its limitations are understood, and its conclusions are relevant to the decision being made.

1. A distribution describes observations; it does not prove a mechanism

The challenge

A lognormal latency distribution does not prove that multiplicative processes generated the latency. A Weibull lifetime fit does not prove hardware wear-out. A Pareto-like tail does not establish a power-law workload. Several different mechanisms can produce similar empirical distributions over a limited observation window.

Statistical compatibility is not causal identification.

The correct response is to separate four questions:

  1. Observation: What behaviour does the telemetry show?
  2. Mechanism: What physical or operational process could produce it?
  3. Model: Which mathematical representation is compatible with that process?
  4. Validation: Does the model remain useful when tested against independent observations or controlled interventions?

A fitted distribution is a candidate explanation, not a certificate of causality. When several models fit similarly, architectural decisions should account for that model uncertainty rather than silently selecting the most convenient one.

2. Production processes are not necessarily stationary

The challenge

Distributed systems change continuously. Traffic composition, tenant populations, software versions, cache states, data volumes, hardware, autoscaling policies, and external dependencies all change the process being measured.

A distribution estimated last month may no longer describe the system after a deployment, a major tenant onboarding, or a change in workload.

Stationarity should therefore be treated as a hypothesis that must be monitored, not as a permanent property of a production service. Different operating regimes may require different models.

Observed behaviour Reasonable modelling response
Approximately stable process Estimate a baseline distribution and monitor its assumptions.
Slowly drifting process Use rolling estimates and drift detection.
Distinct operating regimes Segment observations or use regime-dependent models.
Seasonal workload Model time-dependent arrival rates and seasonal effects.
Deployment-dependent behaviour Maintain version-aware baselines and compare pre- and post-deployment behaviour.
Unknown or changing process Preserve uncertainty and avoid overconfident extrapolation.

A model should be associated with an operating regime, observation window, and validation history. When those conditions change, the model should be re-evaluated.

3. Independence is an assumption, not a default property

The challenge

Replicas may share a region, identity provider, network, storage backend, software release, or control plane. Retry attempts may be more likely to fail precisely because the system is already overloaded. Requests within a tenant or time window may be strongly correlated.

Treating dependent events as independent can materially overstate reliability and understate uncertainty.

For two events, the general relationship is:

\[ P(A \cap B) = P(A)P(B \mid A) \]

The familiar product \(P(A)P(B)\) is justified only when independence is a reasonable assumption. Common-cause failures, correlated retries, shared infrastructure, and clustered observations require models that account for dependence.

The same warning applies to statistical uncertainty. A thousand highly correlated observations do not necessarily provide the information contained in a thousand independent observations.

4. Extreme percentiles are difficult to estimate

The challenge

p99.9 and p99.99 estimates can look precise while being supported by relatively few independent tail observations. Extreme-value theory provides a principled extrapolation framework, but it cannot create information that the observations do not contain.

At an arrival rate of 100 requests per second, the expected number of observations above a percentile over one day is:

These are expected counts, not guarantees of independent observations or reliable tail estimates. Correlation, changing workloads, censoring, and the choice of observation window can reduce the effective evidence substantially.

Extreme-value models should therefore be accompanied by threshold diagnostics, parameter uncertainty, sensitivity analysis, and explicit statements about the extrapolation range. An extrapolated tail estimate should not be presented as a guaranteed production SLA.

5. Analytical models are approximations of production systems

The challenge

Simple queueing models are valuable for understanding utilization, waiting time, and capacity sensitivity. But a real distributed platform may have multiple service classes, priority queues, batching, retries, autoscaling delays, resource contention, backpressure, and non-Poisson arrivals.

An M/M/1 model is not a complete representation of a multi-stage cloud analytics platform.

The answer is not to abandon analytical models. It is to use a model appropriate to the decision and increase model complexity when the consequences or interactions justify it.

  1. Analytical approximation: Understand utilization, queue growth, and sensitivity.
  2. Telemetry and trace analysis: Validate arrival patterns, service times, concurrency, and correlations.
  3. Simulation: Explore interactions that are difficult to solve analytically.
  4. Controlled production experiment: Test whether the proposed control works under actual operating conditions.

A simple model can be useful without being a complete replica of reality. The relevant question is whether it is accurate enough for the decision being made.

6. Simulation precision is not model validity

The challenge

A simulator can reproduce an incorrect model perfectly. Generating one million requests does not make the output trustworthy if the model assumes independent failures, stationary arrivals, or unrealistic service-time distributions.

Two distinct questions must be answered:

  • Verification: Did we implement the mathematical model correctly?
  • Validation: Is the mathematical model a useful representation of the real system for the intended decision?

Reproducible seeds, explicit assumptions, sensitivity analysis, calibration against telemetry, independent validation data, and uncertainty intervals improve the quality of simulation evidence. They do not eliminate model risk.

Remember

Simulation precision is not model validity. A precise answer to the wrong model is still the wrong answer.

7. Reliability controls have economic and operational trade-offs

The challenge

Headroom, replication, admission control, hedged requests, isolation, checkpointing, and frequent worker recycling can improve particular reliability objectives while increasing cost, latency, complexity, or operational burden.

There is no universally optimal reliability architecture. A control should be evaluated against the failure consequences it mitigates and the cost of implementing and operating it.

\[ \text{Net Benefit} = \text{Expected Loss Avoided} - \text{Control Cost} - \text{Operational Cost} \]

This is a decision framework, not a claim that all three terms can always be estimated precisely. Where estimates are uncertain, use scenarios and sensitivity analysis. A high-consequence payment workflow may justify substantial spare capacity; an asynchronous analytical workload may rationally tolerate a different risk profile.

8. AI task success is an evaluation problem as well as a reliability problem

The challenge

An AI system can return HTTP 200, produce valid JSON, invoke the correct tool, and complete a workflow while still giving the user an incorrect answer.

Semantic correctness depends on the task definition, evaluation criteria, ground truth, context, and the quality of the evaluation process itself.

A measured success rate is conditional on the task population and the definition of success. An automated judge may have false positives and false negatives. A changing task distribution can make a previously valid evaluation dataset unrepresentative.

AI reliability therefore requires more than endpoint health and syntactic validation. It requires explicit outcome definitions, representative evaluation, stratified sampling where appropriate, human review for consequential cases, and monitoring of evaluator quality.

A probability estimate is only as meaningful as the event being measured and the process used to observe it.

9. A practical test before trusting a model

Before using a probabilistic model to justify an architectural decision, an engineer should be able to answer the following questions.

  1. What physical or operational mechanism are we modelling?
  2. What is the random variable, its unit, and its observation boundary?
  3. What assumptions are required for this model to be appropriate?
  4. Are observations independent, stationary, representative, and sufficiently complete?
  5. Which competing models could explain the same observations?
  6. What evidence would falsify or invalidate the model?
  7. Does the model predict behaviour on data not used to fit it?
  8. How sensitive is the decision to parameter uncertainty and model choice?
  9. What happens when the proposed control is applied under real operating conditions?
  10. Is the reliability benefit worth the financial and operational cost?
  11. Can another engineer reproduce the calculation and inspect its assumptions?

The architect's responsibility

The objective of probabilistic reasoning is not to eliminate uncertainty. That is impossible in a sufficiently complex distributed system.

The objective is to make uncertainty visible, quantify what can reasonably be quantified, identify what remains unknown, and choose controls that remain defensible when assumptions are imperfect.

A model should be monitored, challenged, recalibrated, or retired when the system it describes changes. The more consequential the decision, the stronger the evidence required.

Good architecture is not built by believing the model. It is built by knowing when the model can be trusted, when it cannot, and what to do in either case.

Important boundary

Constrained decoding can enforce a grammar or schema, but it cannot guarantee that the values are true, authorized, current, or safe. A successful HTTP response, valid JSON document, and completed agent workflow are not equivalent to a correct task outcome. Keep structural, semantic, policy, and business validation as separate controls.

The practical objective is not to make AI infrastructure deterministic. It is to make its failure modes observable, its resource consumption bounded, its side effects controlled, and its quality claims statistically defensible. Use distributions as testable models of physical processes—not as labels attached to fashionable components.
