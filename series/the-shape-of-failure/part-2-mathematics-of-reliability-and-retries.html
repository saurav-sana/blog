Reliability, Redundancy, and the Independence Delusion

October 18, 2026 · Part 2 of 8

“Everything fails, all the time.”

— Werner Vogels, CTO of Amazon

Welcome to the mathematics of things breaking. In systems design, we routinely calculate cluster reliability using simple probabilities. We spin up three database replicas, calculate the probability of one dying, and proudly declare our architecture "highly available" because we assume that if Server A dies, Server B is completely unaffected.

This is Replication Theater: counting replicas without checking whether their failure modes are actually independent. Cloud components can share a rack, power domain, network path, control plane, identity provider, region, or deployment pipeline. Three replicas are useful only to the extent that they can fail separately—and that separation has to be verified, not inferred from three boxes in a diagram.

The useful question is not simply “Which distribution should I use?” It is “What process generates this failure, and which assumptions does my model need?” A probability distribution describes a pattern; it does not explain a shared switch, a bad rollout, a memory leak, or a human entering the wrong command. Model the mechanism first, then decide whether a distribution is a reasonable approximation.

The interactive charts use synthetic samples, not production telemetry. Continuous runs retain the latest 5,000 observations so the browser remains responsive; reset a simulation to start a fresh sample.

1. The Bernoulli Distribution

The Intuition: The Binary Reality

Forget the cluster. Forget the fleet. Forget the 99.99% SLA dashboard. Think about one single request happening right now. Did the HTTP request succeed, or did it return a 500? Did the server boot, or did it hang?

For a particular request and a clearly defined outcome, we can encode success as 1 and failure as 0. A Bernoulli variable is deliberately simple: it does not represent “partially degraded.” Real requests may time out, return an error, or succeed too slowly; your measurement contract must decide which outcomes count as failure before you assign the 0.

For an individual request, the fleet-wide health dashboard is not the same thing as the user’s outcome. One failed request can be a Bernoulli observation even when the rest of the service is healthy. The important caveat: request outcomes are not automatically independent—one outage can fail thousands of requests together.

The Math

The probability mass function for a Bernoulli trial, where p is the probability of success, and k is the outcome (0 for failure, 1 for success):

P(X = k) = pk(1 - p)1 - k
Let's decode this:
  • If the request succeeds (k = 1): The formula becomes p^1 * (1-p)^0, which is just p.
  • If the request fails (k = 0): The formula becomes p^0 * (1-p)^1, which is just 1 - p.

Worked Example: If your single server has a 99% success rate (p = 0.99), the probability of a successful request is 0.99^1 = 0.99. The probability of failure is 1 - 0.99 = 0.01 (or 1%).

The SRE Trap

A Bernoulli model describes one defined trial; it does not, by itself, describe how trials depend on one another. If exactly 1,000,000 requests have a 99.9% success rate, 1,000 requests failed—but they may belong to fewer than 1,000 users, and they may be clustered in a short outage. Report the aggregate, then inspect time windows, tenant/user impact, and correlated failures.

Scenarios & Case Studies

The "Single User Perspective" AWS S3

A request-level success indicator is a Bernoulli observation, but the 2017 S3 disruption was not simply a load balancer dropping one unlucky packet. AWS reported that an incorrectly entered operational command removed more servers than intended, affecting critical S3 subsystems in the Northern Virginia region. The incident is a better lesson in Model Risk—the architecture had independent replicas, but the operational control plane was a shared single point of failure.

Reference: AWS S3 2017 Post-Mortem (Typo took down the fleet)
The "Single Point of Truth" HashiCorp Vault

Vault’s sealed/unsealed status is a binary state, but the transition can depend on a threshold of key shares and other operational conditions. A binary outcome can be modeled as 0/1; that alone does not mean the underlying process is a single independent coin flip.

Reference: Vault Seal/Unseal Architecture
The "Ruthless Executioner" Kubernetes Liveness Probe

With the common default settings, a liveness probe runs every 10 seconds and the default failure threshold is three consecutive failures; both values are configurable. The kubelet then restarts the container according to the probe configuration. Treating each probe as Bernoulli can be a useful first approximation, but consecutive failures are often correlated—for example, during CPU starvation or a dependency stall.

Reference: Kubernetes Liveness Probe Docs

2. The Binomial Distribution

The Intuition: The Architecture Review Lie

If each of n nodes has the same failure probability p, and their outcomes are independent over the interval being modeled, the Binomial distribution gives the probability that exactly k nodes fail. The trials do not have to happen at the exact same instant; what matters is the defined observation window and the model’s assumptions.

This is the kind of calculation that can support a quorum-risk estimate—but only after you define the time window, what counts as a node failure, and whether the node failures are independent. A tiny number from a simplified model is not proof that quorum loss is impossible.

The failure mode to look for: the architecture diagram says “three replicas,” but all three depend on the same network path, identity service, deployment artifact, or control plane. A shared dependency can create correlated failures. Separate availability zones help only when the relevant dependencies and failure paths are actually separated.

The Math

The probability of observing exactly k failures out of n total nodes, where each node has a probability p of failing:

P(X = k) = (n choose k) · pk · (1 - p)n - k
Let's decode this:
  • (n choose k): This is the combinatorics part. It calculates the number of different ways k nodes can fail out of n total nodes. (e.g., If node 1 and 2 fail, or node 2 and 3 fail).
  • pk: The probability that a specified set of k nodes fail, before accounting for which set failed and whether the remaining nodes survive.
  • (1 - p)n - k: The probability that the remaining n - k nodes survive.

Worked example: In a five-voter cluster, a majority is three. If exactly two nodes fail, three remain and quorum is still available (assuming the remaining nodes can communicate). Under an independent Binomial model with n = 5 and per-node failure probability p = 0.01, the probability of exactly two failures is about 0.097%. The probability of losing a three-node majority by having at least three nodes fail is about 0.000985%. Those numbers are conditional on the independence assumption; a shared network partition or common-mode defect needs a different model.

Bridge to Part 3: When the fleet size (n) is massive, but the failure probability (p) is incredibly tiny, the Binomial distribution converges mathematically into the Poisson distribution—which we will use to model traffic bursts in the next part.

The SRE Trap

The Binomial model is not “wrong”; it is conditional. It becomes misleading when shared causes violate its independence assumption. A defective rollout can affect many nodes together, but it is not accurate to say the failure probability automatically becomes 100% for every node: exposure, platform, timing, configuration, and recovery behavior matter. Model the common cause explicitly or test the assumption against incident data.

The Core Problem: Knight Capital (2012)

Knight Capital’s 2012 trading incident is a reminder that catastrophic failures are not always random component lifetimes. A deployment left obsolete code active on one of the firm’s trading servers, and the resulting behavior produced enormous losses in minutes. Replicating the same flawed software, configuration, or procedure can reproduce the same defect—or make its blast radius larger. Redundancy is not a substitute for safe rollout, configuration consistency, and tested rollback.

The lesson: Redundancy helps against the failure modes it was designed to tolerate. It offers less protection against shared dependencies and common-mode defects. Map failure domains, limit shared dependencies, use staged changes, and test failover and recovery under realistic conditions.

Scenarios & Case Studies

The "Correlated Poison" CrowdStrike 2024

A faulty content-configuration update triggered widespread Windows crashes on affected hosts. CrowdStrike’s root-cause analysis describes a mismatch between the number of input fields expected by the sensor and the number supplied by the update, resulting in an out-of-bounds memory read. This is a common-mode software/deployment failure—not evidence that every Windows host had a 100% failure probability. Staged rollouts, canaries, compatibility validation, and fast rollback reduce the size of the blast radius.

Reference: CrowdStrike Channel File 291 Root Cause Analysis
The "Quorum Illusion" Raft / Paxos

In a five-voter consensus group, two unavailable voters can be tolerated only if the other three can communicate and elect or maintain a leader as required by the protocol. A shared network failure can prevent a majority from communicating even when the processes are still running. The failure domain is therefore not just “node up/down”; it can include connectivity and partition topology.

Reference: Ongaro & Ousterhout, "In Search of an Understandable Consensus Algorithm" (Raft Paper)
The "Self-Inflicted DDoS" Redis Cache Stampede

A popular key expiring can cause a cache stampede: many requests miss together and overwhelm the backing store. The exact request count and failure percentage depend on workload and system behavior, so treat this as an illustrative scenario rather than a universal outcome. Request coalescing, leases, jittered expiration, stale-while-revalidate, and bounded origin concurrency can reduce the synchronized burst.

Reference: Facebook, "Scaling Memcache at Facebook" (NSDI '13)

3. The Weibull Distribution

The Intuition: The Ticking Time Bomb

Hardware lifetime is not always well described by a constant failure probability. The Weibull distribution is useful because its hazard rate can decrease, stay constant, or increase with age depending on its shape parameter. One ordinary two-parameter Weibull distribution does not produce the full “bathtub curve” by itself; that pattern generally needs multiple failure mechanisms or a more flexible model. Reliability engineering literature discusses this limitation explicitly.

  • Decreasing hazard (k < 1): Early failures are more likely among newly operating units, and the hazard falls with age. A defective batch can produce this pattern.
  • Constant hazard (k = 1): The exponential distribution is the special case with a constant hazard rate.
  • Increasing hazard (k > 1): Failure hazard increases with age. This may fit some wear-out mechanisms, but it is not proof that a specific device or service follows Weibull behavior.

A Bernoulli variable can still describe whether a component failed during a fixed interval. A lifetime model answers a different question: how does failure risk change with age? Choose the model to match the question and the observed data—not because a particular component “must” follow a famous curve.

The Math

The probability density function for a Weibull distribution, where k is the shape parameter (it controls whether the hazard decreases, stays constant, or increases) and λ is the scale parameter (the characteristic life):

f(x; λ, k) = (k / λ) · (x / λ)k - 1 · e-(x/λ)k
Let's decode this:
  • k (Shape): This parameter determines the direction of the Weibull hazard trend.
    • If k < 1, the failure rate decreases over time (Infant Mortality).
    • If k = 1, the failure rate is constant (Random Failures).
    • If k > 1, the failure rate increases over time (Wear-Out).
  • λ (Scale): The characteristic life. It's the point in time where exactly 63.2% of the components have failed.

Illustrative example: Suppose lifetime data were reasonably fit by a two-parameter Weibull with k = 3 and λ = 5 years. The hazard increases with age, and about 63.2% of modeled lifetimes end by five years. That does not mean each drive is safe until year five, nor that the hazard suddenly spikes at that exact point. The hazard rate is continuously increasing. A drive that survives to year 4 is already much more likely to fail in year 5 than it was in year 1. Fit the parameters to the relevant population and account for censored observations before using the model for planning.

The SRE Trap

The Weibull distribution does not tell you exactly when an individual component will die. It describes a population-level lifetime pattern. Estimate k and λ from relevant data, inspect fit and uncertainty, and account for right-censored units that have not failed yet. Guessed parameters can be useful for sensitivity analysis, but label them as assumptions rather than measured facts.

Scenarios & Case Studies

The "Bathtub" in the Data Center Backblaze HDD Stats

Backblaze publishes fleet-level drive statistics that can help engineers investigate age, model, and cohort effects. Do not infer a universal bathtub curve—or a fixed year-four/five wear-out cliff—from a summary chart alone. Drive populations differ, and observed annualized failure rates should be interpreted alongside sample size, drive age, workload, model, and the published methodology.

Reference: Backblaze Quarterly Hard Drive Stats
The "Silent Killer" SSD / EBS Wear-Out

Flash storage can fail through several mechanisms, including wear, controller faults, firmware issues, and power-related events; reaching a rated endurance figure does not imply every SSD abruptly becomes unusable. A Weibull with k > 1 can represent an increasing hazard when supported by data, but it is not a universal SSD failure law. For managed cloud volumes, the provider abstracts much of the physical device behavior.

Reference: Meza et al., "A Large-Scale Study of Flash Memory Failures in the Field"
The "Slow Death" OOM Kill

A memory leak is often better diagnosed from the memory-growth rate, workload, restart history, and container limit than by assuming a Weibull lifetime. If many instances show variable time-to-OOM, a lifetime distribution may summarize those observations—but first check whether the process is driven by a roughly deterministic resource trajectory.

Reference: Linux Kernel OOM Killer Documentation

Before You Trust the Reliability Number

A distribution is a model, not a warranty. Before turning a calculated probability into an architecture decision, write down the event being modeled, the observation window, the data source, and the assumptions about dependence. Separate random component failures from common-cause events such as a bad release, shared identity dependency, regional disruption, or operator error.

  • Define the outcome: process crash, request failure, lost quorum, and failed recovery are different events.
  • Define the window: “1% failure probability” is meaningless without saying per request, per hour, per year, or per deployment.
  • Check dependence: replicas that share software, configuration, network paths, credentials, or rollout procedures may fail together.
  • Validate the model: compare predictions with observed incidents, account for censored lifetime data, and label assumed parameters honestly.
  • Design the control: use failure-domain separation, canaries, staged rollout, rollback, recovery tests, and monitoring to reduce either the probability or the impact of failure.

In other words: don’t ask probability to rescue an architecture from a failure mode you never modeled.
