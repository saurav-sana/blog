Reliability, Redundancy, and the Independence Delusion

October 18, 2026 · Part 2 of 8

“Everything fails, all the time.”

— Werner Vogels, often quoted just before someone deploys the same failure mode into three availability zones.

There is a familiar scene in an architecture review. Someone draws three database replicas, labels each one “99.9% available”, multiplies three small failure probabilities, and announces that the cluster is practically immortal. The room nods. Nobody asks whether the replicas share a control plane, a kernel update, a certificate issuer, a network fabric, or the same deployment pipeline.

That is replication theater: counting boxes without examining whether their failure modes are independent. Redundancy helps only when the system can lose one component without losing the others—or when the remaining components can still deliver the service users need. Three copies are not three independent chances if one shared event can disable all three.

Before we let anyone near a whiteboard with a dry-erase marker, we have to separate quantities that are casually collapsed into the word reliability. Component reliability is \(R(t)=P(T>t)\): the probability that a component has not experienced its defined failure by age \(t\). Its complement, \(F(t)=1-R(t)\), is cumulative failure probability by that age. Component unavailability is the fraction of time a repairable component is unable to perform its required function. Service unavailability is the fraction of time the complete service cannot meet its stated contract. Quorum loss is the loss of the minimum voting set; a workflow interruption is a user- or job-visible loss of progress. They are related, but they are not interchangeable—no matter how badly an SLA slide wants them to be.

For a lifetime random variable \(T\), the age-conditioned failure hazard (often called the age-dependent failure rate) is \(\lambda(t)=f(t)/S(t)\), where \(S(t)=P(T>t)\). It is an instantaneous conditional rate, not the probability of failure over an arbitrary interval. Only when this hazard is constant does the lifetime model reduce to an exponential, memoryless time-to-failure model. We use \(\mu_{\text{repair}}\) for a repair-completion rate when a rate model is justified; it is not the component failure rate. The long-run unavailability of an alternating up/down repair process is \(U=\text{MTTR}/(\text{MTTF}+\text{MTTR})\), under the renewal assumptions explained below. That expression is not an instantaneous failure probability.

This part examines Bernoulli and Binomial reliability, redundancy, common-cause failure, Weibull survival and repair, then applies the same discipline to a large synchronous AI-training job. The aim is to connect a physical mechanism to a model, expose the assumptions, and derive an engineering control that can be tested before production tests it for you.

The modelling contract

A distribution is a model, not an invariant. Every calculation below is conditional on its stated assumptions. Production telemetry must be used to challenge those assumptions, not merely decorate the equation.

We will keep three evidence labels distinct: documented evidence means a source reports the event or measurement; illustrative model means the arithmetic demonstrates a mechanism; hypothetical stress scenario means the inputs are chosen to test a design, not claimed as observed facts.

1. Bernoulli reliability: one request and many required dependencies

A Bernoulli variable is the simplest possible coin flip in systems engineering: one binary trial. Let \(X=1\) mean that a request fails and \(X=0\) mean that it succeeds. If the failure probability is \(q\), then:

\[ P(X=x)=q^x(1-q)^{1-x},\quad x\in\{0,1\},\qquad E[X]=q \]

This is a deliberately small model. It says nothing by itself about why the request failed, whether the next request will fail, or whether failures arrive in angry herds. Those are separate questions about dependence and system state.

Documented evidence · AWS S3 service event · 28 February 2017

A typo in an operational command removed more servers than intended from parts of the S3 subsystem in the US East (N. Virginia) region. AWS described how the resulting capacity loss affected index and placement services and how recovery was complicated. This is a useful example of a shared operational action changing the system state; it is not evidence that all client retries caused the incident. Read AWS's explanation.

Composite workflows turn small risks into visible failure rates

Modern microservice architectures love turning one function call into a scavenger hunt across twenty network hops. Suppose a gateway query requires just four sequential operations: authenticate the caller, read catalog metadata, obtain a query plan, and fetch a required object. Assume—only for this calculation—that each operation succeeds independently with probability \(0.999\) and that all four are mandatory. Every single team owns a green dashboard and a “three-nines” badge. Yet the workflow succeeds only if all four succeed, so we multiply the success probabilities and take the complement to obtain workflow failure. (Multiplying failure probabilities as \(q^N\) would instead describe the event that all \(N\) operations fail simultaneously, not the event that at least one mandatory operation trips the request. And that multiplication still depends on independence: for two failure events, \(P(F_1\cap F_2)=P(F_1)P(F_2)\) only when they are independent.)

\[ P(\text{workflow succeeds})=0.999^4\approx0.996006 \]
\[ P(\text{workflow fails})=1-0.999^4\approx0.003994=0.3994\% \]

That is about 399 failed workflows per 100,000, even though each dependency individually reports 99.9% success. Every backend team hits its quarterly OKR while the user-facing gateway quietly bleeds four-tenths of a percent of all traffic. The result is not a contradiction: the user experiences the composition of the required steps, not the isolated pride of one microservice owner.

Real workflows are often more complicated. Some calls are parallel, some are optional, some are retried, and failures may share a cause. The four-step example is a simple sequential series system. Do not reuse its multiplication for a fan-out tree or a workflow with graceful degradation without deriving the appropriate model.

Retries: when another attempt helps—and when it weaponizes your own fleet

When an engineer sees a 0.4% failure rate, the instinctive reflex is to slap a @Retry(maxAttempts=3) annotation on the client and go home early. On a whiteboard, the math looks magical. Assume a request has a constant failure probability \(q\) on each attempt, and attempts fail independently. With three total attempts (the initial attempt plus two retries), the probability that all attempts fail is:

\[ P(\text{all 3 attempts fail})=q^3 \]

For \(q=0.001\), that is \(10^{-9}\) per operation under the independence assumption—nine nines summoned out of thin air! For a workflow with 1,000 mandatory operations, and assuming the attempt-exhaustion events are also independent across operations, the illustrative probability of at least one operation exhausting all three attempts is:

\[ 1-(1-10^{-9})^{1000}\approx10^{-6} \]

This is the optimistic case—not a universal retry guarantee. A timeout caused by a transient cosmic-ray packet drop may be followed by a clean second attempt. A timeout caused by an overloaded database connection pool, an exhausted storage tier, a dead DNS resolver, or a locked-up control plane will happily greet your second and third attempts with the exact same brick wall.

When failures are state-dependent, the useful quantity is not the fantasy of \(q^3\). It is the conditional probability of another failure given the observed failure and the current system state: \(P(F_{i+1}\mid F_i,S_i)\). During saturation that probability marches right up to \(1.0\). Retrying then becomes a self-inflicted denial-of-service attack: it shovels fresh work onto the exact same constrained resource while making zero forward progress. The detailed retry-feedback treatment belongs to Part 6; here, the point is narrower: the Bernoulli multiplication is valid only when attempt outcomes satisfy the stated independence and constant-probability assumptions.

A retry is new work, not free reliability

Three total attempts means at most two retries. Three retries means up to four attempts. State which convention you use before your nested SDK wrappers multiply them into 64 attempts. Also distinguish the probability of exhausting attempts from the expected number of attempts and from the load multiplier under overload.

How much extra work can bounded retries create?

Let \(p\) be the probability that one attempt succeeds, independently and with the same probability on every attempt. With at most \(A\) attempts, the expected number of attempts per logical call is:

\[ E[N_A]=\sum_{j=1}^{A}P(N_A\ge j)=\sum_{j=0}^{A-1}(1-p)^j=\frac{1-(1-p)^A}{p} \]

For \(p=0.9\) and \(A=4\) (one initial attempt plus three retries), \(E[N_4]=1.111\). That is a polite 11.1% average attempt tax under the stationary model. Under overload, however, \(p\) is not fixed: those extra attempts inflate queues, burn CPU on context switches, and drag \(p\) toward zero—creating positive feedback that turns a 10% hiccup into a 4x traffic tsunami. The expression is a bounded-attempt expectation, not a prediction for a saturated service.

Architectural controls derived from the model
  • Bound retries and give them a budget. Use a process- or service-wide retry budget, not an unlimited retry loop in every call site. A token-bucket policy is one implementation: successful traffic replenishes a small budget and retries consume it. When the bucket is empty, fail fast.
  • Use exponential backoff with jitter. Spread retries over time; do not synchronize clients on the same fixed delay like a marching band hitting a wooden bridge. Respect the end-to-end deadline and stop retrying when there is insufficient time left for a useful attempt.
  • Classify failures. Retry transient transport failures selectively. Do not retry authorization denials, invalid requests, deterministic schema errors, or operations whose side effects are not protected by idempotency.
  • Protect the dependency. Combine retry budgets with admission control, concurrency limits, circuit breaking, load shedding, and cancellation of abandoned work.
Production falsification · burstiness and conditional failure

Track attempts per logical request, retry success rate, retry traffic as a fraction of total traffic, timeout reason, queue age, and \(P(F_{i+1}\mid F_i)\) by dependency and load band. For error counts in equal one-second buckets, the Fano factor \(D=\operatorname{Var}(C)/E[C]\) can flag over-dispersion relative to a Poisson count model. \(D\gg1\) is evidence of clustering or rate variation—not proof of one particular cause, and \(D\approx1\) does not prove request-level independence.

2. Redundancy, quorum, and the common-cause wall

If \(n\) components each have the same probability \(p\) of being unavailable at one specified observation instant, and those component states are genuinely independent, the number unavailable \(X\) follows a Binomial distribution. A failure-event count over a window can also be Binomial if each component contributes one independent binary event, but that is not automatically the probability of quorum loss at any time during the window:

\[ P(X=k)=\binom{n}{k}p^k(1-p)^{n-k} \]

For a five-voter majority cluster, the quorum rule is \(k=3\): at least three of the five voters must be available for the voting set to exist. Quorum is lost when three or more voters are unavailable. If each voter has independent unavailability \(p=0.01\) at that same observation instant:

\[ P(X \ge 3)=\sum_{k=3}^{5}\binom{5}{k}(0.01)^k(0.99)^{5-k}\approx9.8506\times10^{-6}=0.0009851\% \]

Five nines of quorum survival! This is the exact number that gets pasted into executive architecture decks right before everyone congratulates themselves. It is tiny because the model assumes independent voter unavailability with identical probability. Even on its own terms, it estimates quorum loss under that rule; it does not prove that a service request succeeds. A five-voter group may retain a majority on paper while the service is completely dead in the water because the leader is isolated in an asymmetric network partition, the fabric cannot carry a quorum of messages, storage fsyncs stall across nodes, or the client routing layer cannot reach the cluster. This is not a general availability prediction for etcd, Raft, or another consensus implementation: network partitions, correlated latency, election timing, disk stalls, membership changes and client behavior need additional models.

Documented evidence · CrowdStrike Channel File 291 · 19 July 2024

CrowdStrike's root-cause analysis describes a content configuration update that triggered an out-of-bounds memory read in the Falcon sensor on affected Windows hosts. The impact crossed organizational and geographic boundaries because many machines consumed the same faulty content. It is a strong illustration of a shared software/configuration failure mode—not a measurement of the common-cause probability in the quorum model below. Read the root-cause analysis.

Model the shared event explicitly

Now let reality into the room. Add a shared event—a bad configuration push, an expired root certificate, a buggy kernel module, or a shared top-of-rack power trip—that disables the whole five-voter group with probability \(q_c=0.001\) at that same observation instant. Conditional on that event not occurring, retain the independent per-voter unavailability probability \(p=0.01\). This is a simple two-regime common-cause model:

\[ P(\text{Loss})=q_c+(1-q_c)P_{\mathrm{Binomial}}(X\ge3) \] \[=0.001+0.999(9.8506\times10^{-6})\approx0.00100984=0.100984\% \]

The five-nines mirage evaporates instantly; the common event dominates the result by two orders of magnitude. Notice a subtle accounting trap here: in this coupled model, the marginal unavailability of an individual voter is not 1%; it is \(q_c+(1-q_c)p=1.099\%\). The 1% value is the conditional independent component risk when the shared event is absent. Keeping those quantities separate avoids quietly changing the meaning of \(p\) halfway through the calculation.

Measure Independent-only model Shared-event model Interpretation
Conditional individual risk 1.0% 1.0% when no shared event occurs Not the same as marginal node unavailability in the coupled model
Shared event probability 0 0.1% Illustrative probability at the same instant
Five-voter quorum-loss probability 0.000985% 0.100984% About 102.5 times higher in this scenario
Seven-voter quorum-loss probability 0.00003417% About 0.100034% Extra voters reduce independent risk, not the all-voter shared-event term

Look at the bottom row of that table: scaling from five voters to seven voters crushes the independent failure risk down to \(0.000034\%\), yet total quorum loss barely budges from \(0.1009\%\) to \(0.1000\%\). Buying two more servers did nothing but give the shared configuration bug two more places to crash simultaneously. Adding voters helps against independent failures, but it cannot tunnel underneath a shared event that disables the entire group. The common-cause term acts as a hard floor in this model, not a universal mathematical ceiling for every failure architecture. A more detailed model may distinguish partial shared events, different failure-domain membership, and conditional per-node risks.

This simple construction is related in spirit to common-cause and beta-factor approaches, but it is not itself a fitted classical beta-factor model. In a traditional beta-factor formulation, a fraction of component failure intensity is attributed to common-cause events; parameter definitions, component population and event structure must be stated before comparing results.

Reliability block diagrams: what redundancy actually buys

A reliability block diagram (RBD) makes the service-success condition explicit instead of leaving it implied by pretty arrows. In a series system, every block is required. If component reliabilities are \(R_i(t)\) and failures are independent, then:

\[ R_{\text{series}}(t)=\prod_{i=1}^{n}R_i(t) \]

In an ideal parallel redundant system, the service succeeds if at least one component succeeds. Under independent failures and perfect, instantaneous detection and switchover:

\[ R_{\text{parallel}}(t)=1-\prod_{i=1}^{n}\left(1-R_i(t)\right) \]

For identical independent components with availability \(a\), a \(k\)-of-\(n\) service is available when at least \(k\) components are available:

\[ A_{k:n}=\sum_{j=k}^{n}\binom{n}{j}a^j(1-a)^{n-j} \]

These are idealized RBD equations, and the word “idealized” is doing heavy lifting. They assume the diagram captures every required path, component outcomes are independent where multiplied, switching works flawlessly when needed, and no unmodelled shared dependency defeats the redundancy. A component can fail while redundancy masks that failure; component failure is therefore not automatically component unavailability at the service boundary. Conversely, a hot standby replica whose promotion script fails after six months of bit-rot, a shared load balancer that drops its BGP session, or a quorum that cannot communicate is not represented by simply drawing another parallel box. The five-voter example above uses the equivalent failure-count rule: service-level quorum is lost at three or more unavailable voters, but actual consensus service availability also depends on communication and protocol state.

Independence is an architectural property to test, not assume

Shared fate sneaks in through far more doors than the availability zone label. Replicas deployed across three continents may still share an OS image, kernel version, security agent, certificate authority, identity provider, DNS resolver, storage control plane, CI/CD deployment wave, or a single fatigued operator pasting commands at 2 a.m. Placing boxes in different zip codes does not automatically make any of those software dependencies independent.

Architectural controls derived from the model
  • Map failure domains, not just locations. Record the shared dependencies of each voter: power, network, hypervisor, kernel, agent, control plane, credentials, DNS, storage and deployment wave.
  • Roll out changes in cells. Keep enough voters outside each change wave to preserve quorum. Use health gates and bake time, and make rollback independent of the failed control plane where practical.
  • Keep the data plane resilient to control-plane loss. Cache the minimum required authorization material safely, use locally verifiable signed credentials where appropriate, and define which operations can continue during identity or configuration outages.
  • Test partial and total failures. Exercise loss of one zone, a shared resolver, a certificate issuer, a deployment agent and a network partition. Validate actual quorum and client behavior, not just node process uptime.
Production falsification · shared-fate inventory

Build a machine-readable dependency matrix for each quorum group. Track voter membership by zone, rack, hypervisor pool, kernel/agent version, certificate issuer, resolver, control-plane endpoint and rollout wave. A repeated value is a prompt for failure-domain analysis—not automatic proof of correlation. Validate with fault injection and incident history.

3. Weibull reliability: conditional hazard, aging, and censored data

Not every component has a constant, memoryless failure hazard. Hardware wears out, flash cells lose charge-trap integrity, and burnt-in cohorts shed defective stragglers early. For a non-repairable lifetime measured from a defined origin, and a reasonably homogeneous cohort whose units share the same lifetime mechanism and parameters, a two-parameter Weibull model uses dimensionless shape \(\beta\) and scale \(\eta\) (in the same time or exposure units as \(t\)) to describe survival and age-conditioned hazard. At \(t=\eta\), cumulative failure probability is \(1-e^{-1}\approx63.2\%\): this is a characteristic scale parameter, not the mean lifetime.

\[ S(t)=P(T>t)=e^{-(t/\eta)^\beta},\qquad F(t)=1-S(t) \]
\[ h(t)=\lambda(t)=\frac{f(t)}{S(t)}=\frac{\beta}{\eta}\left(\frac{t}{\eta}\right)^{\beta-1} \]
  • \(\beta<1\): the model's hazard decreases with age. This can describe an early-life “infant mortality” population in which weaker units fail sooner, leaving a more robust surviving cohort.
  • \(\beta=1\): the Weibull reduces to the exponential model with constant, memoryless hazard.
  • \(\beta>1\): the model's hazard increases with age, consistent with physical wear-out or cumulative stress mechanisms.

These are mathematical properties of a fitted model, not diagnostic labels to assign from vibes. Hardware can have multiple competing failure mechanisms at different stages of life. And a word of caution on software: while “software aging” can arise from resource accumulation, heap fragmentation, unclosed file descriptors, or workload-dependent state, a deterministic C++ memory leak is a bug, not a Weibull distribution. Do not dignify a missing free() or an unbounded cache with a stochastic survival curve, and do not infer physical wear-out merely because a curve fit spits out \(\beta>1\); identify a plausible degradation mechanism and test whether age, exposure and cohort effects support it.

Empirical resource · Backblaze drive data

Backblaze publishes drive-level reliability data and quarterly drive statistics. Those data are useful for cohort analysis, but a headline annualized failure rate does not by itself establish a Weibull shape parameter. A defensible fit needs drive age, failure times, observation windows, censoring information, cohort definitions and diagnostics. Explore the published drive data.

Worked example: the risk in the next interval

Illustrative model: suppose a hardware cohort follows a Weibull lifetime with \(\beta=3\) and \(\eta=5\) years. The cumulative probability of failure from birth to year four is:

\[ F(4)=1-e^{-(4/5)^3}=1-e^{-0.512}\approx40.07\% \]

That cumulative probability describes the original cohort from age zero to age four. It is not the probability that a survivor already sitting in your rack at age four will fail next year. For a node that has already survived to age four, the relevant age-conditioned probability of failure between years four and five is:

\[ P(4 < T \le 5 \mid T > 4)=1-\frac{S(5)}{S(4)}=1-e^{-[(5/5)^3-(4/5)^3]}=1-e^{-0.488}\approx38.61\% \]

Compare that with a brand-new node's probability of failing in its first year:

\[ P(0 < T \le 1)=1-e^{-(1/5)^3}\approx0.80\% \]

Under this illustrative increasing-hazard model (\(\beta=3\)), a surviving four-year-old unit has a nearly 48x higher chance of failing in the next year (\(38.61\%\) vs. \(0.80\%\)) than a new unit. That does not mean every long-running server is a ticking time bomb—if \(\beta=1\), the four-year-old unit and the brand-new unit have the exact same next-year risk. The conclusion depends entirely on the fitted cohort model, its age definition, and whether the observed population is reasonably homogeneous.

Survival estimation is not the same as Weibull fitting

Operational datasets rarely hand you a neat failure time for every unit. Most of your fleet is (hopefully) still alive when you run the query. A unit still operating at the end of observation contributes a right-censored lifetime: we know it survived at least until its last observation, but we do not know its eventual failure time. Dropping right-censored survivors from your dataset and averaging only the dead machines is a classic way to underestimate fleet lifetime and terrify your CFO. Similarly, a machine removed during a rack decommission or retired for an upgrade is not automatically a hardware failure. It may be right-censored if removal is independent of the latent failure time under the analysis assumptions; if retirement is related to degraded condition or is itself an outcome of interest, it must be handled as informative censoring or a competing event rather than silently treated as an ordinary survivor.

  • Kaplan–Meier estimates the survival function non-parametrically from observed failure times and right-censored units. Under independent (non-informative) censoring, a unit still operating at its last observation remains in the risk set until that time; it is not counted as a failure. Kaplan–Meier lets the empirical data speak first; it does not estimate Weibull \(\beta\) and \(\eta\).
  • Parametric Weibull estimation can use maximum likelihood with both observed failures and right-censored exposure times. Let \(\delta_i=1\) for an observed failure and \(\delta_i=0\) for a right-censored unit. The likelihood and log-likelihood are:
    \[ \begin{aligned} L(\beta,\eta)&=\prod_{i=1}^{n} f(t_i;\beta,\eta)^{\delta_i}S(t_i;\beta,\eta)^{1-\delta_i}\\ \ell(\beta,\eta)&=\sum_{i=1}^{n}\left[\delta_i\log f(t_i;\beta,\eta)+(1-\delta_i)\log S(t_i;\beta,\eta)\right] \end{aligned} \]
    The product is the likelihood; its logarithm is the log-likelihood. Report parameter uncertainty intervals and check whether the fitted curve actually resembles reality.
  • Diagnostics should compare the fitted parametric survival curve with the empirical Kaplan–Meier curve, inspect probability plots/residuals, examine cohort differences, and test sensitivity to the observation window.

For software workers, record age in meaningful exposure units—wall-clock uptime, requests processed, bytes scanned, compactions, or another mechanism-linked measure. If RSS grows almost deterministically with requests processed, fix the leak or impose a safe resource bound. Do not hide a deterministic defect behind a stochastic lifetime fit. The Kaplan–Meier curve is the empirical, non-parametric survival estimate; the Weibull curve is a parametric model fitted to the censored observations. Compare them rather than treating one as a substitute for the other. Confidence intervals, the number still at risk, cohort stratification and sensitivity to the observation window matter, especially in the tail.

Architectural controls derived from the model
  • Use rejuvenation where the mechanism supports it. Stagger worker recycling, compaction, firmware changes and hardware replacement. Set policy from measured risk and recovery capacity, not an arbitrary cron-job superstition.
  • Avoid synchronized cohort aging. Randomize maintenance windows and rollout cohorts so a shared procurement or deployment date does not become a synchronized fleet-wide cliff.
  • Preserve censoring information. Keep start time, last-seen time, failure time, retirement reason, maintenance history and cohort identity. Treat a graceful deployment restart as a competing event or censoring event according to the question being estimated.
  • Budget recovery throughput. For a repairable component alternating between up and down states, the long-run unavailability is \(U=E[D]/(E[Uptime]+E[D])=\text{MTTR}/(\text{MTTF}+\text{MTTR})\), assuming regenerative cycles with finite mean up- and down-times. If up- and down-times are exponential, \(\lambda\) is the constant failure rate, \(\mu_{\text{repair}}\) is the constant repair-completion rate, MTTF is \(1/\lambda\), MTTR is \(1/\mu_{\text{repair}}\), and \(U=\lambda/(\lambda+\mu_{\text{repair}})\). The renewal expression itself does not require exponential durations. It is a long-run fraction, not the probability that a component of a given age fails in the next minute. Reducing repair time can improve availability, but only if detection, isolation, spare capacity and safe restoration keep pace.
Production falsification · survival data

Publish cohort survival curves with confidence intervals, number at risk, censoring counts, and failure classifications. Compare Kaplan–Meier estimates with the parametric Weibull fit. Monitor age-conditioned failure rates and test whether workload, firmware, host generation or deployment cohort changes the shape.

Failure and repair are different clocks

The failure hazard \(\lambda(t)\) describes the instantaneous rate of first failure conditional on surviving to age \(t\). The repair process starts after a failure and runs on its own clock with its own duration distribution. If repair completion is exponential with constant rate \(\mu_{\text{repair}}\), its mean duration is \(1/\mu_{\text{repair}}\). A constant repair rate does not make the failure process memoryless: the failure hazard may still increase or decrease with component age, as in a Weibull model.

Here \(\text{MTTF}=E[Uptime]\) is the mean operating duration from restoration to the next failure, and \(\text{MTTR}=E[D]\) is the mean down/repair duration from the chosen failure-detection boundary to restored service. Define those measurement boundaries honestly; in production, \(\text{MTTR}\) includes alert delay, human paging, ticket triage, waiting for a spare drive in a warehouse, data rebuild, validation and reintegration—not just the forty seconds it took to run systemctl restart. For an exponential up/down continuous-time Markov model—with constant failure rate \(\lambda\) and constant repair rate \(\mu_{\text{repair}}\)—\(\text{MTTF}=1/\lambda\) and \(\text{MTTR}=1/\mu_{\text{repair}}\), and the steady-state unavailability is:

\[ U_{\infty}=\frac{\lambda}{\lambda+\mu_{\text{repair}}},\qquad A_{\infty}=\frac{\mu_{\text{repair}}}{\lambda+\mu_{\text{repair}}} \]

More generally, for an alternating renewal process with finite mean up- and down-times, the long-run unavailability is \(U_{\infty}=E[D]/(E[Uptime]+E[D])\), whether or not those durations are exponential. The familiar \(\text{MTTR}/(\text{MTTF}+\text{MTTR})\) expression is this long-run reward fraction. It does not give the age-conditioned probability of failure in the next interval; for a lifetime model that probability is \(P(tt)=1-S(t+\Delta)/S(t)\).

In a real service, service unavailability also depends on redundancy, detection, failover, network reachability and repair/rebuild capacity. A component's steady-state availability cannot simply be copied into the service-level SLO.

4. Capstone: reliability economics in a synchronous GPU training fleet

The series-system trap at hyperscale

In synchronous distributed training, 16,384 GPUs march in lockstep across collective communication barriers (such as AllReduce). A single dead rank, a flaky optical transceiver, or a wedged PCIe bus stalls progress for the entire job. More GPUs buy raw FLOP/s, but they also assemble a massive series-like exposure surface. The right model is a job-level interruption model—not a claim that every GPU is literally an independent series component for every failure mode.

Documented evidence · Meta Llama 3 training report

Meta's Llama 3 report describes a 24K-GPU RoCE cluster, with up to 16,384 GPUs used for Llama 3 pre-training. In a 54-day snapshot, it reports 466 job interruptions: 47 planned and 419 unexpected, spanning GPU, host, network, software and maintenance-related causes. The paper also reports more than 90% effective training time. The 16,384-GPU configuration and 419 unexpected events are the inputs used for the illustrative calculations below; they are not a fleet-wide GPU failure rate. Read the Llama 3 report.

Step A · Estimate the observed job-interruption intensity

Over 54 days there are \(54\times24=1,296\) wall-clock hours. Using the 419 unexpected interruptions (excluding 47 planned interruptions), the empirical unexpected-event intensity for this run is:

\[ \hat\Lambda_{\mathrm{job}}=\frac{419}{1,296}\approx0.3233\text{ interruptions/hour} \]

The reciprocal gives an average interval between reported unexpected interruptions of:

\[ \widehat{MTBI}=\frac{1}{\hat\Lambda_{\mathrm{job}}}\approx3.09\text{ hours}\quad(185.6\text{ minutes}) \]

Every three hours, on average, something punches the training job in the face. Keep the label clean: this is an observed run-level unexpected-interruption intensity. It is not an H100 hardware MTBF, GPU lifetime, node lifetime, rack lifetime, or fleet replacement rate. It excludes the 47 planned interruptions and does not prove that unexpected events form a stationary Poisson process. The calculation treats each reported unexpected interruption as one event over the stated exposure window. A production forecast should stratify by cause, distinguish job interruption from node failure, include planned stoppages in the checkpoint schedule, and test whether the rate changes with cluster configuration, workload phase, repairs and software rollout.

If, purely as a first approximation, unexpected job interruptions followed a homogeneous Poisson process at this rate, the probability of surviving a full 24-hour day without a single unexpected interruption would be:

\[ P(N(24)=0)=e^{-0.3233\times24}\approx0.00042=0.042\% \]

A 0.042% chance of a quiet day is a visceral stress signal for checkpoint and recovery design—not a claim that the next training run has exactly this probability. The observed rate may include multiple failure mechanisms and changing operating conditions.

Step B · Checkpoint frequency is an economic tug-of-war (The Young–Daly Model)

When a job halts every three hours, you survive by saving checkpoints. This sets up a fundamental economic tug-of-war: checkpoint too frequently, and you burn millions of dollars of GPU time freezing the training loop to write terabytes of weights and optimizer states to storage; checkpoint too rarely, and a crash wipes out hours of forward progress, forcing the entire cluster to replay steps it already computed.

The Young–Daly model frames this trade-off as a first-order optimization problem. Let \(M\) be the mean interval implied by the unexpected-interruption intensity used in this illustrative scenario (\(M = 1/\Lambda_{\mathrm{job}}\)), \(\delta\) the blocking time per checkpoint, \(R\) the restart overhead after an interruption, and \(\tau\) the checkpoint interval (our control variable). Planned maintenance interruptions are excluded from this value of \(M\) and would need to be represented in a full schedule-aware model. Under the simplified Young–Daly approximation, the total fraction of wall-clock time lost to overhead and recovery, \(W(\tau)\), is the sum of two competing taxes:

\[ W(\tau)=\underbrace{\frac{\delta}{\tau}}_{\text{Proactive Tax}}+\underbrace{\frac{\tau/2+R}{M}}_{\text{Reactive Tax}} \]
  • 1. The Proactive Tax — Checkpoint Overhead (\(\frac{\delta}{\tau}\)): In every scheduled training cycle of length \(\tau\), the training loop is frozen for \(\delta\) minutes while weights and optimizer states are serialized and flushed to persistent storage. The fraction of wall-clock time surrendered to this voluntary I/O pause is simply the ratio \(\frac{\delta}{\tau}\). As you lengthen the interval \(\tau\), this tax shrinks hyperbolically.
  • 2. The Reactive Tax — Crash & Recovery Cost (\(\frac{\tau/2+R}{M}\)): Over a long run of duration \(T\), the job suffers approximately \(T/M\) unexpected interruptions. If interruptions arrive as a memoryless Poisson process, a crash is equally likely to strike at any point inside a checkpoint window \([0,\tau]\). By the properties of a continuous uniform distribution on \([0,\tau]\), the expected amount of uncommitted training work destroyed by a crash is the midpoint: \(\frac{\tau}{2}\). On top of that lost work, every crash charges a fixed restart penalty \(R\)—the time required to detect the dead rank, cordon the bad node, re-initialize the communicator (e.g., ncclCommInitRank), load the last checkpoint from storage, and resume the step loop. Because each interruption costs \((\tau/2 + R)\) minutes and strikes once every \(M\) minutes on average, the fraction of total time consumed by crashes is \(\frac{\tau/2+R}{M}\). As you lengthen \(\tau\), this tax grows linearly.

Because the proactive tax falls as \(1/\tau\) and the reactive tax rises linearly with \(\tau\), the total waste curve \(W(\tau)\) is convex. To find the optimal checkpoint interval \(\tau^*\) that minimizes wasted time (and maximizes goodput, \(G(\tau)=1-W(\tau)\)), differentiate with respect to \(\tau\) and set the derivative to zero:

\[ \frac{dW}{d\tau}=-\frac{\delta}{\tau^2}+\frac{1}{2M}=0 \quad \implies \quad \frac{\delta}{\tau^2}=\frac{1}{2M} \quad \therefore\quad\tau^*=\sqrt{2\delta M} \]

Three architectural insights hidden inside \(\tau^*=\sqrt{2\delta M}\)

  1. \(R\) vanishes from the optimal interval \(\tau^*\): Look closely at the derivative—the restart overhead \(R\) completely disappears! While a sluggish 20-minute restart \(R\) directly punishes your overall goodput \(1-W(\tau)\), it does not change how often you should checkpoint. You cannot compensate for a slow container orchestrator, bloated Docker image pulls, or sluggish NCCL initialization by checkpointing more frequently.
  2. Square-root scaling: If you scale your cluster up and the mean time between interruptions \(M\) drops by a factor of 4, you do not checkpoint 4 times as often—you checkpoint \(\sqrt{4}=2\) times as often, as economic leverage shifts between I/O pause and rework risk.
  3. Why asynchronous checkpointing changes the game: Moving checkpoint serialization off the critical path (for example, snapshotting weights to pinned host RAM via copy-on-write and flushing to distributed storage asynchronously in the background) shrinks the blocking pause \(\delta\) by an order of magnitude (say, from 2 minutes down to 12 seconds). Because \(\tau^*\propto\sqrt{\delta}\), slashing \(\delta\) lets you checkpoint much more frequently while simultaneously driving down both the proactive pause tax and the reactive rework tax.

Where the first-order approximation breaks

The linear equation \(W(\tau)=\frac{\delta}{\tau}+\frac{\tau/2+R}{M}\) is a first-order approximation of a renewal-reward process. Before betting a cluster budget on it, know where its assumptions bend and break:

  • Small-ratio assumption (\(\tau \ll M\) and \(\delta \ll \tau\)): In the exact renewal formulation, the denominator of the proactive tax and the numerator of the expected rework are conditioned on surviving the interval. Young (1974) and Daly (2006) showed that when \(\tau\) becomes a sizable fraction of \(M\), higher-order terms matter, leading to Daly's perturbed solution:
    \[ \tau^*_{\mathrm{Daly}} = \sqrt{2\delta M}\left(1 + \frac{1}{3}\sqrt{\frac{\delta}{2M}} + \frac{1}{9}\left(\frac{\delta}{2M}\right)\right) - \delta \]
    For typical cluster parameters where \(\delta \ll M\), the clean \(\sqrt{2\delta M}\) formula is accurate within 1–2%.
  • Unbounded loss at extreme failure rates: Because the linear expression adds the two fractions directly, extreme stress inputs (where \(R > M\) or \(\delta\) is huge) can push \(W(\tau) \ge 1\) (implying 100%+ waste and negative goodput). In Interactive Lab 4 below, this is why const valid = rawLoss < 1 is explicitly guarded.
  • No failure during recovery or checkpointing: The basic equation assumes crashes only strike during useful compute (\(\tau\)), ignoring the probability of a secondary node dying while you are in the middle of the \(R\)-minute restart or \(\delta\)-minute checkpoint write. It also does not automatically model incremental checkpoints, correlated failure bursts, age-dependent job hazards, or recovery that overlaps with useful work.

Hypothetical planning inputs, not Meta cost data: Let us plug in \(M=185.6\) minutes (the reciprocal of the observed unexpected-interruption intensity above), blocking checkpoint time \(\delta=2\) minutes, restart overhead \(R=20\) minutes, modeled job allocation of 16,384 GPUs, and an assumed blended cost of $2.50 per GPU-hour.

\[ \tau^*=\sqrt{2\times2\times185.6}\approx27.2\text{ minutes} \]

At this interval, the estimated lost-time fraction is:

\[ W(27.2)\approx\frac{2}{27.2}+\frac{13.6+20}{185.6}\approx25.5\%, \qquad \text{goodput}\approx74.5\% \]

For a 54-day run, the modeled job allocation's assumed compute spend is \(16,384 \times 1,296 \times \$2.50 \approx \$53.08\) million. Applying the simplified waste fraction gives approximately $13.51 million of time-equivalent compute cost. This is an illustrative opportunity-cost calculation, not a reported Meta cost or a cash invoice. The modelled 74.5% goodput is not an estimate of Meta's reported effective training time (above 90%): the checkpoint pause, restart duration and GPU-hour price are hypothetical, the model uses the unexpected-event rate only, and the simple approximation omits the production system's detailed recovery and scheduling behavior.

Notice the financial leverage here: tuning a single config parameter from hourly checkpoints (\(\tau=60\)) to the Young–Daly optimum (\(\tau=27.2\)) recovers $2.6 million in time-equivalent compute without buying a single piece of hardware. Pushing further—slashing blocking pause \(\delta\) to 0.2 minutes and restart \(R\) to 4 minutes—recovers nearly $10 million more. That third row is not “async checkpointing automatically produces 93.2% goodput.” It is the result of changing the model inputs to a 0.2-minute blocking cost and four-minute restart. An asynchronous design must still establish a consistent recovery point, ensure checkpoint durability, manage host-memory/NVMe pressure, and account for background flush contention. If the checkpoint is truly non-blocking, replace \(\delta\) with the measured residual pause and model the background resource cost separately.

Step C · A spare pool is a queueing problem, not just a percentage

Nobody wants a $53M training job sitting idle waiting for an RMA truck. So you keep hot spares on the floor. Suppose—hypothetically—that every interruption corresponds to one repairable node entering a 24-hour repair pipeline. At the observed unexpected-interruption rate, the expected number of events during 24 hours is:

\[ \Lambda_{24}=0.3233\times24\approx7.76 \]

If repair arrivals were Poisson and independent, with expected 24-hour count \(\Lambda_{24}=7.76\), then a spare pool of \(S=18\) nodes would have:

\[ P(X>18\mid\Lambda_{24}=7.76)\approx0.000455=0.0455\% \]

That is below 0.1% stockout risk under the stated model. But the calculation is useful only if the assumptions hold: one unexpected interruption must map to one spare-consuming repair, repairs must take approximately 24 hours, arrivals must be reasonably Poisson, and failures must not arrive in correlated bursts (like a bad firmware push bricking 30 NICs at once). The Llama 3 interruption count includes multiple causes, so this is a hypothetical buffer-sizing example, not a spare recommendation derived from the report.

In a real fleet, model the spare pool as an inventory/repair system (such as an \(M/G/\infty\) or finite-repair-server queue). Measure repair-time distribution, simultaneous failures, spare compatibility, maintenance backlog, time to detect, time to isolate, and whether a spare can join the same rail-optimized network topology without creating a new bottleneck.

Do not turn a GPU interruption rate into a rack replacement policy

One of the fastest ways to embarrass yourself in capacity planning is to take a job interruption rate, divide by 16,384, call it “GPU lifetime,” and use it to schedule data-center rack replacements. There are at least four different asset populations in a large accelerator fleet, and each has a different failure process:

  • GPU lifetime: time or exposure until a GPU-specific fault makes that accelerator unfit for service. HBM, package, board and firmware faults may have different mechanisms.
  • Node lifetime: time until the server as an integrated unit cannot meet its role. A node can fail because of its GPU, CPU, memory, NIC, power supply, cooling or motherboard; the GPU's lifetime is not the node's lifetime.
  • Rack lifetime: time until a rack-level assembly or shared subsystem—power distribution, liquid cooling manifolds, top-of-rack networking, cabling or structural infrastructure—requires intervention or replacement. Rack failures can be common-cause events for many nodes.
  • Fleet replacement policy: a portfolio decision shaped by age cohorts, capacity demand, maintenance windows, spare inventory, supply lead time, compatibility, energy efficiency and planned refresh cycles. It is not obtained by multiplying one GPU's failure probability by the fleet size.

An age-based replacement policy can be evaluated for a clearly defined, homogeneous asset. Let \(T\) be its lifetime, \(S(t)\) its survival function, and \(a\) the planned replacement age. Under a renewal model in which a replacement starts a new cycle, the expected operating time per cycle is \(E[\min(T,a)]=\int_0^a S(t)\,dt\). A simplified long-run cost rate per unit of operating time is:

\[ g(a)=\frac{S(a)C_P+\int_0^a f(t)C_F(t)\,dt}{\int_0^a S(t)\,dt} \]

Here \(C_P\) is the net planned-replacement cost at age \(a\), and \(C_F(t)\) is the failure-path cost if failure occurs at age \(t\). The failure-path cost should explicitly include corrective replacement, repair, downtime, lead-time exposure and any lost production; planned and failed removals should account for residual value where recoverable. This renewal-reward expression assumes a failure ends the asset cycle and a replacement restores an as-good-as-new unit, with comparable cycles in a stationary population. If the same unit is repaired and retains its accumulated age, use an imperfect-repair or virtual-age model instead. It reports cost per unit of operating time; if the decision metric is cost per calendar hour, repair and procurement lead-time downtime must also be represented in the cycle duration. It is a decision framework, not a universal formula for rack economics.

Run sensitivity analysis over the fitted failure hazard, repair duration, replacement and repair costs, downtime valuation, spare compatibility, procurement lead time and residual value. Estimate separate survival curves and cost models for GPU, node and rack populations. Then aggregate them into a fleet policy that staggers cohorts and preserves enough compatible spare capacity. The Llama 3 interruption count supplies none of those asset-level lifetime or cost parameters, so no actual hyperscaler replacement optimum can be inferred from it.

Architectural controls derived from the model
  • Measure job goodput, not just node uptime. Define goodput as useful, recoverable training progress committed per unit wall-clock time. Include stalled collectives, checkpoint overhead, replayed work, and recovery time.
  • Make checkpoint semantics explicit. Track checkpoint duration, residual pause, durable completion, bytes written, background flush pressure, and restart-from-checkpoint time. Test corruption and partial checkpoint failures.
  • Classify interruptions. Separate GPU/HBM faults, network and fabric events, host failures, software defects, scheduler actions, and planned maintenance. Each cause has a different control.
  • Use spare capacity based on the repair process. Size by the distribution of concurrent spare demand and repair duration, then validate against burst scenarios—not just the average event rate.
  • Isolate degraded ranks quickly. Correlate collective timeouts with PCIe, NVLink, NIC and switch telemetry. Cordon a suspect node before restarting the whole job onto the same failure.
Production falsification · fleet reliability ledger

For every interruption, record timestamp, job/rank, component, cause confidence, detection time, isolation time, lost progress, checkpoint age, restart duration, repair duration and whether the event was correlated with another. Plot interruption intensity over time and by failure class; test for burstiness and regime changes before using a stationary Poisson approximation.

Use this table as a review aid the next time someone brings suspiciously clean availability math to a design review. The important question is never “Which distribution should I use?” It is “What physical process generated this observation, and what production evidence would force me to throw this model in the trash?”

Mechanism Candidate model Common modelling mistake Evidence to inspect Engineering control
One request fails Bernoulli Assuming the next attempt is independent during saturation Attempt-level outcomes, conditional retry success, error bursts, queue age Bounded retries, backoff, jitter, retry budgets, admission control

Reliability models tell us how components, redundant groups and workflows fail—and why repair capacity and shared dependencies matter far more than how many boxes you can fit on a slide.
