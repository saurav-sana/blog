The Stochastic Shape of AI Systems

November 28, 2026 · Part 8 of 8 · AI/LLM Frontier

“The fundamental problem of communication is that of reproducing at one point either exactly or approximately a message selected at another point.”

— Claude Shannon, "A Mathematical Theory of Communication"

Welcome to the frontier. If you thought distributed databases were chaotic, you haven't tried running an autonomous LLM agent in production. The entire stack is built on a foundation of literal random number generators and probabilistic matrix multiplications.

We are currently in the "PoC Euphoria" phase of AI, where companies are stringing together multi-step agents and crossing their fingers. But the mathematics of AI systems are the exact same mathematics we've explored in this series. The underlying physics haven't changed; the failure surfaces have just moved.

1. The Categorical Distribution (Token Sampling)

The Intuition: The Weighted Dice Roll

An LLM doesn't "think" of the next word. It outputs a probability distribution over its entire vocabulary (e.g., 50,000 possible tokens) and rolls a weighted die. The Categorical distribution models a single draw from a set of possibilities that each have a distinct probability.

The temperature parameter is your dial for flattening or sharpening those probabilities. Temperature = 0 makes it deterministic (always pick the highest probability token). Temperature = 1.0 lets the model roll the dice based on its raw probabilities. Temperature > 1.0 flattens the distribution, making the model hallucinate wildly.

The Math

The probability of sampling token i, where pi is the raw probability assigned by the model's Softmax layer:

P(X = i) = pi (where Σ pi = 1)
Let's decode this:
  • X: The discrete category (the token chosen).
  • pi: The probability weight of that specific token.
  • Temperature (T): Applied before the Softmax. The formula is \(e^{z_i / T} / \sum e^{z_j / T}\).

Worked Example: If the model assigns a 40% chance to the word "Data", 30% to "Model", 20% to "Magic", and 10% to "Garbage". If you set T = 1.0, "Data" is chosen 40% of the time. If you set T = 2.0, the probabilities are flattened, and "Garbage" might suddenly be chosen 20% of the time.

The SRE Trap

If you leave the temperature > 0, your application is non-deterministic. Your unit tests will pass locally and fail in production because the model rolled a different token. For high-reliability structured data extraction, you must force temperature to 0 (greedy decoding).

Scenarios & Case Studies

The "Non-Deterministic Test" CI/CD Pipelines

Your tests check for a specific string output. But the model has a temperature of 0.7. On the 15th run, it generates a semantically identical but syntactically different string, and your CI pipeline goes red. You cannot unit test a stochastic system without setting T=0.

Reference: OpenAI: Temperature and Determinism
The "Hallucination Spiral" High Temperature Agents

An agent is set to a high temperature to "encourage creativity." It encounters an ambiguous input, samples an unlikely token, and then compounds the hallucination in subsequent steps, confidently outputting a completely fabricated answer.

Reference: Yao et al., "Tree of Thoughts" (Exploration vs. Exploitation)
The "Top-P Mask" Nucleus Sampling

Top-P truncates the distribution to only include the top tokens that sum to probability P (e.g., 0.9). This removes the long tail of absolute nonsense, but restricts the model's ability to recover from a bad path.

Reference: Holtzman et al., "The Curious Case of Neural Text Degeneration"

2. The Exponential Distribution (TTFT & Inference)

The Intuition: The Waiting Room for the First Token

When you send a prompt to an LLM, you are waiting for the Time to First Token (TTFT). This is a queueing problem. The GPU has a fixed number of KV-cache blocks. If they are full, your request goes into a waiting room. The time you spend waiting is modeled by the Exponential distribution.

Just like the bus stop in Part 3, it is "memoryless." The probability of your request starting in the next 10 milliseconds is exactly the same, regardless of how long you've already been waiting in the queue. This is why TTFT spikes are so frustrating for users.

The Math

The probability density function for the time until the first token is generated, given a service rate λ:

f(x) = λ · e-λx
Let's decode this:
  • λ: The rate at which the GPU can ingest prompts (e.g., 50 requests per second).
  • x: The TTFT in seconds.

Worked Example: If your GPU can process 100 prompts per second (λ=100), the probability that a request takes more than 50ms (x=0.05s) to generate its first token is e^(-100 * 0.05) = e^-5 ≈ 0.67%. This seems tiny, but at 1 million requests, that's 6,700 users experiencing a massive lag spike.

The SRE Trap

Context windows matter. A prompt with 100,000 tokens requires vastly more KV-cache memory and compute than a prompt with 100 tokens. The λ is not static; it collapses as the context window fills up. You must monitor TTFT by context length, not just globally.

Scenarios & Case Studies

The "KV-Cache Exhaustion" vLLM / TGI

During a traffic spike, the KV-cache fills up. vLLM implements "continuous batching" to handle this, but when the cache is full, TTFT skyrockets as new requests are paused until existing sequences finish and free up blocks.

Reference: vLLM: Easy, Fast, and Cheap LLM Serving
The "Cold Start" Serverless Inference

A serverless GPU takes 30 seconds to load a 70B parameter model into VRAM. The first request after a cold start experiences a TTFT of 30+ seconds. This breaks the Exponential assumption because the hazard rate is effectively 0 for the first 30 seconds.

Reference: NVIDIA Triton Inference Server
The "Chunked Prefill" Continuous Batching

To prevent long prompts from blocking short ones, modern serving engines break prompts into chunks. This smooths out the TTFT distribution, making it less Exponential and more deterministic, but increases the Inter-Token Latency (ITL).

Reference: Agrawal et al., "Taming Throughput-Latency Tradeoff in LLM Inference"

3. The Geometric Distribution (Structured Outputs)

The Intuition: "JSON is Hard, Let's Retry"

You prompt an LLM: "Return a JSON object with keys 'name' and 'age'." The LLM responds: "Sure! Here is the JSON: \`\`\`json { "name": "Alice" } \`\`\`". Your parser fails. You retry.

The Geometric distribution models the number of retries required to get a valid, parseable output. Every request is a Bernoulli trial (Valid JSON vs. Invalid JSON). If the model has a 90% success rate at generating JSON, the Geometric distribution tells you how many loops you'll run before it finally works.

The Math

The probability of needing exactly k attempts to get the first valid JSON, where p is the probability of success:

P(X = k) = (1 - p)k-1 · p
Let's decode this:
  • k: The total number of attempts.
  • p: The probability the model outputs valid JSON on any single attempt.

Worked Example: If the model succeeds 80% of the time (p=0.8), the chance it takes exactly 3 attempts is 0.2^2 * 0.8 = 0.032 (3.2%). But if you have 10,000 API calls per day, that means 320 requests require 3 attempts, burning 3x the tokens and inflating your latency and cost.

The SRE Trap

Retrying with the exact same prompt and temperature > 0 is a recipe for an infinite loop. If the model fails once, it might fail the same way again. You must change the prompt (e.g., "Fix the JSON errors in your previous response") or lower the temperature on the retry.

Scenarios & Case Studies

The "Token Tax" Cost Management

If your validation fails 20% of the time, your effective token usage is 1.25x higher than expected. At scale, this geometric compounding destroys your FinOps budget. You must use constrained decoding (like OpenAI's JSON mode) to force p to 1.0.

Reference: OpenAI JSON Mode
The "Parser Exception" LangChain

LangChain's OutputParsers throw an exception if the LLM adds conversational filler ("Here is your JSON!"). This forces the framework to retry, which loops back to the model and creates a geometric latency spiral.

Reference: LangChain Output Parsers
The "Infinite Loop" Agent Tool Calling

An agent tries to call an API with the wrong arguments. The API returns a 400 error. The agent retries with the exact same arguments. Without a circuit breaker, this loop runs until the maximum token limit is reached.

Reference: LangChain Max Iterations

4. The Binomial Distribution (Agent Compounding)

The Intuition: The 10-Step Agent

You build an autonomous agent. It has to do 10 sequential steps: search the web, parse the HTML, extract the data, write to a database, etc. You benchmark the model on a single step and see a fantastic 95% success rate.

The Binomial distribution dictates that if each step is an independent Bernoulli trial, the probability of the entire workflow succeeding is \(0.95^{10} \approx 59\%\). You just built an agent that fails 41% of the time, despite having a "world-class" model.

The Math

The probability of k successes out of n independent steps, where each step has a probability p of success:

P(X = k) = (n choose k) · pk · (1 - p)n - k
Let's decode this:
  • n: The number of sequential steps in your agent workflow.
  • k: The number of successful steps.
  • p: The probability of success on a single step.

Worked Example: If you have a 20-step agent with a 95% per-step success rate, the probability of 20 out of 20 successes is 0.95^20 = 35.8%. This means a third of your user sessions will encounter a failed state. You cannot fix this by fine-tuning the model; you must reduce the number of steps (n) or add deterministic guardrails (raise p).

The SRE Trap

Agent steps are not independent. If step 2 hallucinates a wrong URL, step 3 (parsing the HTML) will fail, step 4 (extracting the data) will fail, and the whole pipeline collapses. The Binomial math is actually overly optimistic because it doesn't account for error cascades.

Scenarios & Case Studies

The "Compounding Hallucination" AutoGPT

Early autonomous agents like AutoGPT were notorious for getting stuck in loops. A single wrong assumption in step 1 led to compounding errors in steps 2 through 50. The agent would eventually run out of context window or start hallucinating tools that didn't exist.

Reference: Wang et al., "A Survey on Large Language Model based Autonomous Agents"
The "Cascading Failures" Multi-Agent Systems

When you have multiple agents talking to each other (e.g., a "Coder" agent and a "Reviewer" agent), the failure rate compounds exponentially. The Reviewer misses a bug, the Coder introduces 3 more bugs while trying to fix it, and the whole system collapses.

Reference: Qian et al., "Communicative Agents for Software Development"
The "Deterministic Guardrail" NeMo Guardrails

The only way to make agents reliable is to wrap the non-deterministic steps in deterministic guardrails. If an agent tries to call a tool with invalid arguments, the guardrail catches it before the API is hit. This artificially raises p for the workflow.

Reference: NVIDIA NeMo Guardrails
The Final Reality: Human-in-the-Loop

AI systems don't fail because the math is different. They fail because the math is the same. A 20-step agent is just a distributed system with a 40% failure rate.

The Lesson: You cannot prompt-engineer your way out of the Binomial distribution. You must build deterministic architectures that constrain the AI's stochastic nature. For any high-stakes workflow, you need a human-in-the-loop. The AI proposes; the deterministic system disposes.
