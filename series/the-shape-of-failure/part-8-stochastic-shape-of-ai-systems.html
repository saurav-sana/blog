The Stochastic Shape of AI Systems

November 28, 2026 · Part 8 of 8 · AI/LLM Frontier

“The fundamental problem of communication is that of reproducing at one point either exactly or approximately a message selected at another point.”

— Claude Shannon, "A Mathematical Theory of Communication"

In Part 7, we built an operational validation framework to detect when our latency, traffic, and reliability models drift away from physical reality. Throughout Parts 1 to 7, our proving ground was a deterministic Multi-Tenant Analytics Gateway: a request arrived with a formal SQL query or API payload, and our job was to route, cache, shard, and execute it without violating tail-latency SLOs or exhausting memory boundaries. If the infrastructure returned an HTTP 200 and passed checksum validation, the response was deterministic and correct by construction.

Welcome to the frontier. Now suppose leadership asks us to extend that same Multi-Tenant Analytics Gateway with an AI Query Assistant and Autonomous Reconciliation Agent. Tenants can ask natural-language questions, retrieve Iceberg table metadata via RAG, synthesize analytical SQL, repair validation errors, and execute multi-step reconciliation workflows. Suddenly, an HTTP 200 with a 180 ms response time can still be a catastrophic production failure—because a syntactically valid JSON payload containing a plausible-looking SQL query just joined the wrong tenant partition or fabricated a regulatory metric.

An AI system in production is not a single inscrutable probability box; it is a layered stochastic pipeline combining discrete token sampling, batch-scheduled GPU queues, high-bandwidth memory constraints, conditional retry loops, and multi-stage state machines. As throughout this series, our core discipline holds: a distribution is a model, not an invariant. The useful architectural question is not “How do we make an LLM deterministic?” It is: Where does randomness enter the pipeline, which failure layer does it threaten, and what deterministic control plane bounds the blast radius?

The AI Reliability Stack: Five Distinct Failure Layers

Before fitting any distribution to an AI service, an architect must separate five distinct success events that traditional APM dashboards conflate into a single “200 OK” counter:

  1. Serving Reliability (Eserve): The inference engine accepts the request, allocates KV-cache memory, and streams tokens within the TTFT and inter-token latency budgets without HTTP 5xx, timeout, or OOM preemption.
  2. Structural Correctness (Estruct): The generated output conforms to the syntactic contract—valid JSON, matching grammar, or a parseable AST without truncation.
  3. Data & Schema Grounding (Edata): Referenced entities, table names, column types, and tool parameters actually exist in the target catalog and respect tenant authorization boundaries.
  4. Semantic Correctness (Esem): The logically executable output actually answers the user's intent and preserves domain invariants (for example, filtering by settlement date rather than trade creation date).
  5. End-to-End Task Success (Etask): The complete multi-step workflow—including downstream tool execution, validation, and side effects—completes safely within cost and deadline budgets.

By the chain rule of probability, task success is the product of conditional probabilities across every layer: P(E_task) = P(E_serve) · P(E_struct | E_serve) · P(E_data | E_struct, E_serve) · P(E_sem | E_data, …) · P(E_task | E_sem, …). Optimizing one layer (such as forcing valid JSON via constrained decoding) drives P(E_struct | E_serve) → 1, but does nothing to guarantee P(E_sem).

1. The Categorical Distribution (Token Sampling)

The Intuition: The Weighted Dice Roll

At each autoregressive decoding step, a language model computes a vector of unnormalized scores (logits) across its entire vocabulary. A Softmax transformation converts those scores into a discrete probability vector, and the sampler draws a single token. The Categorical distribution models that single discrete draw conditioned on the exact token prefix generated so far.

Temperature (T) controls the entropy of that draw by scaling logits prior to exponentiation. Lower values concentrate probability mass onto the highest-logit token; higher values flatten the distribution toward uniformity. Crucially, temperature controls lexical diversity—not the epistemic probability that a statement is factually true.

The Math

Let Xt be the random variable representing the token index selected at decoding step t from a vocabulary of size K (dimensionless index i ∈ {1, …, K}), conditioned on the preceding context x<t. Given raw logit zi ∈ ℜ and temperature T > 0 (dimensionless scaling parameter), the probability of sampling token i prior to top-k or top-p truncation is:

P(Xt = i | x<t) = pi(T) = exp(zi / T) / Σj=1K exp(zj / T) = pi(1)1/T / Σj=1K pj(1)1/T
Let's decode this:
  • Xt: Discrete random variable for the single token selected at step t.
  • zi: Unnormalized logit for vocabulary token i produced by the final linear projection layer.
  • T: Temperature parameter (T > 0). As T → 0+, probability mass concentrates on argmaxi zi (greedy decoding). As T → ∞, pi(T) → 1/K for finite logits.
  • Sequence vs. Step Distinction: A single token draw is Categorical, but an L-token response is a non-homogeneous autoregressive stochastic process where each draw Xt alters the conditioning prefix x<t+1 and shifts the logit vector at step t+1.

Worked example: Suppose at T = 1.0 the distribution over four candidate tokens—Data, Model, Magic, and Garbage—is p(1) = [0.40, 0.30, 0.20, 0.10]. If an engineer raises temperature to T = 2.0 to make responses “more creative,” the new unnormalized weights are pi(1)1/2 = [√0.40, √0.30, √0.20, √0.10] ≈ [0.6325, 0.5477, 0.4472, 0.3162], which sum to 1.9436. Renormalizing yields p(2) ≈ [32.54%, 28.18%, 23.01%, 16.27%]. The probability of drawing the undesirable tail token (Garbage) jumps from 10.00% to 16.27%—a 62.7% relative increase on a single step. (Note: this is an illustrative single-step calculation, not a direct measurement of multi-token hallucination rate.)

The SRE Trap

Temperature greater than zero makes sampling stochastic by design, so exact-string unit tests fail intermittently even when the answer is semantically valid. Conversely, setting temperature = 0 selects the greedy token at each step, but it is not a hardware-level reproducibility guarantee. Floating-point non-associativity in GPU matrix reductions, variable dynamic batch sizes, Mixture-of-Experts (MoE) routing capacity, and silent provider model snapshots can still alter tie-breaking logits. For CI/CD regression suites, pin the model snapshot, prompt template, decoding parameters, and tool schemas; assert structural and semantic invariants rather than raw prose strings.

When this model breaks: Do not treat token sampling probability as a calibrated confidence score for factual truth. When a model is miscalibrated or lacks grounding data in its context window, the factually wrong token can easily hold the highest logit (p1 = 0.85), meaning greedy decoding (T → 0) will select the falsehood 100% of the time.

Case Study 1: Temperature-Induced SQL Dialect Drift in the Analytics Gateway
Illustrative Production Model

1. The Incident: After rolling out the natural-language-to-SQL (NL2SQL) assistant on the Multi-Tenant Analytics Gateway, 14.8% of multi-join analytical queries began failing in the DuckDB execution worker with parser errors (invoking PostgreSQL-only regex operators or Spark-specific LATERAL VIEW EXPLODE syntax).

2. The Architectural Assumption: The application team reused a shared chat-completion client configured with temperature = 0.7 and top_p = 0.95, assuming that because the system prompt explicitly specified “Generate valid DuckDB SQL,” minor token diversity would only affect SQL alias naming.

3. The Physical Mechanism: In code and SQL generation, syntax tokens at dialect branch points (such as date-truncation functions or array unnesting) compete closely in logit space across pre-training dialects (Postgres, Spark SQL, Snowflake, DuckDB). At T = 0.7, the Categorical sampler occasionally draws a runner-up token from a competing dialect; once that token enters the prefix x<t, autoregressive conditioning locks the remainder of the clause into the wrong SQL dialect.

4. The Mathematical Model: Let a complex analytical query contain m = 8 dialect-sensitive syntax branch points. At T = 0.7, suppose the valid DuckDB token holds probability pi = 0.98 and competing SQL dialect tokens share the remaining 0.02 at each branch point (assumed independent across branch points for a first-order baseline).

5. The Calculation: The probability that all m = 8 branch points sample the valid DuckDB token at T = 0.7 is P(Estruct) = 0.988 ≈ 0.8508 (85.1%), yielding a 14.9% query syntax failure rate (1 - 0.8508 = 0.1492). Lowering T → 0 (greedy decoding) selects the dominant token (0.98 > 0.02) deterministically at all 8 branch points whenever the correct dialect token is the mode.

6. The Architectural Decision: Split decoding profiles by task class: enforce temperature = 0.0 for all code, SQL, and tool-argument generation, and attach a deterministic pre-execution AST transpiler/validator (sqlglot) inside the gateway before dispatching queries to DuckDB workers. Trade-off: Greedy decoding eliminates sampling diversity, meaning if a prompt is genuinely ambiguous and the wrong dialect token has the highest logit, a simple retry at T = 0 will fail identically unless the validator injects the AST parse error into the repair prompt.

7. Production Verification: Track gateway_sql_ast_parse_error_rate segmented by decoding profile and monitor sqlglot_transpile_rewrite_count. Following the configuration change, unparseable dialect failures dropped from 14.8% to 1.9% (the residual 1.9% representing epistemic schema gaps rather than sampling variance).

Operational Scenarios

The Non-Deterministic Test CI/CD Pipelines

A test expects one exact sentence, but a model returns a valid answer with different wording. The test fails even though the product behaviour is acceptable. Separate deterministic contract tests (schema, required fields, allowed tool calls, safety invariants) from probabilistic quality evaluations (groundedness, relevance, task success). Use temperature zero when appropriate, but do not treat it as a substitute for robust assertions.

Reference: OpenAI API: Advanced usage and reproducibility considerations
Autoregressive Error Propagation Generation Dynamics

Each sampled token becomes part of the context for later tokens. A mistaken entity, number, or premise can therefore influence what follows. This is a plausible error-propagation mechanism, not a rule that every low-probability token causes a confident hallucination. Grounding, retrieval, verification, and constrained task boundaries are more direct controls than temperature alone.

Reference: Holtzman et al., “The Curious Case of Neural Text Degeneration”
The Top-P Cutoff Nucleus Sampling

Top-p sorts tokens by descending probability, retains the smallest prefix whose cumulative probability reaches or exceeds the configured threshold, then renormalizes the retained probabilities. It trims the low-probability tail; it does not know which tokens are “nonsensical,” and it cannot guarantee factuality.

Reference: Holtzman et al., “The Curious Case of Neural Text Degeneration”

2. The Exponential Distribution (A Queueing Baseline for Inference)

The Intuition: The Waiting Room for the First Token

LLM serving latency is governed by two physically distinct phases: Prefill (processing the input prompt in parallel to populate the Key-Value cache, which governs Time to First Token, TTFT) and Decode (autoregressively generating output tokens one step at a time, which governs Inter-Token Latency, ITL). Neither metric is automatically exponentially distributed, but a stationary M/M/1 queue provides the essential analytical baseline for how waiting time explodes as GPU utilization approaches saturation.

Real LLM inference engines violate textbook M/M/1 assumptions in specific, measurable ways: continuous batching, quadratic prefill compute in prompt length, and hard high-bandwidth memory (HBM) limits for the KV-cache. Treat the exponential sojourn distribution as a null-hypothesis baseline to test against production traces—not as a law of GPU physics.

The Math

For a stationary M/M/1 queue with Poisson request arrival rate λa (requests/second), exponential service rate μ (requests/second), single FCFS server discipline, and stability condition ρ = λa / μ < 1, the total sojourn time in the system W (queueing delay plus service time, in seconds) follows an Exponential distribution with net rate θ = μ - λa (s−1):

fW(t) = θe−θt,   P(W > t) = e−θt,   t ≥ 0

However, on a physical GPU running continuous batching, effective service rate μ degrades discontinuously when active sequences exceed the available KV-cache memory budget Mmax (in bytes). For a transformer with L layers, nkv KV heads per layer, head dimension dhead, precision b (bytes per element), and S total active tokens across the running batch, the physical KV-cache footprint is:

MKV(S) = 2 · b · L · nkv · dhead · S
Let's decode this:
  • λa, μ, ρ: Mean arrival rate (req/s), mean service rate (req/s), and server utilization (ρ = λa/μ).
  • θ = μ - λa = μ(1 - ρ): Net rate parameter of the M/M/1 sojourn-time distribution (s−1). As ρ → 1, θ → 0 and mean latency 1/θ → ∞.
  • W: Total sojourn time (s) under stationary M/M/1 assumptions.
  • MKV(S): Exact HBM memory (bytes) required to store Key and Value tensors (hence the factor of 2) for S active tokens.

Worked example: Let λa = 8 req/s and μ = 10 req/s (ρ = 80%). Then θ = 2.0\text{ s}^{-1}, the mean sojourn time is 1/θ = 0.50\text{ s}, and the theoretical 99th percentile is t_{0.99} = \ln(100)/θ = 4.605 / 2.0 = 2.30\text{ s} (4.605× the mean). The probability of waiting longer than 2.0\text{ s} is e−2×2 ≈ 1.83%.

The SRE Trap

Do not fit a single exponential curve to aggregate TTFT telemetry. Because prompt lengths often span three orders of magnitude (from 100-token chat turns to 32,000-token RAG contexts), service time has high coefficient of variation (Cs2 ≫ 1). As we saw with Kingman's approximation in Part 3, heavy-tailed service times inflate queueing delay far beyond the M/M/1 baseline even at moderate utilization.

Dense full self-attention still requires O(n²) arithmetic operations in prompt sequence length n during prefill. FlashAttention reduces HBM bandwidth bottlenecks through IO-aware SRAM tiling and avoids materializing the full n × n attention matrix in HBM, but it does not make dense prefill compute asymptotically linear. Meanwhile, MKV(S) grows linearly with total cached tokens across all concurrent requests. When MKV(S) > Mmax, the engine must preempt running sequences—turning a smooth queueing curve into a bimodal cliff.

Case Study 2: KV-Cache Exhaustion and PagedAttention Preemption in the Analytics Gateway
Illustrative Production Model

1. The Incident: During the 09:30 market-open burst, the Analytics Gateway's LLM serving tier (running a 70B-parameter FP16 model across a tensor-parallel GPU node with 24 GiB of HBM reserved for KV-cache) suffered a sudden p99 TTFT spike from 1.8 s to 19.4 s, accompanied by mid-stream freezes in token streaming.

2. The Architectural Assumption: Capacity planners sized the GPU worker pool using average request throughput (λa = 6 req/s) and configured the vLLM scheduler with max_num_seqs = 32, assuming 32 concurrent sequences would comfortably fit in GPU memory based on a historical average prompt length of 1,500 tokens.

3. The Physical Mechanism: A new enterprise tenant enabled automated schema-RAG, injecting full Apache Iceberg table manifests and 50-column DDL definitions (averaging 6,400 input tokens + 600 output tokens = 7,000 tokens per sequence) into each request. When concurrent long-context requests filled the 24 GiB KV-cache ceiling, the serving engine triggered sequence preemption—evicting partially decoded requests from HBM and later recomputing their entire prefill from scratch.

4. The Mathematical Model: For the 70B GQA architecture (L = 80 layers, nkv = 8 KV heads, dhead = 128, b = 2 bytes in FP16), per-token KV state is Mtoken = 2 × 2 × 80 × 8 × 128 = 327,680\text{ bytes} = 320\text{ KiB/token}. With Mmax = 24\text{ GiB} = 25,165,824\text{ KiB}, the hard physical capacity boundary is Smax = Mmax / Mtoken = 78,643\text{ tokens}.

5. The Calculation: Under the legacy workload (1,500\text{ tokens/seq}), 32 concurrent sequences required 32 × 1,500 × 320\text{ KiB} = 14.65\text{ GiB} (61% of KV budget, zero preemptions). Under the schema-RAG burst, just N = 12 concurrent sequences required 12 × 7,000 = 84,000\text{ tokens} > 78,643\text{ tokens} (25.63\text{ GiB} > 24\text{ GiB}). Attempting to run 20 concurrent sequences forced continuous thrashing: each evicted 6,400-token request incurred an extra ~420 ms of quadratic prefill recomputation, reducing effective service rate μ below λa (ρ > 1).

6. The Architectural Decision: Replace request-count concurrency limits with token-budget admission control at the NGINX/FastAPI gateway layer (capping in-flight active tokens per replica at Slimit = 65,000, or 82% of KV capacity), enable chunked prefill (sizing chunks at 1,024 tokens so long prefills do not stall active decodes), and route requests exceeding 4,096 prompt tokens to a dedicated long-context worker pool with FP8 KV-cache quantization (b = 1\text{ byte}, doubling Smax to 157,286 tokens). Trade-off: Admission control rejects or queues excess long-prompt bursts at the edge (HTTP 429 with Retry-After), trading explicit edge backpressure for stable core GPU throughput.

7. Production Verification: Alert whenever vllm:num_preemptions_total rate exceeds 0, monitor vllm:gpu_cache_usage_perc (enforcing a p99 ceiling below 85%), and track TTFT and ITL histograms stratified by prompt-token bucket (<1k, 1k–4k, >4k).

Operational Scenarios

KV-Cache Pressure vLLM / PagedAttention

When available KV-cache blocks are insufficient, serving engines may preempt sequences and later recompute their state; exact behaviour depends on engine version and configuration. Preemption and recomputation can increase end-to-end latency and disturb tail behaviour. Monitor cache utilization, preemption counts, queue delay, TTFT, and inter-token latency together.

Reference: vLLM documentation: performance and preemption
Cold-Start Cliff Serverless GPU Scaling

A 70-billion-parameter model stored in FP16 has approximately 140 GB of raw parameter weights (70 billion × 2 bytes), before runtime overhead, metadata, and other allocations. Loading time is not a universal 20–45 seconds: it depends on storage throughput, network path, parallelism, quantization, host memory, GPU topology, and whether weights are already cached. Measure cold-start latency on the actual deployment path and model its separate cold and warm populations.

Engineering note: publish a measured benchmark with model format, hardware, storage path, and timing boundaries before attaching a fixed load-time claim.
Chunked Prefill Sarathi-Serve

Chunked prefill divides long prompt processing into smaller chunks so that prefill work can be scheduled alongside ongoing decode work. This can reduce decode stalls and improve the throughput/latency trade-off, but it does not eliminate contention: chunk size and scheduler policy still matter. Track TTFT and inter-token latency (ITL/TBT) separately because an optimization can improve one while affecting the other.

Reference: Agrawal et al., “Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve”

3. The Geometric Distribution (Structured Outputs and Retries)

The Intuition: “JSON Is Hard, Let's Retry”

A model returns malformed JSON, omits a required Pydantic field, or references a non-existent Iceberg column. A deterministic validator catches the defect and triggers a retry. If each attempt had the same independent probability of passing validation, the number of attempts would follow a Geometric distribution (the same memoryless retry baseline we examined in Part 6).

In LLM orchestration, however, a retry loop is rarely stationary or memoryless. When frameworks like Instructor or LangGraph append the failed output and the validator traceback into the next prompt, two things change simultaneously: the conditional probability of success pk changes on attempt k, and the input prompt token count Ck grows on every iteration.

The Math

Under the baseline assumption of independent trials with constant per-attempt validation success probability p ∈ (0, 1], let K ∈ {1, 2, …} be the number of model invocations required up to and including the first valid response:

P(K = k) = (1 − p)k−1p,   E[K] = 1 / p

In production, unbounded retries are forbidden. Under a bounded policy capped at m total invocations (Km = min(K, m)), the expected number of invocations per user request is:

E[Km] = Σk=1m (1 − p)k−1 = [1 − (1 − p)m] / p,   P(All m fail) = (1 − p)m

When retries are stateful repair loops where attempt k has conditional pass rate pk = P(\text{Pass}_k \mid \text{Fail}_{1\dots k-1}) and consumes Ck total tokens, expected token consumption per request is:

E[Tokens] = C1 + Σk=2m Ck ∏j=1k−1 (1 − pj)
Let's decode this:
  • K, Km: Unbounded and m-bounded invocation counts (dimensionless attempts per incoming request).
  • p: Stationary single-attempt probability of passing both syntactic (Estruct) and schema (Edata) validation.
  • pk, Ck: Conditional validation pass probability and total token cost (prompt + completion tokens) on attempt k.

Worked example: If p = 0.80, an unbounded geometric model predicts E[K] = 1 / 0.80 = 1.25 attempts per request, and the probability of needing 3 or more attempts is (1 - 0.80)2 = 4.0%. At 100,000 requests/day, that generates 25,000 extra model invocations/day. Capping total invocations at m = 3 yields E[K3] = (1 - 0.203) / 0.80 = 0.992 / 0.80 = 1.24 invocations/request, while bounding worst-case amplification at 3× and leaving a 0.203 = 0.8% terminal failure rate routed to a deterministic fallback.

The SRE Trap

Distinguish syntactic grammar failures (Estruct) from semantic or domain-constraint failures (Edata, Esem). Grammar-constrained decoding (such as finite-state automata in Outlines or provider-native Strict JSON Schema modes) masks invalid vocabulary tokens during the Softmax step itself, driving syntactic JSON parse failures to nearly zero (barring `max_tokens` truncation). That eliminates the need to spend retries on missing commas or unclosed braces.

However, constrained decoding cannot prevent semantic hallucinations: the model will happily emit 100% schema-compliant JSON containing a fabricated trade ID or a logically inverted SQL `WHERE` clause. Worse, when retries burst simultaneously during a downstream schema drift event, the 1/p call multiplier increases arrival rate λa at the GPU pool (Section 2), driving utilization ρ → 1 and triggering a classic retry storm.

Case Study 3: Self-Correction Prompt Bloat in NL2SQL Schema Validation
Illustrative Production Model

1. The Incident: Following an upstream Apache Iceberg table migration that renamed three settlement columns across 18 tenant namespaces, daily LLM token spend on the Analytics Gateway spiked by 68% within four hours, while GPU queue depth doubled—even though external user query volume remained flat at 50,000 requests/day.

2. The Architectural Assumption: Engineers wrapped the NL2SQL generator in a validation loop with m = 4 max attempts. They assumed that if first-attempt validation dropped from 92% to 65%, the geometric call multiplier (1 / 0.65 ≈ 1.54) would increase token costs by at most ~50% while automatically healing the queries.

3. The Physical Mechanism: Two compounding mechanisms invalidated the stationary geometric calculation. First, because the RAG vector index still served stale column metadata for the 18 migrated tenants, appending the DuckDB `Binder Error: Referenced column not found` traceback into the retry prompt gave the model contradictory instructions, causing conditional pass rates to collapse on retries (p1 = 0.65, p2 = 0.25, p3 = 0.10). Second, each retry appended the failed 600-token SQL block plus a 1,400-token catalog dump, inflating token cost Ck super-linearly.

4. The Mathematical Model: We model the 4-attempt stateful repair chain using non-stationary pass probabilities p1 = 0.65, p2 = 0.25, p3 = 0.10, p4 = 0.05 and measured per-attempt token costs C1 = 2,500, C2 = 4,500, C3 = 6,500, and C4 = 8,500 tokens.

5. The Calculation: The probability of reaching attempt 2 is 1 - p1 = 0.35; reaching attempt 3 is 0.35 × (1 - 0.25) = 0.2625; reaching attempt 4 is 0.2625 × (1 - 0.10) = 0.23625. Expected invocations per request is E[K4] = 1 + 0.35 + 0.2625 + 0.23625 = 1.849 attempts. Expected token spend is E[\text{Tokens}] = 2,500 + (0.35 × 4,500) + (0.2625 × 6,500) + (0.23625 × 8,500) = 2,500 + 1,575 + 1,706.25 + 2,008.13 = 7,789\text{ tokens/request}—a 3.12× token cost multiplier over the 2,500-token baseline, with 23.625% × 0.95 = 22.4% of requests still failing after all 4 attempts.

6. The Architectural Decision: Implement three controls: (a) enforce grammar-constrained decoding for structural JSON validity so retries are never wasted on syntax; (b) classify validation errors—if DuckDB returns a `ColumnNotFound` binder error, trigger an immediate deterministic catalog cache refresh before attempting a single repair (m = 2 max attempts) rather than blindly prompting the LLM to guess column names; and (c) enforce a cluster-wide 10% token retry budget (if retry tokens exceed 10% of primary tokens over a 5-minute window, trip a circuit breaker on repair loops). Trade-off: Capping repair attempts at m = 2 slightly reduces recovery on complex multi-error queries (~1.5% lower salvage rate) in exchange for eliminating runaway GPU saturation and FinOps blowouts.

7. Production Verification: Instrument empirical conditional pass rates \hat{p}_1, \hat{p}_2 by error class (`syntax_error`, `schema_binder_error`, `timeout`) and alert when \hat{p}_2 < 0.50 (indicating that the repair prompt is burning tokens without fixing the underlying cause).

Operational Scenarios

The Token Tax FinOps & Constrained Decoding

At a 70% first-attempt pass rate, the unbounded geometric baseline is 1/0.70 = 1.43 calls per successful request. Real token cost can be higher or lower than this simple call multiplier because failed outputs and validation feedback may be added to later prompts, while prompt and completion lengths differ. Track input tokens, output tokens, retries, and final success separately.

Reference: Willard & Louf, “Efficient Guided Generation for Large Language Models” (Outlines)
Self-Correction Bloat Retry Prompting

Feeding a validation error back into the next prompt may improve the next attempt's conditional success probability, but it also increases prompt length and may carry previous malformed output into the context. Model the retry chain with measured p1, p2, … and per-attempt token costs rather than assuming every attempt is an identical geometric trial.

Reference: Instructor: structured extraction and validation retries
The Unbounded Tool Loop Agent Tool Calling

An agent repeatedly calls an API with an invalid date format. A bounded iteration budget, typed tool contract, actionable error response, and explicit terminal failure state prevent the workflow from spending indefinitely on the same defect. Make side-effecting tools idempotent or protect them with idempotency keys.

Engineering control: enforce maximum attempts, wall-clock deadline, token budget, and per-tool rate limits in the orchestrator.

4. The Binomial Distribution (Agent Compounding)

The Intuition: The 10-Step Agent Fallacy

Imagine an autonomous workflow with ten required sequential stages: classify intent, select tenant catalog, retrieve table schemas, formulate SQL, check policy constraints, execute query, inspect anomalies, draft summary, verify citations, and publish report. If every stage independently succeeds with probability 0.95, the probability that all ten stages succeed is 0.9510 ≈ 59.87%—just as independent component failures compounded in Part 2.

That simple exponential decay is a vital architectural warning against long unverified chains, not a literal predictor for every agent. Real workflows exhibit strong cross-stage dependencies, heterogeneous stage difficulty, and deterministic verification checkpoints. The independence assumption must be explicitly stated, audited, and engineered out of the system.

The Math

Under the baseline assumption of n independent Bernoulli stages with homogeneous per-stage success probability p ∈ (0, 1), the total number of successful stages X ∈ {0, 1, …, n} follows a Binomial distribution, and end-to-end workflow completion requires X = n:

P(X = k) = C(n, k)pk(1 − p)n−k,   P(X = n) = pn

In real production workflows where stage success rates differ and later stages depend on the artifacts produced by earlier stages, let Si ∈ {0, 1} denote the indicator that stage i is both structurally and semantically valid. End-to-end reliability is governed by the general chain rule:

P(S1 = 1, …, Sn = 1) = ∏i=1n P(Si = 1 | S1 = 1, …, Si−1 = 1)
Let's decode this:
  • n: Number of mandatory sequential stages in the workflow (dimensionless stage count).
  • X: Random variable counting how many of the n stages succeed under the i.i.d. Binomial model.
  • pn: Probability of a flawless end-to-end run when all n stages are independent and share success probability p.
  • Si: Indicator event that stage i succeeds according to both syntactic and semantic invariants.

Worked example: For n = 20 independent required stages, each with p = 0.95, the expected number of successful stages is E[X] = np = 19.0 stages. Yet because a serial pipeline fails if even a single required stage fails without recovery, the probability of a complete end-to-end success is 0.9520 ≈ 35.85% (a 64.15% workflow failure rate). Conversely, if an architect replaces 16 of those 20 LLM steps with deterministic code (pdet ≈ 0.9999) and retains only n = 4 essential LLM stages at p = 0.95, baseline serial reliability jumps from 35.85% to 0.954 × 0.999916 ≈ 81.32% before even adding stage-level validation retries.

The SRE Trap: Correlation and State-Space Collapse

Agent stages are almost never independent. If Stage 2 retrieves the wrong tenant's schema, Stages 3, 4, and 5 (SQL synthesis, execution, and narrative explanation) are conditioned on a false premise: P(S3 = 1 | S2 = 0) ≈ 0. Importantly, positive correlation across stages does not automatically make pn an upper bound or a lower bound on true end-to-end reliability—the direction depends on how marginal probabilities pi were measured (in isolation on golden inputs vs. conditioned on upstream pipeline outputs).

When stages have distinct independent success probabilities p1, …, pn, the count of successful stages follows a Poisson-Binomial distribution, and all-stage reliability is ∏i=1n pi. If an architect adds a deterministic validator and a bounded m-attempt recovery loop around stage i, the effective stage reliability rises from pi to pi,eff = 1 - (1 - pi)m—turning a fragile serial chain into a governed state machine.

Case Study 4: Collapsing an Autonomous Trade-Reconciliation Agent into a Deterministic Control Plane
Illustrative Production Model

1. The Incident: A prototype autonomous reconciliation agent built on top of the Multi-Tenant Analytics Gateway was tasked with investigating end-of-day trade breaks across tenant partitions. In staging evaluations over 500 historical breaks, the agent completed only 48.2% of investigations accurately, while 19.0% terminated with silent semantic errors (attributing breaks to the wrong counterparty or computing fee deltas with floating-point hallucinations).

2. The Architectural Assumption: The engineering team designed an open-ended 12-step ReAct agent loop where the LLM autonomously decided which tool to invoke next, parsed raw JSON tool payloads, performed currency-conversion arithmetic in-context, and wrote the final discrepancy ticket.

3. The Physical Mechanism: Each autonomous reasoning turn introduced an unverified stochastic branch. Even though individual prompt benchmarks showed ~94% per-turn accuracy on golden unit tests, chaining 12 open-ended turns meant small errors in early tool selection or in-context arithmetic poisoned the context window for all subsequent steps.

4. The Mathematical Model: Under the initial n = 12 serial LLM-turn architecture with benchmarked per-stage reliability p = 0.94 (assuming conditional independence on valid prefixes), baseline all-stage success is P(\text{All 12}) = p12. Under the refactored architecture, we replace 9 deterministic tasks (tenant routing, schema lookup, SQL execution, currency arithmetic, threshold comparison, and ticket formatting) with standard Python/DuckDB code (pcode = 0.9995) and retain only n = 3 bounded LLM nodes (unstructured counterparty email extraction, fuzzy anomaly classification, and executive summary synthesis), each wrapped in a deterministic validator with m = 2 bounded attempts and conditional repair probability pi,eff = 1 - (1 - pi)(1 - pi,\text{retry}}).

5. The Calculation: In the original 12-turn autonomous loop, P(\text{Success}) = 0.9412 ≈ 0.4759 (47.6%, closely matching the 48.2% staging result). In the refactored 3-node state machine, each LLM stage has first-pass accuracy pi = 0.94 and validated retry recovery pi,\text{retry}} = 0.65, giving per-stage effective reliability pi,eff = 1 - (0.06 × 0.35) = 0.9790. Combined with the 9 deterministic code steps (0.99959 ≈ 0.9955), end-to-end task completion rises to P(\text{Success}) = 0.97903 × 0.9955 ≈ 0.9383 × 0.9955 = 0.9341 (93.4%)—nearly doubling end-to-end reliability while cutting average LLM invocations from 12.0 to 3 × 1.06 = 3.18 calls per workflow (a 73.5% reduction in inference load).

6. The Architectural Decision: Replace unconstrained ReAct loops with an explicit directed acyclic graph (DAG) or finite state machine in the orchestrator. Enforce the rule that LLMs never perform arithmetic, authorization checks, or control-flow routing when deterministic code can compute the exact answer. Require idempotency keys on all side-effecting tool calls and route the residual 6.6% of workflows that fail validation to a human-in-the-loop review queue with pre-populated DuckDB evidence tables. Trade-off: A fixed state-machine topology cannot spontaneously invent a novel investigation path for an unseen class of trade break; novel failure modes cleanly trigger an explicit `UNCLASSIFIED_BREAK` escalation rather than an improvised hallucination.

7. Production Verification: Log step-level transition matrices in OpenTelemetry spans (`agent.stage.id`, `agent.stage.attempt`, `agent.stage.validation_status`), track empirical conditional transition probabilities \hat{P}(S_i = 1 \mid S_{i-1} = 1) weekly, and audit semantic correctness (Esem) via stratified daily sampling against deterministic reconciliation ledger balances.

Operational Scenarios

Compounding Work in an Autonomous Loop Bounded Execution

For illustration, a 30-stage workflow with independent 98% stage reliability has an all-stage success probability of 0.98^30 ≈ 54.5%. This is not evidence that a particular agent framework failed at that rate. It shows why an architect should bound iterations, define stop conditions, validate intermediate artifacts, and measure end-to-end task completion—not just isolated model accuracy.

Background: Wang et al., “A Survey on Large Language Model based Autonomous Agents”
The Multi-Agent Echo Chamber Multi-Agent Topologies

Multiple agents can share the same mistaken premise, training biases, retrieved evidence, or tool output. Debate may improve some tasks, but agreement is not independent verification. Require evidence provenance and an external check—such as a compiler, database constraint, deterministic calculation, or independently sourced fact—before treating consensus as correctness.

Background: Du et al., “Improving Factuality and Reasoning in Language Models through Multiagent Debate”
The Deterministic Control Plane Workflow Architecture

Reduce unnecessary model calls by replacing predictable reasoning with ordinary code. Put each remaining model call behind typed input/output contracts, validators, bounded retries, deadlines, token budgets, and explicit state transitions. Use idempotency keys for side effects, audit the evidence used, and provide compensation or rollback paths where possible. Deterministic orchestration makes execution governable; it does not make model-generated content inherently correct.

Reference: NVIDIA NeMo Guardrails

The Final Reality: Constrain the Stochastic Core

Across all eight parts of The Shape of Failure, one engineering truth has remained constant: production outages happen in the gap between convenient mathematical assumptions and physical system boundaries. Whether you are sizing a distributed cache in Part 1, surviving a retry storm in Part 6, or orchestrating an LLM agent in Part 8, a probability distribution is a diagnostic lens, never a guarantee.

The Architect's Rule for AI Systems: Isolate stochastic models to the narrow semantic tasks that genuinely require them. Surround every model invocation with deterministic code for routing, arithmetic, authorization, schema validation, token-budget admission control, and idempotent state transitions. Measure end-to-end semantic task completion (Etask), not just HTTP 200 serving reliability (Eserve). The AI proposes; the deterministic control plane validates and authorizes.
