The Stochastic Shape of AI Systems

November 28, 2026 · Part 8 of 8 · AI/LLM Frontier

“The fundamental problem of communication is that of reproducing at one point either exactly or approximately a message selected at another point.”

— Claude Shannon, "A Mathematical Theory of Communication"

In Part 7, we built an operational validation framework to detect when our latency, traffic, and reliability models drift away from physical reality. Throughout Parts 1 to 7, our proving ground was a traditional Multi-Tenant Analytics Gateway: a request arrived with a formal SQL query or API payload, and our job was to route, cache, shard, and execute it without violating tail-latency SLOs or exhausting memory boundaries.

Those traditional data gateways guarantee reproducible execution paths given identical state. They are not, however, "correct by construction." They can still fail catastrophically via stale Iceberg snapshots, schema drift, authorization bugs, or broken SQL business logic. But the failure modes are deterministic: the same broken SQL run against the same database state yields the same error every time.

Welcome to the frontier. Now suppose leadership asks us to extend that same Multi-Tenant Analytics Gateway with an AI Query Assistant and Autonomous Reconciliation Agent. Tenants can ask natural-language questions, retrieve Iceberg table metadata via RAG, synthesize analytical SQL, repair validation errors, and execute multi-step reconciliation workflows. Suddenly, an HTTP 200 with a 180 ms response time can still be a catastrophic production failure—because a syntactically valid JSON payload containing a plausible-looking SQL query just joined the wrong tenant partition or fabricated a regulatory metric.

An AI system in production fundamentally changes the failure surface because both the execution runtime (stochastic queueing, dynamic continuous batching, KV-cache eviction) AND the output generation mechanism itself (autoregressive token sampling, semantic grounding) are non-deterministic. As throughout this series, our core discipline holds: a distribution is a model, not an invariant. The useful architectural question is not “How do we make an LLM deterministic?” It is: Where does randomness enter the pipeline, which failure layer does it threaten, and what deterministic control plane bounds the blast radius?

The AI Reliability Stack: Five Distinct Failure Layers

Before fitting any distribution to an AI service, an architect must separate five distinct success events that traditional APM dashboards conflate into a single “200 OK” counter:

  1. Serving Reliability (\(E_{\text{serve}}\)): The inference engine accepts the request, allocates KV-cache memory, and streams tokens within the TTFT and TPOT latency budgets without HTTP 5xx, timeout, or OOM preemption.
  2. Structural Correctness (\(E_{\text{struct}}\)): The generated output conforms to the syntactic contract—valid JSON, matching grammar, or a parseable AST without truncation.
  3. Data & Retrieval Correctness (\(E_{\text{data}}\)): Referenced entities, table names, column types, and tool parameters actually exist in the target catalog and respect tenant authorization boundaries. (For RAG, this includes chunk recall and freshness).
  4. Semantic Correctness (\(E_{\text{sem}}\)): Faithfulness to retrieved context and user intent. The output is logically executable, preserves domain invariants, and contains zero hallucinations.
  5. End-to-End Task Success (\(E_{\text{task}}\)): The complete multi-step workflow—including downstream tool execution, validation, policy compliance, and side effects—safely completes the user's goal.

By the chain rule of probability, task success is the product of conditional probabilities across every layer:

\[ P(E_{\text{task}}) = P(E_{\text{serve}}) \cdot P(E_{\text{struct}} \mid E_{\text{serve}}) \cdot P(E_{\text{data}} \mid E_{\text{struct}}, E_{\text{serve}}) \cdot P(E_{\text{sem}} \mid E_{\text{data}}, \dots) \dots \]

Optimizing one layer (such as forcing valid JSON via constrained decoding) drives \( P(E_{\text{struct}} \mid E_{\text{serve}}) \to 1 \), but does nothing to guarantee \( P(E_{\text{sem}}) \). This mathematically explains how \( P(E_{\text{serve}}) = 0.999 \) can routinely coexist with \( P(E_{\text{task}}) = 0.65 \).

1. The Categorical Distribution (Token Sampling)

The Intuition: The Weighted Dice Roll

At each autoregressive decoding step, a language model computes a vector of unnormalized scores (logits) across its entire vocabulary. A Softmax transformation converts those scores into a discrete probability vector, and the sampler draws a single token. The Categorical distribution models that single discrete draw conditioned on the exact token prefix generated so far.

Temperature (\(T\)) controls the entropy of that draw by scaling logits prior to exponentiation. Lower values concentrate probability mass onto the highest-logit token; higher values flatten the distribution toward uniformity. Crucially, temperature controls lexical diversity—not the epistemic probability that a statement is factually true.

If an engineer raises temperature to \(T = 2.0\) to make responses “more creative,” the distribution flattens. The probability of drawing the undesirable tail token (Garbage) jumps from \(10.00\%\) to \(16.27\%\)—a 62.7% relative increase on a single step. (Note: this is an illustrative single-step calculation, not a direct measurement of multi-token hallucination rate.)

The SRE Trap: The "Deterministic" Illusion

Temperature greater than zero makes sampling stochastic by design, so exact-string unit tests fail intermittently even when the answer is semantically valid. Conversely, setting \(T = 0\) selects the greedy token at each step, but it is not a hardware-level reproducibility guarantee in production.

In distributed GPU clusters, floating-point non-associativity in split-K matrix reductions, variable continuous-batching composition, MoE routing capacity constraints, and silent provider model snapshots can alter the raw \(z_i\) values just enough to flip tie-breaking logits. For CI/CD regression suites, pin the model snapshot, prompt template, decoding parameters, and tool schemas; assert structural and semantic invariants rather than raw prose strings.

When this model breaks: Do not treat token sampling probability (low entropy) as a calibrated confidence score for factual truth. When a model is miscalibrated or lacks grounding data in its context window, the factually wrong token can easily hold the highest logit (\(p_1 = 0.85\)), meaning greedy decoding (\(T \to 0^+\)) will confidently select the falsehood 100% of the time (a confident hallucination).

The Non-Deterministic Test CI/CD Pipelines

A test expects one exact sentence, but a model returns a valid answer with different wording. The test fails even though the product behaviour is acceptable. Separate deterministic contract tests (schema, required fields, allowed tool calls, safety invariants) from probabilistic quality evaluations (groundedness, relevance, task success). Use temperature zero when appropriate, but do not treat it as a substitute for robust assertions.

Reference: OpenAI API: Advanced usage and reproducibility considerations
Autoregressive Error Propagation Generation Dynamics

Each sampled token becomes part of the context for later tokens. A mistaken entity, number, or premise can therefore influence what follows. This is a plausible error-propagation mechanism, not a rule that every low-probability token causes a confident hallucination. Grounding, retrieval, verification, and constrained task boundaries are more direct controls than temperature alone.

Reference: Holtzman et al., “The Curious Case of Neural Text Degeneration”
The Top-P Cutoff Nucleus Sampling

Top-p sorts tokens by descending probability, retains the smallest prefix whose cumulative probability reaches or exceeds the configured threshold, then renormalizes the retained probabilities. It trims the low-probability tail; it does not know which tokens are “nonsensical,” and it cannot guarantee factuality.

2. Inference Queueing & KV-Cache Physics

The Intuition: Prefill vs. Decode

LLM serving latency is governed by two physically distinct phases:

  • Prefill Phase (Compute-Bound): The GPU processes all \(L_{\text{in}}\) prompt tokens in parallel to populate the Key-Value (KV) cache. This dense matrix multiplication determines the Time to First Token (TTFT). Without chunking, large prefills cause head-of-line blocking for other requests.
  • Decode Phase (Memory-Bandwidth-Bound): The GPU autoregressively generates \(L_{\text{out}}\) output tokens one step at a time, reading the KV-cache on each step. This dictates the Time Per Output Token (TPOT) or Inter-Token Latency (ITL).

Total request service time \(S\) is therefore highly variable, driven by the heavy-tailed distributions of input/output lengths and the active continuous-batch size \(B_j\). Because sequences have different lengths, Request Throughput (req/s) and Token Throughput (tok/s) diverge significantly.

The Math

For a stationary \(M/M/1\) queue with Poisson arrival rate \(\lambda_a\) and exponential service rate \(\mu\), the sojourn time \(W\) follows an Exponential distribution with net rate \(\theta = \mu - \lambda_a\):

\[ f_W(t) = \theta e^{-\theta t}, \quad P(W > t) = e^{-\theta t}, \quad t \ge 0 \]

However, total request service time \(S\) is non-exponential and highly variable due to the physical separation of the Prefill and Decode phases:

\[ S = T_{\text{prefill}}(L_{\text{in}}) + \sum_{j=1}^{L_{\text{out}}} T_{\text{step}}(B_j) \]

Furthermore, on a physical GPU running continuous batching, effective service capacity degrades discontinuously when active sequences exceed the available High-Bandwidth Memory (HBM) allocated for the KV-cache. For a transformer with \(L_{\text{layers}}\), \(H_{\text{kv}}\) KV heads per layer, head dimension \(d_h\), precision \(b_{\text{bytes}}\) (e.g., FP16/BF16 = 2 bytes), and \(C\) total active tokens across the running batch, the physical KV-cache footprint is:

\[ M_{\text{token}} = 2 \cdot L_{\text{layers}} \cdot H_{\text{kv}} \cdot d_h \cdot b_{\text{bytes}} \]
Let's decode this:
  • \(\lambda_a\), \(\mu\), \(\rho\): Mean arrival rate, mean service rate, and server utilization (\(\rho = \lambda_a/\mu\)).
  • \(\theta = \mu(1 - \rho)\): Net rate parameter of the \(M/M/1\) sojourn distribution. As \(\rho \to 1\), \(\theta \to 0\) and mean latency \(\to \infty\).
  • \(M_{\text{token}}\): Exact HBM memory (bytes) required to store Key and Value tensors (hence the factor of 2) for a single token.

Worked example: For a Llama-3 70B model (\(L_{\text{layers}} = 80, H_{\text{kv}} = 8, d_h = 128\)) running in FP16 (\(b_{\text{bytes}} = 2\)), \(M_{\text{token}} = 2 \cdot 80 \cdot 8 \cdot 128 \cdot 2 = 327,680\) bytes (\(\approx 320\) KiB). If an 80GB A100 reserves 30GB for the KV cache, the hard capacity limit is \(30\text{ GB} / 320\text{ KB} \approx 93,750\) total tokens. A burst of just five 16K-token RAG requests will consume 85% of this budget.

The SRE Trap

Do not fit a single exponential curve to aggregate TTFT telemetry. Because prompt lengths often span three orders of magnitude (from 100-token chat turns to 32,000-token RAG contexts), service time has a high coefficient of variation (\(C_s^2 \gg 1\)). As we saw with Kingman's approximation in Part 3, heavy-tailed service times inflate queueing delay far beyond the \(M/M/1\) baseline.

Dense full self-attention still requires O(n²) arithmetic operations in prompt sequence length \(n\) during prefill. FlashAttention reduces HBM bandwidth bottlenecks through IO-aware SRAM tiling, but it does not make dense prefill compute asymptotically linear. Meanwhile, \(M_{\text{KV}}(C)\) grows linearly with total cached tokens across all concurrent requests. When \(M_{\text{KV}}(C) > M_{\text{max}}\), the engine must preempt running sequences (evicting them to host memory or discarding them)—turning a smooth queueing curve into a bimodal cliff.

Case Study 2: KV-Cache Exhaustion and PagedAttention Preemption
Illustrative Production Model

1. The Incident: During the 09:30 market-open burst, the Analytics Gateway's LLM serving tier suffered a sudden p99 TTFT spike from 1.8 s to 19.4 s, accompanied by mid-stream freezes in token streaming.

2. The Architectural Assumption: Capacity planners sized the GPU pool using average request throughput (\(\lambda_a = 6\) req/s) and configured the vLLM scheduler with max_num_seqs = 32, assuming 32 sequences would comfortably fit in GPU memory based on a historical average of 1,500 prompt tokens.

3. The Physical Mechanism: A new tenant enabled automated schema-RAG, injecting full Iceberg table manifests (averaging 7,000 total tokens per sequence). When concurrent long-context requests filled the 24 GiB KV-cache ceiling, the engine triggered sequence preemption—evicting partially decoded requests and later recomputing their entire prefill from scratch (thrashing).

4. The Mathematical Model: With \(M_{\text{token}} = 320\) KiB and a 24 GiB budget, the physical limit is 78,643 tokens. Under the legacy workload, 32 sequences required ~14.6 GiB (61% utilization). Under the RAG burst, just 12 concurrent sequences required 84,000 tokens—exceeding the 78,643 limit.

5. The Architectural Decision: Replace request-count limits with token-budget admission control at the Gateway (capping in-flight active tokens per replica at an illustrative admission-control threshold of 65,000 tokens, or ~82% of capacity). Enable chunked prefill so long prefills do not stall active decodes, and route requests exceeding 4,096 prompt tokens to a dedicated long-context pool with FP8 KV-cache quantization (doubling token capacity). Trade-off: Strict admission control trades internal GPU thrashing for explicit edge backpressure (HTTP 429).

6. Production Verification: Alert whenever vllm:num_preemptions_total rate exceeds 0, monitor vllm:gpu_cache_usage_perc, and track TTFT/TPOT histograms stratified by input token buckets.

KV-Cache Pressure vLLM / PagedAttention

When available KV-cache blocks are insufficient, serving engines may preempt sequences and later recompute their state; exact behaviour depends on engine version and configuration. Preemption and recomputation can increase end-to-end latency and disturb tail behaviour. Monitor cache utilization, preemption counts, queue delay, TTFT, and inter-token latency together.

Cold-Start Cliff Serverless GPU Scaling

A 70-billion-parameter model stored in FP16 has approximately 140 GB of raw parameter weights (70 billion × 2 bytes), before runtime overhead, metadata, and other allocations. Loading time is not a universal 20–45 seconds: it depends on storage throughput, network path, parallelism, quantization, host memory, GPU topology, and whether weights are already cached. Measure cold-start latency on the actual deployment path and model its separate cold and warm populations.

Engineering note: publish a measured benchmark with model format, hardware, storage path, and timing boundaries before attaching a fixed load-time claim.
Chunked Prefill Sarathi-Serve

Chunked prefill divides long prompt processing into smaller chunks so that prefill work can be scheduled alongside ongoing decode work. This can reduce decode stalls and improve the throughput/latency trade-off, but it does not eliminate contention: chunk size and scheduler policy still matter. Track TTFT and inter-token latency (ITL/TBT) separately because an optimization can improve one while affecting the other.

3. The Geometric Distribution (Structured Outputs and Retries)

The Intuition: “JSON Is Hard, Let's Retry”

A model returns malformed JSON, omits a required Pydantic field, or references a non-existent Iceberg column. A deterministic validator catches the defect and triggers a retry. If each attempt had the same independent probability of passing validation, the number of attempts would follow a Geometric distribution (the same memoryless retry baseline we examined in Part 6).

In LLM orchestration, however, a retry loop is rarely stationary or memoryless. When frameworks like Instructor or LangGraph append the failed output and the validator traceback into the next prompt, two things change simultaneously: the conditional probability of success \(p_k\) changes on attempt \(k\), and the input prompt token count \(C_k\) grows on every iteration.

The Math

Under the baseline assumption of independent trials with constant per-attempt validation success probability \(p \in (0, 1]\), let \(K \in \{1, 2, \dots\}\) be the number of model invocations required up to and including the first valid response:

\[ P(K = k) = (1 - p)^{k-1}p, \quad E[K] = \frac{1}{p} \]

In production, unbounded retries are forbidden. Under a bounded policy capped at \(m\) total invocations (\(K_m = \min(K, m)\)), the expected number of invocations per user request is:

\[ E[K_m] = \sum_{k=1}^{m} (1 - p)^{k-1} = \frac{1 - (1 - p)^m}{p} \]

When retries are stateful repair loops where attempt \(k\) has conditional pass rate \(p_k = P(\text{Pass}_k \mid \text{Fail}_{1\dots k-1})\) and consumes \(C_k\) total tokens, expected token consumption per request is:

\[ E[\text{Tokens}] = C_1 + \sum_{k=2}^{m} C_k \prod_{j=1}^{k-1} (1 - p_j) \]
Let's decode this:
  • \(K\), \(K_m\): Unbounded and \(m\)-bounded invocation counts (dimensionless attempts per incoming request).
  • \(p\): Stationary single-attempt probability of passing both syntactic (\(E_{\text{struct}}\)) and schema (\(E_{\text{data}}\)) validation.
  • \(p_k\), \(C_k\): Conditional validation pass probability and total token cost (prompt + completion tokens) on attempt \(k\).

Worked example: If \(p = 0.80\), an unbounded geometric model predicts \(E[K] = 1 / 0.80 = 1.25\) attempts per request, and the probability of needing 3 or more attempts is \((1 - 0.80)^2 = 4.0\%\). At 100,000 requests/day, that generates 25,000 extra model invocations/day. Capping total invocations at \(m = 3\) yields \(E[K_3] = (1 - 0.20^3) / 0.80 = 1.24\) invocations/request, while bounding worst-case amplification at \(3\times\) and leaving a \(0.20^3 = 0.8\%\) terminal failure rate routed to a deterministic fallback.

The SRE Trap

Distinguish syntactic grammar failures (\(E_{\text{struct}}\)) from semantic or domain-constraint failures (\(E_{\text{data}}, E_{\text{sem}}\)). Grammar-constrained decoding (such as finite-state automata in Outlines or provider-native Strict JSON Schema modes) masks invalid vocabulary tokens during the Softmax step itself, driving syntactic JSON parse failures to nearly zero. That eliminates the need to spend retries on missing commas or unclosed braces.

However, constrained decoding cannot prevent semantic hallucinations: the model will happily emit 100% schema-compliant JSON containing a fabricated trade ID or a logically inverted SQL `WHERE` clause. Worse, when retries burst simultaneously during a downstream schema drift event, the \(1/p\) call multiplier increases arrival rate \(\lambda_a\) at the GPU pool, driving utilization \(\rho \to 1\) and triggering a classic retry storm.

Case Study 3: Self-Correction Prompt Bloat in NL2SQL Schema Validation
Illustrative Production Model

1. The Incident: Following an upstream Iceberg table migration that renamed columns across 18 tenant namespaces, daily LLM token spend on the Gateway spiked by 68% within four hours, while GPU queue depth doubled, even though user query volume remained flat.

2. The Architectural Assumption: Engineers wrapped the NL2SQL generator in a validation loop with \(m = 4\) max attempts. They assumed that if first-attempt validation dropped from 92% to 65%, the geometric call multiplier (\(1 / 0.65 \approx 1.54\)) would increase token costs by at most ~50% while automatically healing the queries.

3. The Physical Mechanism: Two compounding mechanisms invalidated the stationary geometric calculation. First, because the RAG vector index still served stale column metadata, appending the DuckDB `Referenced column not found` traceback into the retry prompt gave the model contradictory instructions, causing conditional pass rates to collapse (\(p_1 = 0.65, p_2 = 0.25, p_3 = 0.10\)). Second, each retry appended the failed 600-token SQL block plus a 1,400-token catalog dump, inflating token cost \(C_k\) super-linearly.

4. The Mathematical Model: We model the 4-attempt stateful repair chain using non-stationary pass probabilities \(p_1 = 0.65, p_2 = 0.25, p_3 = 0.10, p_4 = 0.05\) and measured per-attempt token costs \(C_1 = 2,500\), \(C_2 = 4,500\), \(C_3 = 6,500\), and \(C_4 = 8,500\) tokens.

5. The Calculation: The probability of reaching attempt 2 is \(1 - p_1 = 0.35\); reaching attempt 3 is \(0.35 \times (1 - 0.25) = 0.2625\); reaching attempt 4 is \(0.2625 \times (1 - 0.10) = 0.23625\). Expected invocations per request is \(E[K_4] = 1 + 0.35 + 0.2625 + 0.23625 = 1.849\) attempts. Expected token spend is \(E[\text{Tokens}] = 2,500 + (0.35 \times 4,500) + (0.2625 \times 6,500) + (0.23625 \times 8,500) = 7,789\text{ tokens/request}\)—a 3.12x token cost multiplier over baseline, with \(22.4\%\) of requests still failing after all 4 attempts.

6. The Architectural Decision: Implement three controls: (a) enforce grammar-constrained decoding for structural JSON validity; (b) classify validation errors—if DuckDB returns a `ColumnNotFound` binder error, trigger an immediate deterministic catalog cache refresh before attempting a single repair (\(m = 2\) max attempts); and (c) enforce a cluster-wide 10% token retry budget (if retry tokens exceed 10% of primary tokens over a 5-minute window, trip a circuit breaker). Trade-off: Capping repair attempts at \(m = 2\) slightly reduces recovery on complex multi-error queries in exchange for eliminating runaway GPU saturation.

7. Production Verification: Instrument empirical conditional pass rates \(\hat{p}_1, \hat{p}_2\) by error class (`schema_binder_error`, `timeout`) and alert when \(\hat{p}_2 < 0.50\) (indicating the repair prompt is burning tokens without fixing the underlying cause).

At a 70% first-attempt pass rate, the unbounded geometric baseline is 1/0.70 = 1.43 calls per successful request. Real token cost can be higher or lower than this simple call multiplier because failed outputs and validation feedback may be added to later prompts, while prompt and completion lengths differ. 4. The Binomial Distribution (Agent Compounding)

The Intuition: The 10-Step Agent Fallacy

Imagine an autonomous workflow with ten required sequential stages: classify intent, select tenant catalog, retrieve table schemas, formulate SQL, check policy constraints, execute query, inspect anomalies, draft summary, verify citations, and publish report. If every stage independently succeeds with probability \(0.95\), the probability that all ten stages succeed is \(0.95^{10} \approx 59.87\%\)—just as independent component failures compounded in Part 2.

That simple exponential decay is a vital architectural warning against long unverified chains, not a literal predictor for every agent. Real workflows exhibit strong cross-stage dependencies, heterogeneous stage difficulty, and deterministic verification checkpoints. The independence assumption must be explicitly stated, audited, and engineered out of the system.

The Math

Under the baseline assumption of \(n\) independent Bernoulli stages with homogeneous per-stage success probability \(p \in (0, 1)\), the total number of successful stages \(X \in \{0, 1, \dots, n\}\) follows a Binomial distribution, and end-to-end workflow completion requires \(X = n\):

\[ P(X = k) = \binom{n}{k}p^k(1 - p)^{n-k}, \quad P(X = n) = p^n \]

In real production workflows where stage success rates differ and later stages depend on the artifacts produced by earlier stages, let \(S_i \in \{0, 1\}\) denote the indicator that stage \(i\) is both structurally and semantically valid. End-to-end reliability is governed by the general chain rule:

\[ P(S_1=1, \dots, S_n=1) = P(S_1=1)\prod_{i=2}^{n} P(S_i=1 \mid S_1=1, \dots, S_{i-1}=1) \]
Let's decode this:
  • \(n\): Number of mandatory sequential stages in the workflow.
  • \(p^n\): Probability of a flawless end-to-end run when all \(n\) stages are independent and share success probability \(p\).
  • \(S_i\): Indicator event that stage \(i\) succeeds according to both syntactic and semantic invariants.

Worked example: For \(n = 20\) independent required stages, each with \(p = 0.95\), the expected number of successful stages is \(E[X] = np = 19.0\) stages. Yet because a serial pipeline fails if even a single required stage fails without recovery, the probability of a complete end-to-end success is \(0.95^{20} \approx 35.85\%\). Conversely, if an architect replaces 16 of those 20 LLM steps with deterministic code (\(p_{\text{det}} \approx 0.9999\)) and retains only \(n = 4\) essential LLM stages at \(p = 0.95\), baseline serial reliability jumps from \(35.85\%\) to \(0.95^4 \times 0.9999^{16} \approx 81.32\%\) before even adding stage-level validation retries.

The SRE Trap: Correlation and State-Space Collapse

Agent stages are almost never independent. If Stage 2 retrieves the wrong tenant's schema, Stages 3, 4, and 5 (SQL synthesis, execution, and narrative explanation) are conditioned on a false premise: \(P(S_3 = 1 \mid S_2 = 0) \approx 0\). Importantly, positive correlation across stages does not automatically make \(p^n\) an upper bound or a lower bound on true end-to-end reliability—the direction depends on how marginal probabilities \(p_i\) were measured (in isolation on golden inputs vs. conditioned on upstream pipeline outputs).

When stages have distinct independent success probabilities \(p_1, \dots, p_n\), the count of successful stages follows a Poisson-Binomial distribution, and all-stage reliability is \(\prod_{i=1}^n p_i\). If an architect adds a deterministic validator and a bounded \(m\)-attempt recovery loop around stage \(i\), the effective stage reliability rises from \(p_i\) to \(p_{i,\text{eff}} = 1 - (1 - p_i)^m\)—turning a fragile serial chain into a governed state machine.

Case Study 4: Collapsing an Autonomous Trade-Reconciliation Agent into a Deterministic Control Plane
Illustrative Production Model

1. The Incident: A prototype autonomous reconciliation agent built on top of the Gateway was tasked with investigating end-of-day trade breaks. In staging evaluations over 500 historical breaks, the agent completed only 48.2% of investigations accurately, while 19.0% terminated with silent semantic errors (attributing breaks to the wrong counterparty or computing fee deltas with floating-point hallucinations).

2. The Architectural Assumption: The engineering team designed an open-ended 12-step ReAct agent loop where the LLM autonomously decided which tool to invoke next, parsed raw JSON tool payloads, performed currency-conversion arithmetic in-context, and wrote the final discrepancy ticket.

3. The Physical Mechanism: Each autonomous reasoning turn introduced an unverified stochastic branch. Even though individual prompt benchmarks showed ~94% per-turn accuracy on golden unit tests, chaining 12 open-ended turns meant small errors in early tool selection or in-context arithmetic poisoned the context window for all subsequent steps.

4. The Mathematical Model: Under the initial \(n = 12\) serial LLM-turn architecture with benchmarked per-stage reliability \(p = 0.94\), baseline all-stage success is \(P(\text{All 12}) = p^{12}\). Under the refactored architecture, we replace 9 deterministic tasks (tenant routing, schema lookup, SQL execution, currency arithmetic, threshold comparison, and ticket formatting) with standard Python/DuckDB code (\(p_{\text{code}} = 0.9995\)) and retain only \(n = 3\) bounded LLM nodes, each wrapped in a deterministic validator with \(m = 2\) bounded attempts and conditional repair probability \(p_{i,\text{eff}} = 1 - (1 - p_i)(1 - p_{i,\text{retry}})\).

5. The Calculation: In the original 12-turn autonomous loop, \(P(\text{Success}) = 0.94^{12} \approx 0.4759\) (47.6%, closely matching the 48.2% staging result). In the refactored 3-node state machine, each LLM stage has first-pass accuracy \(p_i = 0.94\) and validated retry recovery \(p_{i,\text{retry}} = 0.65\), giving per-stage effective reliability \(p_{i,\text{eff}} = 1 - (0.06 \times 0.35) = 0.9790\). Combined with the 9 deterministic code steps (\(0.9995^9 \approx 0.9955\)), end-to-end task completion rises to \(P(\text{Success}) = 0.9790^3 \times 0.9955 \approx 0.9341\) (93.4%)—nearly doubling end-to-end reliability while cutting average LLM invocations from 12.0 to \(3 \times 1.06 = 3.18\) calls per workflow (a 73.5% reduction in inference load).

6. The Architectural Decision: Replace unconstrained ReAct loops with an explicit directed acyclic graph (DAG) or finite state machine in the orchestrator. Enforce the rule that LLMs never perform arithmetic, authorization checks, or control-flow routing when deterministic code can compute the exact answer. Require idempotency keys on all side-effecting tool calls and route the residual workflows that fail validation to a human-in-the-loop review queue.

7. Production Verification: Log step-level transition matrices in OpenTelemetry spans, track empirical conditional transition probabilities \(\hat{P}(S_i = 1 \mid S_{i-1} = 1)\) weekly, and audit semantic correctness (\(E_{\text{sem}}\)) via stratified daily sampling against deterministic reconciliation ledger balances.

Operational Scenarios

Compounding Work in an Autonomous Loop Bounded Execution

For illustration, a 30-stage workflow with independent 98% stage reliability has an all-stage success probability of 0.98^30 ≈ 54.5%. This is not evidence that a particular agent framework failed at that rate. It shows why an architect should bound iterations, define stop conditions, validate intermediate artifacts, and measure end-to-end task completion—not just isolated model accuracy.

Background: Wang et al., “A Survey on Large Language Model based Autonomous Agents”
The Multi-Agent Echo Chamber Multi-Agent Topologies

Multiple agents can share the same mistaken premise, training biases, retrieved evidence, or tool output. Debate may improve some tasks, but agreement is not independent verification. Require evidence provenance and an external check—such as a compiler, database constraint, deterministic calculation, or independently sourced fact—before treating consensus as correctness.

Background: Du et al., “Improving Factuality and Reasoning in Language Models through Multiagent Debate”
The Deterministic Control Plane Workflow Architecture

Reduce unnecessary model calls by replacing predictable reasoning with ordinary code. Put each remaining model call behind typed input/output contracts, validators, bounded retries, deadlines, token budgets, and explicit state transitions. Use idempotency keys for side effects, audit the evidence used, and provide compensation or rollback paths where possible. Deterministic orchestration makes execution governable; it does not make model-generated content inherently correct.

5. Semantic Evaluation and LLM-as-a-Judge

The Intuition: Judges Have False Positives

When using an LLM-as-a-Judge to evaluate Semantic Correctness (\(E_{\text{sem}}\)), the judge itself is a stochastic classifier subject to False Positives (\(\alpha_{\text{fp}}\)) and False Negatives (\(\beta_{\text{fn}}\)). You cannot take the raw pass rate on a dashboard at face value.

The Math

If an LLM Judge evaluates a pipeline where the true pass rate is \(p_{\text{true}}\), the observed pass rate \(p_{\text{obs}}\) on the dashboard is the sum of True Positives and False Positives. We apply the Rogan-Gladen prevalence adjustment:

\[ p_{\text{obs}} = p_{\text{true}}(1 - \beta_{\text{fn}}) + (1 - p_{\text{true}})\alpha_{\text{fp}} \]

Solving for the true semantic pass rate yields:

\[ \hat{p}_{\text{true}} = \frac{p_{\text{obs}} - \alpha_{\text{fp}}}{1 - \alpha_{\text{fp}} - \beta_{\text{fn}}} \]
Worked example: A deterministic regression suite confirms your Judge has a 5% False Positive rate (\(\alpha_{\text{fp}} = 0.05\)) and a 10% False Negative rate (\(\beta_{\text{fn}} = 0.10\)). If the dashboard shows an 80% observed pass rate (\(p_{\text{obs}} = 0.80\)), the true semantic reliability is actually \((0.80 - 0.05) / (1 - 0.05 - 0.10) = 0.75 / 0.85 \approx 88.2\%\).

The Final Reality: Constrain the Stochastic Core

Across all eight parts of The Shape of Failure, one engineering truth has remained constant: production outages happen in the gap between convenient mathematical assumptions and physical system boundaries. Whether you are sizing a distributed cache in Part 1, surviving a retry storm in Part 6, or orchestrating an LLM agent in Part 8, a probability distribution is a diagnostic lens, never a guarantee.

The Architect's Rule for AI Systems: Isolate stochastic models to the narrow semantic tasks that genuinely require them. Surround every model invocation with deterministic code for routing, arithmetic, authorization, schema validation, token-budget admission control, and idempotent state transitions. Measure end-to-end semantic task completion (\(E_{\text{task}}\)), not just HTTP 200 serving reliability (\(E_{\text{serve}}\)). The AI proposes; the deterministic control plane validates and authorizes.
