The Stochastic Shape of AI Systems

November 28, 2026 · Part 8 of 8 · AI/LLM Frontier

“The fundamental problem of communication is that of reproducing at one point either exactly or approximately a message selected at another point.”

— Claude Shannon, "A Mathematical Theory of Communication"

Welcome to the frontier. If you thought distributed databases were chaotic, try running an autonomous LLM agent in production. The stack is not one giant probability machine: it combines numerical computation, stochastic decoding, queueing, memory management, and orchestration.

The underlying mathematics will feel familiar. What changes is where uncertainty enters—and how quickly a small modelling mistake can become a production incident. The useful architectural question is not “How do we make the model deterministic?” It is “Where is randomness acceptable, where must behaviour be constrained, and how do we detect failures at the boundary?”

1. The Categorical Distribution (Token Sampling)

The Intuition: The Weighted Dice Roll

At each autoregressive step, an LLM produces logits for its vocabulary. A decoder transforms those scores into a probability distribution and selects the next token. The categorical distribution models that single discrete draw.

Temperature controls how sharply the logits are distributed. Lower values concentrate probability on high-logit tokens; higher values flatten the distribution. That changes diversity—not the probability that a response is factually correct.

The Math

The probability of sampling token i from a vocabulary of size K, given logit zi and temperature T, before any additional decoding filters:

P(X=i) = pi = exp(zi/T) / Σj=1K exp(zj/T)
Let's decode this:
  • X: The token selected at the current generation step.
  • zi: The unnormalized score (logit) for token i.
  • T: The temperature applied before Softmax. As T grows without bound, the distribution approaches uniformity, assuming finite logits.

Worked example: Suppose the distribution at T=1 is [40%, 30%, 20%, 10%] for the illustrative tokens Data, Model, Magic, and Garbage. At T=2, the probabilities are proportional to the square roots of the original probabilities: approximately [32.55%, 28.19%, 23.01%, 16.27%]. The illustrative “Garbage” category rises from 10% to 16.27%—about a 63% relative increase. This is a toy token distribution, not a measurement of hallucination probability.

The SRE Trap

Temperature greater than zero makes sampling stochastic by design, but exact-string tests are brittle even when the underlying answer is acceptable. Temperature zero usually selects the highest-scoring token (greedy decoding), but it is not a universal reproducibility guarantee. Backend/model revisions, numerical kernels, request parameters, and tool behaviour can still matter. For regression tests, pin the model snapshot where possible, prompt, decoding parameters, tool versions, and structured contract; assert semantic invariants rather than one exact prose string.

Random seeds, where supported, are generally best-effort reproducibility aids—not promises of identical output across backend changes. Check the specific provider and API version before relying on seed semantics.

Operational Scenarios

The Non-Deterministic Test CI/CD Pipelines

A test expects one exact sentence, but a model returns a valid answer with different wording. The test fails even though the product behaviour is acceptable. Separate deterministic contract tests (schema, required fields, allowed tool calls, safety invariants) from probabilistic quality evaluations (groundedness, relevance, task success). Use temperature zero when appropriate, but do not treat it as a substitute for robust assertions.

Reference: OpenAI API: Advanced usage and reproducibility considerations
Autoregressive Error Propagation Generation Dynamics

Each sampled token becomes part of the context for later tokens. A mistaken entity, number, or premise can therefore influence what follows. This is a plausible error-propagation mechanism, not a rule that every low-probability token causes a confident hallucination. Grounding, retrieval, verification, and constrained task boundaries are more direct controls than temperature alone.

Reference: Holtzman et al., “The Curious Case of Neural Text Degeneration”
The Top-P Cutoff Nucleus Sampling

Top-p sorts tokens by descending probability, retains the smallest prefix whose cumulative probability reaches or exceeds the configured threshold, then renormalizes the retained probabilities. It trims the low-probability tail; it does not know which tokens are “nonsensical,” and it cannot guarantee factuality.

Reference: Holtzman et al., “The Curious Case of Neural Text Degeneration”

2. The Exponential Distribution (A Queueing Baseline for Inference)

The Intuition: The Waiting Room for the First Token

Time to First Token (TTFT) is an end-to-end metric. It includes request admission, queueing, prefill computation, scheduling, and transport. It is not automatically exponentially distributed. An M/M/1 queue gives us a useful baseline for understanding how waiting time behaves under a deliberately simplified set of assumptions.

Real LLM serving is more complicated: requests have different prompt lengths, generation lengths, batch membership, KV-cache footprints, and preemption histories. Treat the exponential curve as a candidate model to test against traces—not as a law of GPU inference.

The Math

For a stationary M/M/1 queue with Poisson arrival rate λa, exponential service rate μ, one FCFS server, and λa<μ, the total time in the system (waiting plus service) has an exponential distribution with rate θ=μ-λa:

fW(t) = θe-θt,   P(W>t) = e-θt
Let's decode this:
  • λa: Mean arrival rate (requests/second).
  • μ: Mean service rate (requests/second).
  • θ=μ-λa: Net rate parameter of the M/M/1 sojourn-time distribution—not a generic GPU “drain rate.”
  • W: Total time in the queueing system under the stated assumptions.

Worked example: Let λa=8 requests/s and μ=10 requests/s. Then θ=2/s, the mean sojourn time is 1/θ=0.5s, and the model's p99 is ln(100)/θ=2.30s. Thus p99 is 4.605 times the mean—but only under this M/M/1 model. The tail probability beyond 2s is e^(-2×2) ≈ 1.83%.

The SRE Trap

Do not label a fitted exponential curve “the TTFT distribution” without checking it. Stratify measurements by prompt-token bucket, output-token bucket, model, hardware, batch size, queue depth, cache state, and preemption. Compare empirical quantiles and tail probabilities with the candidate model; use a richer queueing or trace-driven model when the fit fails.

Dense full self-attention still has O(n²) arithmetic in sequence length. FlashAttention reduces high-bandwidth-memory traffic through IO-aware tiling and avoids materializing the full attention matrix; it does not make dense attention asymptotically linear. KV-cache memory generally grows linearly with cached token count, with the constant determined by layers, KV heads, head dimension, dtype, and architecture. A long prompt can consume disproportionate prefill compute and KV capacity, delaying shorter requests.

Operational Scenarios

KV-Cache Pressure vLLM / PagedAttention

When available KV-cache blocks are insufficient, serving engines may preempt sequences and later recompute their state; exact behaviour depends on engine version and configuration. Preemption and recomputation can increase end-to-end latency and disturb tail behaviour. Monitor cache utilization, preemption counts, queue delay, TTFT, and inter-token latency together.

Reference: vLLM documentation: performance and preemption
Cold-Start Cliff Serverless GPU Scaling

A 70-billion-parameter model stored in FP16 has approximately 140 GB of raw parameter weights (70 billion × 2 bytes), before runtime overhead, metadata, and other allocations. Loading time is not a universal 20–45 seconds: it depends on storage throughput, network path, parallelism, quantization, host memory, GPU topology, and whether weights are already cached. Measure cold-start latency on the actual deployment path and model its separate cold and warm populations.

Engineering note: publish a measured benchmark with model format, hardware, storage path, and timing boundaries before attaching a fixed load-time claim.
Chunked Prefill Sarathi-Serve

Chunked prefill divides long prompt processing into smaller chunks so that prefill work can be scheduled alongside ongoing decode work. This can reduce decode stalls and improve the throughput/latency trade-off, but it does not eliminate contention: chunk size and scheduler policy still matter. Track TTFT and inter-token latency (ITL/TBT) separately because an optimization can improve one while affecting the other.

Reference: Agrawal et al., “Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve”

3. The Geometric Distribution (Structured Outputs and Retries)

The Intuition: “JSON Is Hard, Let's Retry”

A model returns malformed JSON, omits a required field, or violates a type constraint. A validator catches the defect and the caller retries. If each attempt had the same independent probability of success, the number of attempts would follow a geometric distribution.

That assumption is a starting point, not a perfect description of repair loops. A retry that includes the validation error changes the prompt; later attempts therefore have conditional success probabilities and may have different token costs.

The Math

For independent attempts with constant success probability p, the probability that the first valid response arrives on attempt k is:

P(K=k)=(1-p)k-1p,   E[K]=1/p
Let's decode this:
  • K: Number of invocations up to and including the first success.
  • p: Per-attempt probability of passing the defined validation contract.

Worked example: If p=0.80, the unbounded geometric model gives 1.25 expected attempts per request. The probability of needing at least three attempts is (1-.8)² = 4%. At 100,000 requests/day, that is an expected 4,000 requests reaching attempt three or later, and 25,000 expected additional invocations across all requests.

A bounded retry policy is easier to operate. With at most m=3 attempts, the probability all attempts fail is (1-p)^m = 0.8%. Expected invocations are [1-(1-p)^m]/p = 1.24 per request. This calculation still assumes equal, independent attempts; measure actual conditional success and token use in production.

The SRE Trap

Retrying an unchanged request does not systematically repair a deterministic schema mismatch. Conversely, setting temperature to zero does not prove every failure will repeat identically across all providers and serving configurations. Make retries bounded, classify errors, and change the recovery strategy when appropriate.

Use provider-native JSON Schema / structured-output modes where supported, or grammar-constrained decoding tools such as Outlines. These can constrain the generated structure, but they do not guarantee semantic correctness, business-rule validity, completeness, absence of truncation, or successful transport. Validate those properties in application code.

Operational Scenarios

The Token Tax FinOps & Constrained Decoding

At a 70% first-attempt pass rate, the unbounded geometric baseline is 1/0.70 = 1.43 calls per successful request. Real token cost can be higher or lower than this simple call multiplier because failed outputs and validation feedback may be added to later prompts, while prompt and completion lengths differ. Track input tokens, output tokens, retries, and final success separately.

Reference: Willard & Louf, “Efficient Guided Generation for Large Language Models” (Outlines)
Self-Correction Bloat Retry Prompting

Feeding a validation error back into the next prompt may improve the next attempt's conditional success probability, but it also increases prompt length and may carry previous malformed output into the context. Model the retry chain with measured p1, p2, … and per-attempt token costs rather than assuming every attempt is an identical geometric trial.

Reference: Instructor: structured extraction and validation retries
The Unbounded Tool Loop Agent Tool Calling

An agent repeatedly calls an API with an invalid date format. A bounded iteration budget, typed tool contract, actionable error response, and explicit terminal failure state prevent the workflow from spending indefinitely on the same defect. Make side-effecting tools idempotent or protect them with idempotency keys.

Engineering control: enforce maximum attempts, wall-clock deadline, token budget, and per-tool rate limits in the orchestrator.

4. The Binomial Distribution (Agent Compounding)

The Intuition: The 10-Step Agent Fallacy

Imagine a workflow with ten required stages: classify intent, formulate SQL, validate schema, execute, inspect results, and so on. If every stage independently succeeds with probability 0.95, the probability that all ten succeed is 0.9510 ≈ 59.9%.

That is a useful warning about composition, not a universal prediction for agents. Real workflows have dependencies, retries, branches, validation, and recovery paths. The independence assumption must be stated and tested.

The Math

For n independent Bernoulli stages with common success probability p, the number of successful stages X is binomial:

P(X=k) = C(n,k)pk(1-p)n-k;   P(X=n)=pn
Let's decode this:
  • n: Number of required stages.
  • k: Number of successful stages, regardless of order.
  • p: Common per-stage success probability under the model.
  • pn: Probability all stages succeed, only when the stages are independent and share the same p.

Worked example: For 20 independent required stages, each with p=0.95, the expected number of successful stages is np=19. But the probability all 20 succeed is 0.95^20 ≈ 35.85%. This is the probability of a flawless run under the assumptions—not a measured failure rate for a real agent.

The SRE Trap: Correlation Changes the Model

Agent stages are often dependent. A wrong table name can cause SQL execution, result interpretation, and summarization to fail in sequence. But positive correlation does not automatically make pn an upper bound or a lower bound on end-to-end reliability. The direction depends on the joint distribution and the conditioning.

For an ordered workflow, use the chain rule:

P(S1,…,Sn) = P(S1) × P(S2|S1) × … × P(Sn|S1,…,S(n−1)).

Estimate those conditional probabilities from traces, or model the workflow as a state machine / reliability graph. If stages have different independent success rates, all-stage reliability is Π pᵢ; the count of successful stages follows a Poisson-binomial distribution, not a common-p binomial.

Operational Scenarios

Compounding Work in an Autonomous Loop Bounded Execution

For illustration, a 30-stage workflow with independent 98% stage reliability has an all-stage success probability of 0.98^30 ≈ 54.5%. This is not evidence that a particular agent framework failed at that rate. It shows why an architect should bound iterations, define stop conditions, validate intermediate artifacts, and measure end-to-end task completion—not just isolated model accuracy.

Background: Wang et al., “A Survey on Large Language Model based Autonomous Agents”
The Multi-Agent Echo Chamber Multi-Agent Topologies

Multiple agents can share the same mistaken premise, training biases, retrieved evidence, or tool output. Debate may improve some tasks, but agreement is not independent verification. Require evidence provenance and an external check—such as a compiler, database constraint, deterministic calculation, or independently sourced fact—before treating consensus as correctness.

Background: Du et al., “Improving Factuality and Reasoning in Language Models through Multiagent Debate”
The Deterministic Control Plane Workflow Architecture

Reduce unnecessary model calls by replacing predictable reasoning with ordinary code. Put each remaining model call behind typed input/output contracts, validators, bounded retries, deadlines, token budgets, and explicit state transitions. Use idempotency keys for side effects, audit the evidence used, and provide compensation or rollback paths where possible. Deterministic orchestration makes execution governable; it does not make model-generated content inherently correct.

Reference: NVIDIA NeMo Guardrails
The Final Reality: Constrain the Stochastic Core

A multi-step AI workflow is a reliability problem with probabilistic components. The exact end-to-end failure probability depends on stage dependencies, retries, branches, validation, and recovery—not merely the number of prompts.

The Architect's Rule: Use models for the semantic work that genuinely needs them. Use deterministic code for routing, arithmetic, authorization, schema checks, state transitions, and side effects. Measure the real end-to-end outcome, not just token-level or isolated-step accuracy. The AI proposes; the control plane validates and authorizes.
