The Stochastic Shape of AI Systems

November 28, 2026 · Part 8 of 8 · AI/LLM Frontier

“The fundamental problem of communication is that of reproducing at one point either exactly or approximately a message selected at another point.”

— Claude Shannon, "A Mathematical Theory of Communication"

In Part 7, we built an operational validation framework to detect when our latency, traffic, and reliability models drift away from physical reality. Throughout Parts 1 to 7, our proving ground was a traditional Multi-Tenant Analytics Gateway: a request arrived with a formal SQL query or API payload, and our job was to route, cache, shard, and execute it without violating tail-latency SLOs or exhausting memory boundaries.

Traditional query engines offer a narrower contract than “deterministic execution.” For a deterministic query over a fixed snapshot, logical query semantics are defined: the same SQL, session settings, and data should return the same rows, as a multiset unless ORDER BY fixes the order. They do not promise an identical physical execution plan or path. Optimizer and statistics changes can select a different plan, parallel scheduling and concurrency reorder operators, floating-point aggregation can differ in low-order digits when partial sums combine in a different order, nondeterministic functions (random(), now()) and external dependencies change results, queries without ORDER BY return unordered rows, and a different Iceberg snapshot is a different input. They are also not “correct by construction”: stale snapshots, schema drift, authorization bugs, and wrong business logic still produce wrong answers. The practical difference is diagnosability: pin the snapshot, settings, and plan, and a failure can usually be reproduced.

Welcome to the frontier. Now suppose leadership asks us to extend that same Multi-Tenant Analytics Gateway with an AI Query Assistant and Autonomous Reconciliation Agent. Tenants can ask natural-language questions, retrieve Iceberg table metadata via RAG, synthesize analytical SQL, repair validation errors, and execute multi-step reconciliation workflows. Suddenly, an HTTP 200 with a 180 ms response time can still be a catastrophic production failure—because a syntactically valid JSON payload containing a plausible-looking SQL query just joined the wrong tenant partition or fabricated a regulatory metric.

An AI system in production fundamentally changes the failure surface because both the execution runtime (stochastic queueing, dynamic continuous batching, KV-cache eviction) AND the output generation mechanism itself (autoregressive token sampling, semantic grounding) are non-deterministic. As throughout this series, our core discipline holds: a distribution is a model, not an invariant. The useful architectural question is not “How do we make an LLM deterministic?” It is: Where does randomness enter the pipeline, which failure layer does it threaten, and what deterministic control plane bounds the blast radius?

The AI Reliability Stack: Five Distinct Failure Layers

Before fitting any distribution to an AI service, an architect must separate five distinct success events that traditional APM dashboards conflate into a single “200 OK” counter:

  1. Serving Reliability (\(E_{\text{serve}}\)): The inference engine accepts the request, allocates KV-cache memory, and streams tokens within the TTFT and TPOT latency budgets without HTTP 5xx, timeout, or OOM preemption.
  2. Structural Correctness (\(E_{\text{struct}}\)): The generated output conforms to the syntactic contract—valid JSON, matching grammar, or a parseable AST without truncation.
  3. Data & Retrieval Correctness (\(E_{\text{data}}\)): Referenced entities, table names, column types, and tool parameters actually exist in the target catalog and respect tenant authorization boundaries. (For RAG, this includes chunk recall and freshness).
  4. Semantic Correctness (\(E_{\text{sem}}\)): Faithfulness to retrieved context and user intent, judged against measurable acceptance conditions (Section 5): factual support, tenant correctness, domain invariants, numerical tolerance, citation validity, permitted uncertainty, and task-specific acceptance. It is reported as an observed error rate with an interval, not asserted as “zero hallucinations.”
  5. End-to-End Task Success (\(E_{\text{task}}\)): The complete multi-step workflow—including downstream tool execution, validation, policy compliance, and side effects—safely completes the user's goal.

Treat the five layers as a nested success chain. The order is a modelling convention (retrieval, for example, runs before generation); the point is that each factor is conditioned on the layers before it, so the factors must not be multiplied as independent probabilities unless independence is justified. Let \(E_{\text{exec}}\) be downstream tool execution, policy checks, and side effects completing correctly; \(E_{\text{task}}\) is the event that all five layers hold:

\[ \begin{aligned} P(E_{\text{task}}) &= P(E_{\text{serve}}) \cdot P(E_{\text{struct}} \mid E_{\text{serve}}) \cdot P(E_{\text{data}} \mid E_{\text{struct}}, E_{\text{serve}}) \\ &\quad \cdot P(E_{\text{sem}} \mid E_{\text{data}}, E_{\text{struct}}, E_{\text{serve}}) \cdot P(E_{\text{exec}} \mid E_{\text{sem}}, E_{\text{data}}, E_{\text{struct}}, E_{\text{serve}}) \end{aligned} \]

Optimizing one layer, such as constrained decoding, drives \( P(E_{\text{struct}} \mid E_{\text{serve}}) \) toward 1 (apart from truncation and refusals) but does not bound \( P(E_{\text{sem}} \mid \dots) \). Illustratively, \( P(E_{\text{serve}}) = 0.999 \) alongside \( P(E_{\text{task}}) = 0.65 \) is arithmetically consistent: every infrastructure health check can pass while most tasks fail semantic acceptance. These values are illustrative, not industry benchmarks.

1. The Categorical Distribution (Token Sampling)

The Intuition: The Weighted Dice Roll

At each autoregressive decoding step, a language model computes a vector of unnormalized scores (logits) across its entire vocabulary. A Softmax transformation converts those scores into a discrete probability vector, and the sampler draws a single token. The Categorical distribution models that single discrete draw conditioned on the exact token prefix generated so far.

Temperature (\(T\)) controls the entropy of that draw by scaling logits prior to exponentiation. Lower values concentrate probability mass onto the highest-logit token; higher values flatten the distribution toward uniformity. Crucially, temperature controls lexical diversity—not the epistemic probability that a statement is factually true.

The Math

Let \(w_t\) be the random variable representing the token index selected at decoding step \(t\) from a vocabulary \(V\) (where \(i \in \{1, \dots, |V|\}\)), conditioned on the preceding context \(w_{\lt t}\). Given raw logit vector \(z \in \mathbb{R}^{|V|}\) and temperature \(T > 0\), the probability of sampling token \(i\) prior to Top-\(k\) or Top-\(p\) (Nucleus) truncation is the temperature-scaled Softmax:

\[ P(w_t = i \mid w_{\lt t}) = \frac{\exp(z_i / T)}{\sum_{j=1}^{|V|} \exp(z_j / T)} \]
Let's decode this:
  • \(w_t\): Discrete random variable for the single token selected at step \(t\).
  • \(z_i\): Unnormalized logit for vocabulary token \(i\).
  • \(T\): Temperature parameter (\(T > 0\)). As \(T \to 0^+\) (greedy decoding), probability mass concentrates entirely on \(\text{argmax}_i z_i\). As \(T \to \infty\), the distribution approaches uniformity \(1/|V|\).
  • Top-\(k\) / Top-\(p\) (Nucleus): Truncation techniques that assign zero probability to the long tail of unlikely tokens (equivalently a logit of \(-\infty\)) and renormalize the remainder before the draw, so highly improbable tokens cannot be sampled even at higher temperatures.
  • Sequence vs. Step Distinction: A single token draw is Categorical, but an \(L\)-token response is a non-homogeneous autoregressive stochastic process where each draw \(w_t\) alters the conditioning prefix \(w_{\lt t+1}\) and shifts the entire logit vector at step \(t+1\).

Worked example: Suppose at \(T = 1.0\) the Softmax distribution over four candidate tokens—Data, Model, Magic, and Garbage—is \(p = [0.40, 0.30, 0.20, 0.10]\). If an engineer raises temperature to \(T = 2.0\) to make responses “more creative,” the distribution flattens. The probability of drawing the undesirable tail token (Garbage) jumps from \(10.00\%\) to \(16.27\%\)—a 62.7% relative increase on a single step. (Note: this is an illustrative single-step calculation, not a direct measurement of multi-token hallucination rate.)

The SRE Trap: The "Deterministic" Illusion

Temperature greater than zero makes sampling stochastic by design, so exact-string unit tests fail intermittently even when the answer is semantically valid. Conversely, setting \(T = 0\) selects the greedy token at each step, but it is not a hardware-level reproducibility guarantee in production.

In distributed GPU clusters, floating-point non-associativity in split-K matrix reductions, variable continuous-batching composition, MoE routing capacity constraints, and silent provider model snapshots can alter the raw \(z_i\) values just enough to flip tie-breaking logits. For CI/CD regression suites, pin the model snapshot, prompt template, decoding parameters, and tool schemas; assert structural and semantic invariants rather than raw prose strings.

When this model breaks: Do not treat token sampling probability (low entropy) as a calibrated confidence score for factual truth. When a model is miscalibrated or lacks grounding data in its context window, the factually wrong token can easily hold the highest logit (\(p_1 = 0.85\)), meaning greedy decoding (\(T \to 0^+\)) will select the falsehood on every run for that prefix, barring numerical variation (a confident hallucination).

Case Study 1: Temperature-Induced SQL Dialect Drift in the Analytics Gateway
Illustrative Engineering Model

1. The Scenario: After rolling out the NL2SQL assistant on the Gateway, roughly 15% of multi-join analytical queries began failing in DuckDB with parser errors (e.g., invoking PostgreSQL-only regex operators or Spark-specific LATERAL VIEW EXPLODE).

2. The Architectural Assumption: The application team reused a shared chat-completion client configured with \(T = 0.7\) and \(\text{Top-}p = 0.95\), assuming that because the system prompt explicitly specified “Generate valid DuckDB SQL,” minor token diversity would only affect SQL alias naming.

3. The Physical Mechanism: Syntax tokens at dialect branch points (such as date-truncation functions) compete closely in logit space across pre-training dialects (Postgres, Spark, Snowflake, DuckDB). At \(T = 0.7\), the Categorical sampler occasionally draws a runner-up token from a competing dialect. Once that token enters the prefix \(w_{\lt t}\), autoregressive conditioning locks the remainder of the clause into the wrong dialect.

4. The Mathematical Model: Let a query contain \(m = 8\) dialect-sensitive branch points. At \(T = 0.7\), suppose the valid DuckDB token holds probability \(p_i = 0.98\) and competing dialect tokens share the remaining \(0.02\) at each branch point (assumed independent for this baseline).

5. The Calculation: The probability that all \(m = 8\) branch points sample the valid DuckDB token is \(P(E_{\text{struct}}) = 0.98^8 \approx 0.8508\) (85.1%), yielding a 14.9% syntax failure rate. Lowering \(T \to 0^+\) selects the dominant token at all 8 branch points. The product treats branch points as independent with equal probability; real branch probabilities are conditional on the prefix and differ by token, so \(0.85\) is a baseline to be replaced by a measured parse-error rate.

6. The Architectural Decision: Split decoding profiles by task class: enforce \(T = 0.0\) for all code, SQL, and tool-argument generation, and attach a deterministic pre-execution AST validator (sqlglot) before dispatching to DuckDB. Trade-off: Greedy decoding eliminates sampling diversity; if the wrong dialect token genuinely holds the highest logit, a simple retry at \(T = 0\) will fail identically unless the validator injects the AST parse error into the repair prompt.

7. Production Verification: Track gateway_sql_ast_parse_error_rate segmented by decoding profile. In this illustrative scenario the goal is for unparseable failures to fall from roughly 15% to a small residual attributable to schema gaps rather than sampling variance; the segmentation by decoding profile, not the numbers, is the reusable part.

Operational Scenarios

The Non-Deterministic Test CI/CD Pipelines

A test expects one exact sentence, but a model returns a valid answer with different wording. The test fails even though the product behaviour is acceptable. Separate deterministic contract tests (schema, required fields, allowed tool calls, safety invariants) from probabilistic quality evaluations (groundedness, relevance, task success). Use temperature zero when appropriate, but do not treat it as a substitute for robust assertions.

Reference: OpenAI API: Advanced usage and reproducibility considerations
Autoregressive Error Propagation Generation Dynamics

Each sampled token becomes part of the context for later tokens. A mistaken entity, number, or premise can therefore influence what follows. This is a plausible error-propagation mechanism, not a rule that every low-probability token causes a confident hallucination. Grounding, retrieval, verification, and constrained task boundaries are more direct controls than temperature alone.

Reference: Holtzman et al., “The Curious Case of Neural Text Degeneration”
The Top-P Cutoff Nucleus Sampling

Top-p sorts tokens by descending probability, retains the smallest prefix whose cumulative probability reaches or exceeds the configured threshold, then renormalizes the retained probabilities. It trims the low-probability tail; it does not know which tokens are “nonsensical,” and it cannot guarantee factuality.

Reference: Holtzman et al., “The Curious Case of Neural Text Degeneration”

2. Inference Queueing & KV-Cache Physics

The Intuition: Prefill vs. Decode

LLM serving latency is governed by two physically distinct phases:

  • Prefill Phase (Compute-Bound): The GPU processes all \(L_{\text{in}}\) prompt tokens in parallel to populate the Key-Value (KV) cache. This dense matrix multiplication determines the Time to First Token (TTFT). Without chunking, large prefills cause head-of-line blocking for other requests.
  • Decode Phase (Memory-Bandwidth-Bound): The GPU autoregressively generates \(L_{\text{out}}\) output tokens one step at a time, reading the KV-cache on each step. This dictates the Time Per Output Token (TPOT) or Inter-Token Latency (ITL).

Total request service time \(S\) is therefore highly variable, driven by the heavy-tailed distributions of input/output lengths and the active continuous-batch size \(B_j\). Because sequences have different lengths, Request Throughput (req/s) and Token Throughput (tok/s) diverge significantly.

The Math

For a stationary \(M/M/1\) queue with Poisson arrival rate \(\lambda_a\) and exponential service rate \(\mu\), the sojourn time \(W\) follows an Exponential distribution with net rate \(\theta = \mu - \lambda_a\):

\[ f_W(t) = \theta e^{-\theta t}, \quad P(W > t) = e^{-\theta t}, \quad t \ge 0 \]

However, total request service time \(S\) is non-exponential and highly variable due to the physical separation of the Prefill and Decode phases:

\[ S = T_{\text{prefill}}(L_{\text{in}}) + \sum_{j=2}^{L_{\text{out}}} T_{\text{step}}(B_j) \]

The prefill pass produces the first output token, so a request with \(L_{\text{out}}\) output tokens has \(L_{\text{out}}-1\) decode steps, and \(B_j\) is the batch size at step \(j\). Latency metrics are defined per request on that timeline:

\[ \begin{aligned} \text{TTFT} &= t_{\text{first}} - t_{\text{arrive}} = W_q + T_{\text{prefill}}, \\ \text{TPOT} &= \frac{t_{\text{last}} - t_{\text{first}}}{L_{\text{out}} - 1}, \qquad L_{\text{out}} \ge 2 \end{aligned} \]

TTFT includes queueing delay \(W_q\), prefill, and the first sample (plus network and tokenization when measured at the client). TPOT excludes the first token: it is the mean of that request's \(L_{\text{out}}-1\) inter-token latencies (ITL), while the ITL distribution keeps the individual gaps, so its p99 exposes stalls from prefill interference or preemption that a mean hides. Tools differ on both choices, so state where the clock starts (client, gateway, or engine) and whether the first token is excluded. Per-request and batch-level measures also differ: one decode step with batch size \(B\) takes \(T_{\text{step}}(B)\) and emits one token per sequence, so the per-request token rate is about \(1/\text{ITL}\) while batch token throughput is about \(B / T_{\text{step}}(B)\) tokens/s. Raising \(B\) usually raises throughput and lengthens ITL.

Furthermore, on a physical GPU running continuous batching, effective service capacity degrades discontinuously when active sequences exceed the available High-Bandwidth Memory (HBM) allocated for the KV-cache. For a transformer with \(L_{\text{layers}}\), \(H_{\text{kv}}\) KV heads per layer, head dimension \(d_h\), precision \(b_{\text{bytes}}\) (e.g., FP16/BF16 = 2 bytes), and \(C\) total cached tokens across the running batch, the KV-cache footprint is (weights, activations, and allocator overhead are extra):

\[ M_{\text{token}} = 2 \cdot L_{\text{layers}} \cdot H_{\text{kv}} \cdot d_h \cdot b_{\text{bytes}}, \qquad M_{\text{KV}}(C) = C \cdot M_{\text{token}} \]
Let's decode this:
  • \(\lambda_a\), \(\mu\), \(\rho\): Mean arrival rate, mean service rate, and server utilization (\(\rho = \lambda_a/\mu\)).
  • \(\theta = \mu(1 - \rho)\): Net rate parameter of the \(M/M/1\) sojourn distribution. As \(\rho \to 1\), \(\theta \to 0\) and mean latency \(\to \infty\).
  • \(M_{\text{token}}\): HBM bytes required to store Key and Value tensors (hence the factor of 2) for one token, before paging, fragmentation, and quantization-scale overhead.

Worked example (illustrative configuration): For a Llama-3 70B-class model (\(L_{\text{layers}} = 80, H_{\text{kv}} = 8, d_h = 128\)) with an FP16 KV-cache (\(b_{\text{bytes}} = 2\)), \(M_{\text{token}} = 2 \cdot 80 \cdot 8 \cdot 128 \cdot 2 = 327{,}680\) bytes \(= 320\) KiB. The FP16 weights alone are about 140 GB, so a replica spans several GPUs with tensor parallelism; suppose 30 GiB of aggregate HBM across the group is reserved for the KV-cache. The hard limit is then \(30\ \text{GiB} / 320\ \text{KiB} = 98{,}304\) cached tokens. Five concurrent 16K-token RAG requests (\(5 \times 16{,}384 = 81{,}920\) tokens before any output) consume about 83% of that budget. This is a capacity ceiling for admission control, not a latency prediction.

The SRE Trap

Do not fit a single exponential curve to aggregate TTFT telemetry. Because prompt lengths often span three orders of magnitude (from 100-token chat turns to 32,000-token RAG contexts), service time has a high coefficient of variation (\(C_s^2 \gg 1\)). As Kingman's approximation in Part 3 showed, high service-time variability inflates queueing delay well beyond the \(M/M/1\) baseline; the approximation assumes finite variance, so where prompt-length tails are heavy enough that the sample variance does not stabilise, measure the empirical distribution instead.

Dense full self-attention still requires O(n²) arithmetic operations in prompt sequence length \(n\) during prefill. FlashAttention reduces HBM bandwidth bottlenecks through IO-aware SRAM tiling, but it does not make dense prefill compute asymptotically linear. Meanwhile, \(M_{\text{KV}}(C)\) grows linearly with total cached tokens across all concurrent requests. When \(M_{\text{KV}}(C) > M_{\text{max}}\), the engine must preempt running sequences (evicting them to host memory or discarding them)—turning a smooth queueing curve into a sharp cliff.

Case Study 2: KV-Cache Exhaustion and PagedAttention Preemption
Hypothetical Stress Scenario

1. The Scenario: During the 09:30 market-open burst, the Analytics Gateway's LLM serving tier suffered a sudden p99 TTFT spike from 1.8 s to 19.4 s, accompanied by mid-stream freezes in token streaming.

2. The Architectural Assumption: Capacity planners sized the GPU pool using average request throughput (\(\lambda_a = 6\) req/s) and configured the vLLM scheduler with max_num_seqs = 32, assuming 32 sequences would comfortably fit in GPU memory based on a historical average of 1,500 prompt tokens.

3. The Physical Mechanism: A new tenant enabled automated schema-RAG, injecting full Iceberg table manifests (averaging 7,000 total tokens per sequence). When concurrent long-context requests filled the 24 GiB KV-cache ceiling, the engine triggered sequence preemption—evicting partially decoded requests and later recomputing their entire prefill from scratch (thrashing).

4. The Mathematical Model: With \(M_{\text{token}} = 320\) KiB and a 24 GiB budget, the physical limit is 78,643 tokens. Under the legacy workload, 32 sequences required ~14.6 GiB (61% utilization). Under the RAG burst, just 12 concurrent sequences required 84,000 tokens—exceeding the 78,643 limit.

5. The Architectural Decision: Replace request-count limits with token-budget admission control at the Gateway (capping in-flight active tokens per replica at an illustrative admission-control threshold of 65,000 tokens, or ~83% of capacity, counting each request’s prompt plus its reserved maximum output tokens because the KV-cache grows during decode). Enable chunked prefill so long prefills do not stall active decodes, and route requests exceeding 4,096 prompt tokens to a dedicated long-context pool with FP8 KV-cache quantization (roughly doubling token capacity, before scale-factor overhead, subject to validated output quality). Trade-off: Strict admission control trades internal GPU thrashing for explicit edge backpressure (HTTP 429).

6. Production Verification: Alert whenever vllm:num_preemptions_total rate exceeds 0, monitor vllm:gpu_cache_usage_perc, and track TTFT/TPOT histograms stratified by input token buckets.

Operational Scenarios

KV-Cache Pressure vLLM / PagedAttention

When available KV-cache blocks are insufficient, serving engines may preempt sequences and later recompute their state; exact behaviour depends on engine version and configuration. Preemption and recomputation can increase end-to-end latency and disturb tail behaviour. Monitor cache utilization, preemption counts, queue delay, TTFT, and inter-token latency together.

Reference: vLLM documentation: performance and preemption
Cold-Start Cliff Serverless GPU Scaling

A 70-billion-parameter model stored in FP16 has approximately 140 GB of raw parameter weights (70 billion × 2 bytes), before runtime overhead, metadata, and other allocations. Loading time is not a universal 20–45 seconds: it depends on storage throughput, network path, parallelism, quantization, host memory, GPU topology, and whether weights are already cached. Measure cold-start latency on the actual deployment path and model its separate cold and warm populations.

Engineering note: publish a measured benchmark with model format, hardware, storage path, and timing boundaries before attaching a fixed load-time claim.
Chunked Prefill Sarathi-Serve

Chunked prefill divides long prompt processing into smaller chunks so that prefill work can be scheduled alongside ongoing decode work. This can reduce decode stalls and improve the throughput/latency trade-off, but it does not eliminate contention: chunk size and scheduler policy still matter. Track TTFT and inter-token latency (ITL/TBT) separately because an optimization can improve one while affecting the other.

Reference: Agrawal et al., “Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve”

3. The Geometric Distribution (Structured Outputs and Retries)

The Intuition: “JSON Is Hard, Let's Retry”

A model returns malformed JSON, omits a required Pydantic field, or references a non-existent Iceberg column. A deterministic validator catches the defect and triggers a retry. If each attempt had the same independent probability of passing validation, the number of attempts would follow a Geometric distribution (the same memoryless retry baseline we examined in Part 6).

In LLM orchestration, however, a retry loop is rarely stationary or memoryless. When frameworks like Instructor or LangGraph append the failed output and the validator traceback into the next prompt, two things change simultaneously: the conditional probability of success \(p_k\) changes on attempt \(k\), and the input prompt token count \(C_k\) grows on every iteration.

The Math

Under the baseline assumption of independent trials with constant per-attempt validation success probability \(p \in (0, 1]\), let \(K \in \{1, 2, \dots\}\) be the number of model invocations required up to and including the first valid response:

\[ P(K = k) = (1 - p)^{k-1}p, \quad E[K] = \frac{1}{p} \]

In production, unbounded retries are forbidden. Under a bounded policy capped at \(m\) total invocations (\(K_m = \min(K, m)\)), the expected number of invocations per user request is:

\[ E[K_m] = \sum_{k=1}^{m} (1 - p)^{k-1} = \frac{1 - (1 - p)^m}{p} \]

When retries are stateful repair loops where attempt \(k\) has conditional pass rate \(p_k = P(\text{Pass}_k \mid \text{Fail}_{1\dots k-1})\) and consumes \(C_k\) total tokens, expected token consumption per request is:

\[ E[\text{Tokens}] = C_1 + \sum_{k=2}^{m} C_k \prod_{j=1}^{k-1} (1 - p_j) \]
Let's decode this:
  • \(K\), \(K_m\): Unbounded and \(m\)-bounded invocation counts (dimensionless attempts per incoming request).
  • \(p\): Stationary single-attempt probability of passing both syntactic (\(E_{\text{struct}}\)) and schema (\(E_{\text{data}}\)) validation.
  • \(p_k\), \(C_k\): Conditional validation pass probability and total token cost (prompt + completion tokens) on attempt \(k\).

Worked example: If \(p = 0.80\), an unbounded geometric model predicts \(E[K] = 1 / 0.80 = 1.25\) attempts per request, and the probability of needing 3 or more attempts is \((1 - 0.80)^2 = 4.0\%\). At 100,000 requests/day, that generates 25,000 extra model invocations/day. Capping total invocations at \(m = 3\) yields \(E[K_3] = (1 - 0.20^3) / 0.80 = 1.24\) invocations/request, while bounding worst-case amplification at \(3\times\) and leaving a \(0.20^3 = 0.8\%\) terminal failure rate routed to a deterministic fallback.

The SRE Trap

Distinguish syntactic grammar failures (\(E_{\text{struct}}\)) from semantic or domain-constraint failures (\(E_{\text{data}}, E_{\text{sem}}\)). Grammar-constrained decoding (such as finite-state automata in Outlines or provider-native Strict JSON Schema modes) masks invalid vocabulary tokens during the Softmax step itself, driving syntactic JSON parse failures to nearly zero (truncation at the maximum-token limit, refusals, and unsupported schema features can still break structure). That eliminates the need to spend retries on missing commas or unclosed braces.

However, constrained decoding cannot prevent semantic hallucinations: the model will happily emit 100% schema-compliant JSON containing a fabricated trade ID or a logically inverted SQL WHERE clause. Worse, when retries burst simultaneously during a downstream schema drift event, the \(1/p\) call multiplier increases arrival rate \(\lambda_a\) at the GPU pool, driving utilization \(\rho \to 1\) and triggering a classic retry storm.

Case Study 3: Self-Correction Prompt Bloat in NL2SQL Schema Validation
Hypothetical Stress Scenario

1. The Scenario: Following an upstream Iceberg table migration that renamed columns across 18 tenant namespaces, token spend per request rose sharply and GPU queue depth grew within hours, even though user query volume remained flat. The calculation below sizes that effect (about 2.1× tokens per request).

2. The Architectural Assumption: Engineers wrapped the NL2SQL generator in a validation loop with \(m = 4\) max attempts. They assumed that if first-attempt validation dropped from 92% to 65%, the geometric call multiplier (\(1 / 0.65 \approx 1.54\)) would rise from \(1/0.92 \approx 1.09\) to \(1/0.65 \approx 1.54\) calls per request (about +42%) and that the extra calls would heal the queries.

3. The Physical Mechanism: Two compounding mechanisms invalidated the stationary geometric calculation. First, because the RAG vector index still served stale column metadata, appending the DuckDB Referenced column not found traceback into the retry prompt gave the model contradictory instructions, causing conditional pass rates to collapse (\(p_1 = 0.65, p_2 = 0.25, p_3 = 0.10\)). Second, each retry appended the failed 600-token SQL block plus a 1,400-token catalog dump, inflating token cost \(C_k\) super-linearly.

4. The Mathematical Model: We model the 4-attempt stateful repair chain using non-stationary pass probabilities \(p_1 = 0.65, p_2 = 0.25, p_3 = 0.10, p_4 = 0.05\) and assumed per-attempt token costs \(C_1 = 2,500\), \(C_2 = 4,500\), \(C_3 = 6,500\), and \(C_4 = 8,500\) tokens.

5. The Calculation: The probability of reaching attempt 2 is \(1 - p_1 = 0.35\); reaching attempt 3 is \(0.35 \times (1 - 0.25) = 0.2625\); reaching attempt 4 is \(0.2625 \times (1 - 0.10) = 0.23625\). Expected invocations per request is \(E[K_4] = 1 + 0.35 + 0.2625 + 0.23625 = 1.849\) attempts. Expected token spend is \(E[\text{Tokens}] = 2,500 + (0.35 \times 4,500) + (0.2625 \times 6,500) + (0.23625 \times 8,500) = 7,789\text{ tokens/request}\)—3.12× the one-shot cost \(C_1\). The same chain with the pre-migration first-attempt rate \(p_1 = 0.92\) (keeping \(p_2, p_3, p_4\) unchanged for comparison) costs \(3{,}709\) tokens/request, so the migration raises expected tokens per request by \(7{,}789 / 3{,}709 \approx 2.1\times\), against \(\approx 1.4\times\) in calls under the stationary geometric model. About \(22.4\%\) of requests still fail all 4 attempts (\(0.35 \times 0.75 \times 0.90 \times 0.95\)).

6. The Architectural Decision: Implement three controls: (a) enforce grammar-constrained decoding for structural JSON validity; (b) classify validation errors—if DuckDB returns a ColumnNotFound binder error, trigger an immediate deterministic catalog cache refresh before attempting a single repair (\(m = 2\) max attempts); and (c) enforce a cluster-wide 10% token retry budget (if retry tokens exceed 10% of primary tokens over a 5-minute window, trip a circuit breaker). Trade-off: Capping repair attempts at \(m = 2\) slightly reduces recovery on complex multi-error queries in exchange for eliminating runaway GPU saturation.

7. Production Verification: Instrument empirical conditional pass rates \(\hat{p}_1, \hat{p}_2\) by error class (schema_binder_error, timeout) and alert when \(\hat{p}_2 \lt 0.50\) (indicating the repair prompt is burning tokens without fixing the underlying cause).

4. The Binomial Distribution (Agent Compounding)

The Intuition: The 10-Step Agent Fallacy

Imagine an autonomous workflow with ten required sequential stages: classify intent, select tenant catalog, retrieve table schemas, formulate SQL, check policy constraints, execute query, inspect anomalies, draft summary, verify citations, and publish report. If every stage independently succeeds with probability \(0.95\), the probability that all ten stages succeed is \(0.95^{10} \approx 59.87\%\)—just as independent component failures compounded in Part 2.

That simple exponential decay is a vital architectural warning against long unverified chains, not a literal predictor for every agent. Real workflows exhibit strong cross-stage dependencies, heterogeneous stage difficulty, and deterministic verification checkpoints. The independence assumption must be explicitly stated, audited, and engineered out of the system.

The Math

Under the baseline assumption of \(n\) independent Bernoulli stages with homogeneous per-stage success probability \(p \in (0, 1)\), the total number of successful stages \(X \in \{0, 1, \dots, n\}\) follows a Binomial distribution, and end-to-end workflow completion requires \(X = n\):

\[ P(X = k) = \binom{n}{k}p^k(1 - p)^{n-k}, \quad P(X = n) = p^n \]

In real production workflows where stage success rates differ and later stages depend on the artifacts produced by earlier stages, let \(S_i \in \{0, 1\}\) denote the indicator that stage \(i\) is both structurally and semantically valid. End-to-end reliability is governed by the general chain rule:

\[ P(S_1=1, \dots, S_n=1) = P(S_1=1)\prod_{i=2}^{n} P(S_i=1 \mid S_1=1, \dots, S_{i-1}=1) \]
Let's decode this:
  • \(n\): Number of mandatory sequential stages in the workflow.
  • \(p^n\): Probability of a flawless end-to-end run when all \(n\) stages are independent and share success probability \(p\).
  • \(S_i\): Indicator event that stage \(i\) succeeds according to both syntactic and semantic invariants.

Worked example: For \(n = 20\) independent required stages, each with \(p = 0.95\), the expected number of successful stages is \(E[X] = np = 19.0\) stages. Yet because a serial pipeline fails if even a single required stage fails without recovery, the probability of a complete end-to-end success is \(0.95^{20} \approx 35.85\%\). Conversely, if an architect replaces 16 of those 20 LLM steps with deterministic code (\(p_{\text{det}} \approx 0.9999\)) and retains only \(n = 4\) essential LLM stages at \(p = 0.95\), baseline serial reliability jumps from \(35.85\%\) to \(0.95^4 \times 0.9999^{16} \approx 81.32\%\) before even adding stage-level validation retries.

The SRE Trap: Correlation and State-Space Collapse

Agent stages are almost never independent. If Stage 2 retrieves the wrong tenant's schema, Stages 3, 4, and 5 (SQL synthesis, execution, and narrative explanation) are conditioned on a false premise: \(P(S_3 = 1 \mid S_2 = 0) \approx 0\). The direction of the error from assuming independence is not fixed: if the \(p_i\) are true production marginals and stage successes are positively associated, \(\prod p_i\) understates all-stage success, but \(p_i\) measured in isolation on golden inputs overstate production marginals, and a poisoned stage has a conditional probability far below its isolated one. Measure \(P(S_i = 1 \mid S_1 = \dots = S_{i-1} = 1)\) on real upstream outputs.

When stages have distinct independent success probabilities \(p_1, \dots, p_n\), the count of successful stages follows a Poisson-Binomial distribution, and all-stage reliability is \(\prod_{i=1}^n p_i\). If an architect adds a validator and a bounded \(m\)-attempt recovery loop around stage \(i\), reliability rises only for failures the validator detects. With detection coverage \(d_i\) and conditional retry pass probabilities \(r_{i,k} = P(\text{pass on retry } k \mid \text{earlier attempts failed})\), \(p_{i,\text{eff}} = p_i + (1 - p_i)\, d_i \bigl[1 - \prod_{k=1}^{m-1}(1 - r_{i,k})\bigr]\). The familiar \(1 - (1 - p_i)^m\) is the special case of perfect detection and independent, identical retries; undetected (silent) errors pass straight through.

Case Study 4: Collapsing an Autonomous Trade-Reconciliation Agent into a Deterministic Control Plane
Illustrative Engineering Model

1. The Scenario: A prototype autonomous reconciliation agent built on top of the Gateway was tasked with investigating end-of-day trade breaks. Suppose a staging evaluation over 500 historical breaks (an illustrative scenario, not a published benchmark) found that the agent completed only 48.2% of investigations correctly, while 19.0% ended in silent semantic errors (attributing breaks to the wrong counterparty or computing fee deltas with floating-point hallucinations).

2. The Architectural Assumption: The engineering team designed an open-ended 12-step ReAct agent loop where the LLM autonomously decided which tool to invoke next, parsed raw JSON tool payloads, performed currency-conversion arithmetic in-context, and wrote the final discrepancy ticket.

3. The Physical Mechanism: Each autonomous reasoning turn introduced an unverified stochastic branch. Even though individual prompt benchmarks showed ~94% per-turn accuracy on golden unit tests, chaining 12 open-ended turns meant small errors in early tool selection or in-context arithmetic poisoned the context window for all subsequent steps.

4. The Mathematical Model: Under the initial \(n = 12\) serial LLM-turn architecture with benchmarked per-stage reliability \(p = 0.94\), baseline all-stage success is \(P(\text{All 12}) = p^{12}\). Under the refactored architecture, we move 9 steps into deterministic code (including tenant routing, schema lookup, SQL execution, currency arithmetic, threshold comparison, and ticket formatting) with standard Python/DuckDB code (\(p_{\text{code}} = 0.9995\)) and retain only \(n = 3\) bounded LLM nodes, each wrapped in a deterministic validator with \(m = 2\) bounded attempts and effective reliability \(p_{i,\text{eff}} = p_i + (1 - p_i)\, d\, r\), where \(d\) is validator detection coverage and \(r = P(\text{pass on retry} \mid \text{first attempt failed})\).

5. The Calculation: In the original 12-turn loop, treating turns as independent with \(p = 0.94\) predicts \(0.94^{12} \approx 0.476\). The illustrative staging result (48.2%) sitting close to that prediction is consistent with independence but does not prove it; on real data, compare predicted and observed rates to test the assumption. In the refactored 3-node machine take \(p_i = 0.94\) and \(r = 0.65\). With perfect detection (\(d = 1\)), \(p_{i,\text{eff}} = 0.94 + 0.06 \times 0.65 = 0.979\); with nine deterministic steps (\(0.9995^9 \approx 0.9955\)), \(P(\text{Success}) = 0.979^3 \times 0.9955 \approx 0.934\) (93.4%), at an expected \(3 \times 1.06 = 3.18\) LLM calls per workflow versus 12 (a 73.5% reduction). Detection coverage is the sensitive assumption: \(d = 0.8\) gives \(p_{i,\text{eff}} = 0.9712\) and \(P(\text{Success}) \approx 91.2\%\); \(d = 0.5\) gives about 87.9%. The undetected remainder is silent semantic error, so \(d\) must be measured, not assumed. “Success” means a correct completion; workflows that fail validation go to human review and are not counted as correct.

6. The Architectural Decision: Replace unconstrained ReAct loops with an explicit directed acyclic graph (DAG) or finite state machine in the orchestrator. Enforce the rule that LLMs never perform arithmetic, authorization checks, or control-flow routing when deterministic code can compute the exact answer. Require idempotency keys on all side-effecting tool calls and route the residual workflows that fail validation to a human-in-the-loop review queue. Set per-tool timeouts inside the workflow deadline, and treat a timed-out side-effecting call as outcome-unknown: retry it only with the same idempotency key.

7. Production Verification: Log step-level transition matrices in OpenTelemetry spans, track empirical conditional transition probabilities \(\hat{P}(S_i = 1 \mid S_{i-1} = 1)\) weekly, and audit semantic correctness (\(E_{\text{sem}}\)) via stratified daily sampling against deterministic reconciliation ledger balances.

Operational Scenarios

Compounding Work in an Autonomous Loop Bounded Execution

For illustration, a 30-stage workflow with independent 98% stage reliability has an all-stage success probability of 0.98^30 ≈ 54.5%. This is not evidence that a particular agent framework failed at that rate. It shows why an architect should bound iterations, define stop conditions, validate intermediate artifacts, and measure end-to-end task completion—not just isolated model accuracy.

Background: Wang et al., “A Survey on Large Language Model based Autonomous Agents”
Tool Timeouts and Ambiguous Outcomes Tool Execution

A tool call that times out has an unknown outcome: the side effect may or may not have been applied. Classify tools as read-only or side-effecting, give each a deadline inside the workflow deadline, retry side-effecting calls only with a stable idempotency key, and reconcile ambiguous outcomes against the system of record before the agent continues. The timeout is a serving-layer failure; a retried write that duplicates a ticket is a task-layer failure that passes every health check.

Engineering control: per-tool timeouts, idempotency keys, and outcome reconciliation in the orchestrator.
The Multi-Agent Echo Chamber Multi-Agent Topologies

Multiple agents can share the same mistaken premise, training biases, retrieved evidence, or tool output. Debate may improve some tasks, but agreement is not independent verification. Require evidence provenance and an external check—such as a compiler, database constraint, deterministic calculation, or independently sourced fact—before treating consensus as correctness.

Background: Du et al., “Improving Factuality and Reasoning in Language Models through Multiagent Debate”
The Deterministic Control Plane Workflow Architecture

Reduce unnecessary model calls by replacing predictable reasoning with ordinary code. Put each remaining model call behind typed input/output contracts, validators, bounded retries, deadlines, token budgets, and explicit state transitions. Use idempotency keys for side effects, audit the evidence used, and provide compensation or rollback paths where possible. Deterministic orchestration makes execution governable; it does not make model-generated content inherently correct.

5. Semantic Correctness: Measurable Acceptance and LLM-as-a-Judge

The Intuition: “Zero Hallucinations” Is Not a Test

A finite audit can bound an error rate but cannot show that it is zero, and “hallucination” is undefined until a task says what counts as wrong. Production acceptance should be a set of measurable conditions, each with a check and a reported error rate with its uncertainty. Some conditions are invariants that code enforces exactly, where a zero-tolerance rule is meaningful because a control enforces it; the rest are statistical and are reported as bounded rates. This article owns the reliability mechanics; the taxonomy of semantic wrongness belongs to the companion article on semantic wrongness.

Reporting an Observed Error Rate

For \(n\) independently sampled audited outputs with \(x\) failing the acceptance conditions, report \(\hat{e} = x/n\) with an interval. The Wilson 95% interval (\(z \approx 1.96\)) behaves well at small \(n\) and rates near zero; when \(x = 0\), the one-sided 95% upper bound is \(1 - 0.05^{1/n} \approx 3/n\):

\[ \text{CI}_{\text{Wilson}} = \frac{\hat{e} + \dfrac{z^2}{2n} \pm z\sqrt{\dfrac{\hat{e}(1-\hat{e})}{n} + \dfrac{z^2}{4n^2}}}{1 + \dfrac{z^2}{n}} \]
Worked example (illustrative): An audit of \(n = 400\) randomly sampled outputs finds \(x = 8\) failures: \(\hat{e} = 2.0\%\), Wilson 95% interval about \(1.0\%\) to \(3.9\%\). An audit of \(n = 300\) with \(x = 0\) bounds the rate at about \(1 - 0.05^{1/300} \approx 0.99\%\) (95%, one-sided); it does not show the rate is zero. Assumptions: random sampling from the production population, stratified by tenant and task class; the interval describes the audited period, not future drift (Part 7).

Calibrating an LLM Judge

A judge that scores factual support or task acceptance is itself a stochastic classifier with false positives (\(\alpha_{\text{fp}}\): passes a wrong output) and false negatives (\(\beta_{\text{fn}}\): fails a correct one), so the dashboard pass rate is not the true pass rate. If the true pass rate is \(p_{\text{true}}\), the observed rate is:

\[ p_{\text{obs}} = p_{\text{true}}(1 - \beta_{\text{fn}}) + (1 - p_{\text{true}})\alpha_{\text{fp}} \]

Solving gives the Rogan–Gladen correction, valid when \(\alpha_{\text{fp}} + \beta_{\text{fn}} < 1\) and the estimate is clipped to \([0, 1]\):

\[ \hat{p}_{\text{true}} = \frac{p_{\text{obs}} - \alpha_{\text{fp}}}{1 - \alpha_{\text{fp}} - \beta_{\text{fn}}} \]
Worked example (illustrative): A labelled regression suite estimates \(\alpha_{\text{fp}} = 0.05\) and \(\beta_{\text{fn}} = 0.10\). With \(p_{\text{obs}} = 0.80\), \(\hat{p}_{\text{true}} = (0.80 - 0.05)/(1 - 0.05 - 0.10) = 0.75/0.85 \approx 88.2\%\). The error rates are estimates too: if they came from 10 false passes in 200 known-bad items and 20 false fails in 200 known-good items, their Wilson 95% intervals are about 2.7%–9.0% and 6.6%–14.9%, and the corrected rate spans roughly 84%–94% rather than a point value. Assumptions: error rates are the same across the populations being scored, and judge errors are not correlated with generator errors; a judge from the same model family can share the generator's blind spots, so calibrate on stratified labelled sets and keep deterministic checks for anything checkable exactly.

The Final Reality: Constrain the Stochastic Core

Across all eight parts of The Shape of Failure, one engineering truth has remained constant: production outages happen in the gap between convenient mathematical assumptions and physical system boundaries. Whether you are sizing a distributed cache in Part 1, surviving a retry storm in Part 6, or orchestrating an LLM agent in Part 8, a probability distribution is a diagnostic lens, never a guarantee.

The Architect's Rule for AI Systems: Isolate stochastic models to the narrow semantic tasks that genuinely require them. Surround every model invocation with deterministic code for routing, arithmetic, authorization, schema validation, token-budget admission control, and idempotent state transitions. Measure end-to-end semantic task completion (\(E_{\text{task}}\)), not just HTTP 200 serving reliability (\(E_{\text{serve}}\)). The AI proposes; the deterministic control plane validates what can be checked exactly, authorizes side effects, and reports a measured error rate, with its uncertainty, for what cannot.
