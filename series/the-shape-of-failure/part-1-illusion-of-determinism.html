The Shape of Failure · Part 1 of 8

The Illusion of Determinism

Model uncertainty before turning reliability targets into architecture and FinOps decisions

October 17, 2026 · Probability, Queues & Distributed Systems

“If you measure latency using an average, you are measuring the average temperature of the hospital to see if an individual patient is dead.”

— Gil Tene, How NOT to Measure Latency

Every distributed system is, underneath the YAML, RPC stubs, dashboards, and suspiciously clean architecture diagrams, a machine operating under uncertainty.

Requests arrive unevenly. Payloads vary by orders of magnitude. Queues accumulate silently between polling intervals. Downstream dependencies stall. Hardware fails unevenly. Retries synchronize into destructive pulses. Tenants exhibit radically different traffic profiles.

Components assumed to be independent on a whiteboard turn out to share a rack, power domain, top-of-rack switch, hypervisor, control plane, DNS resolver, identity service, or deployment pipeline.

The difficult problem in distributed systems is not merely failure; it is the shape of failure.

Two systems can exhibit identical average latency, identical average CPU utilization, and identical nominal availability while possessing radically different probabilities of catastrophic collapse. One system has relatively thin tails. The other behaves normally for weeks, then produces an exceedance event large enough to consume an entire quarterly error budget in minutes.

The averages are identical. The engineering problems are not.

The recurring architecture

We will use one recurring example throughout this series: a Multi-Tenant Analytics Gateway—stateless DuckDB and Apache Arrow query workers reading Apache Iceberg tables over object storage, with Redis metadata caching and multi-AZ routing.

It is a useful architecture because it contains several sources of uncertainty: cache hits and misses, tenant skew, variable query sizes, queueing, retries, shared dependencies, and expensive tail events.

Evidence discipline: Published research and production guidance are distinguished from illustrative calculations. An illustrative model is not an industry benchmark, and a plausible equation is not proof that production behaves that way.

1. The intellectual spine: model before prescribing

The central question

Do not ask only: "What is the average?"

Ask:

"What process produced this observation? What random variable am I measuring? What assumptions does my model make? What evidence could falsify those assumptions? And what architectural decision changes if the assumptions are wrong?"

The engineering workflow
Observed Telemetry → Physical Mechanism → Random Variable → Assumptions → Candidate Model → Validation → Architectural Control

This is the opposite of statistical cargo-culting:

The anti-pattern
Incident ⇏ Textbook Distribution ⇏ Prescribed Architecture

A log-normal distribution is not a timeout policy. A Poisson process is not a capacity plan. A Weibull curve is not a maintenance strategy. Those are models. The engineering decision is a separate step.

Five tests for a useful model

  1. Mechanistically plausible: Does it reflect the actual execution path and physical constraints?
  2. Empirically defensible: Does it describe the observed distribution, including relevant tail quantiles, on out-of-sample data?
  3. Decision-relevant: Does it estimate the quantity that drives the decision—timeout, queue capacity, headroom, or failure probability?
  4. Robust to model error: Does the system degrade safely when reality deviates from the fitted model?
  5. Monitorable: Can telemetry detect when the workload or operating regime changes?

A distribution is a model, not a fact

A metrics collector records timestamps, counters, and durations. It does not attach labels saying THIS REQUEST = LOG-NORMAL.

Those labels are hypotheses imposed by engineers. Production systems combine state machines, stochastic traffic, temporal dependence, common-cause failures, nonlinear feedback loops, regime changes, and hard physical limits.

The useful question is not "Which distribution does this metric follow?" It is "Which model is sufficiently accurate for the decision I need to make?"

2. A latency histogram can hide two different systems

Worked Scenario A: Cache mixtures, tail latency, and timeout decisions

Gateway timeout sizing · Illustrative analytical model Reproducible calculation

The trap: fitting one curve to two execution paths

Consider a query gateway. Some requests are served from a warm cache. Others miss the cache and have to fetch object-store data, inspect Iceberg manifests, or perform additional metadata work.

Those are not simply fast and slow versions of the same operation. They are different execution paths.

  • Cache-hit path: 85% of requests complete at approximately 18 ms.
  • Cache-miss path: 15% of requests complete between 100 and 300 ms. For this deliberately simple example, assume a uniform distribution.

Let \(X\) be request latency in milliseconds. The illustrative model is a mixture:

$$X = \begin{cases} 18, & \text{with probability } 0.85\\ U(100,300), & \text{with probability } 0.15 \end{cases}$$

The uniform miss distribution is a teaching assumption, not a claim that object-store latency is truly uniform. Its advantage is that every calculation is transparent and reproducible.

Calculate the mean—and notice what it hides

The expected latency is the weighted mean of the two paths:

$$\mathbb{E}[X] = 0.85(18) + 0.15(200) = 45.3\text{ ms}$$

Now notice the awkward result: the average is 45.3 ms, but neither execution path normally completes near 45.3 ms.

The average describes the combined traffic. It does not describe what an individual request experiences.

Calculate the actual percentiles

The cumulative distribution function is:

$$F_X(x)= \begin{cases} 0, & x < 18\\ 0.85, & 18 \leq x < 100\\ 0.85+0.15\left(\frac{x-100}{200}\right), & 100 \leq x \leq 300\\ 1, & x > 300 \end{cases}$$

Because 85% of requests are already at 18 ms, the median is 18 ms. But every percentile above 85% falls into the miss population.

For \(p > 0.85\), invert the CDF:

$$Q(p)=100+200\left(\frac{p-0.85}{0.15}\right)$$
Metric Value Interpretation
Mean 45.3 ms Weighted average across both paths.
p50 18 ms Median request is a cache hit.
p95 233.3 ms Falls inside the cache-miss population.
p99 286.7 ms Deep inside the miss population.
p99.9 298.7 ms Close to the upper end of the assumed miss range.
Important correction

With 85% of requests at 18 ms and all misses between 100 and 300 ms, the p95 cannot be 95 ms. The p95 must be inside the miss population and is 233.3 ms under this model.

A percentile table must be consistent with its stated data-generating process. If real telemetry says otherwise, either the workload assumptions or the model need to change.

Variance: the mixture has a cost of its own

The variance of a mixture contains two components:

$$\mathrm{Var}(X)= \underbrace{\sum_i w_i\sigma_i^2}_{\text{within-path variance}} + \underbrace{\sum_i w_i(\mu_i-\mu)^2}_{\text{between-path variance}}$$

For this example, the hit path has zero variance because it is represented by a fixed 18 ms value. The uniform miss path has:

$$\mathrm{Var}(U(100,300))=\frac{(300-100)^2}{12} =3333.33\text{ ms}^2$$

The total variance is:

$$\begin{aligned} \mathrm{Var}(X) &=0.15(3333.33) +0.85(0.15)(18-200)^2\\ &\approx4723.31\text{ ms}^2 \end{aligned}$$ $$\sigma_X \approx68.73\text{ ms}$$

Most of the variance comes from the difference between execution paths—not merely the variation within each path. That is why segmentation matters.

Production case study: the cold-cache rollout

Now deploy a new worker fleet. The workers start with cold local caches, so the hit ratio falls from 85% to 30%. Keep the same conditional path latencies for the moment to isolate the effect of changing the mixture weights.

The new mean is:

$$\mathbb{E}[X_{\text{cold}}] =0.30(18)+0.70(200)=145.4\text{ ms}$$

The median now falls inside the miss population:

$$Q(0.50)=100+200\left(\frac{0.50-0.30}{0.70}\right) \approx157.1\text{ ms}$$

The resulting comparison is:

Metric Warm cache (85%) Cold cache (30%)
Mean45.3 ms145.4 ms
p5018 ms157.1 ms
p95233.3 ms285.7 ms
p99286.7 ms297.1 ms
p99.9298.7 ms299.7 ms

The mean more than triples. The median moves from 18 ms to 157.1 ms. Yet the p99 changes by only about 10.5 ms.

Why? The p99 was already deep inside the slow population. Changing the mixture weight moves the median dramatically, but cannot move the conditional miss distribution beyond its own 300 ms upper bound.

Production caveat: this calculation changes only the mixture weight. In a real rollout, the additional miss traffic may also increase object-store, metadata, network, and worker contention. That changes the conditional miss distribution itself. Measure both the path proportions and each path's latency.

What should an architect do?

  • Segment the telemetry: record cache_state, tenant_tier, query_class, payload size, and worker version.
  • Warm caches deliberately: use controlled prewarming or gradual traffic shifting when cold-cache performance threatens the service objective.
  • Use progressive rollouts: compare cache-hit ratio and conditional miss latency across old and new worker fleets.
  • Keep admission control: prevent a sudden increase in expensive cache misses from overwhelming the query-worker pool.
  • Preserve the distinction: a changing mixture weight and a slower miss path are different operational problems.

The solution. Model distinct execution paths separately. Use empirical conditional percentiles for each path, monitor mixture weights, and make cache warm-up and rollout policies explicit architectural controls.

3. Timeouts do not make unfinished work disappear

Worked Scenario B: Timeout censoring and zombie work

Deadline design · Observability and cancellation Illustrative calculation

The difference between a slow request and an observed timeout

Suppose the gateway configures a downstream timeout at approximately 298.7 ms—the theoretical p99.9 in our warm-cache example.

Under the model, approximately 0.1% of requests exceed that threshold:

$$1{,}000{,}000 \times 0.001 = 1{,}000 \text{ requests per million}$$

That does not mean 1,000 requests are necessarily broken. Some may be legitimate queries that would have completed at 299 ms or slightly later.

There is a subtle measurement problem here. If the gateway stops waiting at time \(T\), the measured client-side duration becomes:

$$Y=\min(X,T)$$

For a timed-out request, the true completion latency \(X\) is unknown. We know only that it exceeded \(T\), assuming the timeout was triggered by elapsed time rather than another failure condition. This is a right-censored observation.

If a metrics pipeline records every timeout as an ordinary completed observation at exactly \(T\), the resulting histogram does not describe the true completion-time distribution. It describes a mixture of completed requests and observations truncated by the timeout policy.

Three events that must not be confused

Event What happened? What to record
Client timeout The caller stopped waiting. Deadline, timeout reason, elapsed time.
Backend cancellation The worker acknowledged cancellation and stopped. Cancellation request and acknowledgement times.
Late completion The backend continued and eventually completed. Actual completion time and abandoned-work duration.

The zombie-work problem

Imagine a gateway times out a query at 300 ms but does not cancel the DuckDB operation. The client retries immediately. The original query and its retry now consume resources at the same time.

The gateway believes it has rejected the slow request. The worker pool sees two jobs.

Multiply that behavior across tenants and repeated retries, and a timeout policy intended to protect the system can increase the load on the very dependency that is struggling.

Engineering controls

  • Propagate deadlines: pass the remaining caller budget to downstream services rather than assigning each hop a fresh timeout.
  • Propagate cancellation: connect caller cancellation to the query engine's supported interruption mechanism, and verify that the worker actually stops.
  • Measure censored outcomes separately: do not silently treat timeout duration as actual completion latency.
  • Measure cancellation lag: record the time between cancellation request and worker acknowledgement.
  • Control retries: avoid immediate retries for operations whose previous execution may still be running.

The solution. A timeout is a caller-side decision, not proof that backend work stopped. Measure completion, cancellation, and abandonment separately. Use deadline propagation and cancellation acknowledgement as first-class operational signals.

5. Other ways the deterministic story breaks

The cache example demonstrates one important lesson: a single average can conceal distinct populations. Distributed systems introduce several other mechanisms that make deterministic capacity narratives unreliable.

Queueing: utilization is not a linear dial

Preview of Part 3 · Queueing physics

A worker that takes 10 ms to process a request has a nominal service capacity of 100 requests per second. That does not mean operating it at 99 requests per second is a sensible capacity plan.

For a single-server GI/G/1 queue, Kingman's approximation estimates mean queue waiting time:

$$W_q \approx \left(\frac{c_a^2+c_s^2}{2}\right) \left(\frac{\rho}{1-\rho}\right)\mathbb{E}[S]$$

Assume \(c_a^2=c_s^2=1\) and mean service time \(\mathbb{E}[S]=10\) ms:

Utilization Mean queue wait Mean total time
50%10 ms20 ms
80%40 ms50 ms
90%90 ms100 ms
95%190 ms200 ms

This is a single-server approximation for mean waiting time, not a p99 predictor or a multi-server worker-pool formula. It illustrates why headroom and bounded queues matter.

Architectural implication: measure queue wait separately from service execution, apply admission control, and avoid designing around sustained near-100% utilization.

Developed in Part 3. Arrival variability, service-time variability, Little's Law, and multi-server queue behaviour.

Redundancy: two replicas are not necessarily two independent risks

Preview of Part 2 · Reliability and common causes

If each of two replicas has a 1% failure probability and failures are independent, simultaneous failure probability is:

$$0.01 \times 0.01 = 0.0001 = 0.01\%$$

But suppose a shared dependency has a 0.2% probability of disabling both replicas. Let each replica also have a 1% conditional residual failure probability when that shared dependency is healthy.

$$P(\text{both fail}) = q+(1-q)p^2$$ $$=0.002+(0.998)(0.01)^2=0.0020998$$

That is approximately 0.21%, substantially higher than the independent baseline of 0.01% using the conditional residual probability.

The point is not that every deployment has a 0.2% shared failure probability. The point is that replica count alone does not establish independence.

Architectural implication: map shared dependencies and failure domains. Test correlated failures, not just individual process termination.

Developed in Part 2. Reliability models, common-cause failures, redundancy, retry budgets, and recovery behaviour.

Fan-out: a rare slow child becomes a common parent delay

Preview of Part 4 · Aggregation and extreme tails

Suppose a query fans out to 100 independent shards. Each shard has a 1% probability of exceeding a deadline. If the parent must wait for every child, the probability that at least one child is slow is:

$$P(\text{at least one slow child}) =1-(1-0.01)^{100}$$ $$\approx63.4\%$$

A 1% child-level slow probability becomes a 63.4% chance of at least one slow child in a 100-way fan-out, under the independence assumption.

Real shards may be correlated, which can make the independence calculation misleading in either direction.

Architectural implication: bound fan-out, understand aggregation semantics, and use hedging only for eligible idempotent work when spare capacity exists.

Developed in Part 4. Order statistics, tail amplification, and extreme-value modelling.

6. Uncertainty: know what more data can and cannot solve

Not all uncertainty is the same. Treating it all as generic noise leads to flawed architecture.

Class Underlying mechanism Can more data help? Engineering response
Aleatory Intrinsic workload or physical randomness. More data improves estimates, but does not remove the randomness. Headroom, admission control, isolation, and graceful degradation.
Epistemic Incomplete knowledge or sparse observations. Often. Better instrumentation and experiments can reduce it. Canaries, shadow traffic, controlled experiments, and confidence intervals.
Model risk Incorrect structural assumptions. Only if observations and experiments are used to challenge the assumptions. Out-of-sample validation, stress testing, and alternative models.

Faults are not probability distributions

Crash, omission, timing, and Byzantine behaviour describe fault semantics—how systems fail. They are not statistical distributions.

  • Crash: a process halts. Use health detection, safe restart, and fencing where stale actors could mutate state.
  • Omission: a message or packet is lost. Use idempotency, sequence tracking, and durable delivery patterns.
  • Timing: a correct response arrives too late. Use deadlines, cancellation, and explicit status reconciliation.
  • Byzantine: a participant behaves arbitrarily or inconsistently. Use protocol-specific fault tolerance, integrity checks, and cryptographic verification where appropriate.

Do not assign a textbook curve to a fault class without first defining the random variable and validating the mechanism.

7. Availability is a business decision, not a badge collection

A target of five nines permits approximately 5.256 minutes of downtime in a 365-day year. That is a useful constraint, but it does not automatically prescribe multi-region deployment, active-active replication, or any other architecture.

There is no universal industry curve that says five nines costs exactly 80 times as much as two nines. The cost depends on the workload, failure domains, data-loss objectives, recovery requirements, staffing, and business impact.

Worked Scenario: Is a reliability investment worth it?

Business-impact model Deterministic cost-avoidance calculation

Suppose an API targeting 99.99% availability currently experiences 40 minutes of downtime per year. A proposed mitigation reduces that to 15 minutes. The annualized engineering and infrastructure cost is $90,000, and the estimated business impact is $5,000 per minute.

$$\begin{aligned} \text{Net annual value} &=(40-15)\times \$5{,}000-\$90{,}000\\ &=+\$35{,}000 \end{aligned}$$

For these stated inputs, the investment has positive deterministic cost avoidance. This is not yet a full expected-loss model: that would also account for incident frequency, severity distributions, uncertainty in loss rates, and the chance that the mitigation itself fails.

8. The production decision framework

The objective is not to collect distributions like trophies. It is to select a model that helps make a specific engineering decision—and to know when that model has stopped being useful.

Method Random variable Assumptions Validation Engineering control
Empirical quantiles Request latency by path Representative, correctly classified observations. Compare held-out p50/p95/p99; inspect sample size and censoring. Per-class deadlines, cancellation, and capacity headroom.
Mixture models Latency across distinct execution paths Path classification and conditional distributions are meaningful. Validate path weights and conditional quantiles independently. Cache warming, routing, workload isolation, and progressive rollout.
Queueing models Queue wait and in-flight work Arrival and service assumptions are sufficiently representative. Compare measured queue wait with the model under controlled load. Bounded queues, admission control, and concurrency limits.
Extreme Value Theory Tail exceedances above threshold Threshold stability and dependence treatment are defensible. Stability plots, uncertainty intervals, and held-out stress tests. Tail capacity, bulkheads, and load shedding.
Reliability models Component and joint failure events Failure domains and dependence are explicitly modelled. Dependency audits, fault injection, and recovery tests. Isolation, independent recovery paths, and redundancy.
Reusable checklist · From telemetry to an engineering decision
  1. Define the decision and random variable. State exactly what you are configuring and what is being measured.
  2. Collect stratified telemetry. Capture tenant, query class, cache state, payload size, queue wait, service time, retries, and cancellation outcomes.
  3. Select a model from the mechanism. Use empirical quantiles, mixture models, queueing models, or reliability models only when their assumptions fit.
  4. Try to falsify the assumptions. Inspect out-of-sample errors, temporal dependence, sample size, regime changes, and censored observations.
  5. Translate the result into a control. Use bounded queues, deadlines, admission limits, retry budgets, or isolation.
  6. Monitor for model drift. Revisit the model when deployments, workload composition, dependencies, or topology change.

9. The shape of failure is an engineering decision

Probability does not replace engineering judgement. It makes the assumptions behind that judgement visible.

A model can be mathematically elegant and operationally useless. A fitted distribution can describe last month's traffic and fail after a deployment changes the cache-hit ratio. A timeout can protect the caller while leaving expensive work running in the background. A replica count can look reassuring while every replica shares the same failure domain.

The discipline is to connect the measurement to the mechanism, the mechanism to a model, and the model to a control that remains safe when the model is wrong.

That is the real purpose of this series: not to turn architects into distribution collectors, but to make uncertainty something they can reason about, test, and design around.
