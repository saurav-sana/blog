64 Production Inference Is More Than "Put a Model on a GPU"

At this point in the series, we have a "working" inference service. You wrap a model in a FastAPI shell, shove it into Kubernetes, point vLLM at a GPU, and text streams back.

Client → Gateway → Kubernetes → vLLM → GPU → Tokens

That is enough for a demo. It is enough to trick a Product Manager who doesn't know any better.

It is nowhere near enough for production. A production system needs a bouncer. It needs a layer around the inference engine that decides, before a single byte reaches the GPU, whether this client deserves to consume the most excruciatingly expensive resource in your corporate estate.

It is where you stop a $40,000 piece of hardware from becoming the victim of a malformed $0.0001 HTTP request.

65 The Pre-Inference Layer

Before a request reaches a GPU, the platform must answer four questions:

  • Is the caller allowed? (Authentication, authorization, tenant identity).
  • Is the request legal? (Payload size, model access, context window bounds).
  • Can we afford it? (Estimated input tokens, max output tokens, tenant budget).
  • Can the platform serve it? (Queue depth, active sequences, KV-cache pressure).

Only then do you decide: Should it be admitted?

That last question is the difference between active capacity management and "Jesus take the wheel."

Rule 1 of Inference

Relying on the Linux OOM (Out Of Memory) killer for capacity planning is like using a landmine as a speedbump. It works exactly once, and it leaves a massive mess.

66 Guardrails Before the GPU

A guardrail is a constraint that prevents a request from creating unacceptable operational or financial consequences. Think of it as concentric circles of paranoia.

guardrails.yaml
guardrails:
  max_input_tokens: 16000
  max_output_tokens: 4096
  max_total_tokens: 20000

tenant:
  max_concurrent_requests: 20
  max_tokens_per_minute: 100000

global:
  max_queued_requests: 5000

These numbers are examples. The correct values come from your workload, your SLO, and how much you hate waking up at 3 AM to manually reset a frozen node.

67 Tokens Are Resource Limits

For a standard REST API, request payload size is a decent approximation of resource cost. For an LLM, tokens are the true resource approximation.

RequestPayload SizeActual Infrastructure Cost
A2 KBSmall prefill phase, trivial KV cache allocation.
B2 MB (Codebase)Catastrophic prefill, massive KV allocation, memory squatting until the heat death of the universe.

Therefore, your API Gateway cannot just be a dumb pipe. A request should not simply say POST /generate and disappear into the void. The control plane must calculate: "This request could consume 18K input tokens and up to 4K generated tokens."

68 Rate Limiting & Concurrency

A single 100 requests/sec rate limit is spectacularly useless for LLMs. You must rate-limit the dimensions that actually cost blood and treasure.

DimensionProtects
Requests Per Min (RPM)Control plane, gateway routing, authentication systems.
Input Tokens / Min (ITPM)Prefill compute boundary and initial KV cache allocation.
Output Tokens / Min (OTPM)Sequential decode compute, sustained memory bandwidth limits.
Concurrency (C)Active sequences, scheduler slots, and absolute VRAM footprint.
Spend ($)Your job, the company's runway.

69 The Token Bucket

A useful mechanism is a token bucket. For inference, a tenant receives a token budget: say, 100,000 input tokens / minute. Every request consumes estimated_input_tokens. If the bucket cannot cover the request, you return a 429 or route to a lower-priority garbage tier. This is much more meaningful than slapping them with a 429 because they sent 100 empty payloads.

70 Concurrency Is Memory Control

Rate limiting controls arrival rate. Concurrency controls the number of requests simultaneously squatting in VRAM. Without concurrency limits, your GPU becomes a subsidized housing project for zombified requests.

Long requests → More active sequences → More KV Cache → Less Memory → Latency Spike

Enforcing concurrency is effectively enforcing Little's Law physically on the GPU scheduler.

71 Economics: Pre-Flight Cost Estimation

Before submitting a request, estimate its maximum possible cost. If you are using a hosted API (OpenAI, Anthropic, Gemini), the math is trivial:

Costreq = (InputTokens / 1M) · Pin + (OutputTokens / 1M) · Pout

But if you are self-hosting your inference platform, the cost per token is entirely derived from hardware utilization:

Costtoken = GPU hourly cost / (3600 × useful tokens/sec)

And there is the catch. Real infrastructure rarely runs at 100% useful utilization. It runs closer to 30%, while your CFO hyperventilates.

76 Why Input ≠ Output Tokens

Input and output are not symmetric workloads. Input processing (Prefill) is highly parallelizable and compute-bound. Output generation (Decode) is strictly sequential and entirely memory-bandwidth bound.

Therefore, 1M input tokens does not incur the same infrastructure cost as 1M output tokens. This is why commercial providers charge radically different rates for them.

77 Prefix Caching Effects

If you have a 10K-token system prompt and a 500-token user question, recomputing the system prompt every time burns 10,500 tokens of compute. Reusing it from a Radix Tree KV cache burns 500 tokens of compute.

Caching isn't merely a latency optimization. It is a cost optimization.

79 The Self-Hosted Break-Even Equation

To accurately compare self-hosting against a managed API, you cannot just look at the $5/hour sticker price of a GPU. You must use the fully-loaded cost equation:

NGPU·CGPU/hr + CCPU + Cmem + Cstorage + Cplatform Ctoken = ───────────────────────────────────────────────────────────── Tokensgenerated × Availability × SLO-compliance

A system that produces 1 Billion tokens, but delivers half of them after the Time-To-First-Token (TTFT) SLO expires, is not cheaper. It is just a highly optimized engine for disappointing users.

82 Real-World Architecture Implementations

We don't have to guess how to build this; we can steal the homework from the providers. While no one publishes their exact source code, public engineering disclosures reveal a remarkably consistent architecture.

  • OpenAI: Has previously detailed global routing by geography, intra-cluster routing based on KV-cache locality, and speculative decoding to increase token-generation efficiency by double digits.
  • Google Gemini: Employs explicit workload tiering (Standard, Priority, Batch processing) and separate pricing for cached vs. uncached input tokens, directly reflecting the compute realities discussed in Section 77.
  • DeepSeek: In DeepSeek-V2 and V3, they explicitly attacked the memory bottleneck with Multi-head Latent Attention (MLA), massively compressing the KV cache footprint to fit larger batches onto fewer GPUs.
  • Anthropic: Treats the inference server as a strict security boundary, isolating trusted model weights and invokers from untrusted routing/API layers.

87 The Optimization Hierarchy

When the platform becomes too expensive, engineers instinctively want to buy newer hardware. Do not do this. Optimize in this strict order:

LevelLeverAction
1Avoid WorkSemantic caching, prompt truncating, fixing duplicate API calls.
2AdmissionEnforce strict concurrency and rate limits to protect the queue.
3SchedulingImplement Continuous Batching (vLLM) and chunked prefill.
4MemoryPagedAttention, KV Cache prefix sharing, quantization (FP8).
5ComputeSpeculative decoding, optimized CUDA/Triton kernels.
6RoutingLoad-aware, cache-aware, geographic routing.
7ScaleAdd more GPUs. (Notice this is last).

87.5 Continuous Batching Internals

Static batching treats a group of requests as a single unit: they start together and the GPU waits for the slowest sequence to finish before the next batch can begin. That works for training. It is a disaster for interactive LLM traffic, where output lengths vary by orders of magnitude.

Continuous batching (iteration-level scheduling) changes the unit of scheduling from the request to the forward pass. The scheduler regains control after every model step, evicts finished sequences, admits new ones, and rebuilds the batch. The GPU almost never sits idle.

continuous-batching-loop
while True:
    scheduled = scheduler.step(running, waiting, kv_budget)
    outputs = model.forward(scheduled)  # one iteration
    
    for seq in scheduled:
        append_token(seq, sample(outputs[seq]))
        if finished(seq):
            free_kv_blocks(seq)
            return_to_client(seq)
            
    admit_new_requests_into_freed_slots()
“If your first optimization is buying more GPUs, eventually someone else will optimise the software and make your hardware purchase look like a charitable donation to NVIDIA.”

This relies entirely on PagedAttention. Naïve contiguous KV-cache allocation cannot support continuous batching without brutal fragmentation. PagedAttention treats the KV cache like virtual memory: fixed-size blocks (commonly 16 tokens), allocated on demand. Blocks are freed the moment a sequence finishes and can be reused by a newly admitted request in the very same iteration.

Furthermore, because long prefills (compute-bound) stall active decodes (memory-bound), chunked prefill is the standard mitigation. The scheduler splits a long prompt into smaller token chunks and interleaves them with ongoing decode steps to prevent head-of-line blocking.

88 Speculative Decoding & Amdahl's Law

Speculative decoding uses a tiny draft model to quickly guess tokens, which the massive target model verifies in parallel. But how much does this actually speed up your system? Enter Amdahl's Law:

If generating tokens is only 60% of your system's latency (because networking, guardrails, and prefill take 40%), making decoding infinitely fast will only yield a 1.6x overall speedup. Math sets a hard ceiling on hype.

92 The Cold Start Delusion & Enterprise Policy

If you look at idle GPU costs and announce, "We'll just auto-scale pods to zero!", you are lying to yourself. Auto-scaling a 40GB weights file into VRAM takes minutes. By the time your node is ready, the user has closed the tab.

Instead, implement priority classes (P0, P1, P2) as documented in our internal runbooks:

P0 (Interactive Chat) → Strict SLO, reserved capacity. P1 (Standard API) → Shared capacity. P2 (Batch Processing) → Preemptible, runs only on idle GPUs to push utilization to 90%.

97 Can You Prove It? Formal Verification with TLA+

Everything above is a design argument. But in a distributed system, arguments don't prevent deadlocks. We assert that "A GPU is never over-committed on KV cache" and "No tenant exceeds their budget."

Unit tests only check the happy path. To prove the admission controller logic works, we must write a formal specification using TLA+ (Temporal Logic of Actions), allowing the TLC model checker to exhaustively explore the entire reachable state space.

LLMInferencePlatform.tla
------------------------------ MODULE LLMInferencePlatform ------------------------------
EXTENDS Naturals, Sequences, TLC

CONSTANTS GPUs,                 \* number of GPU workers
          MaxConcurrentPerGPU,  \* max concurrent sequences per GPU
          MaxQueueDepth,        \* global queue capacity
          MaxTokensPerRequest,  \* per-request token budget
          MaxCostPerTenant,     \* per-tenant budget
          ReservedGPUs,         \* GPUs reserved for P0 traffic
          Priorities,           \* {"P0","P1","P2"}
          Tenants, Requests

VARIABLES reqState, reqTokens, reqTenant, reqPriority, reqGPU,
          gpuActive, gpuKVUsage, gpuMaxKV, queue,
          tenantConcurrent, tenantTokensUsed, tenantSpend,
          totalAdmitted, totalRejected, totalCompleted

\* ... [Initialization and State mappings omitted for brevity] ...

CanAdmit(r) ==
    /\ reqState[r] = "queued"
    /\ reqTokens[r] <= MaxTokensPerRequest
    /\ tenantSpend[reqTenant[r]] + reqTokens[r] <= MaxCostPerTenant
    /\ Len(queue) < MaxQueueDepth
    /\ \E g \in 0..GPUs-1:
           /\ (reqPriority[r] = "P0" \/ g >= ReservedGPUs)
           /\ gpuActive[g] < MaxConcurrentPerGPU
           /\ gpuKVUsage[g] + reqTokens[r] <= gpuMaxKV[g]

Admit(r) ==
    /\ CanAdmit(r)
    /\ LET g == CHOOSE x \in 0..GPUs-1: (gpuActive[x] < MaxConcurrentPerGPU /\ gpuKVUsage[x] + reqTokens[r] <= gpuMaxKV[x]) IN
        /\ reqState'   = [reqState EXCEPT ![r] = "admitted"]
        /\ reqGPU'     = [reqGPU EXCEPT ![r] = g]
        /\ gpuActive'  = [gpuActive EXCEPT ![g] = gpuActive[g] + 1]
        /\ gpuKVUsage' = [gpuKVUsage EXCEPT ![g] = gpuKVUsage[g] + reqTokens[r]]
        /\ tenantSpend' = [tenantSpend EXCEPT ![reqTenant[r]] = tenantSpend[reqTenant[r]] + reqTokens[r]]
        /\ queue' = SelectSeq(queue, LAMBDA x: x # r)
        /\ UNCHANGED <>

\* Next state relation combines Enqueue, Admit, Preempt, Reject, Inference, Complete
Next == \/ \E r \in Requests: Admit(r) 
        \/ \E r \in Requests: CompleteInference(r)
        \* ...

We then define the Invariants—the properties the universe is not allowed to violate:

Invariants & Theorems
\* 1. No GPU ever exceeds KV cache capacity (The OOM Killer invariant)
NoKVCacheOverflow == \A g \in 0..GPUs-1: gpuKVUsage[g] <= gpuMaxKV[g]

\* 2. No tenant exceeds their budget
NoTenantBudgetViolation == \A t \in Tenants: tenantSpend[t] <= MaxCostPerTenant

\* 3. P0 Reserved Capacity is respected
ReservedCapacityRespected == \A r \in Requests:
    reqState[r] \in {"admitted","inference"} =>
        (reqGPU[r] < ReservedGPUs => reqPriority[r] = "P0")

THEOREM Safety == Spec => [](NoKVCacheOverflow /\ NoTenantBudgetViolation /\ ReservedCapacityRespected)

What the Model Checker Finds

If you write the budget check guard as tenantSpend[reqTenant[r]] < MaxCostPerTenant (checking before the request tokens are added, rather than after), the TLC model checker will spit out an error trace in seconds:

State 1: tenantSpend["A"] = 6 (Limit is 8. Guard passes: 6 < 8) State 2: Admit(r) where reqTokens = 4 tenantSpend'["A"] = 6 + 4 = 10 ← EXCEEDS MAX COST OF 8 Invariant NoTenantBudgetViolation is violated.

That trace is the formal mathematical proof that admission control must evaluate the state a transition leads to, not just the state it starts from. Unit tests miss this. Formal verification does not.

106 The Closing Argument

There are people whose job is to build and train models. That is a deep and highly specialized research discipline.

This article is about a different problem. The model already exists. Now someone has to make it run.

Someone has to put it behind an API. Someone has to provision GPUs. Someone has to calculate whether the KV cache fits. Someone has to decide whether 32K context is operationally sane. Someone has to build the queue. Someone has to enforce rate limits. Someone has to prevent one noisy tenant from consuming the entire fleet. Someone has to calculate cost per million tokens. Someone has to explain why GPU utilization is 97% but TTFT p99 is 8 seconds. Someone has to decide whether another GPU is actually the answer. Someone has to prove the admission controller can’t deadlock — or silently blow through a tenant’s budget. Someone has to survive the next traffic spike. Someone has to make Kubernetes do all of this without accidentally scheduling the world’s most expensive CronJob.

That person doesn't need to be an AI Researcher. They need to be an engineer.

Because once the model enters production, it obeys the same wonderfully inconvenient laws of physics as every other distributed system: memory is finite, bandwidth is capped, queues grow, and capacity costs money.

And eventually, someone gets paged at 3 AM. Spoiler alert: it's you.

That's not artificial intelligence.
That's engineering.
