The Monolith Crisis & The 95% Reality

Breaking the MPP Default and Validating the True Shape of Analytical Load

1. The Motivation: Trading One Bottleneck for Another

The journey away from massive monolithic architectures rarely starts with a clever insight. It usually starts with pain.

For years, our multi-tenant regulatory reporting platform ran on legacy OLTP databases. Without aggressive data purging, multi-tenant event data grew unchecked. Suboptimal indexing, rising volume, and heavy client search patterns eventually made the system both slow and expensive. UI response times collapsed, export pipelines timed out, and basic SLAs became aspirational.

To solve this, we executed the classic enterprise maneuver: a massive transformation project migrating our architecture from OLTP to a modern lakehouse. Real-time event streams were ingested continuously via Spark clusters directly into open table formats (Apache Iceberg), successfully achieving sub-200ms ingestion latency at the 95th percentile. On paper, it was a triumph. By centralizing everything into a single lakehouse, we completely bypassed the dreaded dual-store architecture—no more fragile CDC pipelines syncing operational data to analytical stores, and no more endless engineering tax of out-of-band reconciliation scripts trying to resolve data drift.

Then the hidden tax of real-time dashboards caught up with us.

While the lakehouse elegantly solved our ingestion and storage scaling bottlenecks, it created a severe serving mismatch. Because real users depended on real-time operational dashboards backed directly by the lakehouse, our Spark and MPP compute clusters had to remain powered on 24/7. We were forced to pay a massive baseline infrastructure cost simply to keep heavy, distributed compute idling, waiting for a user to click a dashboard filter or request a modest 50-row UI grid.

The architectural mismatch: the data was large, but an individual request was usually small. The platform was being sized for the first statement while users were paying for the second.

The architecture no longer failed operationally—it scaled smoothly with massive data ingestion. But the economics were entirely broken. When we audited the infrastructure, the raw cost of running a heavy distributed MPP system for small, repetitive point-reads simply could not be justified. We had solved data drift, but we had traded it for a cloud-compute billing inferno.

2. The Realization: The Four Laws of Operational Workloads

When we examined the actual query telemetry, a clear pattern appeared. Almost all traffic consisted of denormalized event-store reads, on-demand aggregations, and exports well under 100 GB.

At first we assumed this was unique to our platform. It wasn’t. The workload obeyed four durable laws of operational data access:

LAW 01

Temporal locality

Operational traffic is usually skewed toward recent partitions. “Last hour”, “last day”, and “last few weeks” are more common than arbitrary full-history scans. Partition pruning can therefore eliminate most of the physical data before execution begins.

LAW 02

Tenant and predicate locality

Serving requests commonly contain strong predicates: tenant, account, device, customer, region, or time window. A query against a petabyte lake is not necessarily a petabyte operation.

LAW 03

Bounded attention

Humans and APIs impose hard practical bounds. A dashboard may need 50 rows, an API may have a two-second budget, and an export endpoint may paginate. The result contract is often dramatically smaller than the underlying dataset.

LAW 04

Long-tail coexistence

The common path does not eliminate the long tail. A platform can have thousands of tiny requests and a few enormous joins at the same time. That argues for workload routing, not for pretending that MPP is obsolete.

The conclusion was unavoidable. We were paying for distributed compute designed for massive scans while almost all real traffic consisted of small, recent, tenant-specific slices. It was the architectural equivalent of using a sledgehammer to swat a fly — and then paying enterprise license fees for the sledgehammer.

3. The Validation: The 95% Reality in Numbers

Internal metrics are easy to dismiss. Public data is harder to ignore.

In 2024, analysis of the Amazon Redshift “Redset” dataset (via MotherDuck) showed the same shape we were seeing internally:

  • Big Data Queries Are Extremely Rare: A minuscule 0.03% of query volume exceeds 10 TB, accounting for just ~5.6% of total compute time.
  • Most Users Never Touch Big Data: Over 93% of users never exceed 10 GB in their largest query.
  • The Core Imbalance: Only 0.25% of queries scan more than 1 TB, yet those outliers consume 16.6% of the total elapsed time.

4. The Architectural Pathology of Legacy MPP: The "Fat Executor" Fallacy

If most analytical traffic is overwhelming small, why do so many teams still run 20–50 giant worker nodes with 128 GB of RAM?

The standard vendor answer is: “You need massive parallelism for large analytical joins.” That answer is only half true — and for operational workloads, it is the misleading half.

The real driver of the hardware footprint is not computational necessity. It is runtime survival, specifically the JVM Heap Tax.

The Anatomy of the JVM Heap Tax

Most foundational Big Data engines (Trino, Presto, Spark, and legacy enterprise query platforms) were built on the Java Virtual Machine. While Java offered exceptional developer velocity in the 2010s Hadoop era, its execution semantics are structurally hostile to high-concurrency, low-latency analytical serving:

  • Object Memory Bloat: Java objects carry headers, pointers, and padding. Storing tabular data this way routinely inflates memory usage by 3–6× compared with contiguous columnar formats such as Apache Arrow or Parquet.
  • Garbage Collection Stop-the-World Latency: When concurrent queries churn through millions of temporary intermediate tuples, the allocation rate in the JVM Eden space explodes. Even modern collectors (G1, ZGC, Shenandoah) produce pauses. A 500 ms–2 s GC pause may be tolerable for batch jobs; for interactive UIs or REST APIs it is an SLA violation.
  • The "Fat Executor" Defense Mechanism: Teams provision 128 GB instances not because the query needs that much math, but because operators must keep a large unallocated safety buffer simply to stop the garbage collector from tipping into long pauses or OOM kills. You are paying for RAM that exists as an insurance policy against the runtime.
  • The Shared-Memory Noisy Neighbor Catastrophe: All concurrent tenants share a single global JVM heap. One poorly scoped query from Tenant A can flood the heap, trigger GC pressure, and pause or kill the queries of every other tenant on that node. In a multi-tenant platform this is an unacceptable isolation failure.

The Scatter-Gather Penalty

Beyond memory, traditional MPP systems enforce a mandatory scatter-gather execution model. The coordinator breaks the query into stages, scatters fragments across networked workers, and later gathers results after a network shuffle.

For a 50-terabyte aggregation this overhead is a necessary cost. For a 50-megabyte tenant-scoped query it is pure waste. Scheduling, network setup, and serialization routinely cost far more than the actual vectorized computation.

Paying for that continuous, heavy hardware footprint to serve small, bounded reads is the true fat-executor fallacy.

5. MPP Landscape: Strengths, Trade-offs, and the Serving Gap

The previous version of this section described competing engines mainly through their weaknesses. That is unfair to the technology and weakens the thesis. These systems exist because they solve hard problems extremely well.

The useful comparison is therefore not “which engine is bad?” but:

What problem is each engine optimized to solve, and what happens when that execution model is used for high-frequency, bounded operational serving?

Trino / Presto Distributed SQL Federated SQL across object stores, databases, and catalogs; excellent for interactive exploration and large distributed scans. For a tiny API request, distributed planning and execution can be more machinery than the query needs. Shared clusters also require explicit resource governance under multi-tenant load. Excellent long-tail engine. Keep it for joins, broad scans, federation, and workloads whose parallelism amortizes its coordination cost. Docs

Per-query economics, startup/planning behavior, and repeated polling patterns can make them a poor fit for a very high-QPS synchronous serving path. The exact cost model depends on service and workload. Excellent for bursty, ad-hoc, and large analytical workloads where operational simplicity matters more than API-style tail latency.

The conclusion is deliberately boring: none of these systems is “the problem.” Each is optimized for a different region of workload space. The architectural mistake is using one execution model as the default for every region.

6. The Design North Star: What Must Be Built

The industry has spent two decades optimizing databases for the rare, large, complex query. Meanwhile, most real operational traffic remains small, local, and repetitive.

We do not need another distributed database. We do not need another proprietary warehouse. What we need is a different kind of layer entirely: a Smart Data Gateway — lightweight, stateless, application-aware, and optimized for the 95% case, while still able to hand the genuine long tail to a real MPP engine.

To succeed where legacy MPP platforms collapse, this gateway must be governed by four uncompromising architectural design goals:
