The Monolith Crisis & The 95% Reality

Characterizing Analytical Query Footprints and Defining the Operational Serving Boundary

1. The Motivation: Trading One Bottleneck for Another

The journey away from massive monolithic architectures rarely starts with a clever insight. It usually starts with pain.

For years, our multi-tenant regulatory reporting platform ran on legacy OLTP databases. Without aggressive data purging, multi-tenant event data grew unchecked. Suboptimal indexing, rising volume, and heavy client search patterns eventually made the system both slow and expensive. UI response times collapsed, export pipelines timed out, and basic SLAs became aspirational.

To solve this, we executed the classic enterprise maneuver: a massive transformation project migrating our architecture from OLTP to a modern lakehouse. Real-time event streams were ingested continuously via Spark clusters directly into open table formats (Apache Iceberg), successfully achieving sub-200ms ingestion latency at the 95th percentile. On paper, it was a triumph. By centralizing everything into a single lakehouse, we completely bypassed the dreaded dual-store architecture—no more fragile CDC pipelines syncing operational data to analytical stores, and no more endless engineering tax of out-of-band reconciliation scripts trying to resolve data drift.

Architecture Note: Table-Format Agnosticism & Ingestion Drivers

While this series implements the gateway pattern using Apache Iceberg, the gateway design itself is table-format agnostic. The architecture requires only two runtime primitives: a metadata parser capable of resolving snapshot manifests into Parquet split locations, and an embedded vectorized compute engine (such as DuckDB) to execute queries over those files.

Our production platform committed to Iceberg specifically because of our ingestion profile: high-velocity regulatory event streams with massive append throughput and virtually zero in-place updates. For teams evaluating storage formats, the choice depends heavily on mutation patterns, catalog independence, and engine diversity:

Format Primary Architecture Sweet Spot Best-Fit Workload Gateway / Embedded Serving Trade-Off

Then the structural overhead of operational dashboards caught up with us.

While the lakehouse elegantly solved our ingestion and storage scaling bottlenecks, it created a severe serving mismatch. Because operators and client consumers depended on real-time operational dashboards backed directly by the lakehouse, our Spark and MPP compute clusters had to remain powered on 24/7. We were forced to pay a massive baseline infrastructure cost simply to keep heavy, distributed compute idling, waiting for an interactive user to click a dashboard filter or request a modest 50-row UI grid.

The architectural mismatch: The underlying dataset was immense, but the individual interactive query was small. Distributed MPP architectures are optimized for batch throughput and massive parallel scans rather than high-concurrency, low-latency point queries. The platform was being sized for the former while users were paying for the structural coordination overhead of the latter.

The architecture did not fail operationally—it scaled smoothly with massive data ingestion. But the economics were deeply inefficient. Distributed query engines introduce structural execution overhead (coordinator plan generation, driver dispatch, distributed task scheduling, stage barrier synchronization, and state tracking) that makes sense when amortized across a 10 TB scan, but represents pure waste on bounded, sub-second reads. We had eliminated dual-store data drift, but we had traded it for a cloud-compute billing inferno.

2. The Realization: The Four Laws of Operational Workloads

When we examined our production query telemetry, a clear pattern appeared. Over 90% of interactive user requests were targeted reads against recent event partitions, tenant-scoped filters, and on-demand aggregations inspecting data well under 10 GB.

At first we assumed this was unique to our regulatory domain. It was not. Across production systems, interactive analytical access routinely adheres to four durable empirical properties:

LAW 01

Temporal locality

Operational traffic is heavily skewed toward recent partitions. Queries inspecting the "last hour", "current business day", or "trailing 30 days" vastly outnumber arbitrary full-history scans. Partition and manifest pruning can eliminate the vast majority of physical data before execution planning finishes.

LAW 02

Tenant and predicate locality

Serving requests commonly contain highly selective predicates: tenant LEI, account ID, device identifier, region, or explicit status codes. A query executed against a multi-petabyte lakehouse table is frequently a sub-gigabyte operation at physical evaluation time.

LAW 03

Bounded attention

Downstream consumers impose strict operational contracts. An interactive AG Grid UI requests a 50-row page, an API enforces a 500 ms SLA timeout, and an export endpoint paginates cursors. The final consumed result contract is orders of magnitude smaller than the underlying dataset.

LAW 04

Long-tail coexistence

The dominance of small operational queries does not eliminate the long tail. A single platform simultaneously experiences thousands of bounded reads alongside multi-terabyte cross-regulatory reconciliations. This demands a workload-aware routing tier, not a dogmatic claim that distributed MPP is obsolete.

Crucial Clarification: Disentangling Bytes Scanned from Execution Cost. Data scan volume is merely a first-order workload filter, not a complete proxy for query complexity. A 50 MB scan featuring unindexed cartesian joins, high-cardinality nested aggregations, or skewed window functions over millions of intermediate tuples can easily saturate executor CPU and memory far beyond a linear 100 GB sequential table scan over sorted Parquet blocks. Scan size indicates suitability for single-node execution, but plan topology determines whether it stays there.

The initial conclusion remained striking: we were running distributed clusters sized for worst-case shuffle joins to serve queries whose physical data footprint and computational graph fit comfortably within a single modern multi-core server.

3. The Validation: The 95% Reality in Numbers

Internal telemetry from a single enterprise platform can always be dismissed as domain-specific bias. However, large-scale fleet telemetry across production data warehouses corroborates this exact distribution.

In analyzed enterprise analytical workloads—most notably demonstrated in the published analysis of the AWS Redshift "Redset" corpus (Jordan Tigani / MotherDuck, 2024)—query volume is overwhelmingly dominated by small scans:

  • Small Scans Dominate Fleet Volume: Over 75% of submitted queries scan under 1 GB, and over 94% scan under 10 GB.
  • Individual User Workflow Footprints: Across the fleet, over 93% of active users never submit a query exceeding 10 GB in their largest single analytical invocation.
  • The Extreme Compute Imbalance: Queries scanning more than 1 TB represent only 0.25% of submitted volume, yet those extreme outliers account for 16.6% of cumulative compute time across the cluster fleet. Queries over 10 TB account for a minuscule 0.03% of volume.

The Engineering Reality of Pre-Aggregated Serving Tiers. Why do queries against petabyte lakes touch small volumes? Because sensible architectures do not scan raw bronze tables at serving time. However, pre-aggregating or maintaining denormalized gold tables introduces non-trivial architectural trade-offs: significant storage amplification (storing the same entity across bronze, silver, and gold states), heavy write amplification on high-frequency commit streams, continuous metadata compaction overhead in Iceberg table maintenance, and unavoidable data staleness windows. Balancing fast serving scans against pipeline write overhead is an architectural tension every platform must navigate.

4. The Architectural Pathology of Legacy MPP: The "Fat Executor" Fallacy

If the median operational query footprint is compact, why do enterprise data platforms universally provision clusters of 10 to 50 giant worker nodes with 64 GB to 256 GB of RAM?

The standard architectural justification is: "We need massive distributed memory and parallelism for complex join execution." While true for large batch jobs, applying this footprint universally introduces severe structural inefficiencies when serving high-frequency, bounded operational queries.

The Anatomy of Runtime Execution Overhead

Foundational distributed engines (Trino, Presto, Spark) were engineered on the Java Virtual Machine. While Java enabled rapid distributed systems engineering and rich connector ecosystems, executing high-concurrency, sub-second operational serving workloads introduces distinct runtime challenges:

  • Allocation Rates and Memory Pressure: Modern garbage collectors (G1, ZGC, Shenandoah) have evolved tremendously, routinely achieving sub-millisecond to single-digit millisecond pause times for steady-state workloads. However, when hundreds of concurrent operational queries churn through millions of temporary intermediate tuples per second, the JVM Eden allocation rate explodes. Under extreme allocation spikes, thread mutators can experience pacing delays, and CPU cycles are diverted from vectorized execution to memory reclamation.
  • Object Boxing and Off-Heap Cache Boundaries: In-memory Java representations carry object headers, pointer indirection, and 64-bit alignment padding. Boxed representations can expand columnar data memory footprints by 3× to 6× relative to dense contiguous formats like Apache Arrow. While modern engines rely extensively on off-heap memory allocators for row-pages and exchange buffers, crossing off-heap/on-heap boundaries introduces serialization and memory-copy overhead.
  • Noisy-Neighbor Heap Contention: In shared multi-tenant deployments, queries from multiple tenants execute concurrently across the same worker JVM process. If Tenant A issues an unconstrained aggregation that consumes disproportionate intermediate memory, the resulting memory pressure and cache eviction ripples across all co-located tenant threads on that node.

The Real Sizing Rationale for "Fat Executors"

It is tempting to claim that 128 GB+ worker nodes exist solely as defensive buffers against runtime overhead. In reality, large executor allocations are an engineering necessity for distributed analytical engines handling arbitrary SQL:

  • In-Memory Hash Join Tables: Building hash tables for high-cardinality broadcast or distributed shuffle joins requires substantial continuous memory.
  • Vectorized Sort and Window Buffers: Multi-column ordering and windowing functions require intermediate memory blocks to prevent pipeline stalls.
  • Columnar Block Caching: Allocating tens of gigabytes to executor-local disk and memory caches (e.g., Alluxio, local SSD block stores) accelerates repeated scans.
  • Spill Prevention: Preventing intermediate partitions from spilling to network-attached block storage (EBS) or NVMe scratch space is paramount, as out-of-core spilling degrades query execution times by an order of magnitude.

The dilemma is not that fat executors are ill-designed; it is that they are sized for the worst-case join, yet kept running 24/7 to serve lightweight, point-read operational traffic.

The Scatter-Gather and Coordination Penalty

Distributed engines are structurally bound to coordinated multi-stage execution plans. The coordinator parses the AST, resolves metadata catalog snapshots, analyzes partition stats, optimizes logical plans, splits tasks across workers, schedules network exchanges, and aggregates scattered results.

Modern Optimizations: To their credit, modern distributed engines incorporate sophisticated execution optimizations. Trino and Presto support dynamic partition pruning (DPP) and broadcast joins to minimize data movement. Spark's Adaptive Query Execution (AQE) dynamically coalesces shuffle partitions, handles data skew, and switches join strategies at runtime. When queries contain highly selective partition filters, coordinator planning can collapse execution to single-worker paths.

Yet even with these optimizations, the fixed coordination overhead—driver dispatch, network RPC handshakes, scheduler barrier synchronization, and result gathering—typically imposes a structural floor of 200 ms to 1,500 ms of latency. When an operational SLA requires sub-50ms or sub-100ms dashboard refreshes, distributed coordination latency alone consumes the entire latency budget before the first vectorized byte is read.

5. MPP Landscape: Strengths, Trade-offs, and the Serving Gap

The comparative analysis between distributed query engines and embedded serving layers should not be framed as "which engine is flawed." Modern distributed platforms are engineering marvels that solve immense, distributed analytics challenges exceptionally well.

The rigorous systems question is:

What workload domain is each platform optimized to execute, and what structural trade-offs emerge when that execution engine is applied to high-concurrency, bounded operational serving?

The Architectural Conclusion: None of these distributed platforms is fundamentally flawed. Each is specialized for a distinct region of the data processing spectrum. The architectural failure occurs when engineering teams default to using a heavy distributed execution model across the entire query workload spectrum, ignoring the lightweight, high-concurrency operational boundary.

6. The Design North Star: What Must Be Built

The enterprise data industry has spent twenty years perfecting distributed engines for the rare, complex, multi-terabyte query. Meanwhile, real-world operational user traffic remains bounded, selective, and high-frequency.

Clear Gateway Positioning: We do not propose an "MPP replacement engine." What we need is a Smart Data Gateway—a lightweight, stateless, application-aware execution boundary and routing tier. The gateway intercepts bounded, sub-second operational queries, executing them directly against open lakehouse formats (Apache Iceberg) using an embedded vectorized C++ engine (DuckDB). Crucially, the gateway shields the primary distributed compute infrastructure (e.g., Spark, Trino) and lakehouse storage from concurrent query lock contention and scheduling saturation, while transparently passing long-tail, unconstrained queries upstream to the full MPP cluster.
