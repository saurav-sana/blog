Production Architecture, Multi-Agent Platforms (MAP), and Build vs. Buy

Concluding the Gateway Design: architectural boundaries, production controls, MCP integration, multi-agent data access, formal decision criteria, and the economics of building the serving layer.

October 5, 2026 ~25 min read Enterprise Platform Architecture Part 5 of 5

The dangerous architecture is not the one that distributes computation. It is the one that distributes computation before the workload requires it.

The Smart Data Gateway is an attempt to place the distribution boundary where the workload actually demands it.

Parts 1–4 built the argument progressively: identify the workload shape, evolve the architecture around that shape, test the production mechanics, and formally reason about correctness. This final part asks the harder architectural question: when should an enterprise actually deploy this design?

TL;DR — The five conclusions

  1. Workload fit beats architectural fashion. A local/vectorized gateway can be an excellent serving architecture for bounded, latency-sensitive analytical workloads, but it is not a universal replacement for distributed analytical systems.
  2. Separate serving from transformation. Interactive APIs, dashboards, reconciliation screens and bounded agent tools should have an execution path optimized for predictable latency. Large joins, broad scans, ETL and asynchronous transformations should remain on engines designed for distributed execution.
  3. MCP is an interface, not a security architecture. The Gateway can expose typed analytical capabilities through an MCP server, but tenant isolation, authorization, query limits, auditing, resource controls and data minimization remain Gateway responsibilities.
  4. Build only where the control surface is the product. Building a custom gateway is justified when workload-specific locality, policy, latency, observability or agent controls create durable value that generic platforms cannot provide economically.
  5. The correct decision is measurable. Deploy the Gateway when the observed workload lies inside its economic, latency and correctness envelope. Route everything outside that envelope to an architecture optimized for it.

1. From “Architectural Superiority” to Architectural Fit

The strongest version of the Gateway argument is not: “MPP is obsolete.”

It is: “A distributed analytical engine is not automatically the optimal serving architecture for every analytical request.”

Distributed systems pay for distribution: coordination, scheduling, network movement, serialization, fault domains, metadata management and resource isolation. Those costs are justified when the computation needs the scale, parallelism or fault tolerance that distribution provides.

Conversely, a single-process vectorized engine pays for locality and bounded execution. It can exploit local memory, SIMD/vectorized execution, local NVMe and a much smaller coordination surface.

2. What the Gateway Actually Is

The production Gateway should not be described as “stateless” in the absolute sense. It has acceleration state: local cache contents, Redis metadata, epochs, prefetch state and routing information.

The more accurate property is: stateless execution with reconstructible acceleration state.

A worker may disappear without losing authoritative business data. Its cache can be repopulated. Its execution state can be discarded. Its identity and authorization state can be reconstructed from the control plane.

Authoritative

Iceberg / Object Storage

Durable analytical truth. Snapshots, manifests, data files and retention policies live here.

Acceleration

Redis + Local NVMe

Cache metadata, epochs, routing hints and frequently accessed byte ranges. Losing them should degrade performance, not correctness.

Execution

DuckDB / Vectorized Engine

Executes bounded analytical requests close to the data and within explicit CPU, memory, scan and result-size budgets.

3. Why Not Just Use the Existing Analytical Platform?

Existing analytical platforms are often excellent systems. The architectural question is whether their execution model is appropriate for the workload being served.

It is therefore misleading to classify Dremio, Trino, Snowflake and similar systems as one “legacy monolith.” They have materially different execution, storage, scheduling, deployment and commercial models.

Dimension Distributed analytical platform Smart Gateway
Primary optimization target Large-scale analytical execution and concurrency Bounded serving latency and workload isolation
Coordination Coordinator / scheduler / workers Minimal request routing and policy layer
Data locality Distributed across execution workers Explicitly exploited through local cache and NVMe
Best workload Large scans, joins, transformations, federation Bounded operational analytics and serving APIs
Scale mechanism Distributed parallelism Horizontal pool of bounded execution workers
Failure philosophy Distributed task recovery Disposable workers + reconstructible acceleration state
Cost model Platform / cluster / query dependent Explicit CPU, memory, storage and scan budgets
Do not turn this into an anti-MPP argument

Distributed execution is often the correct architecture. The COST literature makes the more useful point: scalability should be evaluated together with the overhead introduced by the platform and the baseline it must beat—not treated as an end in itself.

5. Mutations Belong Somewhere Else

One of the most important boundaries in the design is the separation between operational mutation and analytical serving.

A practical implementation can use an operational database as the write authority and publish changes asynchronously into the analytical lakehouse. An outbox pattern prevents the classic failure where the database transaction commits but the corresponding event is lost.

6. Extending the Gateway into a Multi-Agent Data Platform

The agent era introduces a new consumer for the data layer. The problem is not that an LLM cannot generate SQL. The problem is that giving an autonomous system unconstrained access to a large analytical surface creates a new class of resource, security and information-flow risks.

A swarm can issue redundant queries. It can request excessively broad results. It can repeatedly retry an expensive operation. It can select a technically valid but operationally pathological query.

The solution is not simply “put an LLM in front of SQL.” The solution is to expose bounded capabilities.

6.1 Correct MCP topology

Important terminology correction

In MCP, the AI application is the Host. The Host creates MCP Clients, and those Clients connect to MCP Servers. Therefore the Smart Data Gateway should be represented as an MCP Server, not an MCP Host.

7. Do Not Give Agents Arbitrary SQL by Default

The most important security correction in the original design is here. A pattern such as:

safe_sql = sqlglot.parse_one( f"tenant_id = '{tenant_id}'" )

is not a sufficient tenant-isolation mechanism.

Apart from obvious string-interpolation risk, arbitrary SQL makes policy enforcement difficult. A query can contain nested SELECTs, CTEs, UNIONs, joins, views, table functions or other constructs that make a superficial predicate injection insufficient as a security boundary.

Security rule

Tenant isolation must be an authorization property, not a SQL-string rewriting trick. The preferred agent interface is a typed capability whose server-side implementation owns the query shape.

7.1 "Show, Don't Tell": The Interception Code

To safely expose data to an agent swarm, use an MCP tool wrapper that takes typed parameters. The Gateway compiles the SQL dynamically, enforcing row limits and executing locally.

from fastmcp import FastMCP
import sqlglot
from sqlglot import exp
import duckdb

mcp = FastMCP("Enterprise-Data-Gateway")
conn = duckdb.connect()

def compile_agent_query(tenant_id: str, status: str) -> str:
    """Gateway owns the SQL construction, not the LLM."""
    # 1. Base authorized query structure
    base_sql = "SELECT trade_id, amount, status FROM regulatory_ledger"
    ast = sqlglot.parse_one(base_sql, read="duckdb")
    
    # 2. Inject deterministic security & parameters
    filters = sqlglot.parse_one(f"tenant_id = '{tenant_id}' AND status = '{status}'")
    ast = ast.where(filters)
    
    # 3. Protect LLM context windows (Hard row ceiling)
    ast = ast.limit(50)
        
    return ast.sql(dialect="duckdb")

@mcp.tool()
def query_regulatory_ledger(tenant_id: str, status: str) -> str:
    """Safely execute bounded analytical queries for the MAP swarm."""
    safe_sql = compile_agent_query(tenant_id, status)
    
    # Execute locally and return token-dense markdown
    arrow_table = conn.execute(safe_sql).arrow()
    return arrow_table.to_pandas().to_markdown(index=False)

7.2 If arbitrary SQL is genuinely required

Some analyst-facing tools may legitimately need SQL. In that case, the system should explicitly define an allowlisted analytical SQL subset rather than assuming that parsing alone makes arbitrary SQL safe.

  • Reject DDL and DML.
  • Reject ATTACH, INSTALL, LOAD and unrestricted filesystem access.
  • Restrict table and schema references to authorized objects.
  • Control functions that can access external resources.
  • Enforce maximum scan bytes and execution time.
  • Enforce maximum output rows and output bytes.
  • Reject unrestricted cross-tenant joins.
  • Apply authorization after semantic query analysis, not merely by string matching.
  • Audit the normalized query representation and authorization decision.

8. Token-Efficient Results Are Not “Zero-Copy” Results

The original design mixed two different optimization goals: analytical data movement and LLM context consumption. They should be separated.

Path Optimization objective Preferred representation
Gateway → analytical application Minimize copying and serialization Arrow / Arrow Flight where appropriate
Gateway → agent Minimize context while preserving meaning Schema-aware summaries, aggregates, top-N, bounded records
Gateway → audit system Preserve reproducibility Normalized query, identity, snapshot, policy decision, result metadata

A fixed claim such as “75% token reduction” should only appear after a benchmark using representative workloads. The defensible architectural objective is: return the smallest result that preserves the decision-relevant information.

9. Agent Requests Need Resource Budgets

An agent request is not merely a request for data. It is also a request for compute, memory, storage I/O and potentially downstream model context.

Compute budget

Maximum CPU time, worker concurrency and execution class.

Scan budget

Maximum estimated or observed bytes scanned before escalation.

Memory budget

Explicit per-query and per-worker memory limits with spill policy.

Result budget

Maximum rows, bytes and context footprint returned to the agent.

10. Resilience and FinOps Become First-Class Controls

The Gateway's value is not simply that DuckDB is fast. The value is that the serving path provides a narrow place where enterprise policies can be made explicit. Queueing is a design constraint. As utilization approaches saturation, queueing delay becomes highly sensitive to both utilization and variability.

For a G/G/1 system, Kingman's approximation is:

$$W_q \approx \frac{\rho}{1-\rho} \frac{c_a^2+c_s^2}{2} E[S]$$

This is a G/G/1 approximation, not an M/M/C model. The practical lesson is more important than the formula: a Gateway cannot solve tail latency simply by adding average capacity. Burstiness and service-time variability matter.

This is why the production design needs: concurrency limits, separate fast and slow lanes, admission control, bounded retries, backpressure, workload-aware routing, and tail-latency observability.

11. Elasticity: Warm Capacity Beats Magical Milliseconds

A previous version described Kubernetes scale-up or scale-to-zero as if arbitrary compute capacity could appear in milliseconds. That is not a safe architectural assumption. 12. Five Enterprise Pillars

12.1 Zero-trust data access

The Gateway should treat every request as an authorization decision. Identity, tenant, purpose, table access, column access, row-level policy, snapshot visibility and result size should be explicit.

A strong audit record should contain at least:

{
  "request_id": "...",
  "principal": "...",
  "tenant": "...",
  "tool": "query_regulatory_ledger",
  "parameters_hash": "...",
  "normalized_query_hash": "...",
  "snapshot": "...",
  "policy_decision": "allow",
  "scan_bytes": 18473291,
  "result_rows": 42,
  "duration_ms": 187
}

The raw prompt may also be retained where enterprise policy permits, but it should not be treated as a substitute for recording the actual authorization decision and normalized data access.

12.2 Resilience and FinOps

  • Envoy or equivalent admission control.
  • Per-tenant concurrency limits.
  • Per-query memory and execution budgets.
  • Redis-backed cache metadata where appropriate.
  • Local NVMe for bounded acceleration.
  • OpenTelemetry traces connecting API → policy → execution → storage.
  • CPU, memory, scan-byte and storage-request attribution.

12.3 AI-native operations

The Gateway creates a useful control point for agent-assisted operations: anomaly detection, synthetic workload generation, regression analysis, capacity forecasting and incident summarization. But autonomous remediation should remain bounded by the same engineering principles as human remediation.

Do not let “agentic” mean “unbounded authority”

An operational agent should propose, validate and progressively earn authority. Automated promotion should be guarded by measurable invariants: latency, error rate, resource consumption, correctness checks and rollback.

12.4 Federation

The Gateway should not become another universal data federation layer. Catalogs such as Polaris, Unity Catalog, Glue or Nessie can remain responsible for discovery and governance while the Gateway specializes in serving.

A cost-based router can choose among:

  • local DuckDB execution,
  • a larger vectorized/distributed engine,
  • an existing MPP platform,
  • a search engine, or
  • an operational database.

A threshold such as “50 GB” should be treated as a tunable starting point, not a universal physical law. The actual boundary must be derived from benchmarks involving scan rate, concurrency, join shape, memory, cache hit ratio and latency SLO.

12.5 Browser-side analytical execution

DuckDB-WASM or similar browser execution can be powerful for interactive analytical experiences. However, signed byte-range URLs change the authorization boundary. Before adopting this pattern, the architecture must answer:

  • Can the browser access the underlying object directly?
  • How are row- and column-level policies enforced?
  • How long are signed URLs valid?
  • Can browser caches retain sensitive data?
  • Can URLs be forwarded or replayed?
  • Is object-level authorization equivalent to business-level authorization?
Browser execution is not automatically “zero backend cost”

It can reduce backend compute, but it can simultaneously increase egress, expose physical data objects, shift compute to client devices, and complicate data governance.

13. Build vs. Buy: Engineering the Serving Layer

The build-vs-buy question should not be answered with “custom is cheaper.” Custom software transfers cost from license fees to engineering, operations, security, upgrades, incident response and platform ownership.

Before building a custom Gateway, we must evaluate the current landscape of commercial data APIs, semantic layers, and LLM proxies to determine if an off-the-shelf solution already solves the problem.

13.1 Top Off-the-Shelf Gateways

Hasura v3 (DDN)

Excellent edge-native GraphQL routing, data modeling, and API federation. However, it relies heavily on pushing compute down to the backend database, lacking the localized embedded analytical execution (DuckDB) we need for bounded latency.

Cube (Cube Cloud)

A very strong Rust-based Semantic Layer API optimized for proactive caching and UI dashboards. While excellent for BI, it is less focused on raw, safe autonomous AI agent (MCP) interactions and AST-level LLM guardrails.

Closest Match

Spice.ai

Built on Rust, Apache Arrow, and embedded DuckDB. It is explicitly designed for AI integrations, edge caching, and zero-copy Flight execution, making it the closest commercial match to our architectural vision.

13.2 The Verdict: Why Build?

While platforms like Spice.ai offer a highly compelling architecture, adopting them as a managed service or rigid vendor dependency introduces critical limitations for our specific operational realities. Building is justified by the following strategic requirements:

  1. Black-Box Caching Limitations: Off-the-shelf products provide generic caching policies (e.g., TTLs). Our workloads require deeply customized, application-aware caching—such as tying cache invalidation to complex, deterministic state changes in high-stakes regulatory reporting. We need full control to inject custom Lua/NGINX logic at the edge.
  2. Complex Multi-Tenancy Orchestration: We manage over 100 isolated global tenants requiring strict Row-Level Security (RLS). While commercial products can route data efficiently, enforcing dynamic, AST-level query rewriting (via sqlglot) seamlessly requires deep integration into our proprietary authentication frameworks and Automated Client Onboarding Platform (ACOP).
  3. Data Sovereignty & Compliance: In trade regulatory reporting (SEC, CFTC, EMIR), routing raw financial data or query shapes through a third-party SaaS control plane introduces massive compliance overhead. A self-hosted, custom-built data plane ensures data never leaves the VPC.
  4. Extensibility & Portability: A custom-built Python/FastAPI/DuckDB gateway ensures we own the entire execution path. We can seamlessly scale the architecture up to production Kubernetes clusters or run the entire stack locally on a developer's 16GB laptop for experimentation, without being locked into a vendor's product roadmap or pricing tiers.
The SIDG Synthesis

By building the Smart Iceberg Data Gateway (SIDG), we synthesize the best modern primitives (DuckDB, Apache Arrow, Apache Iceberg) into a highly performant, proprietary access layer tailored exactly to our security, cost, and latency requirements.

15. What This Architecture Does Not Claim

A technically credible conclusion needs explicit negative claims.

It does not claim that single-node execution replaces distributed analytics.

  • It does not claim that DuckDB replaces MPP systems universally.
  • It does not claim that all enterprise analytical queries are small.
  • It does not claim that MCP makes agents secure.
  • It does not claim that local caching eliminates cloud-storage cost.
  • It does not claim that browser execution is free, private or automatically compliant.
  • It does not claim that a custom gateway has zero operational cost or zero vendor dependency.
  • It does not claim that one fixed scan-size threshold determines the boundary between local and distributed execution.
  • It does not claim that the same architecture is optimal for every enterprise.
The actual claim

For a measured workload whose request sizes, concurrency, join patterns, freshness requirements and latency objectives fall inside the Gateway's operating envelope, a serving architecture based on local/vectorized execution can reduce unnecessary coordination and improve the ability to control latency, resources and policy.

16. Empirical and Academic Foundation

The evidence behind the architecture should also be stated carefully. Industry workload observations are useful, but they are not universal laws.

16.1 Query sizes: useful evidence, not a universal law

Jordan Tigani's MotherDuck analysis of BigQuery customers spending more than $1,000 per year reported that 90% of the analyzed queries processed less than 100 MB. The analysis is useful evidence that many analytical queries are much smaller than the total data estate they query. It should not be converted into a universal statement that “95% of enterprise queries scan less than 10 GB.”

This distinction matters because the architecture depends on the actual workload distribution of the enterprise deploying it.

16.2 Query repetition is a different observation

Research on Microsoft SCOPE workloads has reported very high query repetition. That is evidence for computation reuse and repeated workload structure—not evidence about scan size.

The two observations can reinforce an architectural hypothesis: repeated, bounded analytical requests may benefit from caching and reuse. But they must remain separate empirical claims.

16.3 COST

The COST framework—Configuration that Outperforms a Single Thread—provides an important methodological lesson: a distributed system should be evaluated against a competent baseline, including the overhead introduced by the distributed architecture. The lesson is not “single-node is better.” The lesson is: measure where distribution begins to pay for itself.

16.4 DuckDB

The foundational DuckDB SIGMOD work establishes the case for an embedded analytical database: analytical execution can live inside the application process rather than requiring every workload to communicate with a separate database server.

16.5 ClickHouse and modern analytical engines

ClickHouse demonstrates that modern analytical engines can combine vectorized execution, pruning, efficient storage and flexible deployment. It is therefore better used in this argument as evidence that the analytical execution layer itself has become highly modular and optimized, rather than as evidence for a universal single-node-versus-cluster result.

16.6 Terabyte-scale GPU analytics

Recent research on terabyte-scale analytics demonstrates another important boundary condition: sufficiently powerful GPU/HPC infrastructure can radically alter the economics of distributed analytics. This is precisely why the Gateway argument must remain workload-conditioned. Hardware evolution can move the distribution boundary.

17. The Laws That Survive the Implementation

The final architecture is not validated because it contains fashionable components. It is validated when the underlying constraints remain true even if individual implementations change.

Law 1 — Distribution has a cost

Coordination, serialization, network movement and scheduling are not free. Distribution should buy something measurable.

Law 2 — Locality has value

Data locality reduces movement and can make bounded workloads substantially easier to reason about.

Law 3 — Utilization amplifies variability

Queueing delay becomes increasingly sensitive to burstiness and service-time variability near saturation.

Law 4 — State needs an authority

Caches and acceleration state may be disposable, but authoritative business state cannot be ambiguous.

Law 5 — Security follows data flow

A protocol boundary does not create authorization semantics. Every data access path needs an explicit policy boundary.

Law 6 — The tail is an architectural property

Average latency cannot certify an architecture whose SLO is defined by p95, p99 or p99.9 behavior.

20. Conclusion — Put the Distribution Boundary Where It Belongs

The central mistake in modern data architecture is not using distributed systems. Distributed systems are one of the most important achievements in computing.

The mistake is treating distribution as the default answer to every analytical request.

A dashboard query, reconciliation screen, operational API or agent tool may have very different physical requirements from a multi-terabyte ETL transformation.

The Smart Data Gateway proposes a deliberate separation:

  • OLTP systems own transactional mutation.
  • Lakehouse storage owns durable analytical history.
  • Distributed analytical systems own large-scale computation.
  • The Smart Gateway owns bounded analytical serving.
  • MCP provides an agent-facing protocol boundary.
  • Gateway policy owns authorization, resource budgets, data minimization and auditability.

Query engines are increasingly becoming composable infrastructure. The differentiating architectural layer is often the boundary around them: who may query, what may be queried, how much computation may be consumed, where the request executes, and what information is allowed to leave.

That is where the Smart Data Gateway becomes more than “DuckDB behind an API.”

It becomes a workload-aware serving control plane: not a replacement for the distributed analytical ecosystem, but a mechanism for deciding when that ecosystem is actually necessary.

The final architectural rule

Deploy the Smart Data Gateway when measured workload characteristics fit its latency, resource, correctness and economic envelope. Route workloads outside that envelope to the architecture designed for them.

The architecture therefore does not end with “Gateway wins.”

It ends with a more useful engineering statement:

Choose the execution boundary from the physics of the workload, not from the popularity of the platform.

"Giving an autonomous LLM swarm direct SQL access to a production database is an excellent way to automatically discover exactly how many tables you forgot to back up."
