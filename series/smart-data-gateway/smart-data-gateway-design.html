The Smart Iceberg Data Gateway: Rethinking Analytical Serving for the 95% Case

How a $55k/month monolithic OLAP bill led to a stateless, DuckDB-powered gateway architecture for AI agents, multi-tenant APIs, and operational dashboards — and why the industry's own usage data says most of us have been over-buying compute for years.

Executive summary

Most organizations do not have a Big Data problem. They have a serving problem: petabytes of history sitting in an open lakehouse, and a stream of operational queries that each touch a few megabytes to a few gigabytes of it. Forcing that traffic through a Massively Parallel Processing (MPP) engine — Dremio, Trino, Databricks, Snowflake — buys distributed-shuffle capability nobody is using, at a licensing and infrastructure cost nobody enjoys paying.

This post documents the design of a Smart Iceberg Data Gateway (SIDG): a stateless, horizontally scalable serving layer that sits in front of an Apache Iceberg lakehouse, executes the ~95% of queries that are small and simple using embedded DuckDB workers, and falls back to a real MPP engine only for the long tail that genuinely needs distributed compute. It covers the motivating cost and latency problem, the industry data that validates the "95% case," the technology selection process, the theoretical grounding (queueing theory, USL, Amdahl, Gustafson), a phase-by-phase architectural evolution from a naive embedded client to a production multi-region system, and the reliability/cost modeling used to size it.

A companion whitepaper (forthcoming) will present the same architecture with a formal TLA+/PlusCal specification for the routing, backpressure, and cache-coherence invariants.

TL;DR

  • Most organizations route nearly all of their analytical traffic through MPP infrastructure (Trino/Dremio/Databricks/Snowflake) sized for terabyte-scale queries almost nobody actually runs.
  • Public usage data from Redshift, BigQuery, and Microsoft's internal Cosmos lake all show the same shape: roughly 75% of queries scan under 1 GB, and queries over 10 TB are about 3 in 10,000 (§2).
  • A stateless gateway — SQLGlot for AST rewriting and tenant isolation, PyIceberg for lazy metadata pruning, DuckDB for embedded execution, Arrow/Arrow Flight for zero-copy transport, NGINX/Redis for caching — can serve that 95% directly off an open Iceberg lakehouse at a fraction of the cost and latency, routing only the genuine long tail to a real MPP engine.
  • This is a systems-engineering account of building that gateway: the failures that shaped each design decision, the theory behind it, and the reliability/cost numbers used to size it — not a product pitch.

Who this is for

Data platform engineers, SRE/infra teams operating a lakehouse, and anyone evaluating whether their organization's Trino/Dremio/Databricks bill actually matches its query patterns. Sections 6 (theory) and 9 (reliability/cost modeling) assume some familiarity with queueing theory and Kubernetes; the glossary immediately below is for readers who know SQL and distributed systems in general terms but haven't necessarily worked with Iceberg, Arrow, or DuckDB specifically — skip it if that's already familiar territory.

A field guide to the ecosystem, for readers new to this stack

This design leans on a handful of relatively young (2019–2024) open-source projects that don't yet have the name recognition of Spark or Postgres. A short glossary, roughly in the order the terms show up:

Term Plain-English definition
Data lakehouse Storing data as plain files (usually Parquet) in cheap object storage (S3 / Azure ADLS / GCS), with a metadata layer on top that provides database-like guarantees — schema, snapshots, transactions — without a database server owning the files.
Apache Parquet A columnar file format. Instead of storing a table row by row, it stores it column by column, so an engine can read only the columns a query needs and compress similar values together. This is why analytical engines are fast at aggregation and structurally bad at single-row updates.
Apache Iceberg An open table format layered on top of Parquet files. It tracks a versioned history of "snapshots", partition metadata, and schema evolution, so multiple different engines (Spark, Trino, DuckDB) can safely read and write the same tables without one shared, always-on database process owning them.
Iceberg REST Catalog The standard HTTP API other engines call to ask "where are table X's files right now, and what's its current schema?" — vendor-neutral, so nobody's locked into one company's proprietary catalog.
PyIceberg The Python library that talks to the Iceberg catalog and answers, before any engine touches actual data, "given this query's filters, which specific Parquet files can I skip entirely?" — called partition pruning.
Apache Arrow An in-memory columnar data format, not a file format — a way for different programs (a Python process, a C++ engine, a network stream) to share tabular data without converting it to JSON or CSV in between. This is what "zero-copy" means everywhere in this post.
Apache Arrow Flight / Flight SQL A network protocol (built on gRPC/HTTP/2) for streaming Arrow data directly between processes — the wire-format sibling of Arrow, purpose-built to move large tabular results fast, as an alternative to REST/JSON.
DuckDB An embedded (in-process, SQLite-style) analytical SQL engine — no server to install or manage, just a library you import — that's very good at exactly the query shapes (filters, aggregations, joins on denormalized data) this design routes to it.
MPP Massively Parallel Processing. The traditional architecture behind "big data" query engines (Trino, Dremio, Presto, Snowflake): a query is split into pieces that run in parallel across many networked worker machines, then partial results are shuffled and combined. Powerful for genuinely huge scans; expensive and comparatively slow for small ones.
OLAP vs. OLTP OLAP = read-heavy, aggregation-heavy queries over historical data. OLTP = write-heavy, row-level, "update this one customer's balance right now" queries — a fundamentally different workload Section 11 explains this architecture is not built for.
"Gateway" Not an API gateway in the Kong/Apigee sense — here it specifically means the layer between clients and the compute engine that handles routing, caching, and protocol translation, distinct from the engine itself.

1. The problem: architectural misalignment in data serving

1.1 The monolith problem

Traditional MPP engines were built for analysts running ad-hoc BI reports, where waiting 15–30 seconds for a result was fine. That assumption is baked into their architecture:

  • They're black boxes. Dremio, Snowflake, Trino, and Databricks own the entire lifecycle — parsing, planning, caching, execution — end to end. You cannot tell their cache to proactively warm a partition because your ETL job just landed, and you cannot inject a deterministic result cache keyed to your own data-versioning scheme.
  • Noisy neighbors. Shared JVM executor fleets (Dremio's "Fat Executors," Trino workers) mean one tenant's heavy aggregation can trigger a GC pause or OOM crash that takes down every other tenant's in-flight query on that node.
  • Concurrency ceilings, not throughput ceilings. These engines are tuned for a small number of analysts running large scans, not hundreds of concurrent operational API callers doing small point lookups.

1.2 The financial reality

A concrete before/after from a production reporting platform ("Report Hub") running on Dremio:

Cost driver Monthly cost Root cause
Proprietary licensing ~$38k ~3x the underlying compute cost, on top of already-open Iceberg/Parquet
JVM over-provisioning ~$13k 20 executors + 8 coordinator/catalog nodes at 16 vCores / 128 GB each, sized to survive GC pauses
Stateful disk overhead ~$5k NVMe/SSD attached directly to stateful executors
Total ~$55k/mo excluding baseline storage

Because the cache is physically coupled to stateful executor nodes, the cluster can't scale to zero overnight — every executor stays powered on 24/7 regardless of load. A multi-year enterprise agreement compounds this: Year 1 at a flat $384k, Year 2 at a $333k base (capped at 16 production nodes) plus $66.5k for non-production, with each additional node at roughly $24k/year.

1.3 The other failure mode: exposing raw compute

The opposite extreme — stripping away the gateway entirely and pointing clients straight at a bare DuckDB or DataFusion process — fails just as badly, for different reasons:

  • Thundering herd. Fifty dashboard users opening the app in the same second means fifty engines independently issuing fifty identical HTTP range requests to object storage, which storage answers with 429 Too Many Requests at scale.
  • Cold-start latency. Compute engines are built to crunch numbers in local RAM, not manage TCP keep-alives or HTTP range headers against remote cloud storage — every query pays full network latency with no local cache.
  • Zero tenant isolation. A compute engine has no concept of WHERE tenant_id = 'X'. Without a gateway inspecting the query at the AST level, cross-tenant data exposure is a matter of when, not if.
  • Protocol mismatch. Clients speak HTTP/REST/gRPC; compute engines speak internal execution vectors. Something has to bridge that gap.

1.4 The AI agent bottleneck

Autonomous agents using the Model Context Protocol (MCP) make this worse, not better, if pointed at either extreme:

  • Context bloat. A raw SQL tool call can return thousands of rows, instantly consuming an LLM's context window.
  • Unbounded scans from hallucinated SQL. Agents routinely emit unpartitioned SELECT * queries; against a shared MPP cluster this can crash executors for every other tenant.
  • Latency-loop mismatch. A ReAct-style agent making 3–5 sequential tool calls turns a 10–30 second-per-query cold-storage read into a multi-minute round trip that blows through client timeouts.
  • Prompt injection and data bleed. Agents are susceptible to indirect prompt injection; without AST-level tenant-predicate injection, a manipulated agent can read across tenant boundaries.
  • Retry storms. An agent's default response to a SQL error is to rewrite and immediately retry — 20 failing queries in a few seconds is enough to monopolize a shared thread pool.

2. The data: is the "95% case" real, or wishful thinking?

This is the load-bearing empirical claim of the whole design, so it's worth grounding in public data rather than intuition.

Query size distribution (Redshift usage analysis, via MotherDuck):

  • Three-quarters of all queries scan less than a gigabyte, and queries over 10 TB — the workload MPP clusters are actually built for — are 3 in 10,000 and consume just 5.6% of total compute time.
  • Rolling the top two size tiers together: just 0.25% of queries ever scan more than 1 TB, yet that sliver still accounts for 16.6% of all elapsed compute time — a massively disproportionate cost-to-volume ratio, and exactly the shape of workload a routing layer should isolate rather than provision every node for.
  • Put differently: the industry is spending a large share of its query-dollars on infrastructure sized for a workload that's a rounding error of its actual traffic.

Per-user scan ceilings tell the same story: 93% of users never exceed 10 GB in their heaviest query — comfortably within what a single embedded engine handles on a laptop-class machine — and 67% never exceed 1 GB. Only 1 user in 600 has ever scanned more than 10 TB.

Even inside organizations that do own petabyte-scale data, day-to-day queries overwhelmingly hit small, pre-aggregated tables: in one analysis, 99% of queries inside "Big Data" organizations targeted tables under 1 TB, because medallion-style architectures summarize raw data into clean serving layers before anyone queries it interactively.

Independent corroboration exists across the industry, not just from one vendor's marketing blog:

  • Microsoft's internal Cosmos/SCOPE data lake (SIGMOD '18) documents heavy, systematic overlap across recurring production queries — the same underlying pattern of small, repetitive, locality-driven traffic.
  • "Scalability! But at what COST?" (HotOS 2015) showed that for the data sizes many published "Big Data" benchmarks actually used, a well-written single-threaded implementation outperformed distributed systems using hundreds of cores.
  • Recent work on GPU-accelerated distributed query engines (VLDB 2025) shows the opposite trend at the very top end. That doesn't contradict the argument here; it reinforces a broader one: hardware has moved faster than most query-engine architectures have adapted to, at both the single-node and the distributed-cluster end.

Why this distribution isn't a coincidence. The pattern is explained by several well-known models stacking together, not one lucky observation:

  • Power-law / Zipfian access — a small head of hot, recent data absorbs almost all traffic; a long tail of historical data is rarely touched at once.
  • Temporal and spatial locality — a tenant's request today is about today's data, in their region, for their account.
  • Denormalization as an economic strategy — engineering teams flatten and pre-join data into wide serving tables specifically so queries only ever touch a narrow byte range.
  • Bounded human/API attention — a UI grid shows 20 rows at a time; an API call serves one transaction context. Neither queries out of idle curiosity.
The conclusion: the "95% case" is not a quirk of one application's workload — it's the expected shape of operational query traffic anywhere humans or bounded API clients are the ones asking the questions.

Two details worth calling out: the REST and Flight paths are asymmetric on purpose — REST traffic goes through workload management (a queue) because it's the path async exports use and can tolerate the extra hop, while Flight traffic bypasses the queue entirely and goes straight to an executor. And the result cache lives inside the gateway boundary as shared state, not per-executor.

A useful mental model: a query engine is the brain (semantic understanding, planning, math); a data gateway is the nervous system (routing, caching, protocol bridging, traffic shaping). Compute engines — DuckDB, DataFusion, Spark, Trino — are increasingly interchangeable commodities. What doesn't commoditize is application-aware caching, query-aware routing, AST-level tenant isolation, and the MCP surface for AI agents.

4. Surveying the market: does this already exist?

4.1 The big three, and why they share the same flaws

Platform Noisy-neighbor risk Caching Customization / cost
Trino High — JVM heap exhaustion on one heavy tenant query OOM-kills shared workers Tightly coupled to worker-local SSD; scale-down destroys it No hook for proactive cache warming; requires a 24/7 baseline fleet
Databricks Medium — thread contention on shared clusters; isolation means separate clusters Delta Cache tied to specific NVMe drives; scaling starts cold Serverless abstracts infra at a steep premium; no room for a custom proxy layer
Snowflake Solved via cost — isolated Virtual Warehouses, paid for individually Local disk cache tied to the warehouse; suspending wipes it Fully closed; no application-aware cache warming or bypass path

4.2 Off-the-shelf gateways & Build vs. Buy

The market has recognized the gap: Hasura v3 does edge-native GraphQL federation but leans on backend compute; Cube provides a strong semantic-layer caching API but isn't built around autonomous agent traffic; Spice.ai is the closest match — Rust, Apache Arrow, embedded DuckDB, explicitly AI- and edge-caching-oriented.

Adopting a managed dependency runs into three walls for a regulated, multi-tenant environment: (1) black-box caching policies that can't be tied to deterministic events; (2) 100+ tenant RLS enforcement that needs deep integration with an existing auth framework; (3) the desire to run the entire stack locally for development. The verdict: build, synthesizing modern primitives into a proprietary layer.

5. Technology selection

5.1 Compute engine shortlist

Engine Strengths Trade-off
Apache DataFusion Rust, Arrow-native, zero persistent daemons, highly extensible Framework, not a ready product — more integration work upfront
DuckDB World-class Parquet reader, native Iceberg extension, graceful out-of-core spill C++ embedded in Python introduces memory-safety edge cases
Daft Arrow-native, Python-first, scales out via Arrow Flight shuffle Best fit if you expect to outgrow single-node

Why DuckDB won: its Parquet reader pairs perfectly with PyIceberg-driven metadata pruning and an NVMe byte-slice cache; it exports Arrow RecordBatches directly into an Arrow Flight server; and it runs entirely in-process.

5.2 The building-block stack, by tier

  • Tier 1 (Primitives): DuckDB (execution), Apache Arrow (in-memory substrate), PyIceberg (lazy metadata evaluation), Iceberg REST Catalog.
  • Tier 2 (Nervous System): L7 load balancer (Envoy), NGINX (NVMe byte-range caching), Redis (shared control-plane cache), SQLGlot (AST-level parsing and RLS), HTTP range requests.
  • Tier 3 (Protocols): Arrow Flight SQL (gRPC), FastAPI (REST), FastMCP (AI agents).
  • Tier 4 (Ops): Kubernetes Operator, Celery, OpenTelemetry, Prometheus, Grafana, Locust, Chaos Mesh.

6. Does theory actually back this up?

6.1 Laws favoring the local gateway (the 95% case)

  • Universal Scalability Law: $$C(N) = \frac{N}{1 + \alpha(N-1) + \beta N(N-1)}$$ The $\beta N^2$ coherency-penalty term is what kills MPP throughput at scale. A stateless gateway hitting local NVMe has $\beta \approx 0$: the scaling curve stays linear.
  • Amdahl's Law: Self-contained workers reading immutable storage directly shrink the serial fraction toward zero.
  • Little's Law ($N = X \times R$): Keeping response time low via local NVMe caching keeps backlog from ever forming.
  • Kingman's Formula: A single-node embedded engine has no stragglers to wait on, avoiding non-linear queue wait time explosions.
  • PACELC: Reading immutable object storage with atomic snapshot updates sidesteps latency-vs-consistency trade-offs.

6.2 Laws favoring MPP (the remaining 5%)

  • Gustafson's Law: For genuinely petabyte-scale, embarrassingly parallel jobs, pooling the memory and CPU of dozens of MPP nodes is mathematically necessary.
  • The out-of-core wall: Every single-node engine is capped by local RAM. MPP horizontally partitions memory itself.
  • Aggregate I/O bandwidth scaling: A single NVMe drive tops out around 7 GB/s. For billions of rows, only aggregating I/O channels gets you real throughput.

7. Architectural evolution: from naive embedded client to production system

7.1 Phase 1 — Embedded mode: solving network latency

Step A — the fat client: Embed DuckDB directly inside the application process. Result: Cross-language serialization tax, zero caching (full cold network latency), and shared fate (a runaway query OOM-kills the host application).

Step B — add an NGINX proxy CDN: 5x latency reduction, but OOM crashes on large tables persist because the bottleneck was memory, not network.

7.2 Phase 2 — Decoupling execution: solving memory and metadata exhaustion

Step C — pull DuckDB into a Python/Arrow service.

Step D — introduce PyIceberg for lazy metadata evaluation. DuckDB's native Iceberg extension eagerly loads the entire manifest tree. PyIceberg streams and filters metadata lazily. This fully resolves the OOM crashes.

Step E — introduce SQLGlot to bridge SQL to PyIceberg. SQLGlot parses the AST, extracts predicates for PyIceberg's pruning, and rewrites the query template for DuckDB.

7.3 Phase 3 — Scaling with load: solving concurrency

Step F — scale NGINX to a 3-node cluster behind consistent hashing.

Step G — move to an async Arrow Flight server. Returns a Ticket instantly while execution is dispatched to a separate OS process (`ProcessPoolExecutor`).

Step H — Redis/Celery task queue, and the "claim check" pattern. Pushing multi-hundred-MB Arrow results into Redis will OOM the broker. The worker streams Arrow IPC output to blob storage and writes only a tiny JSON pointer into Redis. The Gateway subscribes to Redis Pub/Sub instead of polling.

7.4 Phase 4 — the enterprise end state: dual-protocol routing

REST and Arrow Flight are optimized for opposite delivery paradigms:

  • REST's natural shape is async polling — a good match for the decoupled Redis/Celery/Blob path, absorbing long-running exports without holding a synchronous connection past a load balancer timeout.
  • Arrow Flight's purpose is zero-copy streaming — decoupling it through Redis/Blob defeats the point. It belongs on a co-located, stateless-monolith path where DuckDB hands Arrow batches to the API thread via local IPC.

9. Reliability, scaling, and cost engineering

9.1 Load balancer layer selection: Envoy vs. a managed ingress

A managed Layer-7 ingress (e.g., Azure Application Gateway for Containers) is excellent for north–south traffic but is the wrong tool for east–west routing because it lacks Hedged requests and Passive outlier detection. The recommendation is a split: managed ingress at the edge, and in-cluster Envoy Gateway for internal routing, using LEAST_REQUEST and Maglev hashing.

9.3 Sizing the worker pool: the Kubernetes math trap

Requesting a pod at exactly cpu: "8" against an 8-vCPU node fails to schedule. Option C wins: Refactoring to smaller pods (3.5 vCPU / 14 GiB) on D4s_v5 nodes packs tightly, scales in finer increments, and spreads evenly across zones.

10. Implementation details: from design to code

10.1 Metadata pruning handoff: PyIceberg feeding DuckDB

from pyiceberg.catalog import load_catalog
from pyiceberg.expressions import And, GreaterThanOrEqual, EqualTo
import duckdb

catalog = load_catalog("rest_catalog", uri=CATALOG_URI, token=CATALOG_TOKEN)
table = catalog.load_table("lakehouse.trades")

# Lazy, statistics-driven pruning
scan = table.scan(
    row_filter=And(
        EqualTo("tenant_id", tenant_id),
        GreaterThanOrEqual("trade_date", start_date),
    )
)
file_uris = [task.file.file_path for task in scan.plan_files()]

# DuckDB only ever touches the pruned file list
con = duckdb.connect(":memory:")
con.execute(f"""
    SELECT * FROM read_parquet({file_uris})
    WHERE trade_date >= ?
""", [start_date])

10.2 AST rewriting and mandatory tenant isolation

import sqlglot
from sqlglot import exp

def enforce_tenant_isolation(sql: str, tenant_id: str) -> str:
    tree = sqlglot.parse_one(sql, read="duckdb")
    tenant_predicate = exp.condition(f"tenant_id = '{tenant_id}'")

    if tree.find(exp.Select) and not tree.find(exp.Where):
        raise ValueError("unbounded scan rejected: no WHERE clause present")

    where = tree.find(exp.Where)
    where.set("this", exp.And(this=where.this, expression=tenant_predicate))
    return tree.sql(dialect="duckdb")

11. Results: what the proof of concept actually showed

  • Infrastructure: retired 6 "fat" Dremio executors (96 vCores, 768 GB RAM combined) in favor of 2 gateway nodes + 3 reverse-proxy nodes (28 vCores, 56 GB RAM total) — a >50% reduction in CPU and >80% reduction in RAM footprint.
  • Performance: matched legacy performance on the most complex production queries without horizontally scaling the new stack at all.
  • Cost: the gateway handles over 95% of standard reporting natively, letting the proprietary engine be run on a bare-minimum footprint, eliminating several executor licenses.

12. Where this architecture is the wrong tool

This design is a poor fit when the workload needs:

  • High-frequency row mutation (UPDATE/DELETE): Parquet is immutable; frequent edits trigger a compaction storm.
  • Pessimistic row locking: Iceberg is optimistic-concurrency only.
  • Full-text / fuzzy search: Columnar min/max statistics are not an inverted index.
  • B-tree cursor pagination: No index to seek into at \(O(\log N)\).
  • Sub-10ms read-after-write: Streaming ingestion commits in micro-batches.

For those, the better patterns are a transactional-outbox dual-store, Elasticsearch/OpenSearch, or Redis.

13. Where this goes next

Beyond the initial Iceberg-and-Flight scope, natural extensions are: zero-trust governance (OPA-driven dynamic AST masking, WORM audit vaults), multi-catalog federation (Polaris, Unity Catalog, Glue), cost-based tiered routing, autonomous SecOps, and DuckDB-WASM at the edge.

Frequently asked questions

  • Do most companies actually have a "big data" problem? No. Analysis of AWS's Redshift fleet found roughly 75% of queries scan under 1 GB, and queries over 10 TB account for about 3 in every 10,000.
  • Is DuckDB a replacement for Trino, Spark, or Snowflake? No — it's a complement. This design routes the ~95% of queries that are small and simple to embedded workers, and sends the genuine long tail to an MPP engine.
  • Why not just expose DuckDB directly? A compute engine has no concept of tenant isolation, caching, or protocol translation — doing so causes thundering-herd storage meltdowns and cross-tenant data exposure.
  • What happens to AI agent queries that hallucinate bad SQL? They're intercepted at the AST level before execution: unbounded scans and missing tenant predicates are rejected outright.
