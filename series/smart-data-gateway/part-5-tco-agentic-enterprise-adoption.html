Smart Data Gateway · Part 5 · Enterprise Systems

The Final Boundary: Total Cost of Ownership, Agentic Reality, and Enterprise Adoption

Architecture diagrams are the Instagram filters of software engineering. They make everything look perfectly decoupled. The reality of production is far messier.

October 13, 2026

"In theory, there is no difference between theory and practice. But, in practice, there is."

— Jan L. A. van de Snepscheut

The dangerous architecture is not the one that distributes computation. It is the one that distributes computation before the workload actually requires it—usually just because it looked good on a slide deck.

Over the last four parts, we've engaged in an extensive theoretical and mathematical exercise to build a Smart Data Gateway. We've drawn beautiful boxes, argued over queueing physics, and formally verified state transitions. But let's be honest: drawing diagrams is a minute fraction of the job. Making it work reliably in production—when half the network is degraded and a rogue LLM decides to query a billion rows of unstructured data—is an entirely different reality that very few people want to discuss because it is actually hard.

1. The Mandatory AI Section: Agents, MCP, and Denial-of-Wallet

Let’s address the elephant in the room. By law, every architecture document written today must aggressively feature the words "AI" and "Autonomous Agents" if you want anyone to actually read it. But beyond the mandatory hype cycle, this design actually solves a brutally real use case.

Connecting a swarm of autonomous LLMs directly to your traditional Massively Parallel Processing (MPP) data warehouse via raw SQL is essentially a denial-of-wallet attack. LLMs hallucinate schema, write deeply unoptimized cross-joins, and treat your cloud compute like free real estate.

This is where the Model Context Protocol (MCP) comes in, but treating MCP as a mere pass-through to an MPP engine introduces brutal bottlenecks. The Gateway solves these by acting as a strictly governed MCP Server:

Context Window Bloat

The Reality: A simple SELECT * via an MCP tool instantly blows out an LLM's context window, crashing the agent loop.

The Gateway Fix: Top-K Pushdown & Semantic Pagination. The Gateway intercepts the response, executes a statistical summary locally using DuckDB, and returns a schema-aware, token-efficient snippet with cursor pointers for the agent to fetch more if needed.

Protocol Statelessness

The Reality: MCP operates purely request-response. Deep multi-step analytical reasoning by an agent loses temporary table state between tool calls.

The Gateway Fix: Ephemeral Session Injection. A Redis-backed session store hides a session_id in the MCP metadata, allowing an agent to create a temporary analytical space in Call 1, and query it in Call 2.

Synchronous Timeouts

The Reality: Analytical queries take time. 30 seconds of spinning causes the MCP client (and the driving LLM) to hit hard HTTP timeouts.

The Gateway Fix: Async Capability Definitions. We expose a submit_query tool (returning a Job ID) and a check_status tool. The LLM is prompted to poll, keeping the loop alive without holding open a TCP socket.

Arbitrary SQL Injection

The Reality: Injecting auth predicates into an agent's arbitrary SQL string using Regex is a security nightmare waiting to happen.

The Gateway Fix: Governed Capabilities. The agent doesn't send SQL; it sends typed parameters. The Gateway constructs queries from typed parameters and enforces authorization, scan limits, and policy. This reduces the attack surface, but does not eliminate injection, authorization, parser, or policy-engine risks; use parameterization, AST validation, least privilege, and adversarial tests.

2. Defining the Boundary (Or: Where Not to Use This)

A distributed engine (Spark, Trino) is not automatically the optimal architecture just because your data volume is large. Distributed systems pay a heavy coordination tax for scheduling and network shuffles. Conversely, the Gateway uses single-process vectorized engines (DuckDB) to exploit local memory and NVMe speeds without the overhead.

But a serious architecture document needs a failure boundary. If you use this Gateway for everything, you will fail spectacularly. (And no, "we will just auto-scale the pods" is not an architecture.)

Workload Preferred architecture Why it's a terrible fit for the Gateway
High-frequency transactional writes OLTP database (Postgres) The Gateway is stateless analytical serving. It does not handle row-level locks or transaction coordination.
Sub-10 ms read-after-write Redis / Operational Store Lakehouse snapshot visibility and refresh latency generally do not provide a strict sub-10 ms read-after-write contract; use an operational store when that consistency and latency guarantee is required.
Massive historical cross-joins MPP (Trino / Spark) A single-node execution path may exceed memory or latency budgets. Large joins and broad scans often need distributed shuffle and memory, so route them to an engine designed for that workload.
Fuzzy / Full-text search Search Engine (Elastic) Inverted indexes are simply better primitives for relevance sorting than columnar scans.
Bounded analytical serving Smart Data Gateway This is the candidate sweet spot: Locality, vectorized execution, strict resource budgets, and latency targets demonstrated under representative concurrency and failure conditions.

3. The Unsexy Reality of Production Resilience

Everyone loves talking about distributed consensus algorithms; nobody wants to talk about configuring cgroups so an OOM-killed pod doesn't take down the billing system. In modern Agile™ corporate culture, the prevailing wisdom is often "deliver the happy path now, let the SREs fix the edge cases later."

That works fine if you are shipping a frontend button. It is a spectacular way to cause a catastrophic, cross-tenant data bleed when building critical platform infrastructure.

As utilization approaches saturation, queueing delay becomes highly sensitive to burstiness. Adding average capacity does not fix tail latency. Interactive workloads require a warm capacity envelope. Kubernetes autoscaling operates on a control-plane timescale (minutes), which is entirely too slow to absorb a burst of interactive agent requests (milliseconds). The Gateway survives by enforcing strict concurrency limits, admission control, fast/slow routing lanes, and explicitly fast-failing bad requests.

4. Total Cost of Ownership: From Cloud Bill to Query Unit Economics

A lower compute bill is not proof of a lower TCO. The architecture wins only when the complete, comparable cost of delivering the same business outcome is lower.

— The economic rule for this design

A Smart Data Gateway is not automatically cheaper than an MPP warehouse. It creates an opportunity to change the cost curve for a particular workload: bounded, repeated, latency-sensitive analytical reads that do not need a distributed execution plan. Whether that opportunity becomes a real saving depends on the workload mix, cache behaviour, concurrency, freshness requirements, engineering effort, and the price of the capacity that remains behind the Gateway.

The TCO argument must therefore be reproducible. An enterprise buyer should be able to take the workload sample, cost ledger, rate card, and assumptions in this section and recalculate the result. Percentages such as “90% cheaper,” fixed query-size cutoffs, or a universal break-even spend are not architecture facts; they are hypotheses to validate against a specific workload and deployment.

The economic contract

Compare the cost of delivering the same query outcomes at the same security, freshness, availability, and latency objectives. Include the Gateway, the remaining MPP or fallback capacity, data access, support, engineering, and operational risk. Do not compare a fully loaded incumbent bill with only the Gateway's container bill.

4.1 Define the boundary before adding up costs

Choose a measurement period (usually a month) and a consistent workload boundary. Include the application or BI queries that the Gateway is intended to serve, not every ETL job and historical scan in the estate. Keep common costs visible and allocate them consistently rather than making them disappear from one side of the comparison.

4.2 Build a cost ledger from query telemetry

Aggregate cloud invoices tell you what the platform cost, but not which workload caused the cost or whether a particular tenant is profitable. Emit a metering record for each query attempt and reconcile its aggregate totals to infrastructure invoices. A practical ledger includes:

  • tenant_id, query_id, query_class, pricing_version, and a stable request/idempotency key.
  • Outcome and route: accepted, rejected, succeeded, failed, cancelled, cache hit/miss, local execution, or MPP fallback.
  • Resource use: CPU-seconds, peak memory or memory-GiB-seconds, spill bytes, execution time, and queue wait.
  • Data use: remote bytes read, cache bytes read, object-store request counts, catalog calls, result bytes, and separately billable egress.
  • Retry count and reason, plus the attribution of retries to client, dependency, or Gateway failure.

Do not log raw query results, credentials, access tokens, or sensitive parameter values just to support billing. Use opaque identifiers and controlled audit references. Define whether a field is measured, estimated, or derived; a precise-looking metric is not reliable if its collection semantics are ambiguous.

$$ \text{Monthly TCO} = \text{Fixed platform cost} + \text{Usage-driven cost} + \text{Amortized build \& operating cost} $$

Keep cost categories mutually exclusive. For example, if the platform invoice already includes worker compute, do not add the same compute again as a separate allocation. For an internal cost-per-successful-query metric, divide fully loaded monthly cost by successful billable query count, but do not use that average alone to set the rate card: a metadata-only lookup and a multi-gigabyte scan do not consume the same resources.

This hybrid boundary is usually a more defensible business case than promising to replace the warehouse wholesale.

4.4 From TCO to a client price: separate cost accounting from billing

Internal cost accounting should be as granular as practical. Customer billing should be stable, explainable, predictable, and difficult to game. Billing every CPU millisecond or memory allocation directly can produce invoices that customers cannot forecast. Billing every query at one flat rate is easier to explain but subsidizes expensive queries with cheap ones and can encourage inefficient workloads.

A pragmatic commercial model is a monthly platform fee + metered Gateway Execution Units (GEUs) + explicitly listed pass-through or separately metered services. GEUs are a versioned product abstraction, not a universal industry standard. They convert measured resource consumption into understandable usage credits while allowing the implementation to evolve. A contract can instead use direct CPU/byte meters if that better fits the customer.

Charge componentWhat it recoversPricing guidance
Platform feeTenant isolation, policy and audit services, baseline availability, minimum warm capacity, support tier, and a share of fixed operating cost.Monthly subscription or committed minimum. Define included capacity, environments, support response, and retention explicitly.
GEU usageVariable query execution cost, including an allocated share of usage-driven overhead if the rate design says so.Use measured CPU, memory, spill, and execution class to derive credits. Publish the pricing version and how each class is calculated.
Storage / refreshPersistent result cache, materialization, refresh jobs, and retained claim-check payloads.Meter by GB-month, refresh execution, or another observable unit. Avoid charging twice when a resource is already included in GEUs.
Egress / exceptional workMaterial data transfer, large exports, MPP fallback, or asynchronous jobs that have a different cost profile.Show the applicable rate or quote in advance. Never hide an expensive fallback behind a low flat query fee.

4.5 Derive a GEU from measured resources

Start with a representative query corpus. For each query, measure CPU-seconds, memory pressure or memory-GiB-seconds, spill, remote bytes, request count, result bytes, and cache status. Convert these measurements into a resource score using weights calibrated from marginal cost and capacity constraints.

$$ \text{GEU}(q) = \max(\text{minimum charge}, \text{weighted resource score}) $$

One possible internal score is:

$$ \text{Score}(q) = w_{\text{cpu}} \cdot \frac{\text{CPU}(q)}{\text{CPU}_{\text{ref}}} + w_{\text{mem}} \cdot \frac{\text{Mem}(q)}{\text{Mem}_{\text{ref}}} + w_{\text{spill}} \cdot \frac{\text{Spill}(q)}{\text{Spill}_{\text{ref}}} $$

Remote bytes, object-store requests, and result egress may be charged as separate meters if their costs vary materially or customers can understand them better that way. Do not count the same cost both inside GEUs and as a separate line item. The reference values and weights must come from observed cost and capacity data, not intuition alone. Keep the internal resource score separate from the published commercial rate so the latter can be forecastable and contractually stable.

Illustrative query classExample GEUsHow the class is assigned
Light0.2Low CPU and memory use, bounded result, no material spill; commonly a warm-cache or selective lookup.
Standard1.0Reference workload against which the unit is calibrated.
Heavy bounded5.0Higher scan, CPU, memory, or aggregation cost but still inside the Gateway's approved envelope.
Exceptional / routed10+ or separate rateNear-limit work, large export, or MPP fallback; require preflight estimation, explicit policy, or separate pricing.

These GEU values are examples for explaining the method, not recommended production rates. Calibrate the classes on a training sample, then validate them on held-out queries. If two queries assigned the same class have radically different costs, improve the class model or use a separate meter. Version the classifier and rate card; retain the version used for every invoice so that a pricing change does not silently rewrite historical charges.

4.6 Calculate the price per GEU

Define the cost boundary before calculating a rate. Let \( F \) be monthly fixed cost attributable to this service, \( V \) be monthly variable cost for the measured workload, \( U \) be total monthly billable GEUs, and \( m \) be the target gross margin as a fraction (for example, 0.40 for 40%). Fixed and variable costs must be mutually exclusive; do not allocate the same cost to both.

Pure usage-based pricing. If all recoverable costs are carried by usage, the fully loaded cost per GEU is:

$$ C_{\text{GEU}} = \frac{F + V}{U} $$

To achieve target gross margin \( m \), price is cost divided by one minus the margin:

$$ P_{\text{GEU}} = \frac{C_{\text{GEU}}}{1 - m} $$

Recommended hybrid pricing. If the monthly platform fee fully recovers the applicable fixed cost, and GEU usage charges recover variable cost, calculate the two rates separately:

$$ P_{\text{platform}} = \frac{F}{1 - m} $$
$$ P_{\text{GEU}} = \frac{V / U}{1 - m} $$

This hybrid formulation makes the fixed-capacity commitment visible instead of forcing low-volume tenants to absorb all fixed cost through a volatile usage rate. It assumes the platform fee actually recovers the fixed cost assigned to it and that usage revenue recovers the variable costs assigned to GEUs, each at the same target margin. If the fee includes an allowance, discounts, credits, committed capacity, or shared-cost recovery, model those explicitly rather than applying these formulas unchanged.

Gross margin is not markup

A 40% markup on cost means price = 1.4 × cost, which produces a gross margin of only 28.6%. To obtain a 40% gross margin, use price = cost / 0.60. These equations target gross margin on the costs included in COGS; taxes, sales commissions, financing, corporate overhead, and other below-gross-profit costs need separate treatment.

4.8 Check the low-volume and peak-load cases

A usage-only model may not recover fixed cost when adoption is low. With the same $8,000 variable COGS but only 5 million GEUs, variable cost rises to $0.0016 per GEU. At a 40% gross margin, the usage rate would need to be about $0.002667 per GEU. That still does not recover the $12,000 fixed platform cost unless the rate also carries a fixed-cost allocation or the contract includes a platform fee/minimum commitment.

Model at least three demand cases before setting a rate card. Averages hide the economics of warm capacity and concurrency.

4.9 Prove customer savings, not just provider margin

Provider margin is only one side of the business case. Enterprise adoption also requires evidence that the customer can deliver an equivalent serving workload at a lower all-in cost. Compare the Gateway against the incremental serving cost of the incumbent architecture—not the entire data platform if both designs continue to use the same lakehouse storage.

Include the costs that genuinely change:

  • MPP compute and idle or reserved capacity attributable to the serving workload.
  • BI query-serving infrastructure, gateways, and cache infrastructure.
  • Operational support, upgrades, and relevant engineering allocation.
  • Additional Gateway platform charges, storage, egress, and data movement.
  • MPP capacity that must remain because the Gateway cannot serve every query class.

Let \( C_{\text{baseline}} \) be the monthly cost of delivering the equivalent incumbent service and \( C_{\text{gateway,all-in}} \) be the Gateway's monthly all-in cost for the same scope and service level. Then:

$$ S = C_{\text{baseline}} - C_{\text{gateway,all-in}} $$
$$ \text{Savings } \% = \left( \frac{S}{C_{\text{baseline}}} \right) \times 100 $$

For example, if a measured incumbent serving workload costs $60,000/month and the Gateway's fully loaded, equivalent service costs $33,333/month, the modeled saving is $26,667/month, or about 44.4%. This is a hypothetical illustration, not a performance claim. The Gateway-side number must include its platform fee, usage, engineering amortization, retained MPP/fallback capacity, storage, egress, support, and other incremental costs. The baseline must include the cost that actually goes away—not the whole warehouse bill if ETL and other workloads still need it.

Where shared capacity cannot be retired, report both avoidable cost and allocated cost. Avoidable cost supports the near-term cash-saving case; allocated cost helps compare long-run architecture economics. Do not claim savings from a reduction in allocated spend if the cash invoice remains unchanged.

4.10 Billing rules are part of correctness

  • Rejected before execution: schema, authorization, or admission-control rejection should normally incur no execution charge; any platform subscription remains governed by the contract.
  • Gateway-caused retries: do not bill the customer twice for internal retries caused by a platform fault. Track attempts separately from logical requests.
  • Client cancellation: state whether charges reflect measured consumption up to cancellation, and make that rule visible before execution.
  • Cache hits: charge according to the published meter. A lower GEU class is justified only if the cost model shows materially lower consumption; cache hits still incur lookup and retention costs.
  • Fallback and asynchronous jobs: disclose the route and estimated/actual charge before running expensive work where technically possible. Do not silently route a low-cost request into a high-cost execution path.
  • Budgets and idempotency: support tenant budgets, preflight estimates, spend caps, and idempotent billing records so duplicate delivery does not duplicate charges.
  • Invoice evidence: expose tenant, logical query ID, pricing version, units, rate, route, and relevant usage measures without leaking query results or sensitive values.

4.11 A validation plan that can survive procurement

  1. Capture a representative sample. Include query classes, tenant skew, cache warm/cold states, concurrency bursts, snapshot changes, failures, and large-query outliers—not only the easiest dashboard requests.
  2. Establish the baseline. Measure the incumbent service's billable usage, reserved/minimum capacity, data requests, network, support, and the cost of meeting the same SLOs.
  3. Replay on the Gateway. Use equivalent security filters, result semantics, freshness, and correctness checks. Record CPU, memory, remote bytes, request counts, latency percentiles, errors, retries, and fallback rate.
  4. Reconcile cost. Allocate invoices to the measured period and workload. Explain residual/shared costs and amortize implementation costs over an explicit horizon.
  5. Calibrate and hold out. Derive GEU weights and query classes from part of the corpus, then test prediction error on queries not used to tune the model. Publish confidence ranges where metering is estimated.
  6. Run shadow billing. Produce invoices without charging, investigate surprising line items, and test low/expected/peak and cold-cache scenarios before contracts depend on the rate card.
  7. Review quarterly. Reconcile actual COGS, margins, SLOs, and customer savings. Change pricing only through a versioned policy and a transparent customer notice.
The break-even rule

The Gateway is economically justified when the measured, fully loaded cost of the Gateway plus the residual analytical platform is lower than the comparable incumbent cost, while meeting the required correctness, freshness, security, and SLOs. If that inequality does not hold for a workload, keep it on the existing engine. The purpose of the Gateway is to place the boundary correctly—not to win every query.

4.12 What this means for enterprise adoption

Enterprise adoption depends on more than a low unit price. Procurement and platform owners need a repeatable bill of materials, a defensible cost allocation, a published meter, spend limits, auditable invoices, clear fallback behaviour, and evidence that the service remains viable at low and peak utilization. The price model is therefore part of the architecture: it influences admission control, query routing, cache policy, tenant quotas, and which work should be asynchronous.

Do not promise that 80%–95% of queries will be intercepted, that every query under a fixed scan size belongs on the Gateway, or that the design will be 90% cheaper without workload evidence. Instead, measure the query distribution, identify the fraction that fits the Gateway's verified envelope, and publish the resulting economics. That is a stronger enterprise story than a universal savings percentage.

5. The CTO Conversation: Build vs. Buy

At some point, your CTO is going to look at this architecture and rightly ask: "Why on earth are we paying engineering salaries to build a custom data gateway when I just played golf with a vendor who promised their tool does this out of the box?"

It's a fair question. The build-vs-buy question should not be answered with "custom is cheaper" (it isn't). Building is only justified when the workload-specific control surface creates durable business value.

Hasura v3 (DDN)

Great API federation, but relies on pushing compute down to the backend database. Lacks the embedded analytical execution (DuckDB) we need to avoid waking up the warehouse.

Cube (Cube Cloud)

Excellent semantic layer for dashboards, but less focused on sandboxing autonomous AI agent (MCP) interactions and enforcing dynamic AST-level LLM guardrails.

MotherDuck

Managed, serverless DuckDB. Exceptional for hybrid execution and collaborative querying. However, it operates as a cloud data warehouse, meaning compute and data leave your VPC, differing from a pure edge-native stateless gateway.

Spice.ai Closest Match

Built on Rust, Arrow, and embedded DuckDB. Highly compelling edge execution, but adopting a managed service limits total engineering control over bespoke multi-tenant auth integrations and data sovereignty boundaries.

So, what do you tell the CTO? You build it when you need specific capabilities that generic tools can't support out-of-the-box, such as deeply customized Lua edge caching for deterministic state changes, dynamic AST-level OIDC claim injection for Row-Level Security across 100+ global tenants, and strict data sovereignty guarantees where raw execution cannot leave your own VPC.

6. Extending for Enterprise Adoption

This is where the architecture evolves from a specialized Iceberg and Flight engine into a true enterprise data platform. Five specific pillars move the Gateway beyond single-catalog limits and human-only clients:

01 Zero-trust security & governance

Dynamic AST masking

The policy engine validates the query plan and applies approved masking or projection rules before results are exposed; verify that rewrites preserve authorization semantics.

WORM audit vaults

Every query, trace, rewrite and byte count lands in immutable storage.

Agentic guardrails

Timeouts, record limits and row-level security stop runaway scans.

02 Operational resiliency & FinOps

Noisy-neighbour protection

Rate limits cap RAM and spill to NVMe instead of crashing the engine.

Poison-pill dead-letter queues

Malformed payloads are routed aside, so the system heals itself.

Granular tenant chargeback

Versioned resource meters, query outcomes, and cost reconciliation support explainable per-tenant chargeback. Wall-clock time or bytes scanned alone are not a complete cost model.

03 AI-native & autonomous ops

Native MCP server interface

Governed SQL macros reach LLMs, with breakers on runaway agents.

Dual-format object storage

Iceberg analytics join vector memory zero-copy for similarity search.

Autonomous SecOps & upgrades

Agents patch CVEs and promote only when P99 latency bounds hold.

04 Elastic scale & federation

Multi-catalog federation

Polaris, Unity Catalog, Glue and Hive in one Arrow memory space.

Multi-format reads

Iceberg, Delta Lake and Hudi all read natively — no vendor lock-in.

Cost-based tiered routing

Route queries according to measured resource estimates, memory limits, concurrency, SLOs, and policy; route heavier exports to an asynchronous or distributed path when appropriate.

05 Edge analytics (DuckDB-WASM)

Server-planned, edge-executed

The backend applies authorization and policy before issuing narrowly scoped access to permitted data; edge execution must not bypass row-level security, expiry, revocation, or audit requirements.

Zero-copy in-browser compute

DuckDB-WASM can execute bounded analytical work in the browser when data access, browser memory, device capability, and authorization constraints permit.

Compute shifted to the client

Some compute may shift to the client, but delivery, proxying, browser memory, data egress, and client-device variability remain part of the end-to-end cost and reliability model.

The Payoff

Measured cost reduction

Potentially less dedicated warm capacity and fewer repeated reads, if workload replay proves the reduction. Freshness remains bounded by source commits, snapshot visibility, and cache invalidation.

Security decoupled from application logic

Policy, masking and audit live in the gateway, not in every service.

Agents as first-class clients

MCP, guardrails and vector memory make agents a supported path.

7. Conclusion — Put the Boundary Where It Belongs

Query engines are increasingly becoming commoditized, composable infrastructure. The true differentiating layer of the next decade is the boundary around them: determining who may query, what may be queried, how much computation may be consumed, and what information safely leaves.

The Final Architectural Rule

Deploy the Gateway when measured characteristics fit its latency and economic envelope. Route workloads outside that envelope to the distributed architecture designed for them. Choose the execution boundary from the physics of the workload, not from the popularity of the platform.
