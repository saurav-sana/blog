What This Model Proves—and What It Does Not:

Let’s be honest: a verified specification proves that your idealized mathematical dream matches your design logic under explicit assumptions. It doesn't magically mean your production code is immune to typos, cosmic rays, or an overly enthusiastic intern dropping a database table.

Production correctness requires four complementary layers:

  1. Formally verifying the abstract distributed state transitions against safety and liveness invariants.
  2. Validating environmental assumptions (Redis Lua atomicity, Azure Blob durability, Iceberg version monotonicity, worker lease mechanics).
  3. Enforcing model-code conformance through Model-Based Trace Checking (MBTC) in continuous integration.
  4. Validating physical boundaries via performance benchmarking, chaos testing, and SRE load telemetry.

2. The Concurrency Testing Trap: Why Empirical Testing Lies

Anticipating an architecture review board brings a specific kind of dread. Long before anyone actually asks a question, the mind races to imagine the brutal edge cases reviewers love to throw at a distributed design:

Anticipated Review Board Concurrency Challenges:
  • "If an NGINX NVMe replica crashes mid-stream, can consistent-hash re-mapping leak data across tenant partitions?"
  • "If a Celery worker pauses for garbage collection while its lease expires, can a second worker claim the task and commit a duplicate or out-of-order result?"
  • "Can an out-of-band Iceberg snapshot commit race with query planning and deliver stale or inconsistent financial data to a regulatory auditor?"

Thinking through those scenarios exposes a funny quirk in modern software engineering. Entire engineering blogs and conferences are dedicated to test coverage, mocking tools, and CI/CD pipelines, yet almost nobody in everyday tech talks about formal verification. For decades, distributed systems have suffered from the exact same race conditions, while the industry response remains uniform: write more integration tests, cross your fingers, and rely on hope-driven development.

Diving into formal methods out of sheer curiosity reveals a fascinating escape hatch. Finding a mathematical way to prove that a tricky state transition is bug-free feels like finding a cheat code to reality. Naturally, that brief moment of triumph is quickly humbled by the vertical cliff of the TLA+ learning curve. Realizing that tools for mathematical state verification have existed for over thirty years—while everyone just keeps arguing about test runner speeds—brings a strange mix of amusement and exhaustion.

This naturally highlights why formal validation rarely makes it into sprint planning. Try walking into a planning session and telling a product manager, "We need three days to map out a temporal logic state machine before writing code." The response is always a blank stare and a polite reminder about story points and quarterly velocity. To avoid the steep learning curve, the industry relies on a very convenient defense mechanism: slapping an "academic" or "too theoretical" label on formal methods. It acts as a socially acceptable excuse to overlook high-value validation, default to a "ship fast, patch later" mindset, and stick to standard enterprise practices that prioritize speed over mathematical certainty.

To understand why standard software testing is a rigged game, look at how concurrent systems handle instruction execution. In an idealized, textbook system, imagine N identical processes (such as our DuckDB replicas), each executing a uniform sequence of K steps to finish a task.

If every step from every process could be shuffled like a deck of cards, the total number of global permutations is (N × K)!. However, internal order within each process matters—Process A's third step cannot run before its second step. To eliminate these redundant internal orderings, we divide by the product of internal permutations for each process, yielding the classic symmetrical multinomial coefficient:

\[ \text{Total Interleavings (Symmetrical)} = \frac{(N \times K)!}{(K!)^N} \]

Even in this tidy, symmetrical scenario, the numbers explode. For just 3 workers executing 4 steps each, there are 34,650 possible schedules. Scale that up to 5 concurrent workers executing an 8-step lifecycle, and the possibilities exceed 7.6 × 1024.

The Catch: Real Systems Are Gloriously Asymmetrical

Relying solely on the symmetrical case glosses over the true chaos of production. Real-world DuckDB replicas never march in lockstep. One replica might be handling a heavy, multi-phase partition compaction (K1 = 8), another is serving a fast, lightweight cache hit (K2 = 3), a third is committing an Iceberg metadata snapshot (K3 = 6), and a fourth is stuck in an object store retry loop (K4 = 4).

To account for heterogeneous workloads where every replica executes a different number of steps, the uniform formula upgrades to its generalized form:

\[ \text{Total Interleavings (Asymmetrical)} = \frac{\left(\sum_{i=1}^{N} K_i\right)!}{K_1! \times K_2! \times \dots \times K_N!} \]

Plugging those variable step counts (8, 3, 6, 4) across 4 replicas gives a total of 21 instruction steps, resulting in roughly 120 billion possible execution schedules (1.2 × 1011).

Asymmetry turns non-determinism up to maximum. Because some replicas finish instantly while others drag behind, they create micro-windows of resource contention that standard integration tests will never touch. A CI suite running 1,000,000 tests explores a microscopic fraction of that state space. Concurrency bugs hide comfortably in the unexplored remainder, waiting for a minor network jitter or CPU spike in production to break the system.

The Testing Fallacy in Distributed Systems:
Empirical testing asserts: "For the specific inputs and thread schedules we happened to sample during a lucky test run, the system didn't blow up."

Formal verification proves: "Across every single state reachable in the directed state graph—whether symmetrical or wildly asymmetrical—an invariant violation is mathematically impossible." (Even if learning the math requires a lot of coffee).

3. Industrial Precedent: Why AWS, Microsoft, & MongoDB Bet on TLA+

Formal verification is often viewed as academic theory unsuitable for production engineering. In practice, major cloud platforms rely on formal methods because conventional testing breaks down under distributed concurrency.

Amazon Web Services

AWS reported using TLA+ across critical systems including S3, DynamoDB, and EBS, finding subtle design bugs that had escaped conventional reviews and testing. In one notable DynamoDB case, model checking discovered an obscure concurrency bug whose shortest error trace required an interleaving of 35 separate high-level operations across multiple nodes—a sequence virtually impossible to hit through randomized testing.

MongoDB Replication & Realm Sync

When MongoDB engineered its Raft-based replication engine and Realm Sync protocols, developers turned to TLA+ to explore protocol state spaces. Model checking forced engineers to confront edge cases early, uncovering fundamental synchronization and lease bugs in their replication design before committing code to production.

Microsoft Azure CCF

Microsoft verified the Confidential Consortium Framework (CCF)—a 63,000-line C++ secure cloud ledger—using TLA+ specifications and model-based trace checking in CI. Model checking uncovered six critical consensus bugs that had escaped fuzz testing and chaos engineering.

4. The Abstraction Blueprint & The Architecture Assumption Ledger

A common failure mode when adopting formal methods is attempting to transcribe code line-by-line into math. Translating Python syntax, C++ memory management, or NGINX Lua directives creates an unmanageable model that obscures core distributed interactions.

The Abstraction Principle:
If a component's internal operation cannot alter the global reachability of an illegal distributed state, abstract it to an atomic value or immutable function. If a component introduces concurrency, failure modes, or non-deterministic ordering, model it as an explicit state variable and action.

To master this abstract thinking, consider a distributed worker pulling a task from Azure Managed Redis, generating a heavy financial report, and saving it to blob storage. We must ruthlessly separate what happens locally from what happens across the network.

1. Abstract to an Atomic Value (Safe Internal Operations)

You do not model the CPU parsing a JSON task payload, nor do you model the complex SQL joins the worker executes inside DuckDB to build the report.

  • The "Why": Even if the JSON parser takes 500 milliseconds, or the SQL query processes 10 million rows, these actions occur entirely inside one isolated process's memory. They cannot natively cause a race condition with another node in the cluster.
  • The Abstraction: In the formal model, this entire multi-minute execution phase is reduced to a single, instant mathematical function (e.g., report_data = Generate(task_id)). We assume the local computation is deterministic and correct, treating it as a black box.

2. Model as an Explicit State (Dangerous Distributed Operations)

Conversely, you absolutely must model the worker requesting a lease from Redis, the lease's countdown timer, the worker crashing mid-job, and the network request to save the file.

  • The "Why": These steps involve shared state, concurrency, and time. If Worker A's CPU processing takes too long and its Redis lease expires, Worker B might pick up the exact same task. Now both workers are racing to write to the same storage path simultaneously.
  • The Modeling: You map out explicit state transitions that the model checker will test against every possible interleaving: State: Claiming, State: Processing, State: Writing, State: Committing, along with external disruptive actions like Action: Crash and Action: Lease_Timeout.

The Architecture Assumption Ledger

Formal models are only as good as the axioms they rest on. If our real-world infrastructure violates these assumptions, our mathematical proof is void. This ledger defines the strict environmental boundaries for our "Dangerous Distributed" operations:

  • Assumption A1 (Atomic Lease Claims): Redis Lua scripts execute test-and-set task claiming atomically with respect to other workers. (Without this, our mutual exclusion property fails).
  • Assumption A2 (Storage Acknowledgment): Azure Blob Storage acknowledgments guarantee that payload bytes are durably committed before the SAS URI pointer is returned. (Without this, workers could read incomplete data).
  • Assumption A3 (Monotonic Snapshot Ordering): Table catalog snapshots for any given Apache Iceberg table advance monotonically. We abstract the catalog's internal multi-master commit protocol, trusting the engine handles it.
  • Assumption A4 (Isolated Cache Mutations): Cache entries are populated and invalidated exclusively through our modeled gateway and ETL actions, never via out-of-band database edits.
  • Assumption A5 (Boundary Mapping): Physical runtime state transitions in the actual Python/Rust code correspond directly and exclusively to the atomic labels defined in this specification.

5. The TLA+ Primer: Constructing Formal Logic from System Design

To ground mathematical logic in systems engineering, we anchor every formal concept to our concrete system design: the Multi-Tenant Stateless Query Gateway.

The Core Architectural Distinction: Requests vs. Queries
A common trap in modeling analytical gateways is conflating Queries with Requests. A query hash \(Q_1\) represents normalized SQL text. A request \(R_1\) represents an independent client invocation. Two distinct tenants can execute query \(Q_1\) simultaneously, and Tenant A can submit query \(Q_1\) multiple times concurrently. The job registry must be indexed by Requests, while the predictive cache is indexed by \(\langle\text{Tenant}, \text{Query}, \text{Version}\rangle\).

A. Temporal Logic Operators

In standard programming, assertions evaluate conditions at an instantaneous snapshot. TLA+ temporal logic reasons across entire execution paths over infinite time:

State 0 → State 1 → State 2 → … → State n → …
  • 1. Always (\(\Box P\)) — Safety Invariants

    Formal Meaning: Condition \(P\) is true in every reachable state along every valid execution trajectory.

    \[\Box (\forall c \in \text{Clients} : client\_received[c].\text{tenant} = TenantOf[c])\]

    What it proves: No schedule of thread preemption, worker failure, or cache race conditions can ever produce a state where Client A observes data belonging to Tenant B.

  • 2. Eventually (\(\Diamond P\)) — Progress Guarantees

    Formal Meaning: Condition \(P\) is guaranteed to become true in at least one state in the future.

    \[\Diamond (\text{jobs}[r].\text{state} \in \{\text{"COMPLETED"}, \text{"FAILED"}\})\]

    What it proves: Request \(r\) will not stay queued forever; it is guaranteed to reach a terminal state.

  • 3. Leads-To (\(P \leadsto Q\)) — Terminal Liveness

    Formal Meaning: Defined as \(\Box(P \implies \Diamond Q)\). Whenever state \(P\) occurs, state \(Q\) is guaranteed to follow.

    \[(\text{jobs}[r].\text{state} \in \text{Pending}) \leadsto (\text{jobs}[r].\text{state} \in \text{Terminal})\]

    What it proves: Under the model's fairness assumptions and bounded retries, every admitted request eventually reaches a terminal state without hanging indefinitely.

  • 4. Weak Fairness (\(\text{WF}_{\text{vars}}(A)\))

    Formal Meaning: Excludes model behaviors in which action \(A\) remains continuously enabled forever but is never taken.

    Gateway Example: WF_vars(ClaimTask) ensures that if an idle worker sees a queued task, the model checker cannot explore infinite stuttering steps where the worker remains idle forever while work is available.

  • 5. Strong Fairness (\(\text{SF}_{\text{vars}}(A)\))

    Formal Meaning: Excludes model behaviors in which action \(A\) is enabled repeatedly (infinitely often, even if disabled intermittently between steps) but is never taken.

    Gateway Example: SF_vars(ETLCommit) guarantees that background table commits and cache invalidations are never starved out indefinitely by continuous read traffic.

B. Mathematical Logic & Set Operations

  • Universal Quantification (\(\forall x \in S : P(x)\)): Condition \(P(x)\) holds for every item in set \(S\).
  • Existential Quantification (\(\exists x \in S : P(x)\)): There exists at least one item in set \(S\) satisfying \(P(x)\).
  • Prime Operator (\(x'\)): Denotes the variable's value in the next state. The transition is an algebraic constraint: 
    task_queue' = Tail(task_queue)
  • Frame Conditions (UNCHANGED): TLA+ requires explicit definition of unmutated variables. If a variable is omitted, it can take arbitrary values in the next state: 
    UNCHANGED <<catalog_snapshot, cache, blob_storage>>
  • Function Mutation (EXCEPT): Updates specific keys while preserving all others: 
    cache' = [cache EXCEPT ![t][q][v] = [valid |-> TRUE, blob_id |-> b_id]]

6. The Complete Formal Specification in PlusCal

Below is the complete, runnable formal specification of the Smart Data Gateway in PlusCal (SmartDataGatewaySafety.tla). It models the full distributed lifecycle:

  • Decoupled Requests and normalized Queries via function mappings (TenantOf, QueryOf, ClientOf, ProtocolOf).
  • Atomic dequeue and lease-epoch increments simulating Redis Lua scripts (Assumption A1).
  • Bounded worker crashes (MaxCrashes), fair crash recovery, and independent fair lease management.
  • Stale-worker commit rejection preventing double-commits after lease expiration.
  • Rigorous blob inventory accounting (INV-6) guaranteeing zero leaked or double-booked storage pointers.
SmartDataGatewaySafety.tla (Complete Executable Model) 
---------------------- MODULE SmartDataGatewaySafety ----------------------
EXTENDS Naturals, Sequences, FiniteSets, TLC

CONSTANTS
    Tenants,          \* {"T1", "T2"}
    Clients,          \* {"C1", "C2", "C3"}
    Requests,         \* {"R1", "R2", "R3"}
    Queries,          \* {"Q1"}
    Workers,          \* {"W1", "W2"}
    Blobs,            \* bounded blob pool, must satisfy |Blobs| >= |Requests| (A7)
    MaxSnapshot,      \* max table snapshot version
    MaxAttempts,      \* max execution attempts per request
    MaxCrashes,       \* crash budget (finite-failure assumption, needed for liveness)
    TenantOf,         \* Requests -> Tenants
    QueryOf,          \* Requests -> Queries
    ClientOf,         \* Requests -> Clients
    ProtocolOf        \* Requests -> {"FLIGHT", "REST"}

ASSUME
    /\ DOMAIN TenantOf = Requests /\ DOMAIN QueryOf = Requests
    /\ DOMAIN ClientOf = Requests /\ DOMAIN ProtocolOf = Requests
    /\ \A r \in Requests : /\ TenantOf[r] \in Tenants
                           /\ QueryOf[r] \in Queries
                           /\ ClientOf[r] \in Clients
                           /\ ProtocolOf[r] \in {"FLIGHT", "REST"}
    /\ Cardinality(Blobs) >= Cardinality(Requests)

(*--algorithm SmartDataGatewaySafety

variables
    catalog_snapshot = [t \in Tenants |-> 1],
    cache = [t \in Tenants |-> [q \in Queries |-> [v \in 1..MaxSnapshot |->
                [valid |-> FALSE, blob_id |-> "NONE"]]]],
    task_queue = <<>>,
    jobs = [r \in Requests |-> [
        state       |-> "IDLE",
        owner       |-> "NONE",
        lease_epoch |-> 0,
        attempts    |-> 0,
        tenant      |-> TenantOf[r],
        query       |-> QueryOf[r],
        version     |-> 0,
        blob_ptr    |-> "NONE",
        protocol    |-> ProtocolOf[r]
    ]],
    blob_storage = [b \in Blobs |-> [allocated |-> FALSE, tenant |-> "NONE", version |-> 0]],
    client_received = [c \in Clients |-> [blob_id |-> "NONE", tenant |-> "NONE", version |-> 0]],
    available_blobs = Blobs,
    worker_alive = [w \in Workers |-> TRUE],
    commit_count = [r \in Requests |-> 0],
    crashes = 0;

define
    Pending  == {"QUEUED", "CLAIMED", "RUNNING", "RESULT_WRITTEN"}
    Terminal == {"COMPLETED", "FAILED"}

    \* ===================== SAFETY INVARIANTS =====================

    \* INV-1: a client only ever holds a live blob owned by its own tenant
    TenantIsolation ==
        \A c \in Clients :
            client_received[c].blob_id /= "NONE" =>
                /\ \E r \in Requests : ClientOf[r] = c /\ client_received[c].tenant = TenantOf[r]
                /\ blob_storage[client_received[c].blob_id].allocated
                /\ blob_storage[client_received[c].blob_id].tenant = client_received[c].tenant

    \* INV-2: a COMPLETED ticket points at a live blob of matching tenant and version
    ClaimCheckIntegrity ==
        \A r \in Requests :
            jobs[r].state = "COMPLETED" =>
                /\ jobs[r].blob_ptr /= "NONE"
                /\ blob_storage[jobs[r].blob_ptr].allocated
                /\ blob_storage[jobs[r].blob_ptr].tenant = jobs[r].tenant
                /\ blob_storage[jobs[r].blob_ptr].version = jobs[r].version

    \* INV-3: a valid cache entry is for the current snapshot and a live, matching blob
    CacheCoherenceFreshness ==
        \A t \in Tenants : \A q \in Queries : \A v \in 1..MaxSnapshot :
            cache[t][q][v].valid =>
                /\ v = catalog_snapshot[t]
                /\ blob_storage[cache[t][q][v].blob_id].allocated
                /\ blob_storage[cache[t][q][v].blob_id].tenant = t
                /\ blob_storage[cache[t][q][v].blob_id].version = v

    \* INV-4: lease/ticket bookkeeping is internally consistent
    LeaseConsistency ==
        \A r \in Requests :
            /\ jobs[r].state \in {"CLAIMED", "RUNNING", "RESULT_WRITTEN"} => jobs[r].owner \in Workers
            /\ jobs[r].state \in {"IDLE", "QUEUED", "FAILED"} => jobs[r].blob_ptr = "NONE"
            /\ jobs[r].state = "RESULT_WRITTEN" => jobs[r].blob_ptr /= "NONE"

    \* INV-5: each request commits at most once
    SingleCommit == \A r \in Requests : commit_count[r] <= 1

    \* INV-6: no leaked or double-booked blobs
    BlobAccounting ==
        /\ \A b \in Blobs : (b \in available_blobs) <=> ~blob_storage[b].allocated
        /\ \A b \in Blobs : blob_storage[b].allocated => \E r \in Requests : jobs[r].blob_ptr = b

    \* INV-7: Flight and REST paths never cross
    ProtocolSeparation ==
        /\ \A r \in Requests :
              ProtocolOf[r] = "FLIGHT" =>
                  /\ jobs[r].state \in {"IDLE", "COMPLETED"}
                  /\ jobs[r].owner \in {"NONE", "MONOLITH"}
        /\ \A r \in Requests : ProtocolOf[r] = "REST" => jobs[r].owner \in Workers \cup {"NONE"}
        /\ \A i \in 1..Len(task_queue) : ProtocolOf[task_queue[i]] = "REST"

    \* ===================== LIVENESS (needs fairness) =====================
    LiveTermination ==
        \A r \in Requests : (jobs[r].state \in Pending) ~> (jobs[r].state \in Terminal)
end define;

\* =========================================================================
\* CLIENT
\* =========================================================================
fair process ClientProcess \in Requests
variables
    my_tenant   = TenantOf[self],
    my_query    = QueryOf[self],
    my_client   = ClientOf[self],
    my_proto    = ProtocolOf[self],
    req_version = 0;
begin
ClientStart:
    req_version := catalog_snapshot[my_tenant];

CheckCache:
    if cache[my_tenant][my_query][req_version].valid then
        client_received[my_client] := [
            blob_id |-> cache[my_tenant][my_query][req_version].blob_id,
            tenant  |-> my_tenant,
            version |-> req_version
        ];
        goto ClientDone;
    end if;

RouteProtocol:
    if my_proto = "FLIGHT" then
        goto ExecuteFlightSync;
    else
        goto EnqueueRest;
    end if;

EnqueueRest:
    jobs[self] := [
        state       |-> "QUEUED",
        owner       |-> "NONE",
        lease_epoch |-> 0,
        attempts    |-> 1,
        tenant      |-> my_tenant,
        query       |-> my_query,
        version     |-> req_version,
        blob_ptr    |-> "NONE",
        protocol    |-> "REST"
    ];
    task_queue := Append(task_queue, self);

AwaitRest:
    await jobs[self].state \in Terminal;
    if jobs[self].state = "COMPLETED" then
        client_received[my_client] := [
            blob_id |-> jobs[self].blob_ptr,
            tenant  |-> my_tenant,
            version |-> jobs[self].version
        ];
    end if;
    goto ClientDone;

ExecuteFlightSync:
    await available_blobs /= {};
    with b \in available_blobs do
        available_blobs := available_blobs \ {b};
        blob_storage[b] := [allocated |-> TRUE, tenant |-> my_tenant, version |-> req_version];
        jobs[self] := [
            state       |-> "COMPLETED",
            owner       |-> "MONOLITH",
            lease_epoch |-> 1,
            attempts    |-> 1,
            tenant      |-> my_tenant,
            query       |-> my_query,
            version     |-> req_version,
            blob_ptr    |-> b,
            protocol    |-> "FLIGHT"
        ];
        client_received[my_client] := [blob_id |-> b, tenant |-> my_tenant, version |-> req_version];
    end with;

ClientDone:
    skip;
end process;

\* =========================================================================
\* COMPUTE WORKER
\* =========================================================================
fair process ComputeWorker \in Workers
variables
    curr_req   = "NONE",
    curr_epoch = 0,
    curr_blob  = "NONE";
begin
ClaimTask:
    while TRUE do
        await Len(task_queue) > 0 /\ worker_alive[self];
        with r = Head(task_queue) do
            task_queue := Tail(task_queue);
            curr_req   := r;
            curr_blob  := "NONE";
            if jobs[r].state = "QUEUED" then
                curr_epoch := jobs[r].lease_epoch + 1;
                jobs[r] := [jobs[r] EXCEPT
                    !.owner       = self,
                    !.state       = "CLAIMED",
                    !.lease_epoch = jobs[r].lease_epoch + 1
                ];
            else
                curr_epoch := 0;
            end if;
        end with;

    StartExecution:
        if worker_alive[self] /\ curr_epoch > 0
           /\ jobs[curr_req].lease_epoch = curr_epoch
           /\ jobs[curr_req].state = "CLAIMED" then
            jobs[curr_req] := [jobs[curr_req] EXCEPT !.state = "RUNNING"];
        else
            goto ClaimTask;
        end if;

    OffloadBlob:
        if worker_alive[self] /\ jobs[curr_req].lease_epoch = curr_epoch
           /\ jobs[curr_req].state = "RUNNING" /\ available_blobs /= {} then
            with b \in available_blobs do
                available_blobs := available_blobs \ {b};
                curr_blob := b;
                blob_storage[b] := [
                    allocated |-> TRUE,
                    tenant    |-> jobs[curr_req].tenant,
                    version   |-> jobs[curr_req].version
                ];
                jobs[curr_req] := [jobs[curr_req] EXCEPT
                    !.blob_ptr = b,
                    !.state    = "RESULT_WRITTEN"
                ];
            end with;
        else
            goto ClaimTask;
        end if;

    CommitClaim:
        if worker_alive[self] /\ jobs[curr_req].lease_epoch = curr_epoch
           /\ jobs[curr_req].state = "RESULT_WRITTEN" then
            jobs[curr_req] := [jobs[curr_req] EXCEPT !.state = "COMPLETED"];
            commit_count[curr_req] := commit_count[curr_req] + 1;
            if jobs[curr_req].version = catalog_snapshot[jobs[curr_req].tenant] then
                cache[jobs[curr_req].tenant][jobs[curr_req].query][jobs[curr_req].version] :=
                    [valid |-> TRUE, blob_id |-> curr_blob];
            end if;
        end if;
    end while;
end process;

\* FAULTS: crash (optional, budgeted), recovery (fair), lease expiry (fair)
\* =========================================================================
process Crasher = "Crasher"
begin
CrashLoop:
    while crashes < MaxCrashes do
        with w \in {x \in Workers : worker_alive[x]} do
            worker_alive[w] := FALSE;
            crashes := crashes + 1;
        end with;
    end while;
end process;

fair process Recoverer = "Recoverer"
begin
RecoverLoop:
    while TRUE do
        with w \in {x \in Workers : ~worker_alive[x]} do

7. The Mathematical State-Transition Relations (First-Order TLA+)

When PlusCal is compiled, procedural statements are desugared into first-order predicate logic over pairs of states (\(\langle s, s' \rangle\)) and Linear Temporal Logic (LTL) formulas. Below is a mathematical reconstruction of the principal transition relations produced by the PlusCal model.

1. State Space Tuple

\[\text{vars} \triangleq \langle catalog\_snapshot, cache, task\_queue, jobs, blob\_storage, client\_received, available\_blobs, worker\_alive, commit\_count, crashes, pc \rangle\]

2. Initial State Predicate (\(Init\))

\[ Init \triangleq \begin{aligned}[t] & \land catalog\_snapshot = [t \in Tenants \mapsto 1] \\ & \land cache = [t \in Tenants \mapsto [q \in Queries \mapsto [v \in 1..MaxSnapshot \mapsto [valid \mapsto \textsc{False}, blob\_id \mapsto \text{"NONE"}]]]] \\ & \land task\_queue = \langle \rangle \\ & \land jobs = [r \in Requests \mapsto [state \mapsto \text{"IDLE"}, owner \mapsto \text{"NONE"}, lease\_epoch \mapsto 0, attempts \mapsto 0, \\ & \phantom{\land jobs = [r \in Requests \mapsto [} tenant \mapsto TenantOf[r], query \mapsto QueryOf[r], version \mapsto 0, blob\_ptr \mapsto \text{"NONE"}, protocol \mapsto ProtocolOf[r]]] \\ & \land blob\_storage = [b \in Blobs \mapsto [allocated \mapsto \textsc{False}, tenant \mapsto \text{"NONE"}, version \mapsto 0]] \\ & \land client\_received = [c \in Clients \mapsto [blob\_id \mapsto \text{"NONE"}, tenant \mapsto \text{"NONE"}, version \mapsto 0]] \\ & \land available\_blobs = Blobs \land worker\_alive = [w \in Workers \mapsto \textsc{True}] \land commit\_count = [r \in Requests \mapsto 0] \land crashes = 0 \\ & \land pc = [r \in Requests \mapsto \text{"ClientStart"}] \cup [w \in Workers \mapsto \text{"ClaimTask"}] \cup \\ & \phantom{\land pc = } [\text{"Crasher"} \mapsto \text{"CrashLoop"}] \cup [\text{"Recoverer"} \mapsto \text{"RecoverLoop"}] \cup \\ & \phantom{\land pc = } [\text{"LeaseManager"} \mapsto \text{"LeaseLoop"}] \cup [\text{"LakehouseETL"} \mapsto \text{"ETLCommit"}] \end{aligned} \]

3. Selected Core Action Relations

A. Atomic Task Claiming with Lease Epoch (\(WorkerClaim\))

\[ WorkerClaim(w) \triangleq \begin{aligned}[t] & \land pc[w] = \text{"ClaimTask"} \land worker\_alive[w] \land Len(task\_queue) > 0 \\ & \land \text{LET } r \triangleq Head(task\_queue) \text{ IN } \\ & \phantom{\land} \land task\_queue' = Tail(task\_queue) \\ & \phantom{\land} \land \IF jobs[r].state = \text{"QUEUED"} \\ & \phantom{\land \land} \THEN \land jobs' = [jobs \text{ EXCEPT } ![r].owner = w, ![r].state = \text{"CLAIMED"}, ![r].lease\_epoch = jobs[r].lease\_epoch + 1] \\ & \phantom{\land \land \THEN} \land pc' = [pc \text{ EXCEPT } ![w] = \text{"StartExecution"}] \\ & \phantom{\land \land} \ELSE \land pc' = [pc \text{ EXCEPT } ![w] = \text{"ClaimTask"}] \land \text{UNCHANGED } jobs \\ & \land \text{UNCHANGED } \langle catalog\_snapshot, cache, blob\_storage, client\_received, available\_blobs, worker\_alive, commit\_count, crashes \rangle \end{aligned} \]

B. Stale-Worker Commit Guard (\(WorkerCommit\))

\[ WorkerCommit(w, r, epoch, blob) \triangleq \begin{aligned}[t] & \land pc[w] = \text{"CommitClaim"} \land worker\_alive[w] \\ & \land \IF jobs[r].lease\_epoch = epoch \land jobs[r].state = \text{"RESULT\_WRITTEN"} \\ & \phantom{\land} \THEN \land jobs' = [jobs \text{ EXCEPT } ![r].state = \text{"COMPLETED"}] \\ & \phantom{\land \THEN} \land commit\_count' = [commit\_count \text{ EXCEPT } ![r] = commit\_count[r] + 1] \\ & \phantom{\land \THEN} \land \IF jobs[r].version = catalog\_snapshot[jobs[r].tenant] \\ & \phantom{\land \THEN \land} \THEN cache' = [cache \text{ EXCEPT } ![jobs[r].tenant][jobs[r].query][jobs[r].version] = [valid \mapsto \textsc{True}, blob\_id \mapsto blob]] \\ & \phantom{\land \THEN \land} \ELSE \text{UNCHANGED } cache \\ & \phantom{\land} \ELSE \land \text{UNCHANGED } \langle jobs, commit\_count, cache \rangle \quad \text{(* Stale Commit Rejected *)} \\ & \land pc' = [pc \text{ EXCEPT } ![w] = \text{"ClaimTask"}] \\ & \land \text{UNCHANGED } \langle catalog\_snapshot, task\_queue, blob\_storage, client\_received, available\_blobs, worker\_alive, crashes \rangle \end{aligned} \]

C. Snapshot Invalidation (\(ETLCommit\))

\[ ETLCommit(t) \triangleq \begin{aligned}[t] & \land pc[\text{"LakehouseETL"}] = \text{"ETLCommit"} \land catalog\_snapshot[t] < MaxSnapshot \\ & \land \text{LET } new\_v \triangleq catalog\_snapshot[t] + 1 \text{ IN } \\ & \phantom{\land} \land catalog\_snapshot' = [catalog\_snapshot \text{ EXCEPT } ![t] = new\_v] \\ & \phantom{\land} \land cache' = [cache \text{ EXCEPT } ![t] = [q \in Queries \mapsto [v \in 1..MaxSnapshot \mapsto \\ & \phantom{\land \land cache' = } \IF v < new\_v \THEN [valid \mapsto \textsc{False}, blob\_id \mapsto \text{"NONE"}] \ELSE cache[t][q][v]]]] \\ & \land \text{UNCHANGED } \langle task\_queue, jobs, blob\_storage, client\_received, available\_blobs, worker\_alive, commit\_count, crashes, pc \rangle \end{aligned} \]

Verification Levels: Model Checking vs. Inductive Proofs

It is critical to distinguish bounded model checking from unbounded mathematical proof:

  • Level 1 (TLC Model Checking): Exhaustively checks all reachable states within finite bounds (e.g., 3 requests, 2 workers, 3 snapshots). It verifies that no counterexample exists within that state envelope.
  • Level 2 (Inductive Invariants & TLAPS): Proves an invariant \(\text{Inv}\) unbounded across all possible configurations by proving the inductive base and step: \[\text{Init} \implies \text{Inv} \quad \land \quad \text{Inv} \land [Next]_{\text{vars}} \implies \text{Inv}'\] Discharging this proof requires the TLA+ Proof System (TLAPS) rather than TLC.

Mutation Testing: Confirming the Model Catches Invariant Violations

To verify that our invariants are not vacuously true, we introduce deliberate architectural defects and inspect the resulting TLC counterexamples:

Mutation 1: Dangling Pointer in Claim-Check Sequencing

Modification: Invert OffloadBlob and CommitClaim so the ticket is marked complete before the storage blob is allocated.

Expected TLC Counterexample:

Error: Invariant ClaimCheckIntegrity is violated.
State: jobs["R1"].state = "COMPLETED" /\ jobs["R1"].blob_ptr = "NONE"
Action: CommitClaim executed before OffloadBlob.
Mutation 2: Multi-Tenant Key Collision in Result Cache

Modification: Change cache indexing to omit TenantOf[r], indexing only by query hash and version.

Expected TLC Counterexample:

Error: Invariant TenantIsolation is violated.
State: client_received["C2"] received blob allocated to Tenant "T1".
Action: Request R2 (Tenant T2) hit cache entry populated by Request R1 (Tenant T1) for shared query Q1.
Mutation 3: Stale Worker Commit After Lease Revocation

Modification: Remove the jobs[curr_req].lease_epoch = curr_epoch check in CommitClaim.

Expected TLC Counterexample:

Error: Invariant SingleCommit is violated.
State: commit_count["R1"] = 2.
Action: Stale worker W1 committed R1 after LeaseManager reclaimed and requeued it to W2.

9. From Model Correctness to Implementation Conformance

A verified specification proves that the design is logically sound under its assumptions. It does not prove that a Python or Rust codebase conforms to the model. To close the model-code semantic gap, we use Model-Based Trace Checking (MBTC), drawing on methodologies from Microsoft's CCF and MongoDB.

Step 2: Parameter-Constrained Trace Replay (`TraceSpec.tla`)

A common bug in trace specifications is checking only action names without binding observed variables. A valid trace spec must bind exact observed identifiers to the formal transitions:

TraceSpec.tla (Parameter-Constrained Replay) 
--------------------------- MODULE TraceSpec ---------------------------
EXTENDS SmartDataGatewaySafety, IOUtils, Json

TraceLog == ndJsonDeserialize("tests/traces/run_trace.ndjson")
VARIABLE trace_idx

TraceInit ==
    /\ Init
    /\ trace_idx = 1

TraceNext ==
    /\ trace_idx <= Len(TraceLog)
    /\ LET event == TraceLog[trace_idx]
       IN /\ \/ /\ event.action = "ClaimTask"
                /\ WorkerClaimWithParams(event.worker_id, event.request_id)
             \/ /\ event.action = "OffloadBlob"
                /\ WorkerOffloadWithParams(event.worker_id, event.request_id, event.blob_id)
             \/ /\ event.action = "CommitClaim"
                /\ WorkerCommitWithParams(event.worker_id, event.request_id, event.blob_id)
          /\ trace_idx' = trace_idx + 1

TraceSpec == TraceInit /\ [][TraceNext]_<<vars, trace_idx>>
========================================================================

In continuous integration, the integration test suite runs under chaos fault injection, exports run_trace.ndjson, and evaluates TraceSpec.tla via TLC. If a code refactoring reorders operations (e.g., publishing to Redis before the storage blob write completes), TLC halts, catching implementation drift before deployment.
