ARCHITECTURAL CONFIDENCE
What formal specification and model checking can establish

A TLA+ specification defines an abstract transition system. If TLC completes a configured run without a counterexample, that is evidence that the checked properties hold for the reachable states in that finite model and configuration. It is not a proof that production code conforms, that omitted behaviors are safe, or that assumptions about Redis, object storage, the catalog, and runtime ordering are true.

Credible production assurance requires complementary evidence:

  1. Checking the abstract state machine with TLC and recording exact bounds, properties, tool version, and results.
  2. Validating environmental assumptions (Redis Lua atomicity, Azure Blob durability, Iceberg version monotonicity, worker lease mechanics).
  3. Building and testing a trace-conformance harness that binds observed event parameters to model transitions; this remains proposed until implemented and run.
  4. Validating physical boundaries via performance benchmarking, chaos testing, and SRE load telemetry.

2. Concurrency Testing and the Limits of Sampling

Anticipating an architecture review board brings a specific kind of dread. Long before anyone actually asks a question, the mind races to imagine the brutal edge cases reviewers love to throw at a distributed design:

Anticipated Review Board Concurrency Challenges:
  • "If an NGINX NVMe replica crashes mid-stream, can consistent-hash re-mapping leak data across tenant partitions?"
  • "If a Celery worker pauses for garbage collection while its lease expires, can a second worker claim the task and commit a duplicate or out-of-order result?"
  • "Can an out-of-band Iceberg snapshot commit race with query planning and deliver stale or inconsistent financial data to a regulatory auditor?"

These scenarios expose a limitation rather than a failure of conventional testing: tests exercise selected inputs, schedules, and failure timings. They are essential for validating concrete implementations, but a test suite alone does not enumerate every behavior of a concurrent system. Formal modeling complements testing by making state transitions and nondeterministic choices explicit.

Formal methods offer a disciplined way to explore whether a precise model admits a forbidden state or an execution that violates a stated temporal property. The result depends on the model, its bounds, and the environmental assumptions; it is not a shortcut around implementation testing or operational evidence.

Formal methods do have a learning and maintenance cost, so their value depends on the consequence of failure, the complexity of the protocol, and the team’s ability to keep the model aligned with the implementation. They are most useful when a small number of state transitions govern high-impact properties such as tenant isolation, durable publication, lease fencing, or recovery.

To understand why schedule coverage is difficult, consider how concurrent systems interleave operations. In an idealized, textbook system, imagine N identical processes (such as our DuckDB replicas), each executing a uniform sequence of K steps to finish a task.

If every step from every process could be shuffled like a deck of cards, the total number of global permutations is (N × K)!. However, internal order within each process matters—Process A's third step cannot run before its second step. To eliminate these redundant internal orderings, we divide by the product of internal permutations for each process, yielding the classic symmetrical multinomial coefficient:

\[ \text{Total Interleavings (Symmetrical)} = \frac{(N \times K)!}{(K!)^N} \]

Even in this tidy, symmetrical scenario, the numbers explode. For just 3 workers executing 4 steps each, there are 34,650 possible schedules. Scale that up to 5 concurrent workers executing an 8-step lifecycle, and the possibilities exceed 7.6 × 1024.

The Catch: Real Systems Are Asymmetrical

Relying solely on the symmetrical case understates the true heterogeneity of production. Real-world DuckDB replicas never march in lockstep. One replica might be handling a heavy, multi-phase partition compaction (K1 = 8), another is serving a fast, lightweight cache hit (K2 = 3), a third is committing an Iceberg metadata snapshot (K3 = 6), and a fourth is stuck in an object store retry loop (K4 = 4).

To account for heterogeneous workloads where every replica executes a different number of steps, the uniform formula upgrades to its generalized form:

\[ \text{Total Interleavings (Asymmetrical)} = \frac{\left(\sum_{i=1}^{N} K_i\right)!}{K_1! \times K_2! \times \dots \times K_N!} \]

Plugging those variable step counts (8, 3, 6, 4) across 4 replicas gives a total of 21 instruction steps, resulting in roughly 12 billion possible execution schedules (1.2 × 1010).

This count is a combinatorial illustration, not a count of production behaviors: real systems have partial orders, nondeterministic inputs, retries, failures, and abstraction choices that this simple shuffle model omits. A million tests do not necessarily cover a million distinct schedules, and model checking does not automatically enumerate the real system’s entire state space. The useful comparison is that tests sample concrete executions while TLC explores all reachable states of the finite transition system that was specified and configured.

Complementary techniques, different evidence:
Tests provide evidence about the implementation under the inputs, schedules, and environments actually exercised.

TLC can exhaustively explore the reachable state graph of a finite model/configuration and report a counterexample if a checked invariant fails. A clean run is conditional on the model, constants, specification, and TLC configuration; it is not a blanket proof about production code.

3. Industrial Precedent: Formal Methods in Distributed Systems

Formal verification is often viewed as academic theory unsuitable for production engineering. In practice, major cloud platforms rely on formal methods because conventional testing breaks down under distributed concurrency.

Amazon Web Services

AWS engineers have publicly described using TLA+ to reason about distributed-service designs and finding design errors before implementation (Newcombe et al., "How Amazon Web Services Uses Formal Methods," CACM 2015). The details vary by case; the lesson is not that testing is futile, but that explicit models can expose unusual interleavings and protocol-level assumptions.

MongoDB Replication & Realm Sync

MongoDB engineers have published accounts of using formal methods, including TLA+, to reason about replication and synchronization protocols (Schaf et al., "Model Checking MongoDB," NSDI 2020). Treat these as examples of a useful engineering practice, not evidence that the Smart Data Gateway has itself been verified.

Microsoft Azure CCF

Microsoft’s Confidential Consortium Framework (CCF) materials describe using formal specification and model-based techniques to strengthen confidence in distributed-system behavior. The exact scope and reported findings should be read in their original publication; this article does not independently reproduce those results.

4. The Architecture Assumption Ledger

A common failure mode when adopting formal methods is attempting to transcribe code line-by-line into math. Translating Python syntax, C++ memory management, or NGINX Lua directives creates an unmanageable model that obscures core distributed interactions. Instead, we must ruthlessly abstract safe internal computation (like a CPU parsing JSON or calculating a SQL join) into atomic functions, while explicitly modeling operations that introduce cross-node concurrency, state sharing, or failure.

Because the model operates at this abstract level, any correctness claims depend entirely on the physical implementation upholding these abstracted assumptions. 5. The TLA+ Primer: Constructing Formal Logic from System Design

TLA+ combines state-based mathematics with temporal logic to describe possible system behaviors over sequences of states. In this gateway, it can express safety conditions (something bad never happens) and liveness conditions (something good eventually happens under stated assumptions). A specification is only as meaningful as its state variables, actions, and environment model.

The Core Architectural Distinction: Requests vs. Queries
A common trap in modeling analytical gateways is conflating Queries with Requests. A query hash \(Q_1\) represents normalized SQL text. A request \(R_1\) represents an independent client invocation. Two distinct tenants can execute query \(Q_1\) simultaneously, and Tenant A can submit query \(Q_1\) multiple times concurrently. The job registry must be indexed by Requests, while the result cache is indexed by \(\langle\text{Tenant}, \text{Query}, \text{Snapshot}, \text{SecurityContext}\rangle\).

1. Temporal Logic Operators

In standard programming, assertions evaluate conditions at an instantaneous snapshot. TLA+ temporal logic reasons across entire execution paths over infinite time:

State 0 → State 1 → State 2 → … → State n → …
  • 1. Always (\(\Box P\)) — Safety Invariants

    Formal Meaning: Condition \(P\) is true in every reachable state along every valid execution trajectory.

    \[\Box (\forall r \in \text{Requests} : client\_received[r].\text{delivered} \implies client\_received[r].\text{tenant} = AuthenticatedTenantOf[r])\]

    Intended property: Under the model’s admission, authorization, cache-key, and delivery assumptions, no reachable modeled state lets a request receive a result bound to a different authenticated tenant. This conclusion is only as strong as the modeled state and checked configuration.

  • 2. Eventually (\(\Diamond P\)) — Progress Guarantees

    Formal Meaning: Condition \(P\) is guaranteed to become true in at least one state in the future.

    \[\Diamond (\text{jobs}[r].\text{state} \in \{\text{"ACCEPTED"}, \text{"FAILED"}\})\]

    Interpretation: This eventuality is a liveness claim only when checked as part of the behavior specification with explicit fairness and environment assumptions. By itself, a state formula with \(\Diamond\) is not a claim that all requests succeed; the permitted terminal outcomes explicitly include failure states (e.g., resources exhausted or timeout limits reached).

  • 3. Leads-To (\(P \leadsto Q\)) — Terminal Liveness

    Formal Meaning: Defined as \(\Box(P \implies \Diamond Q)\). Whenever state \(P\) occurs, state \(Q\) is guaranteed to follow.

    \[ \text{Reclaimable}(b) \leadsto \text{Reclaimed}(b) \]

    Intended liveness claim: If the executable specification includes the required fairness and recovery assumptions, every blob that becomes eligible for garbage collection eventually reaches a reclaimed state.

2. The Fairness Assumptions

Liveness guarantees in TLA+ fundamentally depend on the environment properties provided to the model. We explicitly define the following fairness assumptions (preventing infinite stuttering where enabled actions are ignored forever) to verify system progress:

  • Weak Fairness (\(\text{WF}_{\text{vars}}(A)\)): The model assumes the scheduler will eventually allocate CPU to processes. Specifically, we apply Weak Fairness to WorkerClaim, StartExecution, CommitJob, and PopulateCache, ensuring active workers aren't permanently starved while work is available.
  • Strong Fairness (\(\text{SF}_{\text{vars}}(A)\)): Applied to actions that might only be intermittently enabled. We apply Strong Fairness to GCReclaim and ETLCommit to guarantee that background daemons (like garbage collection and cache invalidation) are never permanently starved out by a continuous flood of read traffic.

3. Mathematical Logic & Set Operations

  • Universal Quantification (\(\forall x \in S : P(x)\)): Condition \(P(x)\) holds for every item in set \(S\).
  • Existential Quantification (\(\exists x \in S : P(x)\)): There exists at least one item in set \(S\) satisfying \(P(x)\).
  • Prime Operator (\(x'\)): Denotes the variable's value in the next state. The transition is an algebraic constraint: 
    task_queue' = Tail(task_queue)
  • Frame Conditions (UNCHANGED): TLA+ requires explicit definition of unmutated variables. If a variable is omitted, it can take arbitrary values in the next state: 
    UNCHANGED <<catalog_snapshot, cache, blob_storage>>
  • Function Mutation (EXCEPT): Updates specific keys while preserving all others: 
    cache' = [cache EXCEPT ![t][q][v] = [valid |-> TRUE, blob_id |-> b_id]]

6. State Variables, Actions, and the 6-Stage Lifecycle

Without a strict state machine, a distributed query gateway will eventually serve corrupted, stale, or cross-tenant data. To prevent a catastrophic race condition between a worker writing a result (staging) and a client reading it (delivery), the formal specification mandates a strict 6-Stage Lifecycle:

  1. Admit: Client connects, JWT is verified against the payload, and the request is routed.
  2. Bind: Request firmly locks onto the current authoritative Iceberg catalog snapshot.
  3. Execute: Compute worker claims the task from the queue and evaluates the query.
  4. Stage (PublishPointer): The worker writes the raw data to a temporary blob/S3 path. Crucially, the job is not yet complete.
  5. Accept (CommitJob): The Authoritative Boundary. An atomic transaction validates that the worker's lease is still active and the snapshot hasn't advanced. Only if true, the state transitions to "ACCEPTED".
  6. Deliver: The client reads the blob. This action is strictly gated; a client can only read if job.state == "ACCEPTED".

Initializes the selected state variables:

3. Selected Core Action Relations

A. Atomic Task Claiming with Lease Epoch Increment (\(WorkerClaim\))

\[WorkerClaim(w) \triangleq \begin{aligned} & \land pc[w] = \text{"ClaimTask"} \land worker\_alive[w] \land Len(task\_queue) > 0 \\ & \land \text{LET } r \triangleq Head(task\_queue) \text{ IN } \\ & \phantom{\land} \land task\_queue' = Tail(task\_queue) \\ & \phantom{\land} \land \textbf{IF } jobs[r].state = \text{"QUEUED"} \\ & \phantom{\land \land} \textbf{THEN } \land jobs' = [jobs \text{ EXCEPT } ![r].owner = w, ![r].state = \text{"CLAIMED"}, ![r].lease\_epoch = jobs[r].lease\_epoch + 1] \\ & \phantom{\land \land \textbf{THEN}} \land pc' = [pc \text{ EXCEPT } ![w] = \text{"StartExecution"}] \\ & \phantom{\land \land} \textbf{ELSE } \land pc' = [pc \text{ EXCEPT } ![w] = \text{"ClaimTask"}] \land \text{UNCHANGED } jobs \\ & \land \text{UNCHANGED } \langle catalog\_snapshot, cache, blob\_storage, client\_received, available\_blobs, worker\_alive, commit\_count \rangle \end{aligned}\]

B. The Authoritative Acceptance Boundary (CommitJob)

This action represents the authoritative acceptance boundary (Stage 5 of the lifecycle). To prevent a distributed race condition where a background ETL process updates the Iceberg catalog while a worker is staging a task, this step atomically enforces both lease-epoch fencing and snapshot freshness. If catalog_snapshot has advanced, the commit is rejected, even if the worker's lease is valid.

\[CommitJob(w, r, epoch) \triangleq \begin{aligned} & \land pc[w] = \text{"CommitJob"} \land worker\_alive[w] \\ & \land HoldsLease(r, epoch, w, \text{"RESULT\_STAGED"}) \\ & \land jobs[r].version = catalog\_snapshot[jobs[r].tenant] \\ & \land jobs' = [jobs \text{ EXCEPT } ![r].state = \text{"ACCEPTED"}, ![r].owner = \text{"NONE"}] \\ & \land commit\_count' = [commit\_count \text{ EXCEPT } ![r] = commit\_count[r] + 1] \\ & \land pc' = [pc \text{ EXCEPT } ![w] = \text{"PopulateCache"}] \\ & \land \text{UNCHANGED } \langle catalog\_snapshot, cache, task\_queue, blob\_storage, client\_received, available\_blobs, worker\_alive \rangle \end{aligned}\]

C. Best-Effort Cache Population (\(PopulateCache\))

Commit is modelled as distinct from the best-effort result-cache write (PopulateCache). Splitting them is deliberate: real systems can crash between the two, leaving a job ACCEPTED but uncached. The result cache is therefore treated as best-effort and never assumed to hold an entry just because a job completed.

\[PopulateCache(w, r, blob) \triangleq \begin{aligned} & \land pc[w] = \text{"PopulateCache"} \land worker\_alive[w] \\ & \land jobs[r].state = \text{"ACCEPTED"} \land jobs[r].blob\_ptr = blob \\ & \land jobs[r].version = catalog\_snapshot[jobs[r].tenant] \\ & \land BlobMatches(blob, jobs[r].tenant, jobs[r].query, jobs[r].version, jobs[r].security\_context) \\ & \land \textbf{IF } FlightPopulatesCache \lor ProtocolOf[r] = \text{"REST"} \\ & \phantom{\land} \textbf{THEN } cache' = [cache \text{ EXCEPT } ![jobs[r].tenant][jobs[r].query][jobs[r].version][jobs[r].security\_context] = [valid \mapsto \text{TRUE}, blob\_id \mapsto blob]] \\ & \phantom{\land} \textbf{ELSE } \text{UNCHANGED } cache \\ & \land pc' = [pc \text{ EXCEPT } ![w] = \text{"ClaimTask"}] \\ & \land \text{UNCHANGED } \langle catalog\_snapshot, task\_queue, jobs, blob\_storage, client\_received, available\_blobs, worker\_alive, commit\_count \rangle \end{aligned}\]

D. Tenant-Isolated Snapshot Advance (\(ETLCommit\))

The background ETL process independently advances the authoritative catalog snapshot. Cache invalidation is decoupled from this monotonic advance and treated as an asynchronous optimization; cache correctness does not depend on invalidation timing because freshness checks happen authoritatively at lookup and result acceptance.

\[ETLCommit(t) \triangleq \begin{aligned} & \land pc[\text{"LakehouseETL"}] = \text{"ETLCommit"} \land catalog\_snapshot[t] < MaxSnapshot \\ & \land \text{LET } new\_v \triangleq catalog\_snapshot[t] + 1 \text{ IN } \\ & \phantom{\land} \land catalog\_snapshot' = [catalog\_snapshot \text{ EXCEPT } ![t] = new\_v] \\ & \phantom{\land} \land cache' = [cache \text{ EXCEPT } ![t] = [q \in Queries \mapsto [v \in 1..MaxSnapshot \mapsto [s \in SecCtxs \mapsto \\ & \phantom{\land \land cache' = } \textbf{IF } v < new\_v \textbf{ THEN } \text{NoEntry} \textbf{ ELSE } cache[t][q][v][s]]]]] \\ & \land pc' = [pc \text{ EXCEPT } ![\text{"LakehouseETL"}] = \text{"ETLCommit"}] \\ & \land \text{UNCHANGED } \langle task\_queue, jobs, blob\_storage, client\_received, available\_blobs, worker\_alive, commit\_count \rangle \end{aligned}\]

4. PlusCal Source Architecture & Behavioral Assumptions

The complete, reproducible PlusCal specification source and TLC configuration files powering the model checker are maintained in the data-lakehouse-gateway-formal GitHub Repository. Rather than duplicating the full executable module, the overview below outlines the high-level structural components, concurrent process loops, and behavioral assumptions modeled in DataLakehouseGateway.tla.

A. Core Concurrent Process Modules

The PlusCal specification models the gateway as a concurrent distributed system comprising clients, asynchronous compute workers, background maintenance daemons, and fault-injection actors:

  • Client Request Lifecycle (ClientProcess): Handles request admission, tenant security verification bounds, immutable catalog snapshot version binding, result cache lookups, and protocol-specific routing.
    • Flight Path: Modeled as a deliberate synchronous, in-VM execution path that bypasses network queues, leases, and worker crash windows for atomic performance, optionally writing through to the cache when enabled.
    • REST Path: Enqueues asynchronous multi-tenant jobs into a shared task queue for workers to claim.
  • Compute Worker Process (ComputeWorker): Implements claim-check execution loops. Workers pull tasks from the queue, increment lease epochs, bind tenant security predicates at execution time (modeling the presence of an authorization step via `rls_applied`, rather than evaluating the data-level semantics of row filtering), allocate and stage immutable result blobs, publish pointers via epoch fencing, commit jobs to the ACCEPTED state, and perform best-effort cache population.
  • Lease & Fault Management (LeaseManager, Crasher, Recoverer): Explicitly models distributed failure semantics. The LeaseManager revokes leases upon worker death or operational timeouts (creating zombie workers handled by epoch fencing). The Crasher injects bounded worker crashes, while the Recoverer brings replacement workers online only after dead leases are fully reaped.
  • Background Maintenance Daemons (GarbageCollector, CacheEvictor, LakehouseETL): Runs perpetual cleanup loops. The GarbageCollector reclaims orphaned staged blobs (fenced out by superseded epochs) and published blobs no longer referenced by active jobs, cache entries, or clients. The CacheEvictor abstracts TTL/LRU result cache expiration, and the LakehouseETL independently advances tenant Iceberg snapshots.

TLC model checking exhaustively verifies explicit bounds. The table below outlines the core properties our abstract model guarantees.

Additional Transition Rules (PROPERTIES) Verified in Model:

  • EpochMonotonic \(\left(\Box [\text{epoch}' \ge \text{epoch}]_{\text{vars}}\right)\): Lease epochs never go backwards (fencing-token guarantee).
  • SnapshotFixedWithinAttempt: A snapshot selected for one execution attempt does not change during that attempt. A retry starts a new attempt and resolves the latest published, readable snapshot again.
  • CatalogMonotonic & CommitMonotonic: Catalog snapshots only advance, and commit counts never decrease.
  • TerminalAbsorbing: ACCEPTED, FAILED, and UNAUTHORIZED states never change.
  • DeliveryImmutable: A delivered result's blob and version never change.
  • GCReclaimsGarbage: For every blob that remains reclaimable and is not protected by a live reference, it is eventually reclaimed \(\left(\text{Reclaimable}(b) \leadsto \text{Reclaimed}(b)\right)\).

1. Design Gaps Found by Static Formal Analysis

Static review and iterative TLC runs of the specification highlighted several distributed failure modes. While the updated TLA+ specification now mathematically proves these issues are resolved within the model, the burden shifts to the physical system to actually enforce them. The table below outlines the critical design gaps caught during formal modeling and the specific architectural and coding mandates required in the physical implementation to ensure these gaps remain closed in production.

# Gap Found Why It Matters Physical Implementation Requirement
1 Stale cache entry risk: Invalidation may be delayed or incomplete. A stale snapshot's cached result stayed servable for one more commit. Implement a conditional read/write or strictly validate the Iceberg snapshot ID during the Redis/DuckDB cache lookup and final result commit. Do not rely solely on asynchronous cache invalidation loops.
2 The Silent Leak: No delivered result blob was ever reclaimed because job and client references never expired. The blob pool leaks under load. The earlier "GC fix" was effectively inert. Code explicit TTLs in Redis/Blob storage for cached items and expose a client-side API endpoint (e.g., DELETE /results/{id}) to trigger early Garbage Collection.
3 The Ghost Check: The tenant-mismatch check compared values that had not yet been assigned in the same step. PlusCal evaluates right-hand sides in the pre-step state, so the check compared placeholders, making UNAUTHORIZED dead code. Enforce JWT cryptographic tenant extraction directly in the API Gateway / NGINX layer before the request ever reaches the queue or worker logic.
4 The Vacuous Terminator: Lease expiry was unconditional. Any job could be expired at any time, so "every job terminates" held vacuously by ending in FAILED. Implement a reliable heartbeat mechanism (e.g., Celery/Redis heartbeat) and enforce maximum retry limits strictly in the worker execution loop before setting status to FAILED.
5 The Cross-Tenant Slip-Up: The cache key claimed to include the security context but held one entry per query. A second security context overwrote the first, causing thrashing and weak authorization isolation. The Redis cache key construction must be strictly hardcoded as a composite string: {tenant_id}:{query_hash}:{snapshot_id}:{security_context}.
6 The Orphan Maker: Result write and pointer publication were a single atomic step. The model could not produce the real failure: a zombie worker writes a blob, fails the epoch fence, and leaves an orphan. Implement the 6-stage lifecycle model: Workers must first write a staging file (Stage 4), then use a transactional CAS in Redis/Iceberg to accept it (Stage 5).
7 The Premature Reaper: The GC could not tell an in-flight blob from an orphan. Freeing a staged blob that a live worker is about to publish would corrupt results. The background GC service must explicitly read the current active lease epoch from Redis and compare it against the blob's embedded staging epoch before issuing an S3 DELETE.
8 The Cache Race: Cache population can race with client release and the GC. A cache entry could point at a freed or reused blob. Use a Redis Lua script or a conditional PUT to atomically check the blob's physical existence and metadata before committing the cache entry.
9 The Unbounded Pin: Cache entries pin blobs and nothing evicts them. A full pool with a never-evicting cache can starve new jobs. Configure Redis with volatile-lru eviction policies or append explicit EXPIRE commands on all result keys to apply backpressure safely.
10 The Zombie Revival: A crashed worker could return before its leases were reclaimed. Jobs stay CLAIMED with no actor left to advance them. The Kubernetes/Nomad orchestrator or recovery loop must explicitly reap and fence dead worker leases in Redis before it schedules or allows a replacement pod to accept work.
11 The Mid-Flight Crash: Commit and cache write were one atomic step. Real systems can crash between them, leaving a job ACCEPTED but uncached. Separate the database commit transaction from the Redis cache write in the worker code. Handle cache write failures gracefully (fire-and-forget) to keep the caching layer strictly "best-effort".
12 Latest-snapshot acceptance race: A new catalog snapshot may publish after an attempt starts but before its result is accepted. Attempt-level consistency alone does not satisfy the selected freshness policy. Cache invalidation can also lag publication. Pass the resolved Iceberg snapshot_id in the task payload. The worker must include this ID in its final CAS commit; if the catalog has advanced in the interim, the commit must be rejected at the Authoritative Boundary.
13 The Unfenced Flight: The Flight path has no fencing or recovery by design. A VM crash mid-execution has no gateway-side recovery. The Arrow Flight server must be entirely stateless. Client SDKs must be explicitly configured to catch connection drops and retry the query against a new gateway node.

2. Verification Anti-Goals: What This Model Cannot Find

A formal specification defines a system at a specific level of abstraction. By explicitly declaring what is excluded, we define the boundary where formal model checking ends and physical SRE chaos engineering must begin. This TLA+ model is intentionally blind to the following physical realities:

Fault Class Why the Model Misses It Production Mitigation
Byzantine Faults Assumes fail-stop worker crashes. A worker that maliciously corrupts memory or lies about its state is not modeled. mTLS, signed payloads, memory-safe execution environments.
Clock Skew Relies on strictly ordered logical lease epochs (fencing tokens). Wall-clock drift between nodes is abstracted away. NTP monitoring, strictly relying on Redis/storage for serialization.
Message Loss / Duplication Assumes reliable memory-to-queue transitions within the modeled steps. Idempotent worker execution, at-least-once message brokers.
Resource Exhaustion Models finite abstract pools to verify logic, but cannot detect physical Out-Of-Memory (OOM) errors, disk-full events, or connection pool starvation. Cgroups, Kubernetes pod evictions, Envoy circuit breakers.
Implementation Bugs Verifies the abstract algorithm. A Python or Rust worker that diverges from the PlusCal specification will introduce unmodeled flaws. Model-Based Trace Checking (MBTC), unit test coverage.
Integer Overflow TLA+ math uses unbounded integers. Abstractions hide 32-bit or 64-bit boundaries. Strongly-typed languages, static analysis, fuzzing.
Telemetry Loss Assumes total observability of state transitions. Blind to the trace-conformance gap where log drops hide illegal states from the auditor. Reliable log shipping pipelines, alert-on-missing-telemetry.

8. The Defensible Evidence Ladder & TLC Results

A common trap in formal methods is "TLA+ theater"—where engineers run a model checker, see a green success message, and assume the actual Python or C++ code is bug-free. To avoid this, we structure our claims around a strict Defensible Evidence Ladder: a 6-step framework moving from plain-English intent all the way down to physical implementation enforcement.

Evidence Ladder Example: Cache Freshness Isolation

1. Plain-English Invariant: "A cached query result must never be served to a client if the underlying Iceberg data snapshot has advanced, even if the worker computing it had a valid lease."

2. TLA+ Spec (Safety):

3. TLC Bounds Explicitly Stated: We verified isolation using TLC bounded to exactly 3 workers, 2 tenants, 2 data snapshots, and 3 physical blobs.

4. TLC Output (Proof of Safety): Completed. State space exhausted. Note: This run proves safety within these bounds (we never return wrong data). It does not guarantee liveness (the system might reject all requests if snapshots churn too fast).

5. Mutation Test (Falsification): We deliberately removed the jobs[r].version = catalog_snapshot check from the CommitJob action. TLC instantly found a counterexample where a worker raced the background ETL process, validating that our formal check is not passing vacuously.

6. Integration Test Enforcement: A Redis conditional update and an Iceberg catalog update are not automatically atomic. Our physical implementation uses Redis as the strict atomic boundary to fence leases, while treating Iceberg as the eventually consistent backing store. Integration tests explicitly enforce that if the Redis CAS fails, the Python worker discards the staged blob.

3. Mutation Testing: Confirming the Model Catches Invariant Violations

Mutation testing serves as our falsification step: deliberately injecting security bypasses or sequencing errors into the specification to verify that our formal safety invariants are non-vacuous. By successfully catching these mutants, we demonstrate that selected defects are detected by our checks.

Mutation 1: Security Check Bypass (MC_mutant)

Modification: Enabled MutantSkipTenantCheck = TRUE to simulate a flawed admission controller that honors the unverified request payload instead of the cryptographically verified JWT identity.

The Execution Trace: The abridged sequence below demonstrates how TLC traces the mutation to a critical failure and catches the vulnerability before the malicious job can execute.

2. <Start(r4)>         : Gateway receives the REST invocation.
3. <BindSnapshot(r4)>  : r4 locks in the latest valid table state.
4. <CheckCache(r4)>    : Cache miss; r4 requires materialization.

Mutation 4: Stale Worker Commit After Lease Revocation (MC_stale_commit)

Modification: Removed the lease_epoch check from the worker commit action.

Result: Passed without violation. Why? Because the worker still checks jobs[r].owner = w. When the LeaseManager times out a lease, it actively resets the ownership string. Therefore, a zombie worker fails the string match anyway, making the integer epoch mathematically redundant within this specific model scope.

Architectural Conclusion: Passing this mutant demonstrates a redundancy in the current mathematical abstraction, but it highlights a crucial physical reality: Merely including lease_epoch in logs or blob metadata does not fence writes. The external resource itself (e.g., Iceberg or Redis CAS) must actively reject stale tokens, because the physical external storage API cannot read the gateway's internal owner strings.

9. From Model Correctness to Implementation Conformance

Here is the uncomfortable truth about formal methods: TLA+ proves that your design is mathematically flawless, but it does absolutely nothing to prevent your physical Python or Rust code from being a chaotic mess. If a developer later "optimizes" a worker by swapping the order of two database calls, the implementation drifts from the model, and all those beautiful mathematical guarantees instantly evaporate.

To bridge the "Math-to-Metal Gap," we must bind the physical runtime back to the abstract model. We propose doing this through Model-Based Trace Checking (MBTC). Instead of just writing unit tests, we force the production system to emit a strict immutable ledger of its state transitions, and we feed those logs backward through an adapter into the TLA+ model to ensure real-world executions perfectly trace valid mathematical paths. Note that this trace-conformance harness remains a proposed design until fully implemented and integrated into CI.

The Rosetta Stone: The Minimum Trace Contract

Standard application logs (e.g., INFO: Worker starting task) are completely useless for formal verification. The system must emit highly structured, deterministic events that act as a "Rosetta Stone." A custom adapter must then translate these physical events into corresponding TLA+ pc (program counter) state transitions.

To establish this contract, every critical telemetry event must capture:

  • Identity & Authorization: requested_tenant_id vs. authenticated_tenant_id. If these diverge and the request isn't immediately followed by an UnauthorizedRejected event, the trace checker knows a security bypass occurred.
  • Causality & Sequencing: request_id and a strict sequence integer. You cannot rely on log arrival timestamps—network jitter will reorder logs. The sequence integer reconstructs the exact local order of operations. Note that cross-service causality requires correlation IDs or a well-defined authoritative acceptance event, as local sequences cannot establish global ordering.
  • State Fencing Variables: worker_id, lease_epoch, snapshot_id, and blob_id. These are the mathematical load-bearing columns. The checker needs these to verify that a worker didn't write a result using a stale catalog version.

How the Checker Catches "Implementation Drift"

Let's look at a concrete example of how this proposed pipeline prevents silent corruption.

The Scenario: The "Optimized" Pull Request

Six months after launch, a well-meaning developer notices that writing blobs to S3 is slow. They decide to "optimize" the worker loop by publishing the result pointer to Redis before the S3 blob finishes uploading, wrapping it in an async promise.

The Catch: In production, the worker crashes immediately after the Redis commit but before the S3 upload finishes. Redis now points to a ghost file. Clients start receiving 404 Not Found errors.

How MBTC stops this in CI/CD: During integration testing, the trace harness records the telemetry and feeds it via the adapter to TLC. TLC reads the transitions and sees a ResultAccepted event arrive at sequence: 5, but sees no BlobStaged event preceding it. TLC instantly throws a mathematical violation because the trace bypassed the strict state-machine requirement: A pointer cannot be published unless its blob is durable. The build fails, the PR is blocked, and the architecture is preserved.

Enforcing the Conformance Pipeline

To ensure this isn't just an academic exercise, the trace checker must become an uncompromising gatekeeper in your deployment pipeline. The implementation is considered conformant only when it passes the following criteria:

  1. The Happy Path Replay: A known-good integration test suite generates telemetry that successfully replays from start to finish without TLC throwing an illegal state transition.
  2. Falsification (The Red Team): Deliberately mutated traces (e.g., injecting a stale lease epoch, swapping the order of commit and blob creation, or mimicking a tenant mismatch) must be aggressively caught and flagged as PropertyViolated by the harness.
  3. Ambiguity Rejection: A missing log event alone does not inherently prove an illegal action occurred; it often means the evidence is simply incomplete. If events are dropped, duplicated, or missing causality sequences, the harness must report an ambiguous trace error rather than silently treating the execution as legally valid.

10. The Comprehensive Architectural Verification Summary

The comprehensive verification of the Smart Data Gateway requires a multi-tiered strategy spanning theoretical models and physical reality. As explored earlier in Part 3, the foundational targets for speed, scalability, and physical limitations—such as P99 tail latency bounds via Kingman's approximation, cluster throughput scaling under the Universal Scalability Law, and Monte Carlo-simulated cloud unit economics—must be empirically validated through live implementation conformance and rigorous operational SRE testing. Conversely, this current installment (Part 4) evaluates the logic of the system's distributed state through formal verification.

Using bounded TLC model checking, we have exhaustively explored explicit finite state bounds to demonstrate that no counterexample was found in the completed configuration for specific safety invariants—such as TenantBinding (tenant isolation), ClaimCheckIntegrity (pointer safety), and EpochMonotonic. By anchoring the physical implementation to a strict 6-stage lifecycle, mapping properties to the Defensible Evidence Ladder, and bridging the "Math-to-Metal Gap" through trace checking, we establish true confidence within our stated bounds.

A Final Caveat on Row-Level Security: It is critical to acknowledge that the rls_applied state variable modeled in this specification merely proves the presence and correct ordering of an authorization step. The formal model does not establish that the physical SQL predicate actually filters rows correctly. Physical implementation testing must independently verify that caller-supplied payloads cannot weaken the injected RLS policy.

The useful outcome is not a claim of absolute certainty; it is a reviewable chain from requirement to model property, from property to a reproducible TLC run, and from abstract action to implementation evidence.
