ARCHITECTURAL CONFIDENCE
What formal specification and model checking can establish

A TLA+ specification defines an abstract transition system. If TLC completes a configured run without a counterexample, that is evidence that the checked properties hold for the reachable states in that finite model and configuration. It is not a proof that production code conforms, that omitted behaviors are safe, or that assumptions about Redis, object storage, the catalog, and runtime ordering are true.

Credible production assurance requires complementary evidence:

  1. Checking the abstract state machine with TLC and recording exact bounds, properties, tool version, and results.
  2. Validating environmental assumptions (Redis Lua atomicity, Azure Blob durability, Iceberg version monotonicity, worker lease mechanics).
  3. Building and testing a trace-conformance harness that binds observed event parameters to model transitions; this remains proposed until implemented and run.
  4. Validating physical boundaries via performance benchmarking, chaos testing, and SRE load telemetry.

2. Concurrency Testing and the Limits of Sampling

Anticipating an architecture review board brings a specific kind of dread. Long before anyone actually asks a question, the mind races to imagine the brutal edge cases reviewers love to throw at a distributed design:

Anticipated Review Board Concurrency Challenges:
  • "If an NGINX NVMe replica crashes mid-stream, can consistent-hash re-mapping leak data across tenant partitions?"
  • "If a Celery worker pauses for garbage collection while its lease expires, can a second worker claim the task and commit a duplicate or out-of-order result?"
  • "Can an out-of-band Iceberg snapshot commit race with query planning and deliver stale or inconsistent financial data to a regulatory auditor?"

These scenarios expose a limitation rather than a failure of conventional testing: tests exercise selected inputs, schedules, and failure timings. They are essential for validating concrete implementations, but a test suite alone does not enumerate every behavior of a concurrent system. Formal modeling complements testing by making state transitions and nondeterministic choices explicit.

Formal methods offer a disciplined way to explore whether a precise model admits a forbidden state or an execution that violates a stated temporal property. The result depends on the model, its bounds, and the environmental assumptions; it is not a shortcut around implementation testing or operational evidence.

Formal methods do have a learning and maintenance cost, so their value depends on the consequence of failure, the complexity of the protocol, and the team’s ability to keep the model aligned with the implementation. They are most useful when a small number of state transitions govern high-impact properties such as tenant isolation, durable publication, lease fencing, or recovery.

To understand why schedule coverage is difficult, consider how concurrent systems interleave operations. In an idealized, textbook system, imagine N identical processes (such as our DuckDB replicas), each executing a uniform sequence of K steps to finish a task.

If every step from every process could be shuffled like a deck of cards, the total number of global permutations is (N × K)!. However, internal order within each process matters—Process A's third step cannot run before its second step. To eliminate these redundant internal orderings, we divide by the product of internal permutations for each process, yielding the classic symmetrical multinomial coefficient:

\[ \text{Total Interleavings (Symmetrical)} = \frac{(N \times K)!}{(K!)^N} \]

Even in this tidy, symmetrical scenario, the numbers explode. For just 3 workers executing 4 steps each, there are 34,650 possible schedules. Scale that up to 5 concurrent workers executing an 8-step lifecycle, and the possibilities exceed 7.6 × 1024.

The Catch: Real Systems Are Asymmetrical

Relying solely on the symmetrical case understates the true heterogeneity of production. Real-world DuckDB replicas never march in lockstep. One replica might be handling a heavy, multi-phase partition compaction (K1 = 8), another is serving a fast, lightweight cache hit (K2 = 3), a third is committing an Iceberg metadata snapshot (K3 = 6), and a fourth is stuck in an object store retry loop (K4 = 4).

To account for heterogeneous workloads where every replica executes a different number of steps, the uniform formula upgrades to its generalized form:

\[ \text{Total Interleavings (Asymmetrical)} = \frac{\left(\sum_{i=1}^{N} K_i\right)!}{K_1! \times K_2! \times \dots \times K_N!} \]

Plugging those variable step counts (8, 3, 6, 4) across 4 replicas gives a total of 21 instruction steps, resulting in roughly 12 billion possible execution schedules (1.2 × 1010).

This count is a combinatorial illustration, not a count of production behaviors: real systems have partial orders, nondeterministic inputs, retries, failures, and abstraction choices that this simple shuffle model omits. A million tests do not necessarily cover a million distinct schedules, and model checking does not automatically enumerate the real system’s entire state space. The useful comparison is that tests sample concrete executions while TLC explores all reachable states of the finite transition system that was specified and configured.

Complementary techniques, different evidence:
Tests provide evidence about the implementation under the inputs, schedules, and environments actually exercised.

TLC can exhaustively explore the reachable state graph of a finite model/configuration and report a counterexample if a checked invariant fails. A clean run is conditional on the model, constants, specification, and TLC configuration; it is not a blanket proof about production code.

3. Industrial Precedent: Formal Methods in Distributed Systems

Formal verification is often viewed as academic theory unsuitable for production engineering. In practice, major cloud platforms rely on formal methods because conventional testing breaks down under distributed concurrency.

Amazon Web Services

AWS engineers have publicly described using TLA+ to reason about distributed-service designs and finding design errors before implementation. The details vary by case; the lesson is not that testing is futile, but that explicit models can expose unusual interleavings and protocol-level assumptions.

MongoDB Replication & Realm Sync

MongoDB engineers have published accounts of using formal methods, including TLA+, to reason about replication and synchronization protocols. Treat these as examples of a useful engineering practice, not evidence that the Smart Data Gateway has itself been verified.

Microsoft Azure CCF

Microsoft’s Confidential Consortium Framework (CCF) materials describe using formal specification and model-based techniques to strengthen confidence in distributed-system behavior. The exact scope and reported findings should be read in their original publication; this article does not independently reproduce those results.

4. The Abstraction Blueprint & The Architecture Assumption Ledger

A common failure mode when adopting formal methods is attempting to transcribe code line-by-line into math. Translating Python syntax, C++ memory management, or NGINX Lua directives creates an unmanageable model that obscures core distributed interactions.

The Abstraction Principle:
If a component's internal operation cannot alter the global reachability of an illegal distributed state, abstract it to an atomic value or immutable function. If a component introduces concurrency, failure modes, or non-deterministic ordering, model it as an explicit state variable and action.

To master this abstract thinking, consider a distributed worker pulling a task from Azure Managed Redis, generating a heavy financial report, and saving it to blob storage. We must ruthlessly separate what happens locally from what happens across the network.

1. Abstract to an Atomic Value (Safe Internal Operations)

You do not model the CPU parsing a JSON task payload, nor do you model the complex SQL joins the worker executes inside DuckDB to build the report.

  • The "Why": Even if the JSON parser takes 500 milliseconds, or the SQL query processes 10 million rows, these actions occur entirely inside one isolated process's memory. They cannot natively cause a race condition with another node in the cluster.
  • The Abstraction: In the formal model, this entire multi-minute execution phase is reduced to a single, instant mathematical function (e.g., report_data = Generate(task_id)). We assume the local computation is deterministic and correct, treating it as a black box.

2. Model as an Explicit State (Dangerous Distributed Operations)

Conversely, you absolutely must model the worker requesting a lease from Redis, the lease's countdown timer, the worker crashing mid-job, and the network request to save the file.

  • The "Why": These steps involve shared state, concurrency, and time. If Worker A's CPU processing takes too long and its Redis lease expires, Worker B might pick up the exact same task. Now both workers are racing to write to the same storage path simultaneously.
  • The Modeling: You map out explicit state transitions that the model checker will test against every possible interleaving: State: Claiming, State: Processing, State: Writing, State: Committing, along with external disruptive actions like Action: Crash and Action: Lease_Timeout.

5. The TLA+ Primer: Constructing Formal Logic from System Design

TLA+ combines state-based mathematics with temporal logic to describe possible system behaviors over sequences of states. In this gateway, it can express safety conditions (something bad never happens) and liveness conditions (something good eventually happens under stated assumptions). A specification is only as meaningful as its state variables, actions, and environment model.

The Core Architectural Distinction: Requests vs. Queries
A common trap in modeling analytical gateways is conflating Queries with Requests. A query hash \(Q_1\) represents normalized SQL text. A request \(R_1\) represents an independent client invocation. Two distinct tenants can execute query \(Q_1\) simultaneously, and Tenant A can submit query \(Q_1\) multiple times concurrently. The job registry must be indexed by Requests, while the predictive cache is indexed by \(\langle\text{Tenant}, \text{Query}, \text{Snapshot}, \text{SecurityContext}\rangle\).

1. Temporal Logic Operators

In standard programming, assertions evaluate conditions at an instantaneous snapshot. TLA+ temporal logic reasons across entire execution paths over infinite time:

State 0 → State 1 → State 2 → … → State n → …
  • 1. Always (\(\Box P\)) — Safety Invariants

    Formal Meaning: Condition \(P\) is true in every reachable state along every valid execution trajectory.

    \[\Box (\forall r \in \text{Requests} : client\_received[r].\text{tenant} = AuthenticatedTenantOf[r])\]

    Intended property: Under the model’s admission, authorization, cache-key, and delivery assumptions, no reachable modeled state lets a request receive a result bound to a different authenticated tenant. This conclusion is only as strong as the modeled state and checked configuration.

  • 2. Eventually (\(\Diamond P\)) — Progress Guarantees

    Formal Meaning: Condition \(P\) is guaranteed to become true in at least one state in the future.

    \[\Diamond (\text{jobs}[r].\text{state} \in \{\text{"COMPLETED"}, \text{"FAILED"}\})\]

    Interpretation: This eventuality is a liveness claim only when checked as part of the behavior specification with explicit fairness and environment assumptions. By itself, a state formula with \(\Diamond\) is not a claim that all requests succeed; the permitted terminal outcomes explicitly include failure states (e.g., resources exhausted or timeout limits reached).

  • 3. Leads-To (\(P \leadsto Q\)) — Terminal Liveness

    Formal Meaning: Defined as \(\Box(P \implies \Diamond Q)\). Whenever state \(P\) occurs, state \(Q\) is guaranteed to follow.

    \[ (\text{jobs}[r].\text{state} \in \text{Pending}) \leadsto (\text{jobs}[r].\text{state} \in \text{Terminal}) \]

    Intended liveness claim: If the executable specification includes the required fairness and recovery assumptions, every admitted request in the modeled scope eventually reaches a terminal state.

  • 4. Weak Fairness (\(\text{WF}_{\text{vars}}(A)\))

    Formal Meaning: Excludes model behaviors in which action \(A\) remains continuously enabled forever but is never taken.

    Illustrative Gateway Example: WF_vars(ClaimTask) ensures that if an idle worker sees a queued task, the model checker cannot explore infinite stuttering steps where the worker remains idle forever while work is available.

  • 5. Strong Fairness (\(\text{SF}_{\text{vars}}(A)\))

    Formal Meaning: Excludes model behaviors in which action \(A\) is enabled repeatedly (infinitely often, even if disabled intermittently between steps) but is never taken.

    Illustrative Gateway Example: SF_vars(ETLCommit) guarantees that background table commits and cache invalidations are never starved out indefinitely by continuous read traffic.

2. Mathematical Logic & Set Operations

  • Universal Quantification (\(\forall x \in S : P(x)\)): Condition \(P(x)\) holds for every item in set \(S\).
  • Existential Quantification (\(\exists x \in S : P(x)\)): There exists at least one item in set \(S\) satisfying \(P(x)\).
  • Prime Operator (\(x'\)): Denotes the variable's value in the next state. The transition is an algebraic constraint: 
    task_queue' = Tail(task_queue)
  • Frame Conditions (UNCHANGED): TLA+ requires explicit definition of unmutated variables. If a variable is omitted, it can take arbitrary values in the next state: 
    UNCHANGED <<catalog_snapshot, cache, blob_storage>>
  • Function Mutation (EXCEPT): Updates specific keys while preserving all others: 
    cache' = [cache EXCEPT ![t][q][v] = [valid |-> TRUE, blob_id |-> b_id]]

6. State Variables, Actions, and Properties in TLA+

TLA+ is not simply “first-order predicate logic”; it is a formal specification language built around state predicates, action formulas, and temporal properties. A state predicate constrains one state, an action formula relates a current state to a next state, and temporal formulas describe behavior over sequences of states.

PlusCal is an algorithmic notation translated into TLA+ by the PlusCal translator. TLC then model-checks a TLA+ specification; it is not the PlusCal translator. Below are representative state variables, action relations, and properties that map directly to the executed model.

B. Authoritative Result Acceptance (CommitJob)

This action represents the authoritative acceptance boundary (the durable pointer publication). To prevent a distributed race condition where a background ETL process updates the Iceberg catalog while a worker is processing a task, this step atomically enforces both lease-epoch fencing and snapshot freshness. If catalog_snapshot has advanced, the commit is rejected, even if the worker's lease is perfectly valid.

\[CommitJob(w, r, epoch) \triangleq \begin{aligned}[t] & \land pc[w] = \text{"CommitJob"} \land worker\_alive[w] \\ & \land HoldsLease(r, epoch, w, \text{"RESULT\_WRITTEN"}) \\ & \land jobs[r].version = catalog\_snapshot[jobs[r].tenant] \\ & \land jobs' = [jobs \text{ EXCEPT } ![r].state = \text{"COMPLETED"}, ![r].owner = \text{"NONE"}] \\ & \land commit\_count' = [commit\_count \text{ EXCEPT } ![r] = commit\_count[r] + 1] \\ & \land pc' = [pc \text{ EXCEPT } ![w] = \text{"PopulateCache"}] \\ & \land \text{UNCHANGED } \langle catalog\_snapshot, cache, task\_queue, blob\_storage, client\_received, available\_blobs, worker\_alive \rangle \end{aligned}\]

C. Best-Effort Cache Population (\(PopulateCache\))

Commit is modelled as distinct from the best-effort result-cache write (PopulateCache). Splitting them is deliberate: real systems can crash between the two, leaving a job COMPLETED but uncached. The result cache is therefore treated as best-effort and never assumed to hold an entry just because a job completed.

\[PopulateCache(w, r, blob) \triangleq \begin{aligned}[t] & \land pc[w] = \text{"PopulateCache"} \land worker\_alive[w] \\ & \land jobs[r].state = \text{"COMPLETED"} \land jobs[r].blob\_ptr = blob \\ & \land jobs[r].version = catalog\_snapshot[jobs[r].tenant] \\ & \land BlobMatches(blob, jobs[r].tenant, jobs[r].query, jobs[r].version, jobs[r].security\_context) \\ & \land \textbf{IF } FlightPopulatesCache \lor ProtocolOf[r] = \text{"REST"} \\ & \phantom{\land} \textbf{THEN } cache' = [cache \text{ EXCEPT } ![jobs[r].tenant][jobs[r].query][jobs[r].version][jobs[r].security\_context] = [valid \mapsto \textsc{True}, blob\_id \mapsto blob]] \\ & \phantom{\land} \textbf{ELSE } \text{UNCHANGED } cache \\ & \land pc' = [pc \text{ EXCEPT } ![w] = \text{"ClaimTask"}] \\ & \land \text{UNCHANGED } \langle catalog\_snapshot, task\_queue, jobs, blob\_storage, client\_received, available\_blobs, worker\_alive, commit\_count \rangle \end{aligned}\]

D. Tenant-Isolated Snapshot Invalidation (\(ETLCommit\))

\[ETLCommit(t) \triangleq \begin{aligned}[t] & \land pc[\text{"LakehouseETL"}] = \text{"ETLCommit"} \land catalog\_snapshot[t] < MaxSnapshot \\ & \land \text{LET } new\_v \triangleq catalog\_snapshot[t] + 1 \text{ IN } \\ & \phantom{\land} \land catalog\_snapshot' = [catalog\_snapshot \text{ EXCEPT } ![t] = new\_v] \\ & \phantom{\land} \land cache' = [cache \text{ EXCEPT } ![t] = [q \in Queries \mapsto [v \in 1..MaxSnapshot \mapsto [s \in SecCtxs \mapsto \\ & \phantom{\land \land cache' = } \textbf{IF } v < new\_v \textbf{ THEN } \text{NoEntry} \textbf{ ELSE } cache[t][q][v][s]]]]] \\ & \land pc' = [pc \text{ EXCEPT } ![\text{"LakehouseETL"}] = \text{"ETLCommit"}] \\ & \land \text{UNCHANGED } \langle task\_queue, jobs, blob\_storage, client\_received, available\_blobs, worker\_alive, commit\_count \rangle \end{aligned}\]

4. PlusCal Source Architecture & Behavioral Assumptions

The complete, reproducible PlusCal specification source and TLC configuration files powering the model checker are maintained in the data-lakehouse-gateway-formal GitHub Repository. Rather than duplicating the full executable module, the overview below outlines the high-level structural components, concurrent process loops, and behavioral assumptions modeled in DataLakehouseGateway.tla.

A. Core Concurrent Process Modules

The PlusCal specification models the gateway as a concurrent distributed system comprising clients, asynchronous compute workers, background maintenance daemons, and fault-injection actors:

  • Client Request Lifecycle (ClientProcess): Handles request admission, tenant security verification bounds, immutable catalog snapshot version binding, result cache lookups, and protocol-specific routing.
    • Flight Path: Modeled as a deliberate synchronous, in-VM execution path that bypasses network queues, leases, and worker crash windows for atomic performance, optionally writing through to the cache when enabled.
    • REST Path: Enqueues asynchronous multi-tenant jobs into a shared task queue for workers to claim.
  • Compute Worker Process (ComputeWorker): Implements claim-check execution loops. Workers pull tasks from the queue, increment lease epochs, bind tenant security predicates at execution time (modeling the presence of an authorization step via `rls_applied`, rather than evaluating the data-level semantics of row filtering), allocate and stage immutable result blobs, publish pointers via epoch fencing, commit jobs, and perform best-effort cache population.
  • Lease & Fault Management (LeaseManager, Crasher, Recoverer): Explicitly models distributed failure semantics. The LeaseManager revokes leases upon worker death or operational timeouts (creating zombie workers handled by epoch fencing). The Crasher injects bounded worker crashes, while the Recoverer brings replacement workers online only after dead leases are fully reaped.
  • Background Maintenance Daemons (GarbageCollector, CacheEvictor, LakehouseETL): Runs perpetual cleanup loops. The GarbageCollector reclaims orphaned staged blobs (fenced out by superseded epochs) and published blobs no longer referenced by active jobs, cache entries, or clients. The CacheEvictor abstracts TTL/LRU result cache expiration, and the LakehouseETL independently advances tenant Iceberg snapshots while handling cache invalidation.

7. Formal Verification Scope & Core Assumptions

All model checking with TLC is bounded. Once TLC reports no violations, it guarantees that no counterexample exists within the configured bounds (e.g., 2 tenants, 4 requests, 2 workers, 4 blobs, 2 snapshots, 2 attempts, 1 crash, 1 timeout). The verification suites rigorously check the following categories:

D. Transition Rules (PROPERTIES) & Liveness

  • EpochMonotonic ([][\text{epoch}' \ge \text{epoch}]_{\text{vars}}): Lease epochs never go backwards (fencing-token guarantee).
  • SnapshotFixedWithinAttempt: A snapshot selected for one execution attempt does not change during that attempt. A retry starts a new attempt and resolves the latest published, readable snapshot again.
  • CatalogMonotonic & CommitMonotonic: Catalog snapshots only advance, and commit counts never decrease.
  • TerminalAbsorbing: COMPLETED, FAILED, and UNAUTHORIZED states never change.
  • DeliveryImmutable: A delivered result's blob and version never change.
  • LiveTermination (\( \text{Pending} \leadsto \text{Terminal} \)): Every queued or running job eventually reaches a terminal state.
  • ClientsComplete (per-request release liveness): Quantify over each request/client and state the required antecedent and terminal outcome. A bare \( \Diamond \text{released} \) means only that some release eventually occurs; the intended property is per-request, not global.
  • GCReclaimsGarbage: State this per blob, for example "for every blob that remains reclaimable and is not protected by a live reference, it is eventually reclaimed" (\( \Box \Diamond \text{reclaimed} \)), under explicit GC fairness and storage-availability assumptions. The exact quantification belongs in the executable spec. Garbage collection strictly cannot reclaim blobs referenced by active workers or accepted client deliveries.

2. Core Design Assumptions Underlying Guarantees

  • Security: Distinguish untrusted RequestedTenantOf[r] from trusted AuthenticatedTenantOf[r]. Reject mismatches at admission. Model the effective row-level-security predicate/tenant binding, not only a Boolean flag; include tenant, query identity, snapshot, and security context in cache and result metadata.
  • Storage and fencing: Separate immutable blob upload from durable pointer publication. The acceptance/publication operation must conditionally validate the current lease epoch and request state at the authoritative boundary. Fencing only in worker memory is insufficient. Staged blobs are invisible until a pointer is accepted and may later be garbage-collected only when no live attempt can publish them.
  • Workers & faults: State explicitly whether the model assumes fail-stop crashes, lease timeouts, reliable queue delivery, bounded retries, and fair recovery. A timeout does not prove the old worker stopped; fencing must prevent a stale worker from publishing after ownership changes. Clock skew, message loss/duplication, and Byzantine behavior are outside the model unless explicitly added.
  • Flight Path: Flight requests run inside the same VM as admission with no network hop. VM crashes appear to clients as dropped connections, triggering client-side retries as new requests.
  • Liveness fairness: State exactly which actions receive weak or strong fairness and under what environmental assumptions. Bounded retries guarantee at most a terminal outcome, not success; a request may fail when resources are exhausted or the snapshot changes continuously.
  • Abstractions: Snapshots are integers per tenant, queries are opaque IDs, and cache identity uses exact-match indexing on tenant, query, snapshot, and security context.

3. Design Gaps Found by Static Formal Analysis

Static review and iterative TLC runs of the specification highlighted several failure modes. The items below represent critical design gaps caught and resolved during the formal modeling process:

# Gap Found Why It Matters Physical Implementation Requirement
1 Stale cache entry risk: Invalidation may be delayed or incomplete. A stale snapshot's cached result stayed servable for one more commit. Implement a conditional read/write or strictly validate the Iceberg snapshot ID during the Redis/DuckDB cache lookup and final result commit. Do not rely solely on asynchronous cache invalidation loops.
2 The Silent Leak: No delivered result blob was ever reclaimed because job and client references never expired. The blob pool leaks under load. The earlier "GC fix" was effectively inert. Code explicit TTLs in Redis/Blob storage for cached items and expose a client-side API endpoint (e.g., DELETE /results/{id}) to trigger early Garbage Collection.
3 The Ghost Check: The tenant-mismatch check compared values that had not yet been assigned in the same step. PlusCal evaluates right-hand sides in the pre-step state, so the check compared placeholders, making UNAUTHORIZED dead code. Enforce JWT cryptographic tenant extraction directly in the API Gateway / NGINX layer before the request ever reaches the queue or worker logic.
4 The Vacuous Terminator: Lease expiry was unconditional. Any job could be expired at any time, so "every job terminates" held vacuously by ending in FAILED. Implement a reliable heartbeat mechanism (e.g., Celery/Redis heartbeat) and enforce maximum retry limits strictly in the worker execution loop before setting status to FAILED.
5 The Cross-Tenant Slip-Up: The cache key claimed to include the security context but held one entry per query. A second security context overwrote the first, causing thrashing and weak authorization isolation. The Redis cache key construction must be strictly hardcoded as a composite string: {tenant_id}:{query_hash}:{snapshot_id}:{security_context}.
6 The Orphan Maker: Result write and pointer publication were a single atomic step. The model could not produce the real failure: a zombie worker writes a blob, fails the epoch fence, and leaves an orphan. Implement a two-phase commit: Workers must first write a staging file (e.g., s3://bucket/staging/worker_epoch_blob), then use a transactional CAS (Compare-And-Swap) in Redis/Iceberg to publish it.
7 The Premature Reaper: The GC could not tell an in-flight blob from an orphan. Freeing a staged blob that a live worker is about to publish would corrupt results. The background GC service must explicitly read the current active lease epoch from Redis and compare it against the blob's embedded staging epoch before issuing an S3 DELETE.
8 The Cache Race: Cache population can race with client release and the GC. A cache entry could point at a freed or reused blob. Use a Redis Lua script or a conditional PUT to atomically check the blob's physical existence and metadata before committing the cache entry.
9 The Unbounded Pin: Cache entries pin blobs and nothing evicts them. A full pool with a never-evicting cache can starve new jobs. Configure Redis with volatile-lru eviction policies or append explicit EXPIRE commands on all result keys to apply backpressure safely.
10 The Zombie Revival: A crashed worker could return before its leases were reclaimed. Jobs stay CLAIMED with no actor left to advance them. The Kubernetes/Nomad orchestrator or recovery loop must explicitly reap and fence dead worker leases in Redis before it schedules or allows a replacement pod to accept work.
11 The Mid-Flight Crash: Commit and cache write were one atomic step. Real systems can crash between them, leaving a job COMPLETED but uncached. Separate the database commit transaction from the Redis cache write in the worker code. Handle cache write failures gracefully (fire-and-forget) to keep the caching layer strictly "best-effort".
12 Latest-snapshot acceptance race: A new catalog snapshot may publish after an attempt starts but before its result is accepted. Attempt-level consistency alone does not satisfy the selected freshness policy. Cache invalidation can also lag publication. Pass the resolved Iceberg snapshot_id in the task payload. The worker must include this ID in its final CAS commit; if the catalog has advanced in the interim, the commit must be rejected.
13 The Unfenced Flight: The Flight path has no fencing or recovery by design. A VM crash mid-execution has no gateway-side recovery. The Arrow Flight server must be entirely stateless. Client SDKs must be explicitly configured to catch connection drops and retry the query against a new gateway node.

4. Verification Anti-Goals: What This Model Cannot Find

A formal specification defines a system at a specific level of abstraction. By explicitly declaring what is excluded, we define the boundary where formal model checking ends and physical SRE chaos engineering must begin. This TLA+ model is intentionally blind to the following physical realities:

Fault Class Why the Model Misses It Production Mitigation
Byzantine Faults Assumes fail-stop worker crashes. A worker that maliciously corrupts memory or lies about its state is not modeled. mTLS, signed payloads, memory-safe execution environments.
Clock Skew Relies on strictly ordered logical lease epochs (fencing tokens). Wall-clock drift between nodes is abstracted away. NTP monitoring, strictly relying on Redis/storage for serialization.
Message Loss / Duplication Assumes reliable memory-to-queue transitions within the modeled steps. Idempotent worker execution, at-least-once message brokers.
Resource Exhaustion Models finite abstract pools to verify logic, but cannot detect physical Out-Of-Memory (OOM) errors, disk-full events, or connection pool starvation. Cgroups, Kubernetes pod evictions, Envoy circuit breakers.
Implementation Bugs Verifies the abstract algorithm. A Python or Rust worker that diverges from the PlusCal specification will introduce unmodeled flaws. Model-Based Trace Checking (MBTC), unit test coverage.
Integer Overflow TLA+ math uses unbounded integers. Abstractions hide 32-bit or 64-bit boundaries. Strongly-typed languages, static analysis, fuzzing.
Telemetry Loss Assumes total observability of state transitions. Blind to the trace-conformance gap where log drops hide illegal states from the auditor. Reliable log shipping pipelines, alert-on-missing-telemetry.

8. TLC Configurations, Empirical Results & Mutation Testing

The validation workflow separates safety runs (type correctness and state invariants) from liveness runs (temporal properties under stated fairness assumptions) and explicitly tracks deadlock-checking behaviors. The empirical results below were captured using TLC2 Version 2026.10.06.014338 running on Microsoft OpenJDK 11.0.31 (64-bit) under Windows 11 AMD64 with a 3,532MB heap configuration.

Deadlock Checking vs. Temporal Liveness

Across all configurations, CHECK_DEADLOCK FALSE is explicitly utilized. In TLA+, a "deadlock" strictly means a state with no enabled next transitions. Because our TLC configurations evaluate finite, bounded scenarios (e.g., exactly 2 or 3 requests), the system is designed to eventually finish all work, exhaust all possible actions, and legitimately halt. Disabling deadlock checking prevents TLC from flagging these valid terminal states as errors.

However, disabling this check means TLC will also ignore unexpected stalls (e.g., if a worker crashes and no mechanism exists to reassign its CLAIMED task, halting the model prematurely). To ensure this setting doesn't mask true failures, we must clearly distinguish between states:

  • Expected Terminal State: All client requests reach COMPLETED, FAILED, or UNAUTHORIZED, and background daemons block because there is no remaining work. The model halts cleanly.
  • Unexpected Deadlock (Stall): The model halts prematurely while requests are still QUEUED or RUNNING. With deadlock checking disabled, TLC will not flag the structural halt itself.
  • Liveness Property Violation: To catch these unexpected stalls, we rely on explicit temporal properties like LiveTermination (\( \text{Pending} \leadsto \text{Terminal} \)). If the system stalls or enters a meaningless infinite loop, LiveTermination explicitly fails.

Running a separate configuration with ordinary deadlock checking enabled is unsuitable for this bounded model because it would require injecting artificial infinite self-loops (e.g., Idle → Idle) into every process just to silence the checker when work is done. By using CHECK_DEADLOCK FALSE and testing explicit liveness properties separately, we accurately verify system progress.

1. Verification Levels: Model Checking vs. Inductive Proofs

It is vital to distinguish bounded model checking from unbounded mathematical proof:

  • Level 1 (TLC Model Checking): Exhaustively checks all reachable states within finite bounds (e.g., up to 4 requests, 2 workers, 2 snapshots, and 4 physical blobs), verifying the absolute absence of counterexamples within the state envelope.
  • Level 2 (Inductive Invariants & Safety Proofs): (Not performed in this validation phase)

    While Level 1 (TLC) proves correctness within explicit bounds, Level 2 mathematically proves the design is safe at infinite scale (unbounded queue lengths, infinite tenants, infinite execution time). To achieve this, an engineer would formulate and discharge proposed proof obligations based on two mathematical conditions:

    \[\text{Init} \implies \text{Inv} \quad \land \quad \text{Inv} \land [Next]_{\text{vars}} \implies \text{Inv}'\]

    How to perform this validation in practice:

    • Strengthen the Invariant: A target safety property is rarely inductive on its own. You must mathematically formulate a stronger "super-invariant" that conjoins your core properties with structural lemmas and state well-formedness (TypeOK) so that the inductive step holds.
    • Write a Hierarchical Proof: Author a formal, machine-checkable proof directly within the TLA+ module. This breaks the proof of the base case (Init) and the inductive step (Next) into logical, action-by-action steps.
    • Mechanize with TLAPS: Execute the TLA+ Proof System (TLAPS). TLAPS parses your hierarchical proof steps and dispatches them to backend theorem provers and SMT solvers (like Z3, Zenon, or Isabelle/HOL) to mechanically verify the system's logic.

    Because writing machine-checked proofs requires highly specialized tooling and weeks of dedicated mathematical effort, this gateway currently relies exclusively on Level 1 (exhaustive bounded checking) to establish its architectural confidence.

3. Mutation Testing: Confirming the Model Catches Invariant Violations

Mutation testing serves as our falsification step: deliberately injecting security bypasses or sequencing errors into the specification to verify that our formal safety invariants are non-vacuous and robustly fail when broken.

Mutation 1: Security Check Bypass (MC_mutant)

Modification: Enabled MutantSkipTenantCheck = TRUE to simulate a flawed admission controller that honors the unverified request payload instead of the cryptographically verified JWT identity.

The Execution Trace: The 7-step sequence below demonstrates how TLC traces the mutation to a critical failure and catches the vulnerability before the malicious job can execute.


1. <Initial predicate> : Request r4 (Auth: t1, Payload: t2) is staged.
​2. <Start(r4)>         : Gateway receives the REST invocation.
3. <BindSnapshot(r4)>  : r4 locks in the latest valid table state.
4. <CheckCache(r4)>    : Cache miss; r4 requires materialization.

                         "Invariant TenantBinding is violated."

Conclusion: One detected mutant does not establish that all properties are complete or non-vacuous. However, it provides concrete evidence that the modeled TenantBinding invariant correctly traps unauthorized cross-tenant scoping the moment a job attempts to enter the queue.

Mutation 2: Multi-Tenant Key Collision in Result Cache PLANNED

Modification: Simplified cache indexing to omit tenant separation, indexing solely by query name and version.

Note: Needs a request authenticated as t2 that shares a query and security context with a t1 request, or it can't correctly violate TenantIsolation.

Mutation 3: Stale Snapshot Acceptance Race (MC_stale_snapshot)

Modification: Removed the snapshot freshness check (jobs[r].version = catalog_snapshot[jobs[r].tenant]) from the CommitJob action.

The Execution Trace: TLC detects a race condition between the background LakehouseETL daemon and the ComputeWorker, leading to a violation of CacheFreshness and DeliveredResultIntegrity.

2. <ETLCommit(t)>      : LakehouseETL advances catalog_snapshot to v2.

Mutation 4: Stale Worker Commit After Lease Revocation PLANNED

9. From Model Correctness to Implementation Conformance

A model and a production implementation are different artifacts. Model-based trace checking can help compare observed runtime transitions with the abstract specification, but it requires an implemented harness, a stable event schema, a deterministic mapping from events to model actions, and explicit handling of missing or reordered telemetry. The pipeline below is the proposed design for this gateway; it is not represented as already running in CI.

Minimum trace contract

Each event should include enough stable data to bind it to a concrete model transition. At minimum, capture:

  • event_id or monotonic per-request sequence, event_type, timestamp for diagnostics, and request_id.
  • requested_tenant_id and authenticated_tenant_id (or a privacy-preserving stable context identifier), query_id/hash, security_context_id, and snapshot_id.
  • worker_id, lease_epoch, blob_id, and the result-pointer/acceptance outcome where applicable.

Do not rely on log arrival order as execution order. The harness must account for per-request sequence, causality/correlation identifiers, dropped events, duplicate telemetry, and concurrency between independent requests. Sensitive query text or credentials should not be emitted.

The checker should reject acceptance if the blob is not durable, the metadata does not match the request, the lease epoch is no longer current, or the snapshot is not current/readable at the defined acceptance point. The exact event-to-action adapter and trace replay implementation must be written and tested; an illustrative module that imports undefined operators or assumes an unavailable NDJSON parser is not executable evidence.

Acceptance criteria for the harness

  • A known-good trace replays to a legal model state.
  • Mutated traces fail for a specific property: pointer-before-blob, stale lease epoch, tenant/security-context mismatch, stale snapshot acceptance, or blob reclamation while referenced.
  • Missing/duplicate events are reported as incomplete or ambiguous evidence, not silently treated as legal behavior.
  • The harness and fixture traces run in CI with pinned tool versions and retain logs as artifacts.

10. The Comprehensive Architectural Verification Summary

The comprehensive verification of the Smart Data Gateway requires a multi-tiered strategy spanning theoretical models and physical reality. As explored earlier in Part 3, the foundational targets for speed, scalability, and physical limitations—such as P99 tail latency bounds via Kingman's approximation, cluster throughput scaling under the Universal Scalability Law, and Monte Carlo-simulated cloud unit economics—must be empirically validated through live implementation conformance and rigorous operational SRE testing. Conversely, this current installment (Part 4) establishes the mathematical correctness of the system's distributed state through formal validation. Using bounded TLC model checking, we have successfully checked specific safety invariants—such as TenantBinding (tenant isolation), ClaimCheckIntegrity (pointer safety), and EpochMonotonic—within explicit finite state bounds (e.g., the MC_nofaults and MC_flightcache runs), while partially exploring massive fault-injected scenarios (where liveness remains mathematically unverified because the run was interrupted). By combining the empirical performance physics of Part 3 with the rigorous formal state definitions of Part 4, we bridge the critical gap between mathematically bounded logic and physically validated execution.

The useful outcome is not a claim of certainty; it is a reviewable chain from requirement to model property, from property to a reproducible TLC run, and from abstract action to implementation evidence.
