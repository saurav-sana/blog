PART 2 · DATA ENGINEERING & ARCHITECTURE

Architectural Evolution

From Fat Client OOMKills to an Enterprise Dual-Protocol Smart Data Gateway

September 27, 2026

“Good judgment comes from experience, and experience comes from bad judgment.”

— Fred Brooks , The Mythical Man-Month

We All Believe in Learning from Failure. Until it Fails.

Every clean architecture diagram on LinkedIn conceals a graveyard of crashed pods, deadlocked threads, and frantic 2 AM incident calls. We definitely did not know the final architecture when we wrote line one.

In Creativity, Inc., Pixar co-founder Ed Catmull observed that experiments are "great in retrospect but not in prospect," noting that “Failure isn't a necessary evil. In fact, it isn't evil at all. It is a necessary consequence of doing something new.” In enterprise engineering, however, failure sends an immediate invoice: frozen browser tabs, angry regulatory consumers asking why daily trade summaries aren't ready, and cloud egress bills that make your FinOps team send calendar invites with no agenda.

Engineers have an impressive survival instinct: when a prototype works, we call it "intentional system design"; when it implodes, we call it "research." But failure only hardens into true architectural insight when held to an empirical contract:

01 What are we trying to prove?

State the mechanical hypothesis cleanly (e.g., lazy metadata pruning isolates query planning RAM from data-scan memory limits).

02 What will we measure?

Identify hard metrics: candidate split counts, p99 latency, cgroup memory watermarks, and interop serialization CPU ticks.

03 What result changes the design?

Define the discard threshold beforehand so sunk-cost fallacy cannot keep broken prototypes on life support.

04 What did we learn when it broke?

Every failure must definitively expose a physical bottleneck—whether it is the Linux page cache, the Python GIL, or TCP head-of-line blocking.

What follows is not a victory lap. It is the raw chronicle of five successive architectural failure modes that were measured, dismantled, and permanently engineered out of our data platform.

1. Why Now? The Convergence of Primitives

Why wasn't a lightweight, stateless data gateway built like this a decade ago?

Historically, Big Data infrastructure was optimized exclusively for batch throughput rather than interactive operational concurrency. Massively Parallel Processing (MPP) engines—Hadoop, Hive, Spark, Trino, and early cloud data warehouses—were designed for workloads where waiting 15 to 45 seconds for query compilation, driver scheduling, and shuffle staging was an acceptable tax. There was neither the technical tooling nor the economic incentive to place sub-second, application-aware query gateways at the lakehouse storage edge.

Furthermore, database compute was inextricably bound to proprietary storage formats. You could not point a lightweight external engine at Snowflake micro-partitions or Redshift blocks. This stateless gateway paradigm only became viable through the simultaneous maturity of three open-source primitives:

  • Open Table Formats (Apache Iceberg, Delta Lake): Decoupled physical Parquet files from proprietary database engines. For the first time, immutable manifest trees, snapshot trees, and column statistics became open specifications accessible over standard HTTP REST interfaces.
  • Apache Arrow & Arrow Flight: Standardized a columnar, in-memory format that eliminates serialization penalties. While Arrow provides true zero-copy sharing across in-process threads and local shared-memory IPC, network transport via Arrow Flight incurs HTTP/2 framing, serialization, and socket buffer copies. Arrow Flight is properly understood as low-copy, format-aligned columnar transport that streams columnar memory buffers across network boundaries without row-to-object deserialization.
  • Embedded Vectorized Engines (DuckDB, DataFusion): Vectorized analytical compute engines running directly in C++ with SIMD optimizations proved they could execute analytical queries across millions of rows in milliseconds—completely bypassing JVM garbage collection pauses and distributed network shuffle overhead.

2. Technology Selection & Open Storage Format Agnosticism

To build the gateway, we needed an execution engine with a specific profile: a lightweight memory footprint, native Parquet reader optimization, late materialization, and seamless in-memory Arrow integration.

We evaluated Apache DataFusion, Daft, and DuckDB. While DataFusion offers brilliant Rust-level extensibility, DuckDB stood out with its mature Parquet reader, comprehensive SQL dialect coverage, and native zero-copy Arrow memory sharing across in-process threads.

DuckDB Concurrency & Reader/Writer Isolation Contract

Designing a multi-tenant gateway required engineering around DuckDB's underlying concurrency model:

The DuckDB Concurrency Constraint: DuckDB natively supports concurrent readers on an in-memory database instance or read-only attached database file. However, writing or attaching a database file in read-write mode blocks on a single-writer exclusive lock.

To ensure concurrent query requests never block on engine locks, the Smart Data Gateway enforces a strict operational contract:

  • Stateless, Read-Only Consumer Instances: Every Gateway worker node instantiates DuckDB strictly as an in-memory, read-only query processor (duckdb.connect(":memory:")). It never writes back to lakehouse storage, modifies tables, or participates in snapshot commits.
  • Out-of-Band Lakehouse Writes: Ingestion, compaction, snapshot commits, and schema changes are strictly delegated to independent external ETL pipelines (such as PySpark or Flink). Because Gateway engine instances operate exclusively as read-only analytical consumers, they are completely isolated from write locks and table contention.

Why Apache Iceberg — And Why the Pattern Transcends Format

In our regulatory trade reporting systems, we standardized on Apache Iceberg due to our append-heavy event-sourcing model, where high-frequency event streams demand low-latency event-driven commits and deterministic snapshot isolation.

The Open Storage Format Principle: The gateway architecture is strictly format-agnostic. Whether your lakehouse is cataloged using Apache Iceberg, Delta Lake, or Apache Hudi, the gateway pipeline operates identically: it evaluates catalog metadata lazily, prunes candidate file manifests using client predicates, and hands the resulting Parquet URIs to DuckDB for physical execution.
Tier 1: Core Execution Primitives
  • DuckDB C++ Core: Vectorized execution engine executing SIMD query kernels without JVM runtime overhead.
  • Apache Arrow: Zero-copy in-memory IPC format enabling format-aligned streaming to network sockets.
  • Format SDKs (PyIceberg / Delta-RS): Evaluates partition metadata and file-level min/max statistics prior to physical scan.
  • Open Catalogs: REST catalogs (Iceberg REST, Polaris, Nessie) providing authoritative snapshot versions.
Tier 2: Ingress & Security Layer
  • Kubernetes Gateway API: Layer 7 ingress (Envoy/AGFC) handling per-stream HTTP/2 multiplexing.
  • NGINX Edge Proxy: Consistent-hashed SSD byte-range cache mitigating cloud storage WAN latency.
  • Redis Cluster: Fast result-fingerprint store and data-version cache invalidation bus.
  • SQLglot AST Engine: Query transpilation and mandatory Row-Level Security (RLS) predicate injection.
Tier 3: Dual Serving Interfaces
  • Arrow Flight SQL Server: High-throughput gRPC streaming service for programmatic pipelines and notebooks.
  • FastAPI (REST Engine): Low-latency JSON HTTP endpoint optimized for interactive operational dashboard widgets.
  • Model Context Protocol (MCP): Governed tool boundary exposing bounded analytical reads to LLM agents.
Tier 4: Orchestration & Observability
  • Celery & Redis: Asynchronous task queue offloading long-running exports via the Claim-Check pattern.
  • KEDA Autoscaler: Event-driven pod scaling driven by queue backlog depth and active connections.
  • OpenTelemetry: End-to-end W3C trace context propagation linking HTTP/gRPC ingress to DuckDB spans.
  • Azure Data Explorer (ADX): High-scale log and trace analytics querying distributed execution via KQL.

3. Phase 1: Embedded Mode & Network Bottlenecks

Step A: In-Process Fat Client (The "Zero-Infrastructure" Delusion)

Our initial prototype was guided by an enticing dream: Why deploy microservices when you can just embed an analytical database right into your application? Because our primary platform was written in .NET, we used the DuckDB.NET bindings to run DuckDB's C++ core directly inside the client process. The fat client reached out over the WAN directly to Azure Data Lake Storage (ADLS Gen2) via HTTP range requests, evaluated Iceberg Parquet files in-process, and handed results to the dashboard grid.

We felt like architectural geniuses for about five minutes. Then we actually ran queries against production datasets.

Failure Mode: The CLR Interop Tax & The Kernel's Wrath
  • The Boxing/Unboxing Penalty: DuckDB's vectorized execution runs in native C++. But shoving gigabytes of computed records through the C# P/Invoke boundary required massive memory copying, boxing, and unboxing. Our CPU cores spent more time converting C++ native pointers into managed .NET objects than actually computing aggregates.
  • Cold WAN Latency: ADLS Gen2 is optimized for massive throughput, not per-request low latency. Even running SELECT * FROM trades LIMIT 10 on a small table required multiple HTTP round-trips to read Parquet footers across the internet, turning a trivial query into a 4-second spinner.
  • Shared Fate & OOMKill: Compute and UI threads shared the exact same memory space. When a query scanned a wider table, DuckDB pulled large Parquet byte ranges into RAM to evaluate joins. Once the process exceeded the client machine's physical memory limit, the OS kernel stepped in: an ungraceful OOMKill (SIGKILL) that terminated the entire user application without so much as an unhandled exception dialog.

Step B: Fat Client with Proxy CDN (Enter NGINX & OpenResty Lua)

To eliminate the WAN round-trip latency to Azure, we introduced an NGINX reverse proxy in front of the lakehouse to act as an internal caching reverse proxy. We split caching into two distinct tiers:

  • Proactive Metadata Caching: A background daemon polled the catalog and pre-warmed NGINX's cache with fresh metadata every 30 seconds.
  • Reactive Data Caching: Parquet data chunks were cached on local SSDs on-demand using HTTP byte-range caching (proxy_cache_key $uri$slice_range).

To make the caching tier resilient against partial reads and dynamic SAS tokens, we augmented NGINX with OpenResty Lua scripting:

  • Phase Hook Precision: We bound request authentication to access_by_lua_block (validating bearer tokens before touching disk) and dynamic routing to balancer_by_lua_block for consistent hashing without process reloads.
  • Non-Blocking Cosockets: All upstream auth and cache-index lookups in Lua use non-blocking cosockets (lua-resty-http and lua-resty-redis), ensuring the NGINX event loop worker process is never stalled by slow auth providers.
  • Byte-Range URI Normalization: In rewrite_by_lua_block, raw byte ranges are sanitized and mapped to a deterministic 1MB boundary key, preventing duplicate chunk fetches from cloud storage when DuckDB requests overlapping slices.
  • Shared Memory Coordination: Local token validation digests and rate-limiting token buckets live in lua_shared_dict, executing atomic operations across all NGINX worker processes without race conditions.

Failure Mode: The Sidecar Illusion & Ingestion Strain

While NGINX delivered an immediate 5x throughput speedup on cached data, queries against large tables still died horrible deaths.

We attempted to isolate compute by packaging DuckDB as a Sidecar container within the client’s Kubernetes pod. This was an expensive illusion: containers inside the same pod share the exact same underlying Kubernetes cgroups memory ceiling. High-frequency ingestion commits generated hundreds of small Parquet files and complex metadata trees. When DuckDB loaded all those fragment references into RAM, it blew through the pod quota. The Kubernetes scheduler executed an immediate eviction: Exit Code 137. Turns out, putting two processes in the same pod is just sharing a death pact.

4. Phase 2: Decoupled Execution & Metadata Isolation

Step C: Decoupled Query Execution (Python & Arrow Flight)

Running analytical compute within client pods was dead. We extracted query execution into an independent, containerized backend service running in Python, leveraging Arrow Flight to stream columnar RecordBatches directly to clients over gRPC/HTTP/2 as low-copy, format-aligned columnar streams.

The Eager-Loading Ambush

While .NET interop serialization was gone, the decoupled server still experienced sudden OOM crashes on large, actively ingested tables.

We verified that table maintenance (snapshot expiration, compaction, orphan file removal) was operating cleanly. Low-level memory tracing revealed the culprit: the crash was not occurring during data execution, but during query planning. Early releases of DuckDB's native Iceberg extension (such as v1.1.5) performed eager evaluation, pulling the entire Avro manifest tree into host RAM before running predicate filters. An open tracking issue in the repository monitors native lazy manifest parsing; until that capability lands, delegating metadata planning to an external engine remains structurally necessary.

Step D: Metadata Pruning Handoff (Introducing PyIceberg)

To stop the planning-phase crashes, we bifurcated query planning from physical execution:

  1. Metadata Planning (PyIceberg): The PyIceberg SDK connects to the catalog and parses manifests. PyIceberg uses lazy evaluation, iteratively reading Avro manifest files and matching partition statistics against query predicates without blowing up RAM.
  2. Physical Vectorized Execution (DuckDB): PyIceberg resolves the query into a refined list of explicit Parquet URIs. We then instruct DuckDB to bypass the Iceberg catalog entirely and query those files directly via read_parquet([...]), reading only row groups that pass pushdown filters.

Step E: AST Parsing & Query Splitting (SQLglot Automation)

PyIceberg does not understand raw SQL text—it requires programmatic Python filter expressions. Rather than writing brittle regex that would inevitably crumble on nested parentheses, we integrated SQLglot:

  • SQLglot compiles the client’s SQL query into an Abstract Syntax Tree (AST).
  • It traverses the AST, extracts WHERE clauses, and compiles them into native PyIceberg expressions.
  • It rewrites the SQL AST, replacing the table reference with a parameterized template: FROM read_parquet(?).
  • Once PyIceberg returns the pruned file URIs, they are bound into the template and handed to DuckDB for SIMD-accelerated execution.
import sqlglot
from sqlglot import exp

def enforce_tenant_rls(raw_sql: str, tenant_id: str) -> str:
    """Injects mandatory Row-Level Security predicates directly into AST."""
    ast = sqlglot.parse_one(raw_sql)
    tenant_predicate = exp.EQ(
        this=exp.Column(this=exp.to_identifier("tenant_id")),
        expression=exp.Literal.string(tenant_id)
    )
    for select in ast.find_all(exp.Select):
        if select.args.get("where"):
            select.args["where"].this = exp.And(
                this=select.args["where"].this,
                expression=tenant_predicate
            )
        else:
            select.where(tenant_predicate, copy=False)
    return ast.sql()

5. Phase 3: Scaling Concurrency & Task Orchestration

Step F: Consistent-Hashing Multi-Replica Proxy CDN

A single NGINX instance was an obvious throughput bottleneck. However, placing three NGINX replicas behind a standard round-robin load balancer caused the same Parquet chunks to be cached on all three nodes independently, reducing effective SSD capacity by 66%.

We placed a Layer 7 Ingress Controller in front of the NGINX cluster configured with Consistent Hashing on the request URI. If each of 3 replicas has a 200GB Network SSD drive, the system forms a pooled 600GB non-duplicated SSD cache. When a node restarts, the hash ring adjusts, redistributing only a fraction (1/N) of keys without disrupting the rest of the cache.

Step G: Asynchronous Multiprocessing Arrow Flight Server

Because Python relies on a Global Interpreter Lock (GIL), running DuckDB execution directly in the main Flight server thread blocked the event loop during heavy aggregations, causing incoming connections to time out.

We upgraded the server into an asynchronous architecture leveraging pyarrow.flight, asyncio, and concurrent.futures.ProcessPoolExecutor:

  • Fast Handshake: When a client calls GetFlightInfo, the main event loop extracts the target table, pulls the cached Arrow schema from memory, mints an Arrow Ticket, and returns promptly without triggering execution.
  • Non-Blocking Execution: When the client subsequently calls DoGet(Ticket), the query is dispatched to a background child process pool. The main thread remains unblocked to answer new handshakes.
  • Low-Copy IPC: Once computation completes, Arrow batches are passed to the API thread via shared memory (pyarrow.ipc) and streamed across the HTTP/2 wire with format alignment.

Step H: Decoupled Executors & The Claim-Check Pattern

To scale beyond the hardware limits of a single machine, we decoupled the gateway from execution using Redis, Celery, and KEDA (Kubernetes Event-driven Autoscaling). However, placing Celery between our gateway and DuckDB exposed three major distributed scale bottlenecks:

The Three Distributed Scale Killers & Their Fixes:
  1. The Redis Result Backend OOM Crash: DuckDB outputs Arrow batches that are hundreds of megabytes in size. Pushing these byte arrays into Redis as Celery task results exhausted the broker's RAM.
    The Fix (The Claim-Check Pattern): Workers stream large Arrow/JSON payloads directly to temporary cloud storage (Azure Blob). The worker writes a tiny JSON string to Redis containing the URI pointer: {"status": "COMPLETED", "blob_uri": "az://temp/job-42.arrow"}. Redis handles only lightweight coordination metadata.
  2. The Data Bouncing Penalty (Double Hop): Routing data through Worker → Blob → Gateway → Client forced large analytical datasets to traverse the internal Kubernetes network twice.
    The Fix (Distributed Flight Endpoints): The gateway acts as a coordinator, returning a FlightEndpoint pointing the client directly to the worker pod or signed storage URI.
  3. Celery Polling Latency vs Push-Based Pub/Sub: In default, out-of-the-box configurations, Celery clients poll the result backend on a periodic timer (typically every 50ms), adding 50–150ms of artificial latency to queries.
    The Fix (Push-Based Redis Pub/Sub): We replaced result-backend polling with Redis Pub/Sub notifications. When the worker finishes writing data to blob storage, it publishes a completion event to channel:ticket_{uuid}. The gateway receives the event immediately, eliminating polling latency and triggering client streaming in sub-2ms.

Step I: Architectural Fork: The 20-Query POC Heuristic vs. Stateless Monoliths

The 20-Query POC Heuristic [HEURISTIC]: In our specific POC configuration, approximately 20 concurrent analytical queries represented the tipping point where the operational overhead of a distributed queue (Redis, Celery, KEDA) was justified over simpler replicated stateless monoliths.

Below roughly 20 concurrent requests, the operational drag of running Redis brokers, Celery workers, KEDA scalers, and managing ephemeral storage lifecycles outweighs the performance benefit. A Replicated Stateless Monolith packages the Flight API server and DuckDB execution pool into a single container running behind a Layer 7 Load Balancer:

  • Cryptographically Signed Stateless Tickets: During GetFlightInfo, the parsed SQL query is compressed with lz4, encrypted and signed via HMAC-SHA256 (preventing client-side query tampering), and encoded directly into the Arrow ticket bytes. The cluster stores zero session state.
  • Physical Node Memory & Context Isolation: Each DuckDB process is explicitly restricted to prevent host OOMKills, while context-switching is curbed by pinning threads.
-- Enforce absolute host memory bounds and prevent thread thrashing
PRAGMA memory_limit = '6GB';
PRAGMA temp_directory = '/tmp/duckdb_spill';
PRAGMA threads = 2;

Note: The 20-query cutoff is an empirical workload-specific heuristic, not an immutable law. In subsequent parts, we transition from heuristics to mathematical modeling, formally modeling this crossover point using Kingman's formula for queueing latency and the Universal Scalability Law (USL).

6. Phase 4: Enterprise Dual-Protocol Serving & Zero-Trust

Step J: Dual-Protocol Edge Routing (REST vs. gRPC)

REST and Arrow Flight serve fundamentally different data consumption paradigms:

  • Arrow Flight (Internal Pipelines & Heavy UI): Columnar binary streaming over HTTP/2. Best served by our Stateless Monoliths, streaming data directly from memory via local IPC.
  • REST (External Web, Legacy Consumers, LLM Agents): Row-based JSON request-response over HTTP/1.1. Synchronous REST connections fail when analytical queries run for minutes due to load balancer timeouts. REST naturally aligns with our Decoupled Celery Architecture: 202 Accepted → Poll /status → Fetch JSON /result.

A modern Layer 7 ingress (Envoy or Azure Application Gateway for Containers) routes traffic by protocol:

  • Solving the TCP Sticky Trap: HTTP/2 multiplexes hundreds of queries over a single persistent TCP connection. A legacy Layer 4 load balancer routes by TCP connection, dumping all concurrent queries onto a single backend pod. Envoy unpacks HTTP/2 frames, distributing queries across workers on a per-stream basis.
  • Trailer Preservation: gRPC sends status codes inside HTTP/2 trailers appended to the end of the stream. Envoy preserves these trailers, ensuring client applications receive exact SQL error codes and timeout signals.

Step K: Predictive Caching (Proactive Warming & Result Caching)

Up to this point, our caching strategy was entirely reactive: the first user to query the system paid the performance penalty of reading cold data from Azure. We evolved the caching tier into a predictive, multi-tiered caching system:

  1. Proactive Partition Warming: Upstream ETL ingestion pipelines commit new data to Iceberg and write a companion Sidecar JSON metadata file detailing the modified partition dates and file URIs. An independent Warmer Service consumes this file immediately, pre-fetching hot working data (e.g., the last 15 days of trades) into the NGINX Network SSD cache before users log in.
  2. Versioned Result Caching: For repeat dashboard queries, DuckDB execution is skipped entirely. Query outputs are hashed and stored in Azure Blob Storage. When a query arrives, the gateway calculates its AST hash and cross-references a Redis Data Version Registry. If the partition version has not changed, the pre-computed Arrow IPC or JSON payload is streamed straight out of storage, returning results in milliseconds.

Step L: Unified Observability (OpenTelemetry & ADX)

Diagnosing latency regressions across a distributed system requires structured end-to-end tracing:

  • Trace Context Propagation: Every request is stamped with a W3C Trace Context (traceparent). For Arrow Flight, context travels in gRPC metadata headers; for REST, it is injected into Celery task kwargs, linking worker-level DuckDB execution spans to the original HTTP request.
  • Azure Data Explorer (ADX) & KQL: Distributed spans are exported from OTel Collectors to ADX. Engineers run idiomatic KQL queries to trace query waterfalls: 
    traces
| where Timestamp > ago(2h)
| where customDimensions.tenant_id == "tenant_42"
| extend TotalDurationMs = todouble(customDimensions.duration_ms)
| where TotalDurationMs > 30000
| order by TotalDurationMs desc
| project Timestamp, TraceId, OperationName, TotalDurationMs, customDimensions.cache_hit
  • Tail-Based Sampling: Fast cache hits under 50ms are sampled at a 1% rate to control telemetry storage costs, while errors, cache misses, and queries taking over 5 seconds are captured at a 100% rate.

Step M: Zero-Trust Security & Identity Architecture

A production gateway requires a security perimeter that decouples client authentication from infrastructure access keys:

  • Eliminating the IdP Bottleneck (Local JWKS): Forwarding client bearer tokens to an external identity provider (like Dremio) on every query introduced 100ms of latency. Instead, clients authenticate with the IdP once to obtain a signed JWT. The gateway caches the IdP’s public keys (JWKS) to validate signatures locally in sub-milliseconds.
  • SQLglot-Driven Row-Level Security (RLS): The gateway extracts the verified tenant_id from the JWT. SQLglot inspects the query AST and deterministically injects tenant boundary predicates (e.g., AND tenant_id = 'TENANT_42') before compilation, preventing unauthorized cross-tenant data access.
  • Azure Workload Identity: We eliminated static SAS tokens and storage keys. AKS compute pods leverage Azure Workload Identity, exchanging short-lived Kubernetes service account tokens for ephemeral Azure access tokens on the fly.

8. The Architectural Evolution Matrix

Below is the engineering comparison summarizing the architectural trade-offs, primary technical bottlenecks, root causes, and resolutions across every step of our journey:

Step & Pattern Primary Bottleneck Root Cause of Failure Architectural Resolution
Step A: In-Process Fat Client
(.NET + DuckDB.NET)		 Application lockup; fatal OOMKill on wide tables. Memory spike on client heap; heavy boxing/unboxing across the C# CLR to C++ native boundary. Move execution out of process; establish dedicated query services.
Step B: Proxy CDN Tier
(Fat Client + NGINX)		 Crashes persist on high-frequency commit tables. Local SSD cache cannot fix client memory limits; Sidecar containers share pod cgroup memory. Decouple compute into an isolated backend container fleet.
Step C: Decoupled Service
(Python + Arrow Flight)		 Backend worker crashes during query planning. DuckDB native Iceberg extension eager evaluation loads entire Avro manifest trees into RAM. Bifurcate planning from execution; delegate metadata parsing to PyIceberg.
Step D: Metadata Pruning
(PyIceberg Handoff)		 SQL string translation gap & unbuffered concurrency. PyIceberg requires Python expression objects rather than raw SQL strings. Integrate SQLglot to transpile AST expressions automatically.
Step E: SQLglot Injection
(AST Transpiler)		 Single-node concurrency limits; proxy SPOF. Single NGINX cache bottlenecked on bandwidth and SSD storage capacity. Scale out proxy caching tier using consistent hashing topology.
Step F: Clustered Proxy
(Consistent Hashing)		 Execution node vulnerable to thread starvation during traffic spikes. Absence of query queueing causes thread lockups and connection drops. Introduce an asynchronous multi-processing Flight API server.
Step G: Async Flight Server
(ProcessPoolExecutor)		 Machine vertical resource limits cap concurrency. Single-node worker limits cap concurrency without cluster-wide task orchestration. Decouple compute via Redis queue, Celery workers, and KEDA autoscaling.
Step H: Decoupled Queue
(Celery + Claim Check)		 Redis OOM; network double-hop data bouncing. Serializing gigabyte Arrow IPC record batches into Redis backend crashes the message broker. Implement Claim-Check pattern via Azure Blob; adopt push Pub/Sub.
Step I: Stateless Monoliths
(The 20-Query POC Heuristic)		 gRPC ticket payload size limits; connection timeouts. Raw SQL in Arrow Tickets can breach 8KB metadata limits; idle balancer drops. Compress & HMAC-sign tickets; configure memory caps, disk spill, and HTTP/2 Keep-Alive.
Step J: Dual-Protocol Ingress
(REST vs. gRPC via Envoy)		 Protocol mismatch across divergent workload profiles. Forcing streaming columnar pipelines into request-response REST models degrades performance. Bifurcate ingress traffic via L7 Gateway API into Flight Monoliths and REST Workers.
Step K: Predictive Caching
(Warmer + Result Store)		 Cold start latency; redundant vector math on repeated queries. Re-executing complex aggregations on unchanged partition data wastes CPU cycles. Deploy Ingestion Warmer Service and Redis version-controlled Result Caching.
Step L: Observability
(OpenTelemetry & ADX)		 Distributed latency opacity; black-box execution. Decoupled microservice architecture obscures pinpointing execution regressions. Instrument W3C trace propagation; export metrics to Prometheus and traces to ADX.
Step M: Zero-Trust Security
(Local JWKS + Workload Identity)		 Authentication latency; static credential sprawl. Synchronous IdP verification adds latency; static SAS storage keys carry rotation risks. Validate JWTs locally via JWKS; enforce AST-level RLS; use Azure Workload Identity.
The Architecture Verdict: By synthesizing modern primitives (DuckDB, Arrow Flight, open table formats, consistent-hash NGINX caching, and the Kubernetes Gateway API), we constructed a stateless query gateway delivering sub-second serving latencies without keeping multi-node MPP clusters powered on 24/7. This access layer protects the primary lakehouse from unpredictable query patterns, providing deterministic multi-tenant isolation and strict cost control.

While our POC iterations solved immediate memory crashes and eliminated network double-hops, empirical tinkering only takes a design so far. It left a deeper, mathematical question unanswered: At what exact concurrent load does a stateless gateway hit scalability ceilings compared to a dedicated distributed MPP cluster?
