Beyond the MPP Default: Designing a Smart Data Gateway for the 95% Reality

September 25, 2026 · 5-Part Series

XKCD 974: Why we bought a distributed cluster just to pass the salt.

“Most 'Big Data' problems are just 'Small Data' problems wearing a trench coat made of JVM tuning parameters and Kubernetes manifests. We spent a decade convincing the industry to replace millisecond local memory access with 50-node network shuffles, mostly so we could put 'Distributed Systems Architecture' on our resumes.”

— Anonymous Principal Engineer

TL ; DR

The Core Insight: Most organizations don't have a Big Data problem; they have a serving problem. Forcing small, localized operational queries through a Massively Parallel Processing (MPP) engine mathematically guarantees latency spikes and runaway costs.

  • The Distributed Penalty (Universal Scalability Law): Coherency overhead in JVM clusters destroys throughput for queries that would comfortably fit in a single node's RAM.
  • The Storage Mismatch: Direct compute-to-object-storage architectures suffer full network latency. A local NVMe byte-range proxy is physically required to decapitate the P99 tail.
  • The AI Integration Trap: Connecting LLM agents directly to raw databases via the Model Context Protocol (MCP) invites unbounded table scans, token exhaustion, and multi-tenant data bleed.

The Fix: Stop over-engineering for the 1% outlier. Deploy a stateless, horizontally scalable gateway (DuckDB + Arrow Flight + PyIceberg) to serve the 95% case locally, and route only the massive distributed joins to your legacy MPP cluster.
